# 第 1 章　The Context of Cryptography（密碼學的背景）

> 《Cryptography Engineering》— Ferguson, Schneier, Kohno
> 本章頁碼：p.3–22

---

## 1. 本章定位

密碼學原本是「加密的藝術與科學」，現在範圍廣得多，涵蓋認證、數位簽章等各種基本安全功能。它**同時是藝術也是科學**：做出好的密碼系統，需要科學背景，也需要一劑「黑魔法」，也就是經驗加上思考安全問題的正確心態。

這本書一方面範圍**很窄**，只談密碼學的**實務面**，也就是怎麼在真實系統中實作密碼學；另一方面範圍**很廣**，要培養讀者像安全專家一樣思考。

> **密碼學的第一課：保持批判的心態。** 不要盲目相信任何東西，就算是印成書的也一樣。這種批判心態正是作者所說的「**專業的偏執**」的核心。

---

## 2. 密碼學的角色（1.1）

### 2.1 密碼學就像鎖

> **密碼學本身相當無用，它必須是更大系統的一部分。**

- 鎖本身沒有用，必須裝在門、鏈條、保險箱上，而且**使用的人**要記得上鎖、別把鑰匙亂丟。
- 系統的大部分元件像**牆和圍籬**，目的是把**所有人**擋在外面；密碼學則扮演**鎖**的角色，必須**分辨「好的」和「壞的」存取**，這難得多。
- ⇒ 密碼學和它周邊的元素，自然成為任何安全系統的**攻擊點**。

### 2.2 帳篷上的金庫門

> 我們常看到數位版的「**裝在帳篷上的銀行金庫門**」：旁邊的人在爭論門該多厚，卻沒人看看帳篷。

- 很容易花幾個小時爭論金鑰長度，卻沒注意到 Web 應用程式的**緩衝區溢位**。
- 結果可想而知：攻擊者找到緩衝區溢位，**根本懶得去攻擊密碼學**。
- **只有系統其他部分也夠安全時，密碼學才真的有用。**

### 2.3 為什麼密碼學還是要做對

不同的弱點對不同的攻擊者有不同的用處：
- **破解密碼學的攻擊者很難被發現**，因為他的存取看起來就和「好的」存取一樣，不留痕跡。
- 就像小偷：用鐵撬破門至少看得出有人闖入；**撬開鎖的話，你可能永遠不知道被偷過**。
- 對密碼學的攻擊可以是短暫而且隱形的，攻擊者可以**一再回來**。

## 3. ⭐ 最弱環節原則（1.2）

> **把這句話用超大字體印出來，貼在螢幕上方：**
>
> **A security system is only as strong as its weakest link.**
> **（安全系統的強度只取決於它最弱的一環。）**

- 每個安全系統都由很多部分組成，**必須假設對手很聰明，會攻擊最弱的部分**。其他部分多強都沒有關係，就像鏈條，最弱的那一環會先斷。

### 3.1 例子：天花板

> Niels 以前工作的辦公大樓，每間辦公室晚上都上鎖。聽起來很安全？問題是大樓有**輕鋼架天花板**，掀開天花板就可以爬過任何門或牆。
>
> 鎖門讓小偷稍微麻煩一點，但也讓**夜間巡邏的警衛更難檢查**辦公室。整體安全到底是變好還是變差，並不清楚。

**教訓**：強化了一個環節（門），但另一個環節（天花板）仍然很弱，效果頂多很小，副作用甚至可能超過好處。

### 3.2 攻擊樹（attack tree）

要改善系統安全，**必須改善最弱的環節**；要做到這點，就要先知道有哪些環節、哪些比較弱。最好的方法是用**階層式的樹狀結構**：

```
                       進入金庫
         ┌──────────┬─────┴─────┬──────────┐
       穿過牆      穿過地板     穿過門      穿過天花板
                     ┌────────┬──┴──┬────────┬──────────┐
                  破解門鎖    破壞門   拆除門閂   破壞鉸鍊   破壞門框和牆的連接
                     │
                  取得鑰匙 → ……（又是一整棵偷鑰匙的樹）
```

- 每個環節可以再拆成子環節，直到剩下單一元件。對真實系統做這件事**工作量很大**。
- 這棵樹本身也只是更大攻擊樹的一部分：如果目標是偷金庫裡的鑽石，攻擊者也可以**騙員工把鑽石拿出來**再偷。
- **沒有先做這種分析就想保護系統，常常是白費工夫。**

### 3.3 使用者也是環節

- 很容易假設使用者會用好密碼，但實際上他們常選**簡單的短密碼**，為了不被安全系統打擾，什麼事都做得出來。
- 如果系統**每週給使用者一組新的 12 位數隨機密碼**，可以確定他們會把密碼**貼在螢幕上**。這反而讓本來就弱的環節更弱。

### 3.4 縱深防禦（defense in depth）

嚴格來說，**強化最弱環節以外的任何東西都沒有用**，但實務上沒那麼絕對：
- 攻擊者**可能不知道**哪個是最弱環節，而去攻擊稍強的那個。
- 最弱環節**因攻擊者而異**，取決於攻擊者的技術、工具、對系統的存取，以及他的目標。
- ⇒ 值得強化**任何在某種情況下可能是最弱**的環節。
- 而且值得同時強化**多個**環節，讓一個環節失守時其他環節仍能提供安全，這就叫**縱深防禦**。

## 4. 對抗性環境（1.3）

> **安全系統和幾乎所有其他工程最大的不同，就是對抗性環境。**

- 一般工程師要對付暴風、高溫、磨損，這些因素**相當可預測**。
- 安全系統的對手卻**聰明、狡猾、惡意、詭詐**，會做出沒人想過的事，**不照規則走，完全無法預測**。

### 4.1 例子：塔科馬海峽吊橋

- 著名的影片：塔科馬海峽吊橋在穩定的風中扭動，最後斷裂落水。
- 教訓：細長的吊橋可能有共振模式，穩定的風就能讓整座橋振盪到斷裂。
- 解法：改變橋的**空氣動力學**（加厚橋面、欄杆當擾流板），而不是把橋做得強到能抵抗振盪（太貴）。
- **這之所以有效，是因為風相當可預測，不會主動想摧毀橋。**

> 安全工程師必須考慮**「惡意的風」**：如果風上下吹而不是從側面吹呢？如果風剛好用讓橋共振的頻率改變方向呢？橋樑工程師會直接駁回：「別傻了，風不會那樣吹。」**密碼學家沒有這種奢侈。**

### 4.2 攻守之間的根本不平衡

| 防守方（我們） | 攻擊方 |
|---|---|
| 不知道攻擊者是誰、知道什麼、目標是什麼、何時攻擊、有什麼資源 | 可能在系統設計**多年之後**才攻擊，多了 5 到 10 年的研究和未來的技術 |
| 必須保護**所有**地方 | 只需要找到**一個**弱點 |

> 這就是攻擊者和防守者之間的**根本不平衡**，也正是密碼學世界令人興奮的地方。

## 5. ⭐ 專業的偏執（1.4）

> 要在這個領域工作，**你自己必須變得狡猾**，要像惡意攻擊者一樣思考，找出自己作品的弱點。

- 一旦開始思考怎麼攻擊系統，就會套用到身邊的一切，突然看出你可以怎麼騙別人、別人可以怎麼騙你。
- **密碼學家是專業的偏執狂。** 要把專業的偏執和真實生活分開，以免完全瘋掉。
- 作者的註腳：「但要記住：你不偏執，不代表他們沒在打你系統的主意。」

### 5.1 偏執模型（paranoia model）

以電子支付系統為例，參與者有顧客、商家、顧客的銀行、商家的銀行，威脅很難想清楚，所以用**偏執模型**：

> 對**每一個**參與者，都假設**其他所有人**組成了一個大陰謀，要詐騙**這一個**參與者。也假設攻擊者可能有任何其他目標，例如破壞某參與者交易的隱私，或在關鍵時刻讓他無法使用系統。
>
> **如果你的密碼系統能在偏執模型下存活，它在真實世界才至少有一戰之力。**

本書把**專業的偏執**和**偏執模型**統稱為**安全心態（security mindset）**。

### 5.2 更廣泛的好處（1.4.1）

- 就算不當密碼學家，未來設計、實作或評估軟硬體系統時，有安全心態就會**一直想著攻擊者可能做什麼**，能及早發現潛在的安全問題。
- **最重要的是意識到安全問題可能存在**；一旦意識到，找別人幫忙修就容易了。沒有安全心態，可能根本不會發現系統有問題。
- 技術變得很快，今天的熱門安全機制 10 到 15 年後可能就過時了，但**安全心態可以用一輩子**，套用到新技術上。

### 5.3 討論攻擊的文化（1.4.2）

- 面對任何新系統，**第一件事就是想怎麼破解它**。越早找到弱點，越早了解系統。最糟的是做了好幾年，才有人說：「但如果我這樣攻擊呢……？」
- **嚴格區分「攻擊別人的作品」和「攻擊別人本人」**：
  - 任何作品都是公平的目標。有人提出東西，就等於**自動邀請大家攻擊它**。
  - 「如果你破解了我們的系統，我們會為這個攻擊鼓掌，並告訴所有人。」
  - **對你作品的攻擊不是對你的攻擊**；攻擊系統時，要批評**系統**，而不是**設計者**。

**和不熟悉安全文化的人溝通**：

| 做法 | 問題 |
|---|---|
| 太模糊：「安全方面可能有些問題」 | 只會得到「喔，我們會修」這種敷衍的回應，就算基本設計根本有缺陷 |
| 太直接：「如果你這樣這樣做，攻擊者就能這樣」 | 技術上最有效，但對方可能覺得很刺耳 |
| **建議**：「你有沒有想過，如果有人這樣做會怎樣？」 | 引導設計者進入攻擊的討論；也可以稱讚系統其他的優點、說明打造安全系統的挑戰、主動提議幫忙修正 |

## 6. ⭐ 威脅模型（1.5）

> **每個系統都可以被攻擊，不存在完美的安全。** 安全系統的重點就是讓某些人能存取、某些人不能。最終你總得以某種方式信任某些人，而這些人仍然可能攻擊你的系統。

**要知道你在保護什麼、要防範誰**：
- **有價值的資產**是什麼？
- **威脅**是什麼？

說一個系統「安全」，真正的意思是：**它針對特定類型的威脅，為我們關心的資產提供足夠的安全等級**。必須在**指定的威脅模型**下評估系統的安全性。

### 6.1 例子：防火牆

大多數公司用**防火牆**保護區域網路，但很多真正有害的攻擊是**內部人員**做的，防火牆**完全擋不住內部人員**。防火牆再好，也擋不住惡意員工，這就是**威脅模型不符**。

### 6.2 例子：SET 信用卡協定

SET 是線上刷卡購物的協定：

| SET 的特性 | 評價 |
|---|---|
| 加密信用卡號碼，竊聽者無法複製 | 好主意 |
| **連商家都看不到**顧客的信用卡號碼 | 效果不好：有些商家用卡號查顧客紀錄或收附加費，整個商業系統都建立在「商家拿得到卡號」的假設上 |
| 只保護**傳輸中**的資訊 | 但大多數被盜的卡號**不是在傳輸中被攔截的**，而是從**商家的資料庫**偷走的 |
| **用數位簽章授權交易** | **更嚴重的錯誤**，見下 |

**⭐ SET 最嚴重的錯誤：把風險轉嫁給使用者**

- 用一般信用卡線上購物其實**相當安全**。**信用卡號碼不是秘密**，你每次買東西都會給店員。**真正的秘密是你的簽名**，那才是授權交易的東西。
- 商家洩漏卡號的話，你可能會被盜刷，但只要沒有手寫簽名（或 PIN 碼），就沒有接受交易的證明，**也就沒有收費的法律依據**。大多數地方只要申訴就能拿回錢。
- **SET 用使用者的數位簽章授權交易**，看起來比單純用卡號更安全。但想想看：**使用者現在要為他 PC 上 SET 軟體做的任何交易負責**。如果病毒感染 PC、操控 SET 軟體，簽了錯誤的交易，使用者就會損失金錢。

> **從使用者的角度，SET 提供的安全比一般信用卡更差。** 整體支付系統變得更安全了，但 SET 把**剩餘風險從商家和銀行轉嫁到使用者身上**，使用者的威脅模型從「只有簽名被偽造得夠好，我才會損失」變成「簽名被偽造得夠好，**或是聰明的病毒感染了我的 PC**，我就會損失」。

> **威脅模型很重要。** 每次開始一個密碼安全專案，先坐下來想想你的資產是什麼、要防範哪些威脅。**威脅分析的錯誤可能讓整個專案變得毫無意義。** 本書不會多談威脅分析，但在任何真實系統中，都不能忘記為**每一個參與者**做威脅分析。

## 7. 關於密碼學的三個「真相」（1.6–1.8）

### 7.1 密碼學不是解決方案（1.6）

> **密碼學不是你安全問題的解決方案。它可能是解決方案的一部分，也可能是問題的一部分。**

**例子：加密檔案**
- 你有一個不想讓別人讀的秘密檔案。可以直接保護檔案系統不被未授權存取，或是**加密檔案、保護金鑰**。
- 檔案加密之後，人性使然，你可能就**不那麼小心保護它**了，放在 USB 隨身碟裡，掉了也不擔心。
- 但**金鑰要放哪裡**？好的金鑰太長，記不住。有些程式把金鑰**存在磁碟上**，就是原本存秘密檔案的地方。能取得原本秘密檔案的攻擊，現在可以取得金鑰，再用金鑰解密檔案。
- 而且還**引入了新的攻擊點**：如果加密系統不安全，或金鑰的隨機性太低，攻擊者可以直接破解加密系統。
- ⇒ **整體安全反而降低了。**

> 在很多情況下，密碼學**只提供安全感，而沒有真正的安全**。這很誘人，因為大多數使用者要的就是「感覺安全」；這樣用密碼學也可能讓系統符合某些標準和法規，即使結果並不安全。這種情況下（太常見了），**顧客相信的任何巫術都能提供同樣的安全感，效果也一樣好**。

### 7.2 密碼學非常困難（1.7）

- **連資深專家設計的系統，幾年後被破解也很常見**，常見到大家都不意外了。最弱環節原則和對抗性環境聯手讓密碼學家的日子很難過。
- **缺乏測試方法**：**沒有已知的方法可以測試一個系統是否安全。** 研究社群的做法是發表系統、請其他專家檢視，但這不會自動發生；很多發表過的系統根本沒人看過，期刊和會議的審查也不足以事先找出所有問題。就算很多老手看過，安全缺陷也可能好幾年都沒被發現。
- 本書主要談的是社群**了解得相當透徹**的幾個小領域，它們並不簡單，只是大家研究了幾十年，認為知道關鍵問題在哪裡。

> **不要學完就馬上去打造一台新的密碼投票機或其他關鍵安全系統。** 要和其他人合作，尤其是資深的密碼學專家。**連作者自己設計的系統，也會請其他專家審查。**

### 7.3 密碼學是簡單的部分（1.8）

雖然密碼學本身很難，**它仍然是安全系統中比較簡單的部分**：
- 密碼元件就像鎖，有**相當明確的邊界和需求**。
- 整個安全系統難定義得多：授權存取的組織程序、檢查程序有沒有被遵守的程序，情況總是在變。
- **軟體品質**是電腦安全的大問題：如果機器上的軟體有很多會造成安全漏洞的 bug，安全軟體也無法發揮作用。
- 密碼學是簡單的部分，因為**有人知道怎麼做得相當好**，有專家可以聘請（不便宜，而且很難搞，他們會堅持修改系統的其他部分來達成需要的安全性質）。
- **系統其他部分有我們還不知道怎麼解的問題**：金鑰管理和儲存（大多數電腦**沒有安全的地方存金鑰**）、軟體品質差、網路安全更難，再加上使用者就更難了。

## 8. 通用攻擊（1.9）

> **有些安全問題是無法解決的。**

- 對某些類型的系統存在**黑箱攻擊**或**通用攻擊**。
- 經典例子：**DRM（數位版權管理）的「類比漏洞」**。DRM 想控制圖片、歌曲、電影、書籍的複製，但沒有任何技術（密碼學或其他）能防範**系統外部**的通用攻擊：攻擊者可以**拍下螢幕**來複製圖片，或**用麥克風重新錄下歌曲**。
- 要找出系統面臨哪些通用攻擊，**否則可能花大量時間試圖修一個修不好的問題**。
- 反過來，**有人宣稱他的系統能防範通用攻擊時，你就知道要存疑。**

## 9. 安全與其他設計準則（1.10）

> **安全從來不是系統唯一的設計準則**，而只是眾多準則之一。

### 9.1 ⭐ 安全 vs. 效能（1.10.1）

**福斯灣大橋（Firth of Forth Bridge）的故事**：
- 19 世紀的工程奇蹟，和行駛其上的火車比起來**大得驚人**（因此也很貴），**過度設計**到讓人難以置信。
- 但設計者做對了：面對一個從沒成功解決過的問題（建造大型鋼橋），他們做得極好，**這座橋一百多年後仍在使用**。這就是好工程的樣子。
- 之後橋樑設計者學會用更便宜、更有效率的方式建橋，但**第一優先永遠是安全可用的橋**，效率（降低成本）是次要的。

**泰河大橋（Tay Bridge）的教訓**：
- 1878 年 Thomas Bouch 完成當時世界最長的橋，使用鑄鐵加熟鐵的新設計，被視為工程奇蹟。
- **1879 年 12 月 28 日夜裡**，不到兩年，大橋在暴風中倒塌，一列載著 75 人的火車正在過橋，**全員罹難**，是當時最嚴重的工程災難。
- 所以幾年後設計福斯灣大橋時，設計者用了多得多的鋼材，**不只要讓橋安全，也要讓大眾看起來覺得安全**。

> **維多利亞時代工程師的好教訓：如果失敗了，就退一步，變得更保守。**
>
> **電腦產業大致上忘了這個教訓。** 電腦系統發生嚴重安全失敗時（而且太常發生），我們很容易就接受，好像那是命運。很少回到繪圖桌設計更保守的東西，只是不斷推出修補程式，希望能解決問題。

**電腦產業把優先順序倒過來了**：主要設計目標常常包含很嚴格的效率要求，**第一優先永遠是速度**，即使在速度不重要的地方。速度可能是系統本身的速度，也可能是**上市的速度**。結果就是**削減安全成本**，得到一個有點效率、但不夠安全的系統。

**作者的立場**：

> **我們任何時候都會選安全而不是效率。** 願意花多少 CPU 時間在安全上？**幾乎全部。** 如果另一個選擇是更快但不安全的系統，就算 90% 的 CPU 週期都花在可靠的安全系統上，我們也不在乎。
>
> **我們的優先順序是：安全第一、第二、第三，效能排在很後面。**

**90% 聽起來很多，但有一些安慰**：
- 人一秒大概只能打 10 個字元，十年前的慢機器都跟得上；現在的機器快了一千倍以上。用 90% 的 CPU 做安全，電腦看起來就慢十倍，大約是**五年前**電腦的速度，而那些電腦當時已經夠快了。
- 真正需要等電腦的情況很少：等網頁、列印、啟動程式、開機……好的安全系統不會拖慢這些活動。
- 很多大量運算的部分（alpha blending、3D 動畫、語音辨識）**不做任何安全相關的動作**，不會被安全系統拖慢。會有額外負擔的是系統的其他部分，而它們在人類的時間尺度上已經夠快了。

**安全 = 預防 + 偵測 + 回應**：
- 正如 Bruce 在《Secrets and Lies》裡詳細記錄的，好的安全總是**預防、偵測、回應**的組合。
- 密碼學主要負責**預防**，而預防必須非常好，偵測和回應（可以也應該包括人工介入）才不會被淹沒。
- 密碼學也可以用來提供更安全的偵測機制，例如**強固的密碼學稽核記錄**。

**現實的限制**：作者承認這種設計哲學在真實世界不一定做得到：市場現實常常壓過安全需求；系統很少能從頭開發，常常要**逐步**或**部署之後**才加強安全；系統必須和既有的不安全系統**向後相容**。三位作者在這些限制下設計過很多安全系統，「**我們可以告訴你，那樣幾乎不可能做出好的安全系統。**」

### 9.2 ⭐ 安全 vs. 功能（1.10.2）

> **複雜是安全最大的敵人，而複雜幾乎總是以功能或選項的形式出現。**

**基本論證**：
- 想像一個有 **20 個選項**的程式，每個選項可以開或關，就有**超過一百萬種**組態。
- 要讓程式**能用**，只需要測試最常見的選項組合。
- 要讓程式**安全**，必須評估**每一種**組態，確認每一種組態都能抵擋每一種可能的攻擊。**這是不可能的。**
- 而大多數程式的選項遠超過 20 個。
- ⇒ **要對打造安全的東西有信心，最好的方法就是保持簡單。**

**簡單 ≠ 小**：
- 可以打造**很大但仍然相當簡單**的系統。
- **複雜度衡量的是在任何一點上有多少東西互相作用。** 如果某個選項的影響只限於程式的一小部分，它就不會和影響只限於另一部分的選項互相作用。
- 要做出大而簡單的系統，就要在各部分之間提供**非常清楚簡單的介面**，也就是**模組化**。好的簡單介面把系統其他部分和模組的細節隔開，包括模組的選項和功能。

> 本書試著為密碼學基本元件定義**簡單的介面**：沒有功能、沒有選項、沒有特例、不需要額外記什麼，**只有能想到的最簡單的定義**。有些定義是新的，是作者寫書時發展出來的。

> 這和第一本書《C Interfaces and Implementations》的介面設計哲學完全一致：**清楚的合約、隱藏細節、最小的介面**。

### 9.3 安全 vs. 演進中的系統（1.10.3）

- 安全最大的問題之一：**底層安全機制就位之後，整個系統仍然持續演進**。
- 安全機制的設計者不只要有專業的偏執、考慮各種攻擊者和攻擊目標，還要**預期並準備好系統未來的用途**。
- 這可能造成巨大的挑戰，系統設計者必須記住這一點。

## 11. 專業偏執的練習（1.12）

> 學外語最好的方法之一是**沉浸**其中：想學法文，就搬去法國。這些練習是為了讓你**沉浸在密碼學和電腦安全的語言和心態中**。

- 讓你在讀新聞、和朋友聊時事、看 Slashdot 的新產品介紹時，都會**自然地思考安全問題**。甚至遛狗、洗澡、看電影時都會想到。
- 電腦安全從業者（其實所有電腦科學家）也必須意識到**更大的背景**：技術不是孤立存在的，而是由**人、經濟、倫理、文化差異、政治、法律**等組成的更大生態系的一小部分。
- 建議**定期**做這些練習，例如連續一個月每週做，或每讀完幾章做一次；最好和朋友或同學一起討論，你很快就會親身體會到**安全有多微妙、多容易忽略關鍵弱點**。

### 11.1 時事練習（1.12.1）

批判性地分析一則和電腦安全相關的時事，寫一篇給一般讀者看的短文：
1. 摘要事件。
2. 討論事件**為什麼**會發生。
3. 反思事前可以怎麼做（預防、嚇阻或改變後果）。
4. 描述更廣泛的議題（倫理、社會）。
5. 提出可能的回應（大眾、政策制定者、企業、媒體應該怎麼回應）。

### 11.2 ⭐ 安全審查練習（1.12.2）

評估新技術的潛在安全和隱私問題，每份審查應包含：

| 項目 | 內容 |
|---|---|
| **技術摘要** | 一兩段的高階摘要；可以對產品運作方式做假設，但要**明確說出**。**如果連清楚的摘要都寫不出來，大概就不夠了解這個技術，無法評估它的安全** |
| **資產與安全目標** | 至少兩個資產，每個對應一個安全目標，並說明為什麼重要 |
| **威脅** | 至少兩個威脅（攻擊者為了危害資產而採取的行動），各舉一個攻擊者的例子 |
| **潛在弱點** | 至少兩個，並說明理由（不需要確認是否真的是弱點） |
| **潛在防禦** | 系統可以用（或可能已經在用）的防禦 |
| **風險評估** | 這些資產、威脅、弱點的組合有多嚴重 |
| **結論** | 深思熟慮的反思，以及「更大的格局」議題（倫理、技術可能怎麼演進等） |

## 13. 本章重點整理

1. **密碼學只是系統的一部分**，就像鎖；它負責分辨好壞存取，因此是天然的攻擊點。不要把金庫門裝在帳篷上。
2. **最弱環節原則**：系統只和最弱的一環一樣強。用**攻擊樹**找出環節；用**縱深防禦**強化多個環節。
3. **對抗性環境**：對手聰明、惡意、不照規則；攻擊者只要找到一個弱點，防守者必須守住全部。
4. **專業的偏執**：像攻擊者一樣思考；**偏執模型**假設其他人都串通起來對付你；**攻擊作品，不攻擊人**。
5. **威脅模型**：先搞清楚保護什麼、防範誰；SET 的例子說明威脅分析錯誤會怎樣把風險轉嫁給使用者。
6. **密碼學不是解決方案**，用錯了反而降低安全；**密碼學很難**，沒有方法測試安全性；但**密碼學是簡單的部分**，金鑰管理、軟體品質、使用者更難。
7. **通用攻擊**（例如 DRM 的類比漏洞）無法解決，要認出來，別白費力氣。
8. **安全第一、第二、第三**，效能排在很後面；學維多利亞時代工程師：**失敗了就變得更保守**。
9. **複雜是安全最大的敵人**：功能和選項帶來組合爆炸；**簡單 ≠ 小**，靠模組化和簡單的介面。

> **一句話**：密碼學是安全系統中最好處理的一環，但系統只和最弱的一環一樣強；所以要用專業的偏執、清楚的威脅模型和極簡的設計，在一個攻擊者只需要成功一次的對抗性環境中，把整條鏈都顧好。
