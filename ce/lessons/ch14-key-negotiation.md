# 第 14 章　金鑰協商（Key Negotiation）

> 《Cryptography Engineering》— Ferguson, Schneier, Kohno，本章頁碼：p.227–242

---

## 1. 本章定位

終於要處理**金鑰協商協定**：產生一把共享的 session key，交給第 7 章的安全通道使用。

本章的寫法很有教育意義：**不直接給出最終協定**，而是展示一連串逐步改良的版本，每一版修正前一版的問題（中間版本都不完整、各有弱點）。作者也選擇**從頭設計**而不是採用現成的標準協定——為了更清楚地解釋，也為了凸顯每個設計階段的細微之處與挑戰。

```
第一版（§14.2） → 協定永生（§14.3） → 認證慣例（§14.4）
  → 第二版（§14.5） → 第三版（§14.6） → 最終協定（§14.7）
  → 多角度分析（§14.8） → 計算量（§14.9） → 協定複雜度（§14.10）
```

---

## 2. 情境

- Alice 與 Bob 要安全通訊：先跑金鑰協商得到 session key k，再用 k 建立安全通道。
- 安全的金鑰協商需要雙方**能辨識彼此**——這是第四部（PKI）的主題。這裡先**假設 Alice 與 Bob 能互相認證訊息**：用 RSA 簽章（知道彼此的公鑰或有 PKI），或用共享秘密金鑰加 MAC。

**既然已有共享金鑰，為何還要協商？** ⭐

| 理由 | 說明 |
|---|---|
| **金鑰解耦** | session key 外洩（例如安全通道實作有缺陷）時，長期共享金鑰仍然安全 |
| **前向安全** | 協定執行**之後**長期金鑰才外洩，攻擊者仍學不到當時協商出的 session key——**今天弄丟金鑰，昨天的資料仍受保護** |
| **弱秘密 → 強金鑰** | 共享秘密可能只是密碼（使用者不喜歡記 30 個字母的密碼），會受字典攻擊；有些協定能把弱密碼變成強金鑰（§14.12） |

這些性質讓整個系統**更穩健**。

## 3. 第一次嘗試

已知的標準協定如 **Station-to-Station（STS）**。這裡從最簡單的設計開始——子群 DH 加上認證（為簡化，省略了一些必要檢查）：

```
  Alice                                       Bob
  Known: (p, q, g)                            Known: (p, q, g)
  x ∈R 1, …, q − 1
                   ──── X := g^x ────►
                                              y ∈R 1, …, q − 1
                   ◄─── Y := g^y ─────
  k ← Y^x                                     k ← X^y
                   ──── AuthA(k) ────►
                                              check AuthA(k)
                   ◄─── AuthB(k) ─────
  check AuthB(k)
```

這個協定只是把「認證能力」轉成「session key」。問題：

| # | 問題 | 說明 |
|---|---|---|
| 1 | **(p, q, g) 是固定常數** | 為這些值選常數是壞主意（見 §4） |
| 2 | **四則訊息** | 三則就夠 |
| 3 | **session key 被當成認證函式的輸入** | 若認證函式洩漏 k 的幾個位元就糟了，而且需要重新分析整個協定。**經驗法則：一個秘密只用於一件事** |
| 4 | **兩則認證訊息太相似** | 若認證是雙方共享金鑰的簡單 MAC，Bob 只要把 Alice 的認證值原封不動送回去，**不需要金鑰**就能完成協定——反射攻擊 |
| 5 | **認證交換完之前不可使用 k** | 簡單的要求，但「你不會相信有人為了最佳化程式會做出什麼事」 |

## 4. 協定是永生的 ⭐⭐

> 資料庫欄位限制 2000 bytes 也許對某些使用者是問題，但下一版就能拿掉限制。**協定不行。**

- 協定在不同參與者之間執行，每個新版本都必須與舊版本**互通**。修改協定又保持相容非常複雜——不知不覺就要實作好幾個版本，外加一套決定用哪個版本的系統。
- **版本切換本身成為攻擊點**：若舊版較不安全，攻擊者就有誘因逼你使用舊版——**版本回滾攻擊（version-rollback attack）**。作者看過的受害系統多得驚人。
- 不可能預知所有未來需求，有時必須定義第二版；但多版本的成本很高，尤其是整體複雜度。
- **成功的協定幾乎永遠存在**（不成功的我們不在乎），極難從世界上完全移除。

> 所以協定更需要**為未來而設計**——這就是為何不能在協定中規定固定的 DH 參數：即使選得很大，未來的密碼分析進展也可能迫使我們更換。

> 後見之明：SSL 2.0/3.0、TLS 的 **FREAK**（2015）、**Logjam**（2015）、**POODLE**（2014）都是版本或密碼套件**降級攻擊**——攻擊者把連線逼回 1990 年代的「出口等級」弱加密。

## 5. 認證慣例 ⭐⭐⭐

協定常有很多資料元素，很難搞清楚**到底哪些需要認證**——有些協定就是因為漏認證了某些欄位而被攻破。作者用一個簡單的慣例解決：

> **每次送出認證時，認證的資料包含到目前為止交換過的所有資料**：所有先前的訊息，以及認證者自己的訊息中位於認證之前的所有欄位。**也涵蓋通訊雙方的身分。**

以第一版為例：

- Alice 的認證不是對 k，而是對 **Alice 的 ID、Bob 的 ID、X、Y**；
- Bob 的認證涵蓋 **Alice 的 ID、Bob 的 ID、X、Y、AuthA**。

**好處**：

- 消除許多攻擊途徑；
- **成本極低**：密碼協定交換的資料不多，認證計算幾乎都從雜湊輸入開始，而雜湊非常快；
- **簡化記號**：不寫 AuthA(X, Y)，只寫 **AuthA**——要認證的資料由慣例決定。之後本書所有協定都用這個慣例。

**提醒**（呼應 Horton 原則與 ch13）：

1. 認證函式只認證 byte 字串 → 每個要認證的字串必須以一個**唯一識別碼**開頭，指出這是協定中**哪一個位置**的認證；
2. 把先前的訊息和欄位編碼成字串的方式，必須能**不靠額外上下文**還原各訊息與欄位。

> 這個慣例直接修正了第一版的問題 3（不再用 k 當認證輸入）與問題 4（兩則認證的輸入不同，還有不同的位置標籤）。

> 後見之明：TLS 1.3 的 **transcript hash**（所有握手訊息的雜湊被簽章與 MAC）正是這個慣例的標準化版本；TLS 1.2 以前未完整涵蓋 transcript，導致了 **Triple Handshake** 等攻擊。

## 6. 第二次嘗試

讓 Alice 選 DH 參數並送給 Bob，並把四則訊息壓成兩則：

```
  Alice                                           Bob
  選擇合適的 (p, q, g)
  x ∈R 1, …, q − 1
          ── (p, q, g), X := g^x, AuthA ──►
                                                  Check (p, q, g), X, AuthA
                                                  y ∈R 1, …, q − 1
          ◄────── Y := g^y, AuthB ─────────
  Check Y, AuthB
  k ← Y^x                                         k ← X^y
```

改進：不再有固定參數；只用兩則訊息；不直接使用認證金鑰；認證慣例確保被認證的字串不相似。

**新問題**：

| 問題 | 說明 |
|---|---|
| **參數大小分歧** | Bob 的安全政策更嚴格，覺得 Alice 的質數不夠大？Bob 只能中止。送一則「需要至少 k bits」的錯誤訊息？很亂、很複雜，Alice 得用新參數重新開始 |
| **缺乏活性（liveness）** ⭐ | 任何人都能錄下 Alice 的第一則訊息，稍後重送給 Bob。認證檢查通過，Bob 完成協定，以為和 Alice 共享了 k。攻擊者不知道 x 所以學不到 k、也無法入侵系統其他部分——但 **Bob 的日誌會顯示一次「已完成、已認證」的與 Alice 的協定**，這本身就是問題：給調查的管理者錯誤的資訊 |

Bob 無法確定 Alice「活著」，而不是一個重放中的幽靈。**傳統解法：讓 Alice 的認證涵蓋 Bob 選的一個隨機元素。**

## 7. 第三次嘗試

- Alice 不選參數，只送出她的**最低要求 s**；由 **Bob 選擇參數**。
- 訊息數增為**三則**。（作者：「大多數有趣的密碼協定都至少需要三則訊息。我們不知道為什麼，就是這樣。」）
- Bob 只送一則訊息（第二則），裡面包含他的認證 → Alice 必須在第一則訊息中送一個隨機元素：**256-bit 隨機 nonce Na**。

```
  Alice                                           Bob
  s ← min p size
  Na ∈R 0, …, 2^256 − 1
          ──────────── s, Na ───────────►
                                                  選擇 (p, q, g)
                                                  x ∈R 1, …, q − 1
          ◄── (p, q, g), X := g^x, AuthB ──
  Check (p, q, g), X, AuthB
  y ∈R 1, …, q − 1
          ─────── Y := g^y, AuthA ──────►
                                                  Check Y, AuthA
  k ← X^y                                         k ← Y^x
```

**剩下的一個問題**：k 是**可變長度**的數，系統其他部分不好用；更重要的是，k 是用**代數關係**算出來的。

> **在密碼系統中殘留代數結構總是讓我們害怕。** 有少數地方絕對需要這種結構，但能避免就避免。數學是極其強大的工具：過去幾十年有許多新的公鑰系統提案，幾乎全被攻破——**大多是因為它們包含的代數結構**。
>
> **永遠移除你能移除的所有代數結構。**

解法：**對最終金鑰做雜湊**——長度固定，也摧毀殘餘的代數結構。（呼應 §11.8「k 必須先雜湊」與 §12.6 的 K = h(r)。）

## 8. 最終協定 ⭐⭐⭐

### 8.1 短版（易讀）

```
  Alice                                           Bob
  s ← min p size
  Na ∈R 0, …, 2^256 − 1
          ──────────── s, Na ───────────►
                                                  選擇 (p, q, g)
                                                  x ∈R 1, …, q − 1
          ◄── (p, q, g), X := g^x, AuthB ──
  Check (p, q, g), X, AuthB
  y ∈R 1, …, q − 1
          ─────── Y := g^y, AuthA ──────►
                                                  Check Y, AuthA
  k ← SHAd-256(X^y)                               k ← SHAd-256(Y^x)
```

### 8.2 長版（所有必要檢查）

```
  Alice                                           Bob
  sa ← min p size
  Na ∈R 0, …, 2^256 − 1
          ──────────── sa, Na ──────────►
                                                  sb ← min p size
                                                  s ← max(sa, sb)
                                                  s ≤? 2 · sb
                                                  選擇 (p, q, g)，log2 p ≥ s − 1
                                                  x ∈R 1, …, q − 1
          ◄── (p, q, g), X := g^x, AuthB ──
  Check AuthB
  sa − 1 ≤? log2 p ≤? 2 · sa
  255 ≤? log2 q ≤? 256
  Check p, q 皆為質數
  q | (p − 1)  ∧  g ≠ 1  ∧  g^q = 1
  X ≠ 1  ∧  X^q = 1
  y ∈R 1, …, q − 1
          ─────── Y := g^y, AuthA ──────►
                                                  Check AuthA
                                                  Y ≠ 1  ∧  Y^q = 1
  k ← SHAd-256(X^y)                               k ← SHAd-256(Y^x)
```

**p 的大小上限：動態上限** ⭐

- Bob 必須確保 s 合理——不能因為收到一則**未經認證**、s 很大的訊息，就開始產生 100,000-bit 的質數；同樣地，Alice 也不該因為 Bob 送來很大的質數就開始檢查它。所以雙方都要限制 p 的大小。

| 方案 | 問題 |
|---|---|
| 固定上限 | 限制彈性：若密碼分析進展突然迫使你用更大的質數，固定上限會變成真正的問題 |
| 可設定的上限 | 帶來「幾乎沒人懂的設定參數」的所有問題 |
| **動態上限**（本書選擇） | 雙方都**拒絕使用超過自己偏好長度兩倍的質數**——提供良好的升級路徑，又避免過大的質數。因子用 2 還是 3？無所謂 |

**最佳化要小心**：

- 聰明的實作會**快取**合適的 DH 參數：Bob 不必每次產生新參數，Alice 不必每次檢查。
- 應用甚至可以用一組固定參數，或寫在設定檔當預設值，只傳一個**參數集識別碼**。
- 但是：**最佳化可能把協定改到被攻破**。沒有簡單的規則能檢查某個最佳化是否破壞協定——協定設計仍然是藝術多於科學。

## 9. 從不同角度檢視協定 ⭐⭐

### 9.1 Alice 的觀點

- 她只收到 Bob 的**一則**訊息；它經過認證，且認證包含**她的隨機 nonce Na** → 不可能被偽造或是舊訊息的重放。
- 她檢查了 DH 參數 → DH 具備所有預期性質：她保密 y、送出 Y，只有知道 x（使 g^x = X）的人能算出 k。
- Bob 認證了 X，而 Alice 信任 Bob 只在依協定行事時才這麼做 → Bob 知道 x 並保密。
- ⇒ **Alice 確信她在和 Bob 通訊，且推導出的金鑰只有她和 Bob 知道。**

### 9.2 Bob 的觀點

- 第一則訊息幾乎沒有有用資訊：只說「外面有人選了 sa 和一些隨機位元 Na」。
- 第三則訊息（他收到的第二則）不同：經過 Alice 認證；認證涵蓋 **Bob 選的隨機值 X** → 不是重放，而是 Alice **專門為這次執行**認證的。而且 Alice 的認證涵蓋了第一則訊息 → 現在 Bob 也知道第一則是正當的。
- DH 參數是他自己選的，所以安全；只有知道 y 的人能算 k；Alice 認證了 Y，而 Bob 信任 Alice。
- ⇒ **Bob 確信 Alice 是唯一能算出 k 的另一個人。**

### 9.3 攻擊者的觀點

**被動攻擊**：只監聽 → 看得到所有訊息，但 k 由 DH 算出，只要參數安全就學不到任何東西 → 必須主動攻擊。

**主動攻擊**：逐一嘗試修改每個資料元素——馬上被兩個認證擋住。Alice 的最後認證涵蓋**雙方交換的所有資料**，所以除了重放整個預錄的協定執行外，什麼都不能改；而 nonce 與隨機的 X 阻止了重放。

**改大 sa？**
1. 這不算攻擊——只會讓 DH 質數更大、參數更強；
2. 和 3. 兩個認證都會失敗。

**「轉接」不算攻擊**：

```
Alice ──sa, Na──► Bob ──sa, Na──► Charlie
Alice ◄─(p,q,g),X,AuthB'── Bob ◄─(p,q,g),X,AuthC── Charlie
Alice ──Y,AuthA──► Bob ──Y,AuthB''──► Charlie

結果：Alice 以為和 Bob 共享 k，其實是和 Charlie；Charlie 也一樣。
```

這是攻擊嗎？**不算**。Bob 本來就可以分別和 Alice、Charlie 正常協商，再在兩條安全通道間轉送所有訊息——效果相同，而且 Bob 在那種情況下**知道得更多、能做得更多**。Alice 送給 Charlie 的某則訊息可能讓 Charlie 以為 Bob 同意了什麼——但那只會**損害 Bob 自己**。**傷害攻擊者自己的攻擊，不是我們擔心的攻擊。**

**為什麼連 sa 都要認證？** ⭐⭐

大多數設計者不會費心認證 sa——改它不會導致攻擊（雙方各自驗證 p 夠大）。但：

> **讓攻擊者隨意玩弄，永遠是壞主意。我們不想給他們任何多於必要的工具。**

想像一個情境：Bob 偏好使用程式內建清單中的 DH 參數，只在必要時才產生新參數。只要雙方選的大小都在清單中，Bob 永遠不會產生新參數——也就是說，**Bob 的參數產生程式碼和 Alice 的參數驗證程式碼從未被執行，也就不太可能被好好測試**。一個藏在其中的 bug 可能一直潛伏，直到攻擊者把 sa 調大。

> 是的，這種情境不太可能發生。但有成千上萬種「不太可能」的情境，全都對安全不利——**成千上萬個低機率風險加起來，就是高機率風險**。這就是為什麼我們如此偏執地隨時阻止任何一種攻擊：它帶來**縱深防禦**。

> 對照第 8 章：「很少執行的程式碼很少被測試」——和「訊息編號從 1 開始」的理由如出一轍。

### 9.4 金鑰外洩 ⭐

| 情況 | 後果 |
|---|---|
| Alice **遺失**認證金鑰（未被攻擊者得知） | 只是無法再跑這個協定；已建立的 session key 仍可使用（Bob 同理） |
| Alice **遺失** session key（未外洩） | 重新跑金鑰協商即可 |
| Alice 的**認證金鑰外洩** | 攻擊者從此可以冒充 Alice，直到 Bob 被告知並停止接受 Alice 的認證——**無可避免**（弄丟車鑰匙，撿到的人就能開車；這正是鑰匙的功能）。但**過去的通訊仍然保密**：即使攻擊者錄下所有訊息、知道 Alice 的認證金鑰，也算不出已完成協定的 k——**前向安全（forward secrecy）** |
| **session key 外洩** | k 是 g^(xy) 的雜湊，x、y 都隨機選取 → 不提供任何其他金鑰的資訊，更不會洩漏認證金鑰；每次執行的 k 完全獨立（前提是 PRNG 夠好） |

> 註：你有時會看到「**完美**前向安全（PFS）」，但作者不用「完美」這種字眼——**因為它從來都不完美**。

> **本協定對金鑰外洩提供了最好的可能保護。**

## 10. 計算複雜度

假設 DH 參數的選擇與驗證都已快取。每一方各需：

- 3 次子群中的模冪運算（自己的 g^x、檢查對方的 X^q、計算 X^y）；
- 1 次認證產生、1 次認證驗證；
- 若干相對便宜的運算（亂數、比較、雜湊）。

**與 RSA 簽章比較**：

```
DH：3 次 256-bit 指數的模冪 ≈ 3 × 384 ≈ 1150 次模乘法（與 p 的大小無關）
    （較佳的演算法可降到 1000 以下）

RSA 簽章（s-bit 模數）：不用 CRT 約 3s/2 次乘法；CRT 省 4 倍 → ≈ 3s/8 次

3s/8 = 1150  ⇒  s ≈ 3000 bits
```

> **結論**：模數大時 RSA 簽章相對較慢，模數小時相對較快，**損益兩平點約 3000 bits**——因為 DH 永遠用 256-bit 指數，RSA 的指數卻隨模數增長。

- 以本書使用的公鑰大小，DH 計算成本約等於一次 RSA 簽章。
- 若認證用 RSA 簽章，計算量大約**加倍**（RSA 驗證很快，可忽略）。仍然不算過分——CPU 速度快速成長，實務上通訊延遲與開銷通常比計算更花時間。

**最佳化技巧**：

- **加法鏈**啟發法讓每次冪次用更少乘法；
- Alice 同時要算 X^q 與 X^y → 用**加法序列**一次算兩個，省約 250 次乘法（Bos）；
- 還有讓產生隨機 y 並計算 g^y 更快的技巧，但需要太多額外的系統複雜度，作者寧可不用。

## 11. 協定的複雜度 ⭐⭐

這個協定也完美示範了**協定設計為何如此困難**：

- 即使這麼簡單的協定，很快就擴展成一整頁——還沒包括 DH 參數產生的規則，以及在這個抽象層次未知的認證機制檢查；
- 已經很難追蹤所有事情了。更複雜的協定會大得多。

**智慧卡支付系統**：Niels 參與的某系統有十幾個協定，以專有的高度精簡記號寫了 **50 頁**，另有 50 頁密集描述安全關鍵的實作議題。很可能連設計者都無法完全理解。

**兩個協定的破壞性干擾** ⭐（另一個廣泛使用的商用智慧卡系統）：

```
協定 A：由長期卡片金鑰計算 session key（類似本章的金鑰協商）
協定 B：由長期卡片金鑰計算一個認證值

稍加調整，就能用協定 B 讓卡片算出協定 A 的 session key，並把其中一半位元送給你。
知道一半金鑰位元，攻破系統其餘部分就輕而易舉。
```

（同事 Marius Schilder 發現；下一版修正。）——每個協定單獨看都沒問題，**合在一起就出事**。（呼應 §3 的「一個秘密只用於一件事」。）

> **現實系統的協定規格總是非常龐大**：通訊本身就很複雜，加上密碼功能與不信任只會更難。建議：**對協定複雜度要非常小心。**

**根本問題：協定缺乏好的模組化記號**——一切最後都混在一起。本章就是例子：DH 參數大小協商、DH 金鑰交換、認證全部融合在一起，不只是鬆散零件的組合，規格與實作都把它們攪在一起——就像一個沒有任何模組化、非常糟糕又複雜的程式。我們已發展出應付程式複雜度的模組化技術，**卻缺乏協定的模組化技術**，而且發展它們可能並不容易。

> 對照第一本書：Hanson 整本書都在示範 C 程式的模組化技術（介面/實作分離、不透明型別）。本章作者的感嘆正是：**協定還沒有它的「C Interfaces and Implementations」**。（後見之明：Noise Protocol Framework 試圖用「握手模式」語言來模組化協定設計。）

## 13. 從密碼進行金鑰協商

到目前為止都假設有認證系統可用。但很多情況下**你只有一個密碼**。

- 直接用以密碼為金鑰的 MAC 跑本協定？問題：竊聽取得協定記錄後，可以**離線測試任何密碼**——計算認證值看是否正確。
- 人們選的密碼來自很小的集合，有程式專門搜尋所有可能的密碼。
- 理想上需要一種協定：**竊聽者無法進行離線字典攻擊**。

這類協定存在，最知名的是 **SRP**，能顯著改善安全性。本書不詳述；若要使用，也要注意這個領域有**多項專利**。

> 後見之明：這類協定統稱 **PAKE**（Password-Authenticated Key Exchange）；IETF 近年選定 **OPAQUE**（非對稱 PAKE）與 **CPace**（對稱 PAKE）作為推薦方案，相關專利也大多已過期。

## 14. 參考實作（Python）

依長版協定（§8.2）寫成：認證用共享金鑰的 HMAC-SHA-256，依**認證慣例**涵蓋「唯一位置標籤 ‖ 雙方身分 ‖ 到目前為止的所有資料」，並以可唯一解析的長度前綴編碼。示範用 1024-bit 參數並由 Bob 快取（`dh.py`、`primes.py`、`fortuna.py` 為前幾章的參考實作）。

```python
import hmac, hashlib, secrets
from primes import is_prime
from fortuna import shad256
from dh import generate_group

def tlv(*fields) -> bytes:
    """可唯一解析的編碼：每個欄位 = 4-byte 長度 ‖ 內容（整數轉成 bytes）"""
    out = b""
    for f in fields:
        if isinstance(f, int):
            f = f.to_bytes((f.bit_length() + 7) // 8 or 1, "big")
        out += len(f).to_bytes(4, "big") + f
    return out

class Party:
    def __init__(self, name: bytes, peer: bytes, auth_key: bytes, min_pbits: int, cache=None):
        self.name, self.peer, self.K, self.s_min = name, peer, auth_key, min_pbits
        self.cache = cache or {}             # 已產生/已驗證過的 DH 參數

    def auth(self, label: bytes, ids, transcript: bytes) -> bytes:
        # 認證慣例：唯一標籤 ‖ 雙方身分 ‖ 到目前為止交換的所有資料
        return hmac.new(self.K, tlv(label, *ids, transcript), hashlib.sha256).digest()

def check_params(p, q, g, sa):
    assert sa - 1 <= p.bit_length() <= 2 * sa, "p size"
    assert 255 <= q.bit_length() <= 256, "q size"
    assert is_prime(p) and is_prime(q), "not prime"
    assert (p - 1) % q == 0 and g != 1 and pow(g, q, p) == 1, "bad g"

def run(alice: Party, bob: Party, tamper=None):
    ids = (alice.name, bob.name)
    # 訊息 1：Alice → Bob
    sa, Na = alice.s_min, secrets.token_bytes(32)
    m1 = (sa, Na)
    if tamper == "sa": m1 = (sa + 64, Na)

    # Bob
    sa_b, Na_b = m1
    s = max(sa_b, bob.s_min)
    assert s <= 2 * bob.s_min, "Bob: requested p too large"     # 動態上限
    p, q, g = bob.cache[s]                                       # 用快取的參數
    x = 1 + secrets.randbelow(q - 1); X = pow(g, x, p)
    t2 = tlv(sa_b, Na_b, p, q, g, X)
    authB = bob.auth(b"KN-msg2-AuthB", ids, t2)
    m2 = (p, q, g, X, authB)

    # Alice
    p, q, g, X, authB = m2
    t2a = tlv(sa, Na, p, q, g, X)                                # Alice 用「自己送出的」值重建
    assert hmac.compare_digest(authB, alice.auth(b"KN-msg2-AuthB", ids, t2a)), "Alice: AuthB failed"
    check_params(p, q, g, sa)
    assert X != 1 and pow(X, q, p) == 1, "X not in subgroup"
    y = 1 + secrets.randbelow(q - 1); Y = pow(g, y, p)
    authA = alice.auth(b"KN-msg3-AuthA", ids, tlv(t2a, authB, Y))
    kA = shad256(pow(X, y, p).to_bytes((p.bit_length() + 7) // 8, "big"))

    # Bob
    assert hmac.compare_digest(authA, bob.auth(b"KN-msg3-AuthA", ids, tlv(t2, authB, Y))), "Bob: AuthA failed"
    assert Y != 1 and pow(Y, q, p) == 1, "Y not in subgroup"
    kB = shad256(pow(Y, x, p).to_bytes((p.bit_length() + 7) // 8, "big"))
    return kA == kB, kA

if __name__ == "__main__":
    group = generate_group(1024)                      # 示範用小參數；實務 ≥ 2048
    K = secrets.token_bytes(32)                       # Alice 與 Bob 共享的長期認證金鑰
    alice = Party(b"alice", b"bob", K, 1024)
    bob = Party(b"bob", b"alice", K, 1024, cache={1024: group, 1088: group})
    ok, k = run(alice, bob)
    print("session key agreed:", ok, k.hex()[:16], "…")
    try:
        run(alice, bob, tamper="sa")
    except AssertionError as e:
        print("attacker changed s_a: detected ->", e)
```

實測輸出：

```
session key agreed: True 5a438dabec06da80 …
attacker changed s_a: detected -> Alice: AuthB failed
```

> 撰寫這份實作時差點犯了一個錯：一開始讓 Alice 用「收到的」訊息 1（可能已被竄改）而不是「自己送出的」值來重建 transcript，結果竄改 sa 的測試**沒有**被偵測到。改成用自己的 sa 之後才正確失敗。這正好印證了 §11、§12：**即使是兩頁的協定，實作細節也很容易出錯**——而且只有為攻擊情境寫測試才抓得到。

## 15. 設計觀念整理

| 觀念 | 說明 |
|---|---|
| 協商而非直接用長期金鑰 | 解耦 + 前向安全 |
| 一個秘密只用於一件事 | k 不可當認證輸入；兩個協定不可共用長期金鑰的不同用途 |
| 協定永生 | 不可寫死參數；小心版本回滾 |
| **認證慣例** | 認證所有先前資料 + 雙方身分 + 唯一位置標籤 |
| 活性 | 對方的認證必須涵蓋我選的隨機值（nonce / X） |
| 三則訊息 | 大多數有趣的協定都需要 |
| 雜湊最終金鑰 | 固定長度、摧毀代數結構 |
| 動態上限 | 拒絕超過自己偏好兩倍的質數 |
| 最佳化可能破壞協定 | 沒有簡單規則可檢查 |
| 不給攻擊者任何玩具 | 連「無害」的 sa 都要認證 → 縱深防禦 |
| 傷害攻擊者自己的不算攻擊 | 轉接情境 |
| 協定缺乏模組化 | 複雜度是最大的敵人 |

## 18. 本章重點整理

1. 金鑰協商把「認證能力」轉成「session key」，提供金鑰解耦與**前向安全**。
2. 從第一版到最終版，逐步修正：固定參數、訊息過多、k 被當認證輸入、認證太相似、缺乏活性、殘留代數結構。
3. **協定永生**：不寫死參數，小心版本回滾。
4. **認證慣例**：每個認證都涵蓋所有先前資料、雙方身分與唯一位置標籤。
5. **最終協定**：(sa, Na) → ((p,q,g), X, AuthB) → (Y, AuthA)；k = SHAd-256(g^(xy))；動態上限「不超過偏好的兩倍」；完整檢查參數與子群成員。
6. 從 Alice、Bob、攻擊者、金鑰外洩四個角度驗證性質；連 sa 都要認證以求縱深防禦。
7. 計算量：DH 約等於一次 RSA 簽章（損益兩平約 3000 bits）。
8. 協定複雜度是最大的敵人，而協定缺乏模組化技術；**對所有協定保持懷疑**——包括本章這個。
9. 只有密碼時，需要防離線字典攻擊的 PAKE（如 SRP）。

> **一句話**：好的金鑰協商協定是一步步「修」出來的——讓每個認證都涵蓋整段對話、讓對方簽下你的隨機數、最後把結果雜湊掉；而且永遠懷疑它可能還是錯的。
