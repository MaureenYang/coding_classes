# 第 16 章　時鐘（The Clock）

> 《Cryptography Engineering》— Ferguson, Schneier, Kohno，本章頁碼：p.259–268

---

## 1. 本章定位

第四部「金鑰管理」的第一章。在詳談金鑰管理（金鑰伺服器、PKI）之前，還需要一個基本元件：**時鐘**。

乍看之下，時鐘一點也不「密碼學」；但密碼系統經常用到目前時間——憑證的有效期、撤銷、日誌——所以我們需要一個**可靠的**時鐘。

> 本章的結論很坦白：**沒有理想的解法**。重點在於了解風險、**盡量少依賴時鐘**，以及知道真正重要的是時間戳記的**單調性與唯一性**。

---

## 2. 時鐘的用途

| 用途 | 說明 |
|---|---|
| **到期（Expiration）** | 支票、機票、優惠券、甚至著作權都有有效期。數位文件的標準做法是把到期時間寫進文件本身——但要檢查是否過期，就要知道**現在幾點** |
| **唯一值（Unique value）** | 解析度夠高的時鐘能為單一機器提供唯一值，可當 **nonce**。產生 nonce 有兩種通用方法：①時鐘 + 確保同一時間碼不重複使用；②PRNG。隨機 nonce 的缺點是要很大（128-bit 安全需 256-bit nonce，不是所有元件都支援），而且某些平台很難實作 PRNG → 可靠的時鐘是吸引人的替代方案 |
| **單調性（Monotonicity）** | 時間只會前進，不會停止或倒退。把時間放進協定，攻擊者就無法把舊訊息冒充成目前協定的訊息 |
| **稽核與日誌** | 交易系統必須記錄發生了什麼；有爭議時，日誌提供事件的確切順序。沒有時間戳記，就很難知道哪些事件屬於同一筆交易、以什麼順序發生；同步良好的時鐘還能讓不同機器的日誌互相對照 |
| **即時交易** | （Niels 的電子支付系統經驗）兩筆交易 A、B 的先後很重要，因為其中一筆的結果可能取決於另一筆是否已執行。最簡單的記錄方式是給每筆交易時間戳記——前提是時鐘可靠 |

**即時交易中時鐘出錯的不對稱性** ⭐：

- 時鐘**往回走**：危害不大，很容易檢查「現在時間 > 上一筆交易的時間戳記」。
- 時鐘**往前跳**：有問題。若半小時的交易都以 2020 年的時間（遠超過現在）蓋了戳記——**不能手動修改財務記錄**，也**不能**再執行任何時間戳記早於 2020 年的新交易（會打亂由時間戳記決定的順序）。有解法，但可靠的時鐘當然更好。

## 3. 使用即時時鐘晶片（RTC）

多數桌機都有一顆即時時鐘晶片加一顆小電池——內建的小電子錶，讓電腦早上開機時知道現在幾點。為什麼不直接用它？

1. **安全系統的標準更高**：即使敵人試圖操縱，時鐘也應該給出正確時間。
2. **故障的後果更嚴重**：一般用途中時鐘錯了只是惱人；在安全系統中可能造成大得多的損害。

一般硬體的 RTC 沒有我們需要的那麼可靠與安全。作者過去十年親身遇過好幾次 RTC 故障——而且是**自發的**，沒有攻擊者：

- 老機器電池沒電，時鐘停止或重設到 **1980 年**；
- 某天開機，時鐘被設到 **2028 年**的某天；
- 時鐘逐漸變快或變慢（漂移）。

此外還有**主動攻擊**：依電腦而定，改時鐘可能容易也可能困難——有些系統需要管理員權限，有些任何人都能改。

## 4. 安全危險 ⭐⭐

### 4.1 把時鐘調回過去

| 攻擊 | 情境 |
|---|---|
| **恢復已撤銷的權限** | 臨時員工的存取權限已到期；時鐘被調回後，電腦可能再次允許這位前員工存取敏感資料——**每次撤銷某人的權限都可能出現這個問題** |
| **重複觸發自動化任務** | 人資電腦在月底午夜自動發薪（直接轉帳）。攻擊者把時鐘設到 23:55，等任務啟動；完成後再調回去……重複到公司銀行帳戶見底 |
| **金融利息計算** | 利息依交易時間而不同。信用卡背負大額餘額的人，若能讓銀行電腦相信剛才的線上還款其實是**六個月前**付的，就能省下六個月的利息 |

### 4.2 讓時鐘停止

> 每個設計者都有一種本能的認知：**時間不會靜止**。這是一個不言而喻、明顯到連寫下來都不必的假設——他們設計的系統都依賴時間正常運作。時鐘一停，時間看起來就靜止了，事情不會被完成，很多系統會以無法預測的方式運作。

- 簡單的問題：稽核日誌與報表的時間錯誤；交易的確切時間可能有重大財務後果，寄出日期錯誤的正式文件可能引起嚴重麻煩。
- **聰明反被聰明誤的即時顯示**：

```
問題：各系統回報財務交易的延遲不同 → 直接顯示「最新收到的資料」會不一致
      （錢已出現在銀行餘額，但股票還沒從持股中移出 → 會計師討厭數字對不上）

聰明的解法：每筆回報都加時間戳記存入本地資料庫；
           最慢的系統延遲 5 秒 → 顯示「7 秒前」那一刻的財務狀況
           → 稍微延遲，但保證一致

直到時鐘停止：畫面一遍又一遍顯示同一個狀況——（故障時鐘的）7 秒前。糟糕！
```

### 4.3 把時鐘調到未來

| 攻擊 | 情境 |
|---|---|
| **阻斷服務** | 時鐘快四年 → 所有信用卡都「過期」，交易全被拒絕；也訂不到機票——那些日期的航班表還沒出來 |
| **拍賣** | eBay 的大量出價發生在最後幾秒。若能把 eBay 的時鐘稍微調快，就能把許多出價者擋在外面，以更低價格得標 |
| **帳單系統**（作者朋友的真實事件） | 軟體錯誤讓時鐘往前跳了約 30 年 → 系統開始向所有客戶收取 **30 年的未付帳款**。這次沒有直接財務損失，但若用的是銀行帳戶或信用卡自動扣款就難說了——對客戶關係肯定沒好處 |
| **提前取得定時公開的資料** | 某些資料要保密到特定時間才公開；自動化系統中把時鐘調快就能存取。若那是上市公司的**獲利預警**，提前取得就能大賺一筆 |

## 5. 打造可靠的時鐘

作者沒有簡單的解法——細節太依賴實際環境與風險分析。目標是：**增進理解、鼓勵盡量少依賴時鐘、指出要考慮的關鍵問題，並示範如何思考**。

### 5.1 開機後的計數器

- 多數電腦有（或能實作）某種從開機開始計數的計數器：CPU 時脈週期數、刷新計數器等。
- 它**不是時鐘**（不提供實際時間），但只要兩個事件都發生在上次開機之後，就能量測它們的**經過時間**。
- 用途：**檢查 RTC 的意外錯誤**——RTC 運作不正常時，會與計數器出現差異。簡單易測，能對某些 RTC 故障模式提供警告。
- 注意：授權使用者修改時鐘時間時，要更新時鐘時間與計數器值的對應關係。

### 5.2 記錄上次關機時間

- 記住**上次關機**或**上次寫入磁碟**的時間 → 時鐘不應往回跳。機器突然在 1980 年開機？顯然有問題。
- 也可以防止時鐘**往前跳太多**：多數電腦至少每週開機一次 → 若超過一週沒開機，就請使用者**確認日期**——可抓到往前跳超過一週的情況（當然，這假設使用者不是對手）。
- 註腳的妙招 ⭐：大多數使用者看都不看就按 OK，所以最好**請使用者輸入目前日期，而不要顯示時鐘的日期**讓他確認。

> 對照：這和第 1 章「使用者會忽略安全程序」、第 11 章「技術機制勝過使用者紀律」一脈相承——設計時要假設使用者會走最省力的路。

### 5.3 時間伺服器

- 問網際網路或內部網路上的時間伺服器：**NTP**、**SNTP** 等廣泛使用的同步協定，有些還提供時間資料的**認證**，攻擊者無法偽造。
- 但認證需要某種金鑰基礎設施：
  - 手動設定的對稱金鑰——手動設定金鑰很麻煩；
  - PKI——但第 18 章會看到，**大多數 PKI 系統需要時鐘** → **雞生蛋、蛋生雞**的問題。
- 若依賴時鐘同步協定的密碼保護要小心：**整個系統的安全可能就取決於那個協定的安全**。

> 後見之明：**NTS（Network Time Security，RFC 8915，2020）** 為 NTP 加上以 TLS 為基礎的認證；而「憑證驗證需要時間、取得可信時間又需要驗證憑證」的循環，至今仍是實務難題（例如裝置首次開機、RTC 歸零時）。

## 6. 相同狀態問題（The Same-State Problem）⭐⭐

這是某些硬體平台上的嚴重問題：**小型嵌入式電腦**——門鎖、遠端智慧卡讀卡機之類。它們通常只有：小 CPU、少量 RAM、存放程式的非揮發記憶體（如 flash）、一些通訊通道、特定用途的硬體。

**通常沒有 RTC**：要多一顆晶片、一顆石英振盪器，最重要的是**一顆電池**——額外成本之外，電池讓裝置更複雜：要擔心沒電、對溫度變化敏感，某些電池的有毒化學物質甚至讓硬體運送出問題。

**問題**：

> 這種小電腦每次開機都從**完全相同的狀態**開始：從同一個非揮發記憶體讀同一個程式、初始化硬體、開始運作。沒有時鐘或硬體亂數產生器，**嵌入式系統永遠會重複完全相同的行為**。

**大門電腦的攻擊**：

```
第 1 天：攻擊者等到卡車要通過、大門電腦需要開門時，
         在開門前一刻重新開機大門電腦（例如瞬間切斷電源）
         → 初始化後，中央系統經由通訊通道命令大門電腦開門
         → 攻擊者錄下所有訊息

第 2 天：攻擊者再次重新開機大門電腦，送出與第一天完全相同的訊息
         → 大門電腦從相同狀態開始、看到相同輸入 → 行為相同 → 開門
```

- 大門電腦用不用時間同步協定**都沒差**：協定訊息可以從昨天重放，大門電腦無從察覺。
- **相同狀態問題無法用任何協定解決。**

**解法**：

| 解法 | 說明 |
|---|---|
| **RTC 晶片** | 用固定秘密金鑰加密目前時間 → 產生高度隨機的資料，可當協定中的 nonce；RTC 永不重複狀態 → 避開相同狀態陷阱 |
| **硬體亂數產生器** | 效果相同：讓嵌入式電腦每次開機的行為都不同 |
| 從時脈偏差榨取熵 | 本地振盪器與網路時序或另一個振盪器之間的偏差——但很難在短時間內取得足夠的熵；**重新開機要 10 分鐘是不可接受的** |
| **非揮發記憶體中的重開機計數器** | 很少行得通：有些非揮發記憶體只能更新幾千次（不斷更新會讓機器耗損）；有些需要現場沒有的額外程式電壓；有些設計只能「設位元」或「全部清除」（後者會失去主程式）；即使克服這些，也**極難**在電源可能在任意時刻中斷的情況下，讓計數器**可靠地**遞增。少數可行的情況下，可以搭配 CTR 模式與 AES 金鑰產生偽亂數流 |

> **結論**：作者一再遇到相同狀態問題——**必須先改硬體，才能在這種小電腦上做有用的密碼學**。這很難說服管理者，尤其硬體往往已經部署在現場，他們不想聽到「有些事做不到」。
>
> 但是：**沒有一種神奇的安全醬汁，可以淋在既有的不安全系統上讓它變安全。如果不是從一開始就把安全設計進系統，你幾乎永遠得不到好的安全性。**

> 對照第 9 章：VM 從同一快照啟動、備份還原後重用種子檔——本質上也是「相同狀態問題」。

## 7. 時間基準 ⭐

### 7.1 不要用本地時間

本地時間（手錶上的時間）會隨**日光節約時間**與**時區**改變：

- 秋天撥回一小時 → 某些時間值每年**重複**出現 → 不再唯一、不再單調；
- 春天撥快一小時 → 某些時間值**不可能**出現；
- 日光節約時間的起訖日期各國不同，有些國家每幾年就改規則——你不會想為此更新軟體；
- 帶筆電旅行的人可能把時間改成當地時間，問題更糟。

### 7.2 用 UTC

- 基於原子鐘的國際時間標準，全球廣泛使用。
- 每台電腦自己記錄本地時間與 UTC 的偏移，在與使用者互動時使用。

### 7.3 閏秒的問題

- 為了讓 UTC 與地球自轉同步，每隔幾年有一次**閏秒**。到目前為止都是**多**一秒（某一分鐘有 61 秒），理論上也可能**少**一秒——全看地球自轉。
- 閏秒**無法預測**；忽略閏秒會讓跨閏秒的時間間隔量測不準（不算密碼問題，但既然要做好時鐘就做對）。
- **所有電腦軟體都假設每分鐘 60 秒**。直接同步到真實 UTC 時鐘，插入閏秒時最可能造成**內部時鐘重複一秒**——小問題，但同樣破壞了時間值的唯一性與單調性。
- 對大多數應用，**時鐘的精確同步不如時間戳記的單調性與唯一性重要**。只要確保時鐘**不會在閏秒時往回跳**，怎麼解決都無所謂。

> 後見之明：2012 年 6 月 30 日的閏秒讓 Linux 核心的計時器出錯，Reddit、Mozilla 等大量伺服器 CPU 飆高當機。Google 等公司後來改用「**閏秒抹平（leap smear）**」——把那一秒平均分攤到前後 24 小時，正是「不往回跳」的實作。國際度量衡大會已於 2022 年決議在 2035 年前廢除閏秒。

**單調且唯一的時間戳記**（補充示意）：

```c
#include <stdint.h>
#include <time.h>

/* 回傳 64-bit 時間戳記（微秒），保證嚴格遞增，即使系統時鐘倒退或停止 */
uint64_t unique_timestamp(void) {
    static uint64_t last = 0;            /* 實務上要持久化（如上次關機時間）並加鎖 */
    struct timespec ts;
    clock_gettime(CLOCK_REALTIME, &ts);  /* UTC，不受時區/日光節約影響 */
    uint64_t now = (uint64_t)ts.tv_sec * 1000000u + ts.tv_nsec / 1000u;
    if (now <= last)                     /* 時鐘倒退、停止、閏秒重複，或同一微秒內多次呼叫 */
        now = last + 1;
    last = now;
    return now;
}
```

## 8. 結語建議

> 很遺憾，我們沒有理想的解法。打造可靠的時鐘非常棘手，尤其在假設有惡意攻擊者的密碼情境中。最好的解法取決於你的情況。

作者的建議：

1. **意識到**使用時鐘有潛在的安全問題；
2. **盡可能減少對時鐘的依賴**；
3. **保持謹慎**；
4. 最重要的通常是時間戳記的**單調性與唯一性**。

## 9. 設計觀念整理

| 觀念 | 說明 |
|---|---|
| 時鐘是安全元件 | 到期、nonce、單調性、日誌、交易順序都依賴它 |
| 往前跳比往回跳更難處理 | 財務記錄不能手改，也不能倒填 |
| 三種攻擊 | 調回過去（恢復權限、重複任務、利息）、停止（假設失效）、調到未來（DoS、拍賣、提前取得資料） |
| 交叉檢查 | 開機計數器、上次關機時間、超過一週要求輸入日期 |
| 不要顯示預設值讓使用者按 OK | 要他自己輸入 |
| 時間同步的雞與蛋 | PKI 需要時鐘，安全的時鐘同步需要 PKI |
| 相同狀態問題 | 沒有 RTC 或 HW RNG 的嵌入式裝置，任何協定都救不了 |
| 安全要從頭設計 | 沒有可以事後淋上的「安全醬汁」 |
| 用 UTC | 不用本地時間；閏秒時不往回跳 |
| 單調 + 唯一 > 精確 | 對大多數應用最重要的性質 |

> 對照第一本書：Hanson 的介面設計很少涉及時間，但他對**不變量**的堅持在此完全適用——「時間戳記嚴格遞增」就是一個應該由模組強制維持、而不是假設外部世界會遵守的不變量。

## 10. 延伸閱讀重點

- **RFC 5905**（NTPv4）、**RFC 4330**（SNTPv4）、**RFC 8915**（NTS）。
- **Roughtime**（Google，2016）：可驗證、可稽核的粗略時間同步協定，解決首次開機的時間引導問題。
- **Lamport**（1978）：*Time, Clocks, and the Ordering of Events in a Distributed System*——邏輯時鐘，用「順序」取代「時間」。
- **Google Spanner 的 TrueTime**：以「時間區間」表示不確定性。
- **2038 年問題**：32-bit `time_t` 在 2038-01-19 溢位——另一種「時鐘往回跳」。

## 11. 習題摘要

| 題號 | 題目 | 提示 |
|---|---|---|
| 16.1 | 關掉 NTP 一週，每兩小時記錄真實時間與電腦時間，畫出「電腦時間 − 真實時間」對經過時間的圖 | 一般石英振盪器誤差約 ±20–100 ppm → 一週偏差約數秒到一分鐘；圖通常接近直線（固定漂移率），斜率反映頻率誤差；若有跳變，可能是睡眠/休眠或溫度變化 |
| 16.2 | 對五台不同電腦重做 16.1 | 各機器漂移方向與速率不同 → 說明為何不能假設不同機器的時鐘一致，日誌對照需要同步 |
| 16.3 | 找一個使用（或應該使用）時鐘的產品，做安全審查 | 例：TOTP 雙因素驗證（時鐘偏差容忍度）、憑證驗證（過期/尚未生效）、DRM 試用期（把時鐘調回）、智慧門鎖（相同狀態問題） |

---

## 12. 本章重點整理

1. 時鐘用於**到期、唯一 nonce、單調性、稽核日誌、交易排序**。
2. 一般 RTC 不夠可靠：電池沒電、跳到奇怪年份、漂移；還可能被主動操縱。
3. 攻擊：**調回**（恢復撤銷的權限、重複觸發自動任務、偽造交易時間）、**停止**（破壞「時間會前進」的隱含假設）、**調快**（DoS、拍賣、提前取得機密）。
4. 交叉檢查：開機計數器、上次關機時間、長時間未開機請使用者**輸入**日期；NTP 認證有「雞與蛋」問題。
5. **相同狀態問題**：沒有 RTC 或硬體 RNG 的嵌入式裝置會重複相同行為，**任何協定都無法解決**——必須改硬體；安全必須從頭設計。
6. 時間基準用 **UTC**，避免本地時間；處理閏秒時不可往回跳。
7. **盡量少依賴時鐘**；最重要的是時間戳記的**單調性與唯一性**。

> **一句話**：時鐘看似無害，卻是權限、到期與日誌的根基——盡量別依賴它，真要用就只用 UTC，並確保時間戳記永遠嚴格遞增。
