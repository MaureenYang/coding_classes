# 第 17 章　金鑰伺服器（Key Servers）

> 《Cryptography Engineering》— Ferguson, Schneier, Kohno，本章頁碼：p.269–274

---

## 1. 本章定位

終於來到**金鑰管理**——作者毫不懷疑地說，這是**密碼系統中最困難的問題**，所以留到接近最後才談。

- 前面已經談過如何加密、認證資料，以及如何在兩方之間協商共享金鑰。現在要解決：**Alice 和 Bob 如何在網際網路上認出彼此？** 這會很快變得非常複雜。
- 金鑰管理特別難，因為它牽涉的是**人**而不是數學——人難理解、難預測得多。
- 金鑰管理在許多方面是**前面所有內容的頂石**：金鑰管理做不好，密碼學的好處大多會被抵銷。

**範圍界定** ⭐：只談金鑰管理的**密碼面向**，不談**組織面向**——例如：要發金鑰給誰、哪些金鑰能存取哪些資源、如何驗證拿金鑰者的身分、金鑰儲存的安全政策、如何確認政策被遵守……每個組織會依需求與既有組織架構做不同的實作。

處理金鑰管理的一種方式：設一個**可信實體**來發所有金鑰——稱為**金鑰伺服器**。（下一章起討論另一種方式：PKI。）

---

## 2. 基本概念

```
每個人都和金鑰伺服器共享一把秘密金鑰：
    Alice ── KA ── 金鑰伺服器 ── KB ── Bob
    （KA 只有 Alice 和伺服器知道；KB 只有 Bob 和伺服器知道）

Alice 想和 Bob 通訊：
    ✗ 把所有流量都送到伺服器轉交（像一間巨大的郵局）——伺服器負擔太重
    ✓ 讓伺服器為 Alice 和 Bob 建立一把共享金鑰 KAB
```

這把 N(N−1)/2 把金鑰的問題（§11）變成了 N 把。

---

## 3. Kerberos ⭐

廣泛使用的金鑰管理系統，基於 **Needham-Schroeder 協定**。

**最基本的運作方式**：

```
Alice ──「我想和 Bob 通訊」──► KDC（金鑰伺服器）

KDC 產生新的 KAB，回傳給 Alice（全部以 KA 加密，只有 Alice 讀得到）：
    { KAB,  ticket = E_KB(KAB, …) }_KA

Alice ──── ticket ────► Bob
Bob 用 KB 解開 ticket → 得到 KAB

現在 KAB 是只有 Alice 與 Bob 知道的 session key——當然，還有 KDC。
```

**特色：KDC 幾乎不需要更新狀態**：

- KDC 當然要記得與每個使用者共享的金鑰；但替 Alice 和 Bob 建立金鑰後就**完全忘掉**，不記錄建立過哪些使用者間的金鑰。
- 好處：負載很重的金鑰伺服器可以**簡單地分散到多台機器**上——沒有要更新的狀態，Alice 這一刻找一份副本、下一刻找另一份都行。

**但 Kerberos 式系統需要的密碼協定非常複雜** ⭐：

> 一開始設計這類協定看起來很容易，但**連經驗豐富的密碼學家發表的提案都在之後被攻破**——潛入的缺陷非常細微。我們不在這裡解釋這些協定：**拿它們來手動實驗或修改太危險了**，連我們自己都避免重新設計這類協定。若要使用，**就用最新版的 Kerberos**——它已經存在很久，許多有能力的人審視過它。

> 歷史註：Needham-Schroeder 對稱金鑰協定（1978）有一個重放弱點——若舊的 session key 外洩，攻擊者可重放舊 ticket 冒充 Alice（Denning & Sacco，1981）。修正方法是加上**時間戳記**，而這正是 Kerberos 需要可靠時鐘的原因（呼應第 16 章）。

## 4. 更簡單的解法 ⭐⭐

有時無法使用 Kerberos：協定遠非簡單，還有一些限制——**伺服器必須記住所有已接受的 ticket**、**每個參與者都需要可靠的時鐘**。很多情境滿足不了這些要求。而且研究一個更簡單的設計更有啟發性。

**關鍵轉變：允許金鑰伺服器保持狀態**

- 若不那麼強調效率，可以做出**更簡單、更穩健**的方案。
- 現代電腦比 Kerberos 剛設計時強大得多，維護數萬參與者的狀態毫無困難：

```
100,000 位參與者 × 每人 1 KB 狀態 = 100 MB 記憶體
```

- 伺服器仍要夠快以建立所有請求的金鑰，但對現代電腦也不是問題。

**只討論單一金鑰伺服器，而且限於小系統（最多幾千人）** ⭐：

- 有技術可以把伺服器狀態分散到多台電腦，但不深入——因為**你真的不會想要一台服務數萬人的金鑰伺服器，風險太高**：
  - **所有金鑰都在同一個地方** → 非常吸引人的攻擊目標；
  - 金鑰伺服器必須**隨時在線** → 攻擊者隨時都能和它通訊；
  - 現有技術對網路攻擊的防護並不好，把所有金鑰放在一起是**自找災難**。
- 對較小的系統，伺服器保管的金鑰總「價值」較小，威脅也較低。
- 作者註：「我們不喜歡在系統中留下任何未處理的威脅，但在金鑰管理中，**你最後總是得到一個折衷方案**。」
- 更適合超大系統的方案（PKI）在接下來幾章探討。

### 4.1 安全連線

```
1. Alice 與伺服器共享 KA
2. 不直接使用 KA，而是用它（作認證）跑第 14 章的金鑰協商協定
   → 產生一把新鮮的 KA'
   （若 KA 是密碼，最好用 §14.12 適合低熵密碼的協定——前提是專利不是問題）
3. 用 KA' 建立第 7 章的安全通道
   → 機密性、認證、重放保護全部由安全通道提供
4. 之後所有通訊都走這條安全通道
5. 其他所有參與者也各自和伺服器建立類似的安全通道
```

### 4.2 建立金鑰

有了安全通道，設計「替 Alice 和 Bob 建立金鑰」的協定**容易多了**——只需考慮訊息被**遺失、延遲或刪除**的情況，其他所有操縱都被安全通道擋住了。

```
Alice ──(安全通道)──►「請替我和 Bob 建立金鑰」──► 伺服器
伺服器 ──(安全通道)──► 新的 KAB ──► Alice
伺服器 ──(安全通道)──► 新的 KAB ──► Bob
```

- 伺服器甚至可以**透過 Alice** 把給 Bob 的訊息送過去，不必直接和 Bob 通訊——這時 Alice 只是一台**路由器**，轉送「伺服器 ↔ Bob」安全通道的封包（她讀不到內容）。
- **限制**：Alice 請求之前，**Bob 必須已經和伺服器跑過金鑰協商**。是否構成問題、怎麼解決，取決於實際情況。

### 4.3 更換金鑰（Rekeying）

- 和所有金鑰一樣，KA' 必須有**有限的壽命**——很容易安排：Alice 隨時可以重跑金鑰協商（用原本的 KA 認證）建立新的 KA'。
- **大多數情況下，幾小時的金鑰壽命似乎是合理的。**

**因為可以隨時換金鑰，伺服器不必可靠地儲存安全通道的狀態** ⭐：

> 假設伺服器當機、遺失所有狀態資訊——只要它還記得 KA（以及其他參與者對應的金鑰）就沒問題：只需和每位參與者重跑金鑰協商就能恢復。所以金鑰伺服器雖然不是無狀態的，但執行協定時**不必修改它的長期狀態**（存在非揮發媒體上的部分）。

這同時保留了 Kerberos「無狀態」的主要好處（容易恢復），又避開了它的複雜性。

### 4.4 其他性質

- **概念上更簡單**：也許從實作角度不比 Kerberos 簡單，但從概念上簡單得多。安全通道讓**監看可能的攻擊路線**容易得多。
- **模組化的範例** ⭐：沿用已經設計好的金鑰協商協定與安全通道，是**模組化如何幫助密碼協定設計**的好例子。（呼應 §14.10 作者對「協定缺乏模組化」的感嘆——這裡示範了一種可行的模組化：把協定疊在安全通道上。）
- **前向安全**：用金鑰協商建立安全通道 → 若 Alice 的 KA 今天外洩，她舊的安全通道金鑰 KA' **不會**被揭露 → 她過去的所有通訊仍然安全。

**為何本章（及之後各章）不給出詳細設計？**

> 密碼部分相當直接，當然可以描述一個金鑰伺服器系統，但不會很有用。**設計金鑰管理系統，與其說是密碼學問題，不如說是為特定應用收集合適的需求、把使用者介面做對的問題。** 要為具體例子解釋設計選擇，就得虛構並記錄整個周邊的社會與組織結構、威脅環境，以及需要金鑰管理的應用。

---

## 5. 該怎麼選？

- 要實作中央金鑰伺服器：**能用 Kerberos 就用 Kerberos**——廣泛可得、廣泛使用。
- Kerberos 不適用時：就得設計並建置類似本章描述的方案——但那是**大工程**。

> 對於最常見的密碼應用類型，**你應該預期在金鑰伺服器系統上花的時間，和整個應用本身一樣多。**

## 6. 設計觀念整理

| 觀念 | 說明 |
|---|---|
| 金鑰管理最難 | 牽涉人而非數學；做不好就抵銷密碼學的好處 |
| 只談密碼面向 | 組織政策因地制宜 |
| 中心化：N 把金鑰 | 取代 N(N−1)/2 把 |
| Kerberos：無狀態 KDC | 易於分散，但協定複雜、需時鐘、需記住 ticket |
| 別自己設計 Kerberos 式協定 | 專家的提案也一再被攻破 |
| 允許狀態換來簡單 | 現代硬體足以應付 |
| 金鑰伺服器宜小 | 所有金鑰集中、永遠在線 = 誘人目標 |
| **把協定疊在安全通道上** | 只需處理遺失/延遲；模組化的成功範例 |
| 可重建的狀態不必持久化 | 當機後重跑金鑰協商即可 |
| 前向安全 | 用 DH 協商的通道金鑰保護過去通訊 |
| 金鑰管理 = 需求 + 介面 | 不只是密碼學；工作量與整個應用相當 |

> 對照第一本書：Hanson 在 `Mem` 介面中把「配置器」集中管理（含偵錯版的 checking allocator），這和金鑰伺服器「集中管理、單一可信點」的取捨類似——集中帶來一致性與可檢查性，但也成為單一故障點。

## 8. 習題摘要

| 題號 | 題目 | 提示 |
|---|---|---|
| 17.1 | KA' 的合理壽命？太長或太短各有什麼壞處？ | 書中建議**幾小時**。太長：外洩後的暴露窗口變大、前向安全的粒度變粗、單把金鑰加密的資料量增加（§4.8 的上限）；太短：頻繁重跑金鑰協商（DH 運算、伺服器負擔）、更多失敗點與延遲 |
| 17.2 | 攻擊者如何在 KA' 到期**前**取得它？能做與不能做什麼？ | 入侵 Alice 或伺服器的記憶體、實作漏洞、旁通道。能做：解讀並偽造這段期間 Alice ↔ 伺服器的通訊，包括取得 Alice 這段期間請求的 KAB、冒充 Alice 請求新金鑰。不能做：得知 KA（長期金鑰）、解讀先前或之後 KA' 保護的通訊 |
| 17.3 | 攻擊者如何在 KA' 到期**後**取得它？能做與不能做什麼？ | 記憶體/swap/備份殘留（第 8 章）未清除。能做：解讀**當時**錄下的通訊（含那時分配的 KAB）。不能做：冒充 Alice（金鑰已失效）、影響目前或之後的 session |
| 17.4 | 攻擊者錄下所有通訊，之後 KA 與 KB 都外洩，能否回溯讀取 Alice 與 Bob 的資料？ | **不能**（前提是各方已刪除舊的 KA'、KB' 與 KAB）：KAB 經由 DH 協商出的 KA'、KB' 保護，而 DH 提供前向安全；知道長期金鑰 KA、KB 也算不出舊的 DH session key。**但伺服器若保存了 KAB 或通道金鑰**，入侵伺服器就能回溯 |
| 17.5 | 強制重開機金鑰伺服器能否帶來優勢？ | 伺服器遺失通道狀態，所有參與者要重新協商 → 不會洩漏金鑰（長期狀態不變），但造成 DoS；若伺服器的 PRNG 種子處理不當（第 9 章、第 16 章的相同狀態問題），重開機可能導致重複的金鑰或 nonce——這是真正的危險 |
| 17.6 | 攻擊者能否對想通訊的雙方發動 DoS？ | 能：刪除/延遲 Alice ↔ 伺服器或伺服器 ↔ Bob 的訊息（安全通道擋不住刪除）；癱瘓唯一的金鑰伺服器（單一故障點）；若訊息經 Alice 轉送給 Bob，干擾那段路徑；大量發起金鑰協商耗盡伺服器資源 |
| 17.7 | 由伺服器產生 KAB 有什麼政策或法律風險？Alice 和 Bob 會因此不說哪些話？ | 伺服器（及其營運者）知道所有 KAB → 可被傳喚、要求交出或植入監聽；營運者內部人員濫用；雙方會避免談論涉及營運者本身、商業機密、法律敏感的內容——**可被第三方解密的通道會改變人的行為**（呼應 ch13 的誘因分析）。解法：用伺服器分配的金鑰只做**認證**，再跑一次 DH 產生只有雙方知道的金鑰 |

## 9. 本章重點整理

1. 金鑰管理是密碼系統中**最難**的部分，因為牽涉人；本書只談其密碼面向。
2. **金鑰伺服器**：每人與伺服器共享一把金鑰，由伺服器替任兩人建立 KAB。
3. **Kerberos**（基於 Needham-Schroeder）：KDC 發 ticket、不記狀態、易於分散；但協定極其微妙、需要時鐘、伺服器要記住 ticket——**能用就用最新版 Kerberos，絕不自己設計**。
4. **更簡單的方案**：允許伺服器保持狀態；每人先用長期金鑰跑**金鑰協商**、再建立**安全通道**，金鑰分配協定疊在通道上，只需處理遺失與延遲。
5. KA' 壽命數小時；伺服器當機只要記得長期金鑰即可重建；提供**前向安全**。
6. 金鑰伺服器應限於**小型系統**（數千人）——集中與永遠在線讓它成為誘人目標。
7. 設計金鑰管理系統主要是**需求收集與使用者介面**的問題，工作量可能與整個應用相當。

> **一句話**：金鑰伺服器把 N² 把金鑰化為 N 把，但也把所有雞蛋放進一個籃子——能用 Kerberos 就用，否則就把簡單的協定疊在現成的金鑰協商與安全通道之上，並讓系統保持小規模。
