# 第 9 章　產生亂數（Generating Randomness）

> 《Cryptography Engineering》— Ferguson, Schneier, Kohno，本章頁碼：p.137–161

---

## 1. 本章定位

第三部「金鑰協商」的第一章。第二部一直假設「Alice 和 Bob 已經有一把共享金鑰」——那把金鑰總得在某處**產生**出來，而產生金鑰需要**亂數產生器（RNG）**。

> RNG 出錯 → 金鑰變弱。早期版本的 **Netscape** 瀏覽器正是如此（用時間與行程 ID 當種子，SSL 金鑰可在幾分鐘內被猜出）。

**非正式定義**：亂數資料就是**對攻擊者不可預測**的資料——即使他主動採取步驟來破壞我們的隨機性。

### 1.1 熵（Entropy）⭐

熵量測的不是值有幾個位元，而是**你對這個值有多不確定**；可以想成「用理想壓縮演算法描述它平均需要的位元數」。

| 情況 | 熵 |
|---|---|
| 完全隨機的 32-bit 字 | 32 bits |
| 32-bit 字只取 4 種值、各 25% | 2 bits |
| 32-bit 隨機字，但已知恰有 18 個 0、14 個 1 | C(32,14) ≈ 2^28.8 → 28.8 bits |

> **你知道得越多，熵就越小。** 熵是**相對於觀察者**的。

一般定義（Shannon 熵）：

```
H(X) = − Σ P(X = x) · log2 P(X = x)
        x
```

作者說之後不會用到這個公式；也別和物理學的熱力學熵混淆。（註：嚴格來說，攻擊情境下應使用 **guessing entropy**。）

## 2. 真亂數（Real Random）

### 2.1 熵的來源

- 一般電腦的熵源：按鍵的精確時間、滑鼠移動，甚至硬碟內部氣流擾動造成的存取時間變化。
- 這些來源都**有點可疑**：攻擊者可能影響或量測它們。

**對熵要悲觀** ⭐：

- 有軟體宣稱一次按鍵能產生 1–2 bytes 的隨機資料——密碼學家悲觀得多。
- 好的打字員能把按鍵間隔控制在十幾毫秒內；鍵盤掃描頻率限制了量測解析度；打的內容本身也不怎麼隨機。
- 攻擊者可能有額外資訊：**麥克風**錄下鍵盤聲音就能推算按鍵時間。

**物理亂數**（量子現象、電阻熱雜訊、齊納二極體崩潰雜訊）：

- 攻擊者可以試圖**影響**粒子行為使其可預測；
- **竊聽**我們的量測——資料仍然隨機，但對他來說**熵為零**（他知道值了）；
- 用強 RF 場讓偵測器產生偏差；甚至可設想用 **EPR 悖論**顛覆量子隨機性。

**內建硬體 RNG**（如 Intel 晶片組）是重大改進，但只有 OS 能存取，應用程式必須信任 OS。

### 2.2 直接使用真亂數的問題

| 問題 | 說明 |
|---|---|
| **不一定可得** | 沒人打字就沒有按鍵熵——沒接鍵盤的 Web 伺服器怎麼辦？ |
| **數量有限** | 需要大量亂數時只能等 |
| **可能損壞** | 物理 RNG 在嘈雜的電腦環境中比其他零件更容易壞，而且**你可能不知道它壞了** |
| **熵難以估計** | 除非是專門設計的硬體，否則很難知道得到多少熵 |

### 2.3 偽亂數（Pseudorandom）

- 由**種子**經**確定性演算法**產生；知道種子就能預測輸出。
- 傳統 PRNG（如 Knuth TAOCP 第二卷所分析的）只為**消除統計瑕疵**設計，**不能抵抗聰明的對手**。
- **密碼學強度的 PRNG**：即使攻擊者看到大量輸出，也無法預測其餘輸出（未來或過去）。

> **忘掉程式庫裡的 `random()` 函式**——它幾乎肯定不是密碼學 PRNG。除非文件明確說明其密碼學強度，否則絕不使用。

> 對照第一本書：Hanson 書中的測試程式、雜湊表都用一般的 `rand()` 就夠了——那是統計需求；本章處理的是**對抗**需求，兩者完全不同。

### 2.4 真亂數只做一件事：播種 PRNG ⭐

- PRNG 一旦播種，亂數**隨時可得**；
- 持續把收到的真亂數加入種子 → 即使種子曾外洩，也不會**永遠**可預測。

**理論上真亂數比較好？** 某些協定用真亂數可達**無條件安全**，用 PRNG 只有**計算安全**。但：

- 所有密碼協定幾乎處處都依賴計算假設，對某一種攻擊移除計算假設只是微不足道的改進；
- 產生真亂數太難，**嘗試直接使用真亂數反而更可能降低系統安全**——真 RNG 的任何弱點都會直接變成安全損失；
- 用真亂數播種 PRNG，可以對熵源做**更保守**的假設，最終更可能得到安全的系統。

## 3. PRNG 的攻擊模型 ⭐⭐

從種子產生偽亂數很簡單（任何雜湊或區塊加密器都行）；**難的是如何取得隨機種子並在現實中保密**。

PRNG 有**內部狀態**；每次請求用密碼演算法產生輸出，並更新狀態使下次輸出不同。

| 攻擊 | 說明 | 難度 |
|---|---|---|
| **從輸出重建狀態** | 經典密碼攻擊 | 用密碼技術容易防 |
| **狀態外洩** | 實作缺陷、首次開機還沒種子、攻擊者讀到磁碟上的種子檔……**壞事總會發生** | 傳統 PRNG 一旦狀態外洩，攻擊者能跟上所有輸出與更新——**永遠無法恢復安全** |
| **狀態重用** | 兩台以上 VM 從同一狀態開機、讀同一個種子檔 | 難以避免 |
| **少量熵逐次加入** ⭐ | 見下 | 需要「池化」 |

**逐次加入少量熵的攻擊**：

```
攻擊者已知狀態 S
系統混入 30 bits 的事件熵 → S'
攻擊者立刻請求一段輸出 → 用來驗證
窮舉 2^30 種可能的輸入 → 找到 S'      （完全可行）
重複此過程 → 永遠跟上狀態
```

**對策：池化（pooling）**——先把事件收集起來，累積到攻擊者猜不到時才混入。要多少？目標是 2^128 步 → **128 bits 熵**。

**真正的問題**：熵的估計**極其困難、甚至不可能**——它取決於攻擊者知道多少，而設計時無從得知。這正是作者先前設計的 **Yarrow**（與 John Kelsey 合作）的主要問題：它用**熵估計器**，而這種估計器不可能在所有情況都正確。

## 4. Fortuna 概觀

> 實務上，你最好使用廣為接受的密碼程式庫提供的 PRNG。這裡以 **Fortuna**（羅馬命運女神；原本想叫希臘的 Tyche，但沒人知道怎麼念）為例說明設計。

Fortuna 是 Yarrow 的改良，**完全去掉了熵估計器**。三個部分：

```
  熵源 ──事件──► ┌─────────────┐  偶爾重新播種   ┌──────────┐
  熵源 ──事件──► │ Accumulator │ ─────────────► │ Generator│ ──► 亂數輸出
  熵源 ──事件──► │  32 個池     │                │ AES-CTR  │
                 └─────────────┘                 └──────────┘
                        ▲                              │
                        └──── Seed File（開機時使用）──┘
```

| 元件 | 職責 |
|---|---|
| **Generator** | 把固定大小的種子變成任意長度的偽亂數 |
| **Accumulator** | 從多個來源收集熵並池化，偶爾重新播種 generator |
| **Seed file 控制** | 讓 PRNG 在剛開機時也能產生亂數 |

## 5. Generator ⭐

**狀態**：256-bit 區塊加密器金鑰 K + 128-bit 計數器 C。基本上就是 **CTR 模式**（AES、Serpent 或 Twofish 皆可）。

### 5.1 三個精緻化

**① 每次請求後換金鑰（向後安全 / forward secrecy）**

每次請求結束後，再多產生 256 bits 當作新金鑰，**忘掉舊金鑰**——即使之後狀態外洩，也無法重算先前的輸出。

**② 限制每次請求的大小**

真亂數中會有重複區塊；CTR 輸出**永遠不會**有重複區塊（§4.8）。

- 若一把金鑰產生 2^64 個區塊，預期接近一次碰撞；沒有碰撞就露餡了。
- 限制每次請求 **≤ 2^16 區塊（2^20 bytes = 1 MB）**：理想亂數在 2^16 區塊中碰撞機率約 2^-97，要約 **2^97 次請求**才能察覺「缺少碰撞」→ 總工作量 **2^113**。

作者承認這略低於 2^128，但：

- 沒有能提供完整 128-bit 安全的合適元件（用 SHA-256 會慢很多）；
- **人們會為了速度無止盡地爭論不用好的 PRNG**——為了多幾 bits 安全而明顯拖慢 PRNG，會讓太多人乾脆換用很爛的 PRNG，整體安全反而下降；
- 這個攻擊需要**被攻擊的電腦**執行 2^113 次加密——取決於受害者的速度，而不是攻擊者的。（作者不喜歡這類論證，但在現有條件下這是最好的折衷。）
- 若有 256-bit 區塊加密器，就完全沒有這個問題。

**③ 換金鑰時不重設計數器**

若每次都重設計數器，且某把金鑰值重複、請求大小固定，下一把金鑰也會重複 → 可能陷入**短週期**。不重設 128-bit 計數器（永遠不會重複）就自動打破所有循環。

另外：**C = 0 代表 generator 尚未播種**，不能產生輸出。

### 5.2 Generator 本身就很有用

例：**蒙地卡羅模擬**——開始時向 OS 要一次隨機種子並記錄下來，之後所有亂數都由 generator 產生。既隨機，又能用同一種子**完全重現**計算以除錯和驗證。

### 5.3 演算法

```
function InitializeGenerator → G
    (K, C) ← (0, 0)

function Reseed(G, s)
    K ← SHAd-256(K ‖ s)
    C ← C + 1                      C 為 16-byte、LSByte-first 的整數

function GenerateBlocks(G, k) → r      僅供內部使用
    assert C ≠ 0
    r ← ε
    for i = 1..k do
        r ← r ‖ E(K, C)
        C ← C + 1
    od

function PseudoRandomData(G, n) → r
    assert 0 ≤ n ≤ 2^20
    r ← first-n-bytes(GenerateBlocks(G, ⌈n/16⌉))
    K ← GenerateBlocks(G, 2)        換新金鑰，舊 r 無法再被重算
    return r
```

- 需要超過 1 MB 時就**重複呼叫**，不要調高上限（會增加統計偏差）。額外成本只有每 MB 多產生 32 bytes 並跑一次 key schedule。
- 速度：約與底層區塊加密器相同，大請求時每 byte < 20 個時脈週期，可直接取代多數程式庫的 PRNG。

## 6. Accumulator ⭐⭐

### 6.1 熵源

- 只要**至少有一個來源**是攻擊者無法預測的就夠了；你不知道攻擊者會怎麼攻，所以**把所有看起來不可預測的東西都當成來源**：按鍵、滑鼠移動與點擊、硬碟與印表機回應時間……
- 部分來源被攻擊者預測或複製沒關係，只要不是**全部**。
- 實作來源通常要寫進各種硬體驅動程式——在使用者層級幾乎不可能。
- 每個來源有唯一編號 0…255；事件只放**不可預測**的部分（例如精確計時器的最低 2–4 bytes；年月日攻擊者早就知道）。
- **事件編碼必須可唯一解析**：`來源編號(1 byte) ‖ 長度(1 byte) ‖ 資料`。
- 攻擊模型：**某些來源完全由攻擊者控制**（何時產生什麼事件都由她決定），她也能隨時請求亂數。

### 6.2 32 個池 ⭐⭐⭐

```
來源把事件「輪流」分配到 P0, P1, …, P31

第 r 次重新播種時，若 2^i 整除 r，就使用 Pi（用完清空）：

  reseed #   1  2  3  4  5  6  7  8  …  16 …
  P0         ✓  ✓  ✓  ✓  ✓  ✓  ✓  ✓     ✓
  P1            ✓     ✓     ✓     ✓     ✓
  P2                  ✓           ✓     ✓
  P3                              ✓     ✓
  P4                                    ✓
```

**自動適應**：

- 攻擊者對來源所知甚少 → 她猜不到 P0，下次重新播種就恢復安全。
- 攻擊者知道很多、或偽造大量事件 → 她可能跟得上 P0；但 **P1 累積的不可預測資料是兩倍、P2 四倍……**
- 不論她偽造多少事件、知道多少事件，只要**至少有一個她無法預測的來源**，**總有某個池會累積足夠的熵打敗她**。

**恢復時間分析**：設對攻擊者而言熵的流入速率固定為 ρ，重新播種間隔 t：

```
Pi 每 2^i·t 秒被用一次，期間累積 2^i·ρt/32 bits

恢復發生在第一次使用滿足  128 ≤ 2^i·ρt/32 < 256  的 Pi
（上界：否則 P(i−1) 早就有 128 bits 了）

⇒  2^i · t < 8192 / ρ
```

- 恢復點之間的時間，**不超過收集 2^13 bits 熵所需的時間**。
- 為何是 2^13？需要 2^7 = 128 bits；運氣差時剛好差一點，要用下一個池，多一個因子 2；熵分散到 32 = 2^5 個池 → 2^7 · 2 · 2^5 = 2^13。
- 這表示 Fortuna 最多只比理想方案多需要 **64 倍**的隨機性——一個常數因子，保證永遠不會太糟、終究會恢復。
- 而且**完全不需要知道事件有多少熵、攻擊者知道多少**——這就是 Fortuna 勝過 Yarrow 之處。

**為何 32 個池夠？** 若攻擊者注入極多事件，讓 2^32 次重新播種在 2^13 bits 真熵出現之前就發生，連 P31 都不夠。對策：**兩次重新播種至少間隔 100 ms**（每秒最多 10 次）→ 要 13 年以上才會用到（假想的）P32；電腦設備的經濟與技術壽命遠少於十年。

### 6.3 實作考量

**事件該由誰分配到池？**

- 由 accumulator 分配很危險：攻擊者可以在每個「真」事件之前插入假呼叫，操縱真事件落入哪個池。全部落入 P0 → 多池機制失效；全部落入 P31 → 幾乎永遠用不到。
- 解法：**由每個事件產生者自己傳入池編號**。攻擊者要影響池的選擇就得存取產生事件的程式記憶體——到那地步，整個來源大概早已淪陷。

**accumulator 要不要檢查池的輪替順序？** 原則上檢查輸入是好事，但檢查失敗時能做什麼？

| 選項 | 問題 |
|---|---|
| 使用者層級：致命錯誤結束程式 | 一個來源出錯就讓系統失去 PRNG |
| 回傳錯誤碼 | 連 5-bit 循環計數器都寫不好的程式設計師，大概也不檢查回傳碼 |
| 讓 kernel 停止 | 因為一個爛驅動整台機器當掉，太激烈 |
| 懲罰驅動 CPU 時間（延遲約 1 秒） | 但攻擊者送假事件時，被懲罰的是**真的**事件產生者 |

> **結論：accumulator 不檢查池的順序**——偵測到錯誤也做不了任何有用的事。每個來源自己負責輪替；某來源搞砸，頂多失去它的熵（這是預期中的），不會有其他傷害。

> 對照第 8 章「斷言永遠開啟」：這裡是少見的反例，理由是**檢查失敗時沒有任何有意義的處置**，而且攻擊者可以利用檢查來懲罰正當的來源。斷言的前提是「失敗代表程式錯誤」，此處失敗卻可能是攻擊者造成的。

**事件傳遞的執行時間**：

- 許多事件來自即時驅動程式，不能偶爾卡很久。
- 最少的工作：把事件附加到池——不儲存無上限的字串，而是每個池保留短緩衝區，滿了就計算**部分雜湊**（迭代雜湊的好處）。
- 重新播種比加事件貴一個數量級 → **延後到下一次有人請求亂數時才做**：讓受益於亂數的使用者承擔成本，很合理。
- 因此 generator 要被**封裝**起來，accumulator 提供介面相同的 `RandomData`，避免有人直接呼叫 generator 而繞過重新播種。（使用者仍可另建自己的 generator 實例。）
- 緩衝區大小是權衡：大緩衝區 → 一次處理多個雜湊區塊、快取效率好、總 CPU 時間少；但單次加事件的最長時間變長。依環境而定。

### 6.4 演算法

```
function InitializePRNG → R
    for i = 0..31 do Pi ← ε od
    ReseedCnt ← 0
    G ← InitializeGenerator()

function RandomData(R, n) → r
    if length(P0) ≥ MinPoolSize ∧ 上次重新播種 > 100 ms 前 then
        ReseedCnt ← ReseedCnt + 1
        s ← ε
        for i ∈ 0..31 do
            if 2^i | ReseedCnt then
                s ← s ‖ SHAd-256(Pi)
                Pi ← ε
            fi
        od
        Reseed(G, s)
    fi
    if ReseedCnt = 0 then 錯誤：PRNG 尚未播種
    else return PseudoRandomData(G, n)

function AddRandomEvent(R, s, i, e)
    assert 1 ≤ length(e) ≤ 32 ∧ 0 ≤ s ≤ 255 ∧ 0 ≤ i ≤ 31
    Pi ← Pi ‖ s ‖ length(e) ‖ e
```

- **MinPoolSize**：可以用很樂觀的估計。假設每事件 8 bits 熵、在池中佔 4 bytes（2 bytes 資料）→ **64 bytes**。不建議小於 32；太大則延遲重新播種。
- ReseedCnt 從 0 開始，第一次重新播種值為 1 → 只用 P0，正是我們要的。
- 附加池的**雜湊**而非池本身 → 實作只需保存每個池的雜湊中間狀態。
- 一旦某個 i 不整除，後面的 i 也都不會整除 → 可提早跳出迴圈。
- 事件資料上限 32 bytes：來源只該傳遞少數真正不可預測的 bytes；大量資料應先雜湊。`AddRandomEvent` 必須很快返回；多數實作需要 mutex 序列化呼叫（多執行緒要非常小心）。來源若連呼叫的時間都沒有，可先放入緩衝區，由另一個行程餵給 accumulator。

## 7. 種子檔管理 ⭐

問題：重開機後要等熵源產生足夠事件才能第一次重新播種，而且也不保證第一次之後的狀態對攻擊者不可預測。

解法：**種子檔**——PRNG 保留一個裝滿熵的檔案（不給其他人用），重開機後讀它進入未知狀態，**用過後立即重寫**。

```
function WriteSeedFile(R, f)
    write(f, RandomData(R, 64))

function UpdateSeedFile(R, f)
    s ← read(f)
    assert length(s) = 64
    Reseed(G, s)
    write(f, RandomData(R, 64))
```

**為何讀取與更新必須在同一個操作中？** ⭐

```
開機 → 讀種子檔、重新播種
攻擊者在種子檔更新前請求亂數 → 拿到 X → 立刻重開機
開機 → 讀到「同一份」種子檔、重新播種
無辜使用者在更新前請求亂數 → 也拿到 X   ← 機密性被破壞（X 可能是金鑰！）
```

→ 重新播種與寫入新種子之間，**不得有任何其他對 PRNG 的使用**；種子檔要保密；所有更新必須是**原子的**。

### 7.1 何時讀寫

- **每次開機後**讀取並更新。
- 執行期間收集的熵也要反映到種子檔：**關機時重寫**；有些電腦從不正常關機 → **每 10 分鐘左右**也重寫一次。

### 7.2 備份與虛擬機器

PRNG 狀態**絕不能重複**，但檔案系統並非為此設計：

- **備份**：備份整個檔案系統 → 重開機（使用種子檔）→ 之後還原備份 → 再重開機 → **同一份種子檔再次被使用**，在累積足夠熵之前兩次輸出相同。攻擊者可藉此取得他人拿到的亂數。
  - 沒有直接防禦；理想上備份系統要「懂 PRNG」，但大概強人所難。
  - 把種子檔與**目前時間**一起雜湊（除非攻擊者把時鐘調回同一時間），或與備份系統的**還原次數計數器**一起雜湊。
- **虛擬機器**：VM 狀態存檔後啟動兩次 → 兩個實例從同一 PRNG 狀態開始。部分備份的解法也適用。
- 高度依賴平台，值得進一步研究。

### 7.3 檔案系統更新的原子性

- 多數 OS 寫檔只更新記憶體緩衝區，很久之後才真正寫入磁碟；有「flush」命令，但可能非常慢，作者還見過**硬體對軟體說謊**、根本沒正確實作 flush。
- 必須**確定資料已寫入磁性媒體**後，才允許任何使用者請求亂數。
- 檔案資料與檔案管理資訊分開處理 → 重寫時管理資訊可能暫時不一致；此時斷電可能損毀甚至遺失種子檔。
- **日誌式檔案系統（journaling）**較可靠，但很多常見檔案系統只對**管理資訊**記日誌，不夠。
- 在硬體與 OS 支援完全原子、永久的更新之前，不存在完美方案——研究你的平台，盡力而為。

### 7.4 第一次開機

工廠安裝 OS 的新 PC：所有機器完全相同、沒有種子檔，OS 卻馬上要產生一些管理用的金鑰。

- 等事件累積？很久，而且不知道何時才夠產生好金鑰。
- 好方法：**安裝程序為每台機器產生隨機種子檔**——例如用另一台電腦的 PRNG 產生；或請測試人員晃動滑鼠收集初始熵。
- **不提供初始熵不是選項**：重要金鑰很可能在安裝後不久就被產生。外部亂數來源建立第一個種子檔大概是最好的方案。

> 後見之明：2012 年 Heninger 等人掃描網際網路，發現大量嵌入式裝置因**開機時熵不足**而產生了可分解的 RSA 金鑰、相同的 SSH 金鑰（*Mining Your Ps and Qs*）——正是本節警告的情境。

## 8. 選擇隨機元素 ⭐

目標：從 {0, …, n−1} **均勻**選取（每個元素機率完全相同）。

| n | 做法 |
|---|---|
| 0 | 錯誤 |
| 1 | 沒得選 |
| 2^k | 取 k 個隨機位元即可 |
| 其他 | **不能直接取模！** |

**取模的偏差**：取 32-bit 隨機數 mod 5，令 m = ⌊2^32 / 5⌋，則 1、2、3、4 的機率各為 m/2^32，而 0 是 (m+1)/2^32。偏差很小，但在允許攻擊者的 2^128 步內很容易偵測。

**正確方法：試誤法（rejection sampling）**

```
1. 令 k 為使 2^k ≥ n 的最小整數
2. 用 PRNG 產生 k-bit 隨機數 K（範圍 0 … 2^k − 1）
3. 若 K ≥ n，回到步驟 2
4. 回傳 K
```

最壞情況平均丟掉一半的嘗試。**改良版**：選一個方便的 k（如 32），令 q = ⌊2^k / n⌋，先用試誤法在 0 … nq−1 中選 r，回傳 r mod n。
例：2^32 − 1 是 5 的倍數，在 0 … 2^32 − 2 中選（幾乎不用重試），再 mod 5。

> 不丟棄任何隨機位元就做不到非 2 的冪次的均勻分佈——但沒關係，好的 PRNG 不缺隨機位元。

## 9. 參考實作（Python）

依書中虛擬碼寫成（使用 `cryptography` 函式庫；已實測：未播種時拒絕輸出、可正常產生金鑰、`random_below(6)` 6000 次分佈均勻、天真的 `mod 192` 讓 0–63 的機率加倍）。

```python
import hashlib, time
from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes

def shad256(data: bytes) -> bytes:
    return hashlib.sha256(hashlib.sha256(b"\x00" * 64 + data).digest()).digest()

class Generator:
    def __init__(self):
        self.K, self.C = b"\x00" * 32, 0            # C == 0 表示尚未播種

    def reseed(self, s: bytes):
        self.K = shad256(self.K + s)
        self.C += 1

    def _blocks(self, k: int) -> bytes:
        assert self.C != 0, "generator not seeded"
        enc = Cipher(algorithms.AES(self.K), modes.ECB()).encryptor()
        out = []
        for _ in range(k):
            out.append(enc.update(self.C.to_bytes(16, "little")))
            self.C += 1
        return b"".join(out)

    def pseudo_random_data(self, n: int) -> bytes:
        assert 0 <= n <= 2**20
        r = self._blocks((n + 15) // 16)[:n]
        self.K = self._blocks(2)                   # 換金鑰：舊輸出無法再被重算
        return r

class Fortuna:
    MIN_POOL_SIZE = 64

    @staticmethod
    def _new_pool():
        return hashlib.sha256(b"\x00" * 64)        # SHAd-256 的內層：先吃一個全 0 區塊

    def __init__(self):
        self.pools = [self._new_pool() for _ in range(32)]   # 只保留雜湊的中間狀態
        self.pool0_len = 0
        self.reseed_cnt = 0
        self.last_reseed = -1.0
        self.G = Generator()

    def add_random_event(self, s: int, i: int, e: bytes):
        assert 1 <= len(e) <= 32 and 0 <= s <= 255 and 0 <= i <= 31
        self.pools[i].update(bytes([s, len(e)]) + e)
        if i == 0:
            self.pool0_len += 2 + len(e)

    def random_data(self, n: int) -> bytes:
        now = time.monotonic()
        if self.pool0_len >= self.MIN_POOL_SIZE and now - self.last_reseed > 0.1:
            self.reseed_cnt += 1
            s = b""
            for i in range(32):
                if self.reseed_cnt % (1 << i):
                    break                          # 一旦不整除，後面也都不會整除
                s += hashlib.sha256(self.pools[i].digest()).digest()   # = SHAd-256(Pi)
                self.pools[i] = self._new_pool()
                if i == 0:
                    self.pool0_len = 0
            self.G.reseed(s)
            self.last_reseed = now
        if self.reseed_cnt == 0:
            raise RuntimeError("PRNG not seeded yet")
        return self.G.pseudo_random_data(n)

def random_below(prng, n: int) -> int:
    """均勻選取 0..n-1：試誤法（rejection sampling）"""
    assert n >= 1
    if n == 1:
        return 0
    k = (n - 1).bit_length()
    nbytes = (k + 7) // 8
    while True:
        K = int.from_bytes(prng.random_data(nbytes), "little") & ((1 << k) - 1)
        if K < n:
            return K

if __name__ == "__main__":
    f = Fortuna()
    try:
        f.random_data(16)
    except RuntimeError as e:
        print("before seeding:", e)
    src_pool = 0
    for t in range(1000):                          # 模擬一個時序來源
        f.add_random_event(7, src_pool, time.perf_counter_ns().to_bytes(8, "little")[:2])
        src_pool = (src_pool + 1) % 32            # 由來源自己輪流分配池
    print("key:", f.random_data(32).hex())
    print("dice:", [random_below(f, 6) + 1 for _ in range(10)])
    import collections
    c = collections.Counter(b % 192 for b in f.random_data(192000))
    print("naive mod 192: P(0..63)≈%.4f  P(64..191)≈%.4f" % (
        sum(c[i] for i in range(64)) / 64 / 192000, sum(c[i] for i in range(64, 192)) / 128 / 192000))
```

實作重點對照：

| 書中規格 | 程式 |
|---|---|
| C = 0 表示未播種 | `Generator.__init__`、`_blocks` 的 `assert` |
| 每次請求後換金鑰 | `pseudo_random_data` 最後一行 |
| 換金鑰不重設計數器 | `_blocks` 只遞增 `self.C` |
| 只保存池的雜湊中間狀態 | `self.pools` 是 hasher 物件 |
| SHAd-256(Pi) | 池以 64 個 0 bytes 起始，外層再 SHA-256 一次 |
| 由來源指定池編號 | `add_random_event(s, i, e)` |
| 重新播種延後到請求時、間隔 > 100 ms | `random_data` 開頭 |
| 2^i 整除才使用 Pi，否則提早跳出 | `if self.reseed_cnt % (1 << i): break` |
| 均勻選取用試誤法 | `random_below` |

> 種子檔、mutex、記憶體清除等平台相關部分在此省略。

## 10. 設計觀念整理

| 觀念 | 說明 |
|---|---|
| 熵是相對的 | 攻擊者知道越多，熵越少；對熵源要悲觀 |
| 真亂數只用來播種 | 直接使用真亂數反而更脆弱 |
| 狀態外洩後要能恢復 | 傳統 PRNG 一旦外洩永遠不安全 |
| 池化對抗逐次猜測 | 少量熵逐次加入會被窮舉跟上 |
| 不要估計熵 | Yarrow 的估計器不可能正確 → Fortuna 用 32 個指數間隔的池 |
| 常數因子的保證 | 最多 64 倍的隨機性需求，但永遠會恢復 |
| 速度也是安全 | 太慢的好 PRNG 會讓人換成爛 PRNG |
| 封裝 generator | 防止使用者繞過重新播種 |
| 無法處置的檢查不如不檢查 | accumulator 不驗證池順序 |
| 種子檔讀寫要原子 | 重開機重放攻擊；備份與 VM 讓狀態重複 |
| 均勻選取用試誤法 | 取模有偏差 |

> 對照第一本書：Fortuna 把 generator 隱藏在 accumulator 後面、只暴露 `RandomData`，正是 Hanson 的**不透明型別（opaque type）**與「介面只暴露必要操作」的思路——使用者無法觸及內部狀態，也就無法誤用。

## 13. 本章重點整理

1. 亂數 = 對攻擊者**不可預測**；熵是相對於觀察者的，對熵源估計要悲觀。
2. 真亂數難取得、量少、會壞、難估計 → **只用來播種密碼學強度的 PRNG**。
3. 絕不使用程式庫的一般 `random()`。
4. PRNG 要能抵抗：從輸出推狀態、**狀態外洩後恢復**、狀態重用（VM、備份）、少量熵逐次加入的窮舉。
5. **Fortuna** = Generator（AES-CTR、每次請求後換金鑰、每次 ≤ 1 MB）+ Accumulator（**32 個池**，第 r 次重新播種用所有 2^i | r 的池）+ 種子檔。
6. 不需熵估計，最多 64 倍的代價就保證必然恢復。
7. 種子檔：開機即讀取並**原子地**更新；關機與每 10 分鐘重寫；首次開機必須提供外部熵。
8. 選取隨機元素用**試誤法**，不要直接取模。

> **一句話**：別估計熵，讓 32 個指數間隔的池替你兜底——真亂數只拿來播種，輸出交給每次都會換金鑰的 AES-CTR。
