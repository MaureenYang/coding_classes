# 第 6 章　訊息認證碼（Message Authentication Codes）

> 《Cryptography Engineering》— Ferguson, Schneier, Kohno，本章頁碼：p.89–98

---

## 1. 本章定位

第 4 章反覆警告：**加密只防偷看，不防竄改**。本章介紹補上這一塊的工具——**MAC（訊息認證碼）**。

```
Alice                                  Bob
  m, T = mac(K, m)  ───────────►  收到 m', T'
                                   重算 mac(K, m') == T' ?
                                   不符 → 丟棄
```

- MAC 與加密一樣使用**雙方共享、Eve 不知道**的金鑰 K。
- Eve 沒有 K，就算不出被竄改訊息的正確 MAC。
- 本章只談認證；**加密 + 認證如何組合**留到第 7 章。

---

## 2. MAC 做什麼

- 輸入：固定長度的金鑰 K、任意長度的訊息 m。
- 輸出：固定長度的 **MAC 值**，又稱 **tag**。

```
T = mac(K, m)
```

> ⚠️ 「正確使用 MAC」比「把 MAC 套在訊息上」複雜得多——見 §7。

---

## 3. 理想 MAC 與 MAC 的安全性 ⭐

與理想區塊加密器的差別：區塊加密器是**置換**，MAC 不是。

> **定義 8**：理想 MAC 函式是從「所有可能輸入（金鑰 + 訊息）」到 n-bit 輸出的**隨機映射**。
>
> **定義 9**：對 MAC 的**攻擊**，就是能把它與理想 MAC 區分開來的**非泛用方法**。

- 實務上攻擊者不知道 K——或更精確地說，**不完全知道**：系統其他部分的弱點可能洩漏 K 的部分資訊。
- 作者偏好這個定義，因為它**涵蓋範圍廣**：弱金鑰、相關金鑰、部分金鑰洩漏等，在傳統形式化定義中不一定被涵蓋。即使函式被濫用或用在不尋常環境，定義依然穩健。

**較嚴格（較窄）的標準定義——不可偽造性（unforgeability）**：

> 攻擊者自選 n 則訊息並取得它們的 MAC 值，之後必須提出 **n + 1** 則各自帶有效 MAC 的訊息。做不到 → MAC 不可偽造。

---

## 4. CBC-MAC 與 CMAC ⭐

### 4.1 CBC-MAC

用 CBC 模式加密訊息，**只留最後一個密文區塊**：

```
H0  := IV（通常固定為 0）
Hi  := E_K(Pi ⊕ Hi−1)
MAC := Hk          （有時只取一部分，例如一半）
```

**絕對不要讓加密與認證共用金鑰**，尤其是 CBC 加密 + CBC-MAC 同一把金鑰：MAC 會等於最後一個密文區塊；視使用時機與方式，可能同時破壞 CBC 加密的機密性與 CBC-MAC 的真實性。

### 4.2 碰撞攻擊（安全性只剩區塊大小的一半）

CBC-MAC 的結構性質：

```
若 M(a) = M(b)，則 M(a ‖ c) = M(b ‖ c)

因為 M(a ‖ c) = E_K(c ⊕ M(a))
     M(b ‖ c) = E_K(c ⊕ M(b))
```

攻擊兩階段：

1. 收集大量訊息的 MAC，直到碰撞（128-bit 區塊需約 2^64 步，生日悖論）→ 得到 a、b。
2. 讓發送者認證 a ‖ c，再把訊息換成 b ‖ c，**MAC 不變**，接收者照單全收。

> 「讓發送者認證攻擊者造的訊息」在偏執模型中完全合理，現實中也有許多此類情境。即使加上長度欄位與填充規則，此攻擊也有很多變形仍然有效。

**為何是「非泛用」攻擊？** 找碰撞本身對理想 MAC 一樣做得到；但對理想 MAC，拿到 M(a) = M(b) **不能用來偽造新訊息**，對 CBC-MAC 卻可以。

另一變形：若 M(a ‖ c) = M(b ‖ c)（c 為一個區塊），則對任意區塊 d，M(a ‖ d) = M(b ‖ d)。

**理論結果**：在特定證明模型下，**只對同長度訊息使用**時，128-bit 區塊的 CBC-MAC 提供 **64 bits 安全**——低於 128-bit 設計強度。若有 256-bit 區塊的加密器就沒問題了。

### 4.3 可變長度訊息的簡單偽造

若 a、b 各一個區塊，發送者 MAC 了 a、b、a ‖ b，攻擊者可偽造從未送出的訊息：

```
b ‖ (M(b) ⊕ M(a) ⊕ b)    的 tag  =  M(a ‖ b)
```

（證明見習題 6.3。）問題根源：發送者對**不同長度**的訊息做 MAC。

### 4.4 若一定要用 CBC-MAC

1. 構造 s = ℓ ‖ m，其中 ℓ 是 m 的長度，以**固定長度格式**編碼；
2. 填充 s 到區塊大小的倍數（§4.1 的方法）；
3. 對 s 套用 CBC-MAC；
4. 輸出最後一個區塊（或其一部分），**不可輸出任何中間值**。

**CBC-MAC 的優點**：與加密模式用同一種運算。在許多系統中，加密與 MAC 是唯二作用在大量資料上的函式（效能關鍵），共用基本運算讓實作（尤其硬體）更有效率。

### 4.5 CMAC（推薦的替代方案）

- 基於 CBC-MAC，NIST 標準化。
- 唯一的不同：**最後一個區塊**在最後一次加密前，先 xor 一個**由金鑰衍生的特殊值**；依訊息長度是否為區塊倍數，選用兩個值之一。
- 這破壞了 CBC-MAC 在多種長度訊息下的攻擊。

## 5. HMAC ⭐⭐

理想 MAC 是「以金鑰和訊息為輸入的隨機映射」，而雜湊函式（試圖）是「以訊息為輸入的隨機映射」——用雜湊建 MAC 是很自然的想法。

HMAC 設計者很清楚第 5 章的雜湊弱點，所以**不採用**這些簡單構造：

| 構造 | 問題 |
|---|---|
| h(K ‖ m) | 長度擴展：可附加資料並更新 tag |
| h(m ‖ K) | 部分訊息碰撞：找到 h(m) = h(m') 後可互換 |
| h(K ‖ m ‖ K) | 在標準迭代雜湊下仍有問題 |

**HMAC 的定義**：

```
HMAC(K, m) = h( (K ⊕ a) ‖ h( (K ⊕ b) ‖ m ) )
              外層                內層
a、b 為規範指定的常數（opad、ipad）
```

- 訊息只被雜湊**一次**，結果再與金鑰一起雜湊。
- 適用於第 5 章所有迭代雜湊。
- **不受 SHA-1 碰撞攻擊直接影響**：被雜湊的開頭取決於秘密金鑰，攻擊者不知道。所以 HMAC-SHA-1 沒有 SHA-1 本身那麼糟——但攻擊會越來越好，作者仍認為 HMAC-SHA-1 **風險太高，不推薦**。

**安全性**：

- 設計者證明了安全界限；能避免恢復 K 的攻擊，也能避免攻擊者**不與系統互動**就能完成的攻擊。
- 但與 CMAC 一樣，仍受限於 **n/2 bits**——存在利用迭代雜湊內部碰撞的泛用生日攻擊。HMAC 的構造讓它需要 **2^(n/2) 次與受攻擊系統的互動**，比在自己電腦上算 2^(n/2) 次困難得多。

> HMAC 論文舉了很多「基本元件有意料之外性質」導致的問題——這正是作者執著於**為密碼元件提供簡單行為規格**的原因。

作者喜歡 HMAC：簡潔、有效率、易實作、到處都有函式庫。但要達到 128-bit 安全，**只搭配 256-bit 雜湊，例如 SHA-256**。

---

## 6. GMAC

- NIST 新標準化，軟硬體都非常有效率，為 128-bit 區塊加密器設計。
- 與 CBC-MAC / CMAC / HMAC **根本不同**：輸入有三個——**金鑰、訊息、nonce**。nonce 接收方也要知道（明送或隱含，如封包計數器）。
- 介面不同 → 不符合 §3 的「理想 MAC」定義，只能用**不可偽造性**定義。

**內部運作**：

```
tag = CTR 加密( universal_hash(訊息) )，IV 由 nonce 衍生
```

**通用雜湊（universal hash）** 與第 5 章的雜湊完全不同，是一個比 SHA 簡單得多的數學函式。

**作者的警告**：

1. 和 HMAC、CMAC 一樣，**最多 64 bits 安全**。
2. **短 tag 會大幅削弱安全性**：截成 32 bits，直覺以為有 32 bits 安全，但實際上約 **2^16 次嘗試**就能偽造。→ 需要短 tag 時**不要用 GMAC**。
3. **依賴 nonce**：nonce 重複就可能讓安全崩潰；如 §4.7 所說，現實系統一再在 nonce 上出錯 → 避免把 nonce 暴露給應用開發者。

---

## 7. 該選哪個 MAC？⭐

> **HMAC-SHA-256。**

- 想用完整的 256 bits。多數系統用 64 或 96-bit 的 MAC，覺得這已經是不少開銷。
- 依目前所知，按傳統方式使用時，MAC 值沒有碰撞攻擊，所以把 HMAC-SHA-256 **截斷到 128 bits 應該安全**。
- 作者不完全滿意：應該可以有更快的 MAC，但在被發表、分析、廣泛接受之前沒得選。GMAC 快，但最多 64 bits 安全、不適合短 tag、又需要 nonce。

| MAC | 基礎 | 需 nonce | 安全上限 | 作者評價 |
|---|---|---|---|---|
| CBC-MAC | 區塊加密器 | 否 | 64 bits（同長度） | 難以正確使用，不直接推薦 |
| CMAC | 區塊加密器 | 否 | 64 bits | 可接受的替代 |
| **HMAC-SHA-256** | 雜湊 | 否 | 128 bits | ✅ **推薦** |
| GMAC | 通用雜湊 + CTR | **是** | 64 bits；短 tag 更差 | 快，但小心 |

## 8. 使用 MAC ⭐⭐

Bob 收到有效的 mac(K, m)，他只知道一件事：

> **某個知道 K 的人，認可了 m。**

要確認這句話對你需要的所有安全性質都**足夠**。

### 8.1 常見陷阱

| 陷阱 | 情境 | 對策 |
|---|---|---|
| **重放攻擊** | Eve 錄下 Alice→Bob 的訊息，稍後再送一次 | 認證訊息編號 |
| **反射攻擊** | 雙向共用 K，Eve 把 Bob 收到的訊息送回給 Alice | 不同方向用不同金鑰，或認證方向 |
| **額外資料未認證** | 訊息編號、來源、目的地等 header 沒被保護 | 對 d ‖ m 做 MAC（且 d ‖ m 的對應必須一對一） |

### 8.2 Horton 原則 ⭐⭐⭐

> **認證你的「意思」，而不是你「說了什麼」。**
> *Authenticate what is meant, not what is said.*
>
> （名字來自 Dr. Seuss 童書裡的大象 Horton——「I meant what I said, and I said what I meant」。）

MAC 只認證**一串 bytes**；但 Alice 與 Bob 要認證的是**具有特定意義的訊息**。「說的」（傳送的 bytes）與「意思」（如何解讀）之間的落差非常關鍵。

**例子**：Alice 認證 m := a ‖ b ‖ c。Bob 收到後要拆成 a、b、c——**怎麼拆？**

- 欄位固定長度時很簡單。
- 但不久就會出現可變長度欄位，或新版軟體使用更長的欄位，還得向後相容舊版。
- 一旦欄位長度不固定，Bob 就要**從上下文推導**——而**上下文可能被攻擊者操縱**。

```
Alice（舊版，短欄位） ──m, MAC──►  Eve 讓 Bob 以為用的是新協定
                                   Bob（新版）用長欄位拆 m
                                   → MAC 正確，但拿到「經認證的假資料」
```

（MAC 系統不應該依賴系統其他部分的安全。）

**正確做法**：MAC 不只認證 m，還要認證 **Bob 用來把 m 解讀成意義的所有資訊**：

- 協定識別碼、協定版本號、協定訊息識別碼、各欄位大小……
- 部分解法：不要單純串接欄位，改用**不需額外資訊就能解析**的資料結構（例如 XML）。

### 8.3 為何低層認證不夠？

Horton 原則也說明了**低層協定的認證無法滿足高層協定**：IP 封包層的認證不知道 e-mail 程式會如何解讀資料，也就無法檢查「解讀時的上下文」是否與「發送時的上下文」相同。

→ 唯一的解法：e-mail 程式**自己**對交換的資料做認證（當然，低層認證仍保留）。

### 8.4 總結

> 做認證時，永遠仔細想想**還有哪些資訊應該一起認證**；把所有資訊（含訊息）編碼成 bytes 的方式，必須能**唯一地解析回各個欄位**。對 d ‖ m 做認證時，也要有固定規則把它拆回 d 和 m。

## 9. 設計觀念整理

| 觀念 | 說明 |
|---|---|
| 加密與認證分開金鑰 | 尤其不要 CBC 加密 + CBC-MAC 共用 |
| 寬廣的安全定義 | 涵蓋相關金鑰、部分金鑰洩漏等「不尋常用法」 |
| 不要拼裝雜湊 | h(K‖m)、h(m‖K) 都有陷阱 → 用 HMAC |
| 生日界限無所不在 | CBC-MAC、CMAC、HMAC、GMAC 都受 n/2 限制 |
| 避開 nonce | GMAC 快，但把 nonce 責任丟給使用者 |
| **Horton 原則** | 認證意義（含解析規則、版本、欄位長度），而非 bytes |
| 端到端認證 | 低層認證無法替高層保證語意 |

> 對照第一本書：Hanson 在 `Fmt`、`Text` 等介面中強調**明確、無歧義的格式規格**。Horton 原則可以看成同一件事的安全版本：**序列化格式本身就是安全的一部分**——若解析需要「猜」，攻擊者就有機會讓你猜錯。

## 10. 延伸閱讀重點

- **Bellare–Canetti–Krawczyk**（1996）：HMAC 原始論文與安全證明；RFC 2104。
- **NIST SP 800-38B**（CMAC）、**SP 800-38D**（GCM/GMAC）。
- **Ferguson**（2005）：*Authentication weaknesses in GCM*——短 tag 的偽造攻擊。
- 後見之明：**Poly1305** 也是通用雜湊型 MAC，與 ChaCha20 組成廣泛使用的 AEAD；**KMAC**（SHA-3 系）因無長度擴展，可直接用 h(K ‖ m) 的形式。
- **時序攻擊**：驗證 tag 時要用常數時間比較（不要用 `memcmp` 提早結束）。

## 12. 本章重點整理

1. MAC 偵測竄改：`T = mac(K, m)`；有效 tag 只代表「知道 K 的人認可了 m」。
2. 安全定義：與**理想 MAC（隨機映射）**不可區分；較窄的定義是不可偽造性。
3. **CBC-MAC** 有碰撞延伸與可變長度偽造問題；必須前置長度；更好用 **CMAC**。
4. **HMAC** = h((K⊕opad) ‖ h((K⊕ipad) ‖ m))，避開雜湊的長度擴展。
5. 所有常見 MAC 都受生日界限：要 128-bit 安全，用 **HMAC-SHA-256**（可截到 128 bits）。
6. GMAC 快，但需 nonce、短 tag 很危險。
7. 小心重放、反射、未認證的 header；遵守 **Horton 原則**——認證意義，不只是 bytes。

> **一句話**：用 HMAC-SHA-256 認證，但真正難的是「該認證什麼」——把版本、欄位長度、訊息編號等所有影響解讀的資訊都包進去。
