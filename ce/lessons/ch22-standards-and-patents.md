# 第 22 章　標準與專利（Standards and Patents）

> 《Cryptography Engineering》— Ferguson, Schneier, Kohno，本章頁碼：p.317–322

---

## 1. 本章定位

第五部「其他」的第一章。除了密碼學本身，還有兩件事你真的應該知道：**標準**與**專利**。作者在這裡提出他們對兩者的觀點。

> **標準是一把雙面刃。**
> - 一方面，**沒有人會因為你用了標準而怪你**（ch3 談 AES 時就說過：「沒有人會因為選了 AES 而被開除」）；
> - 另一方面，**許多安全標準根本行不通**。
>
> 這是個兩難。本書聚焦於密碼學的**工程**面向，但只要你做任何密碼工程，就會碰到標準——所以需要對它們有些了解。

## 2. 標準的制定過程 ⭐

### 2.1 委員會如何運作

```
標準化組織（IETF、IEEE、ISO、CEN……）
   │ 察覺到對新標準或改良標準的需求
   ▼
成立委員會（工作小組、任務小組……可能有階層結構）
   │ 成員自願加入，幾乎任何人都被接受（有些程序門檻，但沒有實質篩選）
   │ 規模可達數百人 → 拆成子委員會；大部分工作在幾十人以內的小組完成
   ▼
每隔幾個月開會一次：所有人飛到某個城市，在飯店開幾天會
會議之間各自做提案與簡報；會議上決定走向
通常由一位編輯把所有提案整合成一份標準文件
   ▼
緩慢的過程，常常要好幾年
```

### 2.2 誰會來參加？

當委員很**昂貴**：除了時間，旅費與飯店都不便宜——所以**每個人都是公司派來的**。公司的動機：

| 動機 | 說明 |
|---|---|
| **互通** | 要賣必須與其他公司產品互通的產品 → 需要標準，而追蹤標準化過程最好的方法就是在場 |
| **盯住競爭者** | 不能讓競爭者寫標準——他們會讓你處於競爭劣勢：偏向自家技術或需求，或納入他們擁有專利的技術 |
| **拖延** | 有時公司**不想要**標準，於是出席會議設法拖慢進度，讓自家專有方案有時間攻佔市場 |

> 現實中，這些動機（再加上好幾種其他動機）以不同比例混在一起，形成**非常複雜的政治環境**。

（呼應 ch13 的**誘因分析**：先問「誰派他來、他想得到什麼」，就能預測委員會的行為。）

### 2.3 結果

- 不意外地，**相當多標準化委員會失敗**：什麼都沒產出、產出糟透了的東西、或陷入僵局被市場超越，最後只好把已經攻佔市場的系統定為標準。
- 成功的委員會在幾年後產出一份標準文件。
- 標準寫好後大家各自去實作——當然導致**無法互通**的系統 → 還需要第二個過程：**互通性測試**，各廠商調整實作以便彼此相容。

**這個過程的問題** ⭐：

> 委員會的政治結構**很少重視產出好的技術標準**。最重要的是**達成共識**。
>
> **當每個人都同樣不滿意時，標準就完成了。**

- 為了安撫不同派系，標準有許多**選項、擴充功能、無用的替代方案**……
- 每個派系都有自己的想法、意見與焦點 → 最好的妥協常常是**自相矛盾**的。許多標準內部不一致，甚至自我矛盾。
- 更複雜的是：標準化進行中，公司已經根據**草案**開始實作 → 更難改變任何東西（有人已經實作了，不想重做）。不同公司以不同方式實作，然後在委員會中爭吵，要求標準調整以符合自己的實作。**有時唯一的妥協是選一個沒有任何公司實作過的方案**——只為了確保大家同樣不滿意。

> 在這類討論中，**技術優劣根本不是重點**。

### 2.4 標準文件本身

- 大多數標準**極難閱讀**：委員會設計的文件，過程中幾乎沒有壓力要求它清楚、簡潔、精確或易讀。
- 事實上，**極難讀的文件反而更好操作**：只有少數委員看得懂，他們就能在不被其他成員打擾的情況下處理它。
- 啃數百頁寫得很爛的文件一點也不好玩 → 大多數委員最後不讀完整草案，只檢查自己感興趣的有限部分。

### 2.5 功能

- 互通性測試**一定**需要；實作出來的東西常與標準定義的**微妙地不同**，而各公司已經在行銷產品，有時改不了了。
- 作者看過 **A 牌產品藉由 B 牌實作偏離標準的方式來辨認對方**，再調整自己的行為讓雙方能運作。
- 標準常有非常多選項，但實際實作只用特定一組選項（當然還有一些限制和擴充——因為標準文件本身描述的東西**行不通**）；而實作與標準之間的差異，當然**沒有記錄**。

> 整個過程**勉強**可行——但只對**核心功能**。無線網路能讓你連線，但跨廠商的管理功能大概不會動；簡單的 HTML 頁面在所有瀏覽器上都顯示正確，但較進階的排版功能在不同瀏覽器結果不同。我們都太習慣了，幾乎沒注意到。
>
> 很不幸：身為一個產業，我們似乎**無法制定出可讀、正確的標準**，更別說讓不同產品在最基本功能以外互通了。

### 2.6 安全 ⭐⭐

> 這些缺陷意味著：**典型的標準制定方法根本不適用於安全目的。**

- 安全面對**主動的攻擊者**，會去搜尋標準中最偏僻的角落；
- 安全取決於**最弱環節**：任何一個錯誤都可能致命；
- 作者一再強調**簡單**的重要——標準一點也不簡單。委員會流程排除了簡單，必然產出比委員會中任何人能完全理解的還要複雜的東西。**單憑這一點，結果就不可能安全。**

**標準化人士的典型回應**：

> 「技術人員總是想做出完美的標準。」……「政治現實就是我們必須妥協。」……「系統就是這樣運作的。」……「看看我們達成了什麼。」……「事情運作得還不錯。」

**在安全上，這不夠好** ⭐：

> 標準定案後**還需要互通性測試**這件事本身，就證明了委員會標準在安全上行不通：如果標準的**功能**部分（簡單的部分）都不足以在不測試的情況下產生可互通的系統，那**安全**部分不可能不經測試就達到安全——而我們知道，**安全是無法測試的**（ch8）。
>
> 當然，也許能做出一個只實作標準部分功能、而且安全的實作——但這對安全標準來說不夠。**安全標準宣稱：只要遵守它，你就能達到某個安全等級。**
>
> **安全太難了，不能交給委員會。** 所以每當有人建議使用委員會寫的密碼學標準，我們總是極度不情願。

這個領域有少數有用的標準——**沒有一個是委員會寫的**。有時是一小群人做出單一、一致的設計，而結果被採納為標準時沒有經過太多政治妥協——這些標準可以相當好。以下是最重要的兩個。

## 3. SSL

Web 瀏覽器安全連線到 Web 伺服器所用的安全協定。

| 版本 | 說明 |
|---|---|
| **SSL 2** | 第一個廣泛使用的版本，有數個安全缺陷 |
| **SSL 3** | 改良版，**由三個人設計，沒有任何委員會流程**；廣泛使用，普遍被認為是好協定 |
| **TLS** | IETF 工作小組以此名稱進行 SSL 的標準化與後續發展 |

**警告**：

> SSL 是好協定，但這**不代表**任何使用 SSL 的系統都安全。SSL 依賴 PKI 來認證伺服器，而大多數瀏覽器內建的 PKI 用戶端**寬鬆到整體安全等級相當低**。作者的某個瀏覽器有約 **150 個根憑證、來自 70 個不同的 CA**——所以在考慮任何主動攻擊之前，就有**散佈全球的 35 個組織**（作者原文如此）是我們必須把所有 Web 資訊託付給它們的。

（呼應 ch19：「世上沒有任何組織被所有人信任」——Web PKI 卻要你同時信任幾十個。）

- SSL 從未真正被標準化：Netscape 直接實作，成為**事實標準**。
- SSL 與 TLS 的差異看起來相當小，作者沒有理由認為 TLS 不如 SSL 3。
- **但**——考慮到 IETF 最近設計安全協定（例如 **IPsec**）的紀錄，存在**委員會效應再次發威**、不必要地把一個好標準複雜化的危險。

> 後見之明：作者的擔憂部分應驗——TLS 1.0–1.2 累積了大量選項與舊密碼套件，催生出 BEAST、CRIME、Lucky 13、POODLE、FREAK、Logjam 等攻擊；SSL 3 本身也在 2014 年被 POODLE 攻破而廢止。但 **TLS 1.3**（2018）反其道而行：大刀砍掉選項、只保留 AEAD 與前向安全的金鑰交換，並在設計過程中邀請學術界做形式化分析——某種程度上正是採納了本章的批評。

## 4. AES：以競賽制定標準 ⭐⭐⭐

> 對我們來說，**AES 是如何標準化安全系統的閃亮典範**。AES 不是委員會設計，而是**競賽設計**。新的 SHA-3 標準化過程也非常相似。

**流程很簡單**：

```
1. 規範系統應該達成什麼
   （可由一個相當小的團體制定，並納入許多不同來源的意見）
2. 公開徵求提案
   （請專家開發滿足需求的完整方案）
3. 從提案中選擇
   （依各種準則評判的直接競賽）
```

**為何有效？**

- 只要把**安全**當作首要準則，提案者就有**既得利益去找出競爭對手提案的安全弱點**——運氣好的話會帶來有用的回饋。（其他情況下可能需要付費請外部專家做安全評估。）

  > 呼應 ch13 的誘因設計：競賽把「找出別人的弱點」變成了參與者的**誘因**，而不是要靠道德或規則去要求。

- 最後若一切順利，選出**單一**提案——原封不動或只做小修改。

> **這不是把不同提案拼湊在一起的時候**——那只會導致另一個委員會設計。若沒有任何提案滿足需求，而且似乎能做出更好的東西，大概應該**重新徵求提案**。

**NIST 的 AES 競賽**：

```
15 個原始提案
   │ 第一輪評估
   ▼
5 個決選者（Rijndael、Serpent、Twofish、RC6、MARS——見 ch3）
   │ 第二輪評估
   ▼
選出優勝者（Rijndael → AES）
```

> 驚人的是，**五個決選者中任何一個都會是好標準**，而且肯定比任何委員會設計都好。作者主要的擔憂是 AES 標準化過程可能**稍微太快**，也許沒有足夠時間徹底分析所有決選者。但整體過程非常好。

**競賽模式的前提** ⭐：

> 競賽模式只有在你有足夠的專家、能做出至少幾個互相競爭的設計時才行得通。但我們認為：**如果你沒有足夠的專家產生好幾份提案，你就不應該標準化任何安全系統。**
>
> 為了簡單與一致（對整體安全至關重要），安全系統必須由**一小群專家**設計；然後需要**其他專家**分析並攻擊這份提案、尋找缺陷。不論用什麼流程，要有任何希望得到好結果，你需要的專家人數至少要能組成**三個提案團隊**。若你有這麼多專家，就應該用競賽模式——它已經證明能產出好的安全標準。

> 後見之明：競賽模式後來成為密碼學標準化的主流——**SHA-3**（2012，Keccak）、**eSTREAM**（串流加密）、**CAESAR**（AEAD，2019）、**NIST 輕量密碼**（2023，Ascon），以及最重要的 **NIST 後量子密碼**競賽（2016–2024，產出 ML-KEM / Kyber 與 ML-DSA / Dilithium 等）。後量子競賽中 SIKE 在最後階段被一台筆電一小時攻破——正好展示了「讓其他專家攻擊」這一步的價值。

## 5. 專利

- 作者在第一版（*Practical Cryptography*）中長篇討論了專利在密碼學中的角色。之後專利生態有些改變，他們也學到了更多。
- 本版**刻意不提供關於專利的具體建議**，但希望你意識到：**專利在密碼學中扮演一定角色**，可能影響你選擇使用或不使用哪些密碼協定。
- 具體建議請**諮詢你的律師**。

本書中與專利相關的例子：

| 章節 | 例子 |
|---|---|
| ch7 | **OCB** 模式效率極高，但專利限制了採用 → 作者偏好無專利的 **CCM**、**GCM** |
| ch14 | 密碼式金鑰協商（**SRP** 等）有多項專利 |
| 歷史 | RSA 專利（美國，2000 年到期）、橢圓曲線的部分實作技巧專利，都曾影響演算法的普及 |

> 後見之明：OCB 的作者 Rogaway 後來免費授權 OCB 給開源與非軍事用途，相關專利也已在 2020 年代陸續到期；許多 PAKE 專利同樣已過期，IETF 因此能標準化 OPAQUE 與 CPace。

## 6. 設計觀念整理

| 觀念 | 說明 |
|---|---|
| 標準是雙面刃 | 沒人怪你用標準，但很多安全標準行不通 |
| 委員會由誘因驅動 | 互通、盯競爭者、拖延——技術優劣不是重點 |
| 共識 = 大家同樣不滿意 | 選項、擴充、自相矛盾 |
| 難讀的文件有人得利 | 只有少數人看得懂、能操作 |
| 需要互通性測試 = 不可能安全 | 功能都測不對，安全更不可能——而安全無法測試 |
| 安全不能交給委員會 | 複雜度超過任何委員的理解 |
| 好標準來自小團隊 | SSL 3（三個人設計） |
| 用了 SSL ≠ 安全 | PKI 用戶端太寬鬆 |
| **競賽制定標準** | AES、SHA-3：小團隊設計、其他專家攻擊、選一個不拼湊 |
| 專家不夠就別標準化 | 至少能組成三個提案團隊 |
| 專利影響選擇 | 問律師 |

> 對照第一本書：Hanson 的《C Interfaces and Implementations》本身就是「**小團隊（一個人）的單一一致設計**」的範例——24 個介面風格一致、規則統一，正是委員會很難產出的東西。而 ANSI C 標準中那些「實作定義行為（implementation-defined）」與「未定義行為（undefined behavior）」，某種程度上正是委員會為了安撫各家編譯器廠商而留下的妥協——Hanson 在書中多次提醒讀者繞開它們。

## 8. 本章重點整理

1. 標準是**雙面刃**：用標準不會被怪，但許多安全標準行不通。
2. 委員會由公司派員組成，動機包括互通、盯住競爭者、拖延；**共識 = 每個人同樣不滿意**，導致選項繁多、自相矛盾、文件難讀。
3. 需要互通性測試證明委員會連功能都做不對；**安全無法測試**，所以**安全不能交給委員會**。
4. 好的安全標準來自**小團隊的單一一致設計**：例如 **SSL 3**（但使用 SSL 不等於安全——瀏覽器的 PKI 太寬鬆）。
5. **AES 競賽**是標準化安全系統的典範：明確需求 → 公開徵求 → 讓專家互相攻擊 → 選一個、不拼湊。
6. 沒有足夠專家組成至少三個提案團隊，就不該標準化安全系統。
7. **專利**會影響你的選擇；具體問題請諮詢律師。

> **一句話**：安全標準不能靠委員會的妥協產生——要嘛由一小群專家做出單一設計，要嘛像 AES 一樣辦一場讓大家互相找漏洞的競賽。
