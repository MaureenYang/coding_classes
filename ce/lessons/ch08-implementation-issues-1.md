# 第 8 章　實作議題（一）（Implementation Issues I）

> 《Cryptography Engineering》— Ferguson, Schneier, Kohno，本章頁碼：p.115–134

---

## 1. 本章定位

第二部「訊息安全」的最後一章，從密碼學本身轉向**密碼學所處的環境**。

**最弱環節原則**（第 1 章）在實作層最明顯：

> 實務上很少聽說密碼系統「被密碼分析攻破」——不是因為大多數系統的密碼學做得好（作者審查過夠多系統，知道並非如此），而是**找實作漏洞比找密碼弱點容易得多**，聰明的攻擊者不會去碰密碼學。

這裡的「系統」非常大：**任何一旦行為異常就會破壞安全性質的東西**都包含在內——作業系統首當其衝，而廣泛使用的作業系統沒有一個是以安全為首要目標設計的。

作者的坦白結論：

> **不可能實作出安全的系統。我們不知道怎麼做，也不知道有誰知道。**

那就放棄嗎？當然不。我們至少要把**自己負責的部分**做對，理由有三：

1. **密碼攻擊是隱形的**：就像小偷拿到你家鑰匙，只要夠小心，你永遠不會發現。
2. **系統安全受限於最弱環節**——要確保那個環節**永遠不是密碼學**。
3. **密碼系統很難更換**：作業系統只跑在一台電腦上，升級容易；通訊協定牽涉許多電腦，修改是惡夢（許多網路仍在用 1970–80 年代的設計）。今天設計的系統，若被廣泛採用，**30 到 50 年後很可能還在用**。

## 2. 寫出正確的程式

核心問題：**資訊業不知道怎麼寫出正確的程式或模組**（「正確」= 完全依規格運作）。原因有三。

### 2.1 規格 ⭐

沒有規格，連「正確」都無從定義。規格分三個階段：

| 文件 | 內容 | 要點 |
|---|---|---|
| **需求（Requirements）** | 非正式描述程式要達成什麼——「能用它做什麼」 | 可以模糊，著重大方向 |
| **功能規格（Functional specification）** ⭐ | 程式行為的**詳細、完整**定義 | 只能規定**外部可量測**的事 |
| **實作設計（Implementation design）** | 程式內部如何運作 | 外部測不到的都在這；切分成模組後，每個模組描述又成為下一層的「需求」 |

**功能規格的檢驗法**：

> 對每一項，問自己：**能否只用外部行為，寫一個測試判斷它是否被遵守？** 不能 → 它不屬於功能規格。
> 功能規格要**完整**：沒寫在裡面的功能就不必實作。它也是測試的基礎。

三者之中**功能規格最重要**：需求可以非正式，實作設計可以只是白板上的草圖，但沒有功能規格，連完成時「達成了什麼」都無法描述。

> 對照第一本書：Hanson 的整本書就是「功能規格優先」的示範——每個介面先以 `.h` 加上精確的語意描述（包括 checked runtime error），再談實作。介面 = 功能規格，`.c` = 實作設計。

### 2.2 測試與修正

「寫程式 → 測試 → 修 bug → 再測」幾乎是通用做法，但結果只是**在最常見情況下勉強能動**的程式。

> **Dijkstra（1972 年圖靈獎演講）：測試只能證明 bug 的存在，永遠不能證明 bug 的不存在。**

程式正確性證明技術還不足以應付日常程式設計。即使沒有完整解法，基本規則仍要做到：

1. **發現 bug → 先寫一個能偵測它的測試**，確認測試抓得到；修好後確認測試通過；之後**每個版本都繼續跑**（回歸測試）。
2. **想想 bug 的成因**：程式其他地方有沒有類似的 bug？全部去檢查。
3. **記錄每一個 bug**：簡單統計就能看出哪部分特別多 bug、哪類錯誤最常見——品質控管需要這種回饋。

作者對「一套方法論解決一切」的說法一律存疑；真相通常在中間。

### 2.3 散漫的態度

- 文書處理器當掉毀了一天的工作，大家覺得很正常，甚至怪使用者「你應該更常存檔」。
- 軟體公司例行出貨已知 bug 的產品，並在授權條款中免除一切責任——汽車廠商找到瑕疵要召回，其他產業都不被允許這樣做。
- 當我們的工作、經濟乃至生命都依賴軟體時，這種態度是問題。

### 2.4 那該怎麼辦？

> 不要以為只需要好的程式設計師、程式碼審查、ISO 9001 流程、大量測試——甚至以上全部。現實困難得多。

**向航空業學習** ⭐：

- 每個人都參與安全系統；幾乎每項操作都有嚴格規則與程序；故障有多重備援。
- 每顆螺帽螺栓都要經過飛行認證；技師每動一次螺絲起子，都要主管檢查簽核；每項修改都被詳細記錄。
- 每次事故都徹底調查所有根本原因並修正。
- 代價：飛機大概比「把圖紙交給普通工程公司」貴一個數量級。
- 成果：在一台**任何故障都可能致命、不能踩煞車停下、只能降落在少數特別準備的地點**的機器上，飛行成了例行公事。

寫正確的軟體或許要貴一個數量級，但考慮到 bug 的社會成本，長期必然划算。

## 3. 寫出安全的軟體 ⭐⭐

**正確 ≠ 安全**：

| | 正確的軟體 | 安全的軟體 |
|---|---|---|
| 要求 | 指定的**功能**：按 A，就會發生 B | 額外要求**功能的缺席**：不論攻擊者做什麼，她都**不能**做 X |
| 可測試性 | 可以測試功能 | **無法測試功能的缺席** |

> **標準的實作技術，完全不足以寫出安全的程式碼。**

作者的立場：**除非你願意為安全實作投入真正的心力，否則搞密碼學沒什麼意義。** 設計密碼系統也許很有趣，但它通常只是大系統中的一小部分。

## 4. 保守秘密 ⭐⭐

安全通道有兩種秘密：**金鑰**與**資料**。兩者都是**暫時性秘密**（資料只在處理訊息時存在，金鑰只在通道期間存在），存在記憶體中——而大多數電腦的記憶體並不安全。（長期儲存秘密見第 21 章。）

### 4.1 清除狀態（Wiping State）

> **基本規則：一旦不再需要，立刻清除。** 保留越久，被存取的機會越高；而且**在失去對儲存媒體的控制之前**一定要清除。

說來簡單，問題卻出乎意料地多：

| 環境 | 問題 |
|---|---|
| **C 程式庫** | 要靠主程式通知「狀態不用了」（例如連線關閉時呼叫清除函式）——但程式不呼叫也能正常運作，所以很可能沒人呼叫 |
| **C++** | 解構子可以清除，是安全程式碼的標準做法；例外展開時 stack 物件會被解構，但 heap 物件要程式自己負責；呼叫 OS 結束程式可能根本不展開 stack |
| **程式結束** | OS 不保證很快清除記憶體，有些 OS 甚至不清除就交給下一個程式 |
| **編譯器最佳化** ⭐ | 編譯器發現被 `memset` 的陣列之後不再使用，就把 `memset` **最佳化掉**——更快，但行為變了。**要檢查編譯器產生的程式碼。** |
| **Java** | 物件都在 heap、由 GC 回收；finalizer 何時執行沒有規範；例外展開時直接丟棄參考而不清理物件。作者的最佳方案：`main` 用 `try-finally`，在 `finally` 中呼叫 `System.gc()` 與 `System.runFinalization()`——仍無保證 |
| **CPU 暫存器** | 多數語言無法清除；但在暫存器很少的 x86 上，資料不太可能存活很久 |
| **Context switch** | 暫存器值被存到記憶體，可能殘留很久——除了修 OS 外無能為力 |

作者的期望：語言層級支援——宣告變數為「sensitive」並保證清除；更好的是語言**總是**清除不再需要的資料。

**C 中避免清除被最佳化掉的常見寫法**（補充）：

```c
#include <string.h>

/* 方法一：透過 volatile 指標逐 byte 寫入，編譯器不能省略 */
static void secure_wipe(void *p, size_t n) {
    volatile unsigned char *vp = p;
    while (n--)
        *vp++ = 0;
}

/* 方法二：使用平台提供、保證不被最佳化的函式
 *   explicit_bzero(p, n)         glibc / BSD
 *   SecureZeroMemory(p, n)       Windows
 *   memset_s(p, n, 0, n)         C11 Annex K
 */

void process(void) {
    unsigned char key[32];
    /* … 使用 key … */
    secure_wipe(key, sizeof key);   /* 一般 memset 在此可能被刪除 */
}
```

### 4.2 Swap 檔

虛擬記憶體系統可能在**程式毫不知情**的情況下，把任意一塊記憶體（包括存金鑰的那塊）寫到磁碟上的 swap 檔：

- 電腦當機或關機後資料仍留在磁碟上；多數 OS 正常關機也不清除。
- 可能沒有任何清除 swap 的機制，資料無限期殘留——誰知道將來誰會碰到這個檔案？

對策：

| 對策 | 限制 |
|---|---|
| 系統呼叫鎖定記憶體不被換出（如 `mlock`、`VirtualLock`） | 要知道秘密存在哪——heap、static、stack……追蹤很複雜又容易錯 |
| 鎖定**整個程式**的記憶體 | 可能失去 OS 服務（如自動配置的 stack），虛擬記憶體也失效 |
| 加密的 swap | 可能需要使用者自己開啟設定 |

真正的解法是 OS 提供保護機密性的虛擬記憶體——超出我們的控制；即使新版 OS 支援，也要檢查它做得好不好，而且應用往往還得在舊系統上跑。

> 註腳原則：**秘密永遠不應未經加密就寫入任何永久媒體。**

### 4.3 快取

- 快取保存資料的**副本**，包括秘密的副本。
- 清除時，有些系統只寫到快取、沒寫到主記憶體；記憶體若在快取 flush 前就被釋放，清除可能「逃過」寫回主記憶體。
- 多 CPU 系統中，快取線被標為「invalid」時，資料本身通常沒被清除。
- 廠商從未規範如何**保證**清除資料——**沒有規範，就不能信任**。
- 危險不大：排除實體攻擊，通常只有 OS 能直接存取快取機制，而我們本來就得信任 OS。但這顯示這些設計**沒有提供實作安全系統所需的功能**。

### 4.4 記憶體的資料殘留 ⭐⭐

很多人驚訝：**覆寫記憶體並不能真正刪除資料。** 資料在同一位置存放久了，那個位置會慢慢「學會」它。

**SRAM**：同一資料存放夠久，就成為該記憶體**偏好的開機狀態**。

> 作者朋友的故事：自製電腦的 BIOS 用某記憶體位置的魔術值判斷是冷開機還是暖開機。一段時間後機器開不了機——記憶體「學會」了魔術值，每次都當成暖開機，沒初始化該初始化的變數。解法是對調記憶體晶片，打亂學到的值。
> 教訓：**記憶體保留的資料比你想的多。**

**DRAM**：

- 電容上的電荷使周圍絕緣材料受應力，造成雜質遷移 → 實體控制記憶體的攻擊者可能還原資料。
- 斷電後，室溫下數值可維持**數秒**，冷卻後更久。
- **冷開機攻擊（cold boot attack，Halderman 等 2008）**：重開機後從記憶體還原金鑰；甚至把記憶體拔下插到另一台電腦上還原。

**Boojum**（名稱取自 Lewis Carroll《獵捕蛇鯊》）——作者的部分解法，適用於金鑰這類**小量資料**：

```
要存 m：
    產生隨機字串 R
    存放  A = R
          B = h(R) ⊕ m        （A、B 放在相距很遠的位置）

讀取： m = h(A) ⊕ B
寫入： B = h(A) ⊕ m_new
清除： 寫入 m_new = 0

定期刷新（例如每秒）：
    產生新的隨機 R'
    A ← R ⊕ R'
    B ← h(R ⊕ R') ⊕ m
```

- 效果：記憶體中**每個 bit 都被寫入一串隨機值**，晶片上沒有任何實體位置會因秘密而持續受應力或不受應力。
- 只要 R 有 k bits 無法還原，攻擊者就得窮舉這 k bits 才能從 h(R) ⊕ m 還原 m。
- **位置選擇**：R 與 h(R) ⊕ m 在晶片上不可相鄰。多數記憶體以列/行矩陣存放 bits，位址相差 **0x5555** 時幾乎不可能相鄰；更好的方法是在很大的位址空間中選兩個**隨機**位址。
- 快取也適用（但無法控制晶片上的位置）；CPU 一般暫存器使用頻繁，問題不大；但**浮點、MMX 等延伸暫存器**用得少，可能有殘留問題。
- **大量資料**：用 Boojum 太貴 → 把資料**加密**後放在一般記憶體，只有**金鑰**用 Boojum 保護。

> 晶片規格中沒有任何條文禁止晶片保留曾經存過的所有資料——當然沒有晶片這樣做，但這表示我們最多只能達到**啟發式的安全**。

### 4.5 被他人存取

| 途徑 | 說明 |
|---|---|
| 共享記憶體 | 通常需雙方設定；但載入共享函式庫時可能自動建立 |
| **除錯器** ⭐ | Windows 可把除錯器附加到執行中程式，讀取記憶體 |
| **Core dump** | UNIX 可強制產生 core dump，檔案中有程式資料的記憶體映像——包括所有秘密 |
| **超級使用者** | UNIX 的 root 可讀取任何記憶體 |

程式通常無法有效防禦這些，但要針對所在平台考慮（例如 Linux 上用 `setrlimit(RLIMIT_CORE, 0)`、`prctl(PR_SET_DUMPABLE, 0)` 降低風險）。

### 4.6 資料完整性

MAC 保護傳輸中的完整性；但若資料能在**記憶體中**被修改，仍有問題。

**ECC 記憶體** ⭐——驗算：

```
假設每 bit 每秒故障機率 10^-15

128 MB ≈ 10^9 bits   → 每秒期望 10^-6 次故障 → 約 10^6 秒 ≈ 11 天一次
1 GB   ≈ 8.6·10^9 bits → 約 1.2·10^5 秒 ≈ 32 小時一次
```

- 伺服器通常用 ECC（記憶體多、執行時間長）；作者希望所有機器都有同樣的穩定性。
- 注意：有些較便宜的模組不存額外的檢查資訊，而是即時重算——完全失去 ECC 的意義；而且電腦所有元件都要支援 ECC。
- 除錯器與超級使用者也能**修改**記憶體——無能為力，但要意識到。

### 4.7 怎麼做？

- 秘密洩漏的途徑很多，要完全有效就得**全部堵住**；但現有 OS 與語言不提供足夠支援，只能盡力，而且工作都與環境相關。
- 這也讓**密碼函式庫**很難做：保護秘密往往需要修改主程式；而主程式本身也處理機密資料（否則就不需要密碼函式庫了）——**安全考量影響系統的每一部分**。

## 5. 程式碼品質 ⭐⭐

### 5.1 簡單

> **複雜是安全的頭號敵人。** 在安全領域，**簡單為王**。

- 作者對此毫不留情（即使不受歡迎）：刪掉所有能刪的選項；去掉很少人用的花俏功能；**遠離委員會設計**——委員會流程為了妥協，總會增加功能或選項。
- **安全通道沒有任何選項**：不允許只加密不認證、或只認證不加密。人們總會要求這些功能，但多半不了解使用「部分安全功能」的後果；多數使用者沒有足夠知識選擇正確的安全選項。
  - 最佳方案：**沒有選項、預設安全**。非要不可，就只提供一個選項：安全或不安全。
- **多重 cipher suite**：盡可能消除。選一個對所有應用都夠安全的模式——各模式的計算差異不大，密碼學也很少是現代電腦的瓶頸。這同時消除了使用者設定弱 cipher suite 的危險：

> 如果選擇加密與認證模式難到**設計者**都做不了決定，**使用者**更不可能做出明智的選擇。

### 5.2 模組化

管理複雜度的主要（也是唯一有效率的）技術：把系統切成模組，分別設計、分析、實作。

- 模組介面應**簡單直接**，行為符合使用者的合理預期。
- 仔細檢視介面：常有些功能或選項是為了**解決別的模組的問題**而存在——盡可能拔掉。**每個模組解決自己的問題。**
- 當介面開始長出奇怪的功能，就是該重新設計的時候了——那幾乎總是設計缺陷的結果。

**選項的組合爆炸**：

```
20 個模組 × 每個 1 個二元選項 → 2^20 > 100 萬種組態
每一種都要做安全分析 → 不可能
```

**對最佳化保持保守**：很多選項是為了效率而生，但許多「最佳化」沒用、反效果、或無關緊要（沒有最佳化到瓶頸）。作者的做法：謹慎設計，確保工作能以**大塊（chunk）**完成。

> **IBM PC BIOS 的教訓**：在螢幕印字元的常式一次只接受**一個字元**，幾乎所有時間都花在呼叫開銷上。若介面接受**字串**，整串只比印一個字元多花一點時間。結果：所有 DOS 機器的顯示都慢得可怕。
>
> 原則：讓工作能以夠大的區塊完成；只最佳化**量測得到**有顯著效能影響的部分。

> 對照第一本書：這幾乎就是 Hanson 的設計哲學——介面最小而完整、每個模組自給自足、避免「為了別人的問題」而加的功能。Hanson 的 `Fmt`、`Text`、`Seq` 等也都以整塊資料為操作單位。

### 5.3 斷言 ⭐⭐

**專業偏執**用在程式碼上：

- 每個模組都**不信任**其他模組：檢查參數有效性、強制呼叫順序限制、拒絕不安全的操作。
- 例：規格說物件使用前要初始化 → 未初始化就使用 → 斷言錯誤。
- 斷言失敗**一定要中止程式**，並清楚記錄哪個斷言、為何失敗。
- 一般規則：**任何時候能對系統內部一致性做有意義的檢查，就加一個斷言。** 被斷言抓到的錯誤不會變成安全漏洞。

**不要在產品版關閉斷言！**

> 核電廠操作員訓練時開著所有安全系統，上工操作真正的反應爐時卻關掉？跳傘員在地面訓練時背著備用傘，跳出飛機時卻不背？
> **產品程式碼才是你真正需要斷言的地方。** 斷言失敗代表遇到了程式錯誤；忽略它多半導致錯誤的答案——**產生錯誤答案大概是程式能做的最糟的事**。至少要讓使用者知道發生了程式錯誤，不要相信錯誤的結果。
>
> 建議：**所有錯誤檢查都保持開啟。**

> 對照第一本書：Hanson 在第 4 章（Exceptions and Assertions）提出**完全相同的論點**——他逐一反駁「為效率」與「訊息太難懂」這兩個關閉斷言的理由（效率差異要靠量測、通常很小；而斷言失敗代表程式已錯，繼續執行只會換來更糟的 segmentation fault），並讓 `assert` 失敗時引發 `Assert_Failed` 例外。兩本書在這點上英雄所見略同。

### 5.4 緩衝區溢位

- 問題已知數十年，解法也存在同樣久：最早的高階語言之一 **Algol 60** 就以**強制陣列邊界檢查**徹底解決。
- 但緩衝區溢位仍造成網路上大量安全問題；此外還有 format string 攻擊、整數溢位攻擊等。

作者的建議非常直接：

> **避免任何允許緩衝區溢位的語言。具體來說：不要用 C 或 C++。** 而且無論用什麼語言，**永遠不要關閉陣列邊界檢查**。這條簡單的規則大概能解決一半的安全 bug。

> 對照第一本書：這與 Hanson 形成有趣的張力。Hanson 的回答是「如果必須用 C，就用介面把不安全的部分包起來」——`Array`、`Seq`、`Text` 都做邊界檢查（checked runtime error），`Mem` 偵錯版會抓重複釋放。也就是說，CII 本質上是在 C 裡**自己補上**這本書要求語言提供的保證。

### 5.5 測試

> 測試能幫忙找 bug，但**對找安全漏洞沒有用**。永遠不要把測試與安全分析混為一談——兩者互補，但不同。

兩類測試：

| 類型 | 撰寫者 | 依據 | 目的 |
|---|---|---|---|
| **通用測試** | 最好由**另一位**程式設計師撰寫 | 功能規格 | 涵蓋模組完整的操作範圍；雙方理解不一致 → 規格需要釐清 |
| **實作限制測試** | 模組作者本人 | 內部知識 | 例如內部用 4 KB 緩衝區 → 測緩衝區開頭與結尾的邊界 |

- 作者的經驗：測試程式碼大約和正式程式碼**一樣大**，找不到顯著改善的方法。
- **用 PRNG 驅動測試**（第 9 章）：輕鬆跑大量測試；**保存種子**就能重現同一序列，方便除錯。
- **啟動時的快速自我測試**：Niels 實作 AES 時，初始化程式碼會用幾組已知答案測試 AES；若之後開發破壞了 AES 程式碼，很可能被抓到。

## 6. 旁通道攻擊 ⭐

攻擊者擁有**額外的資訊管道**：

- **時序**：量測加密耗時，推導訊息或金鑰資訊。
- **功耗**：智慧卡上量測電流隨時間的變化（功耗分析對智慧卡**極為成功**）。
- 磁場、RF 輻射、對其他資料通道的干擾……

對未考慮旁通道的系統，這類攻擊往往非常成功。

**簡單的預防措施**（Niels 早年做智慧卡的設計規則）：

> **CPU 執行的指令序列，只能依賴攻擊者已經知道的資訊。**

- 阻止時序攻擊；讓功耗分析更難（指令序列不再洩漏資訊）。
- 不是完整解法——現代功耗分析能輕易破解當年的智慧卡；抵抗力永遠來自**軟體與硬體對策的組合**。

本質是**軍備競賽**：防住已知旁通道，就有聰明人發現新的。實際上沒那麼糟：

- 智慧卡完全在攻擊者控制下，旁通道是真實威脅（尤其功耗）。
- 對一般電腦，實務上最重要的旁通道是**時序**與**RF 輻射**。

**常數時間比較（補充）**：

```c
/* 錯誤：memcmp 在第一個不同 byte 就返回，時間洩漏「猜對了幾個 byte」 */
if (memcmp(tag, expected, 32) == 0) { … }

/* 正確：不論內容如何都跑完全部 byte */
int ct_equal(const unsigned char *a, const unsigned char *b, size_t n) {
    unsigned char d = 0;
    for (size_t i = 0; i < n; i++)
        d |= a[i] ^ b[i];
    return d == 0;
}
```

> 後見之明：2018 年的 **Spectre / Meltdown** 證明 CPU 的推測執行本身就是旁通道，正好呼應作者「軍備競賽」與「必須軟硬體一起防」的判斷。

## 7. 本章之外

- 安全**不從密碼設計開始、也不在那裡結束**；系統的每個面向都要盡一份力。
- 實作密碼系統本身就是一門藝術，最重要的是**程式碼品質**——低品質程式碼是真實攻擊最常見的原因，而且相當容易避免。

> 作者的經驗：**從開始到完成產品來算**（而不是從開始到第一個充滿 bug 的版本），寫高品質程式碼所花的時間和寫低品質程式碼差不多。**對程式碼品質要狂熱。做得到，也必須做到——去做吧！**

推薦讀物：

- McGraw，*Software Security: Building Security In*
- Howard & Lipner，*The Security Development Lifecycle*
- Dowd, McDonald & Schuh，*The Art of Software Security Assessment*

## 8. 設計觀念整理

| 觀念 | 說明 |
|---|---|
| 最弱環節在實作 | 攻擊者繞過密碼學，攻擊程式碼 |
| 功能規格 = 可測試 | 寫不出外部測試的項目不屬於功能規格 |
| 正確 ≠ 安全 | 安全是「功能的缺席」，測不出來 |
| 用完即清除 | 小心編譯器、GC、swap、快取、記憶體殘留 |
| Boojum | 讓秘密在記憶體中不斷被隨機化 |
| 簡單為王 | 沒有選項、預設安全、單一 cipher suite |
| 模組自理其事 | 介面長出怪功能 → 重新設計 |
| 大塊操作 | 降低呼叫開銷（BIOS 的教訓） |
| 斷言永遠開啟 | 錯誤答案是最糟的結果 |
| 不用 C/C++ | 或至少永不關閉邊界檢查 |
| 指令序列不依賴秘密 | 旁通道防禦的基本原則 |

## 11. 本章重點整理

1. 實作才是最弱環節：攻擊者繞過密碼學，打程式碼。
2. 密碼系統一旦部署就難以更換，可能使用 30–50 年。
3. 正確程式需要**功能規格**；測試只能證明 bug 存在（Dijkstra）；向**航空業**學習品質文化。
4. 安全 = 功能的缺席，無法測試；標準實作技術不夠。
5. 暫時性秘密：立刻清除（小心編譯器、GC）、防 swap、快取、記憶體殘留（**Boojum**）、除錯器與 core dump；考慮 ECC。
6. 程式碼品質：**簡單**（無選項、單一 suite）、**模組化**、**斷言永不關閉**、避免 C/C++ 與緩衝區溢位、兩類測試 + 啟動自測。
7. 旁通道：**指令序列不依賴秘密**；時序與 RF 是一般電腦上最重要的旁通道。

> **一句話**：密碼學很少被正面攻破，被攻破的是周圍的程式碼——所以要像航空業一樣狂熱地追求品質：簡單、模組化、斷言常開、秘密用完即清。
