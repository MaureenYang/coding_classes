# 第 19 章　PKI 的現實（PKI Reality）

> 《Cryptography Engineering》— Ferguson, Schneier, Kohno，本章頁碼：p.281–294

---

## 1. 本章定位

上一章描述了 PKI 的夢想；本章說明為何**PKI 在真實世界中不像理想情境那樣運作**——不是理論上不行，而是「理論和實務是非常不同的兩回事」。這也是 PKI 的炒作從未與現實相符的原因。

作者的視野不只限於 e-mail 與 Web，也包括 PKI 在**授權**等系統中的角色。

```
名稱（§2）→ 權威（§3）→ 信任（§4）→ 間接授權（§5）→ 直接授權（§6）
→ 憑證系統（§7）→ 修正後的夢想（§8）→ 撤銷（§9）→ PKI 到底有什麼用（§10）→ 怎麼選（§11）
```

---

## 2. 名稱（Names）⭐⭐

PKI 把 Alice 的公鑰綁到她的**名稱**上。**什麼是名稱？**

| 規模 | 名稱與人的關係 |
|---|---|
| **小村莊** | 人人互相認得。名稱唯一，或會被弄成唯一——兩個 John 很快就變成「大 John」和「小 John」。一個名稱對應一個人，但一個人可能有多個名稱：大 John 也許也叫「警長」或「Smith 先生」 |
| **城鎮** | 不再認識所有人。名稱開始脫離人而**獨立存在**——你在酒吧談論那位剛搬來、明年要贊助高中足球隊的有錢 Smith 先生；兩週後才發現他就是兩個月前加入你棒球隊、你叫他 John 的那個人 |
| **城市** | 名稱不再唯一——城裡有一百個 John Smith，知道名字也沒什麼用。名稱的意義開始**依賴上下文**：Alice 在公司說「John」是指樓上業務部的 John，回家說「John」是鄰居家的小孩 |
| **網際網路** | 超過十億人在線，「John Smith」幾乎毫無意義。改用 e-mail 位址：jsmith533@yahoo.com 確實唯一，但實務上連結不到一個你會見到的人；人們常有不同的網路人格；每人都有多個信箱（兩位作者加起來有十幾個），很難判斷兩個信箱是否同一人；也有人**共用**信箱 |

> 這裡說的名稱不是法律文件上的名字，而是**人們用來指稱你的任何符號**。你的「正式」名字只是眾多名稱之一，而且對很多人來說是很少用到的那個。

### 2.1 政府的正式名稱也不可靠

- 多數國家要求每人有單一正式名稱，用在護照等文件上——但名稱**不唯一**，實務上要加上地址、駕照號碼、出生日期等，仍不保證唯一。
- 這些識別資料在一生中會改變：地址、駕照號碼、姓名，甚至性別。幾乎唯一不變的是出生日期——但很多人會**謊報**出生日期，實質上等於改變了它。
- 甚至不是每個人都有單一的正式名稱：無國籍者沒有任何證件；雙重國籍者有兩個政府各自建立正式名稱，可能不一致；兩國可能用**不同文字**，名稱根本不可能相同；有些國家要求名字符合本國語言，會把外國名字改成「合適」的本國名字。
- **身分證號**（美國 SSN、荷蘭 SoFi）：目的就是提供唯一且固定的名稱以追蹤與連結個人行為。大致成功，但人與號碼的連結不夠緊密，某些經濟領域大量使用假號碼；而且只在單一國家有效，沒有全球涵蓋，也不保證全球唯一。
- **隱私法**：歐洲禁止超市在會員計畫中詢問、儲存或處理 SSN/SoFi 號碼——限制了政府命名方案的再利用。

### 2.2 PKI 該用哪個名稱？

> Alice 也許想要兩把金鑰：一把用於工作、一把用於私人通信——但她工作用婚前姓氏，私人用婚後姓氏。試圖建立通用 PKI 時，這類事情會很快導致嚴重問題。

**這是「小型、應用專屬的 PKI 比單一大型 PKI 運作得好得多」的原因之一。**

## 3. 權威（Authority）

- 這個聲稱有權把金鑰指派給名稱的 CA 是誰？是什麼讓它對這些名稱具有**權威**？誰決定 Alice 是有 VPN 權限的員工，還是只有受限權限的銀行客戶？
- 對大部分例子，答案很簡單：**雇主知道誰是員工，銀行知道誰是客戶**——這是「誰該當 CA」的第一個指標。
- 可惜，**通用 PKI 沒有權威來源**——這是通用 PKI 行不通的原因之一。
- 規劃 PKI 時一定要想清楚**誰有權簽發憑證**。公司對自己的員工具有權威：公司不決定員工的法定名字，但知道員工在公司內叫什麼。「Fred Smith」正式名字是 Alfred？沒關係——在公司員工的上下文中，「Fred Smith」是完全合格的名稱。

## 4. 信任（Trust）⭐⭐

> 金鑰管理是密碼學最困難的問題，PKI 是解決它最好的工具之一。但一切都取決於 PKI 的安全，也就是**CA 的可信度**。想想 CA 開始偽造憑證會造成多大傷害：**CA 可以冒充系統中的任何人，安全性完全崩潰。**

通用 PKI 真正失敗的地方就是**信任**：

- 若你是銀行，要和客戶通訊，你會信任世界另一端的某家網路公司嗎？還是你們當地的政府官僚？
- CA 出了可怕的錯，你最多會損失多少錢？CA 願意承擔多少責任？當地銀行法規允許你用外國 CA 嗎？
- 想像一下 CA 的私鑰被貼在網站上會造成什麼損害。

**傳統類比** ⭐：

> CA 是**發放大樓鑰匙**的組織。大多數大型辦公大樓都有警衛，警衛多半外包給保全公司——他們確認規則被遵守，相當直接的工作。但**決定誰拿哪把鑰匙**，通常不會外包給另一家公司，因為那是安全政策的根本部分。同理，**CA 功能不應外包**。

**結論**：

> 世上沒有任何組織被所有人信任，甚至沒有一個被大多數人信任。所以**永遠不會有通用 PKI**。合乎邏輯的結論是：我們必須使用**許多小型 PKI**。

- 銀行可以當自己的 CA——銀行信任自己，所有客戶也早已把錢交給銀行；
- 公司可以當自己 VPN 的 CA；信用卡組織也可以營運自己的 CA。

> 有趣的觀察：CA 所使用的信任關係都是**早已存在、建立在契約關係上**的。設計密碼系統時一向如此：**你所建立的基本信任關係，全都基於契約關係**。（呼應 ch13 的信任來源：法律。）

> 後見之明：Web PKI 正是本章警告的反例——瀏覽器信任上百個 CA，任何一個都能替任何網站簽憑證。2011 年 **DigiNotar** 被入侵簽發假 google.com 憑證（用於監聽伊朗使用者），最終破產；後來發展出 **Certificate Transparency**（公開日誌讓錯誤簽發可被發現）與 CAA 記錄來彌補「信任太多 CA」的問題。

## 5. 間接授權（Indirect Authorization）⭐⭐

這是經典 PKI 夢想的一大問題。考慮**授權系統**：

> PKI 把金鑰綁到名稱，但**大多數系統對人的名字沒興趣**。銀行系統想知道該授權哪些交易；VPN 想知道該允許存取哪些目錄。**這些系統都不在乎金鑰屬於誰，只在乎持有金鑰的人被授權做什麼。**

多數系統使用某種 **ACL（存取控制清單）**——「誰被授權做什麼」的資料庫：

- 有時依使用者排序（Bob 可以：存取 /homes/bob、使用辦公室印表機、存取檔案伺服器）；
- 多數依動作索引（此帳戶的支出必須由 Bob 或 Betty 授權）；
- 通常可以建立群組來簡化 ACL，但基本功能不變。

**三種物件、繞遠路**：

```
經典 PKI：   金鑰 ──(憑證)──► 名稱 ──(ACL)──► 權限

系統真正想知道的：這把金鑰有沒有這項權限？
```

| 攻擊點 | 說明 |
|---|---|
| ① 名稱–金鑰憑證 | PKI 提供的憑證本身 |
| ② ACL 資料庫 | 把名稱綁到權限的資料庫 |
| ③ **名稱混淆** | 名稱如此模糊，怎麼比較 ACL 中的名稱與憑證中的名稱是否相同？怎麼避免兩人有相同名稱？ |

> 分析這種情況會清楚看到：**技術設計照搬了需求的天真表述**。人們以「辨識持鑰人、決定誰該有權存取」的方式思考問題——那是**警衛**處理問題的方式。自動化系統可以用直接得多的方法：**門鎖不在乎誰拿著鑰匙，只要有鑰匙就讓你進去。**

> 對照 ch18 的 RA 問題：同一個錯誤——把人類組織的思考方式直接搬進技術設計。

## 6. 直接授權（Direct Authorization）⭐⭐

**更好的方案：用 PKI 把權限直接綁到金鑰**。憑證不再連結金鑰與名稱，而是連結**金鑰與一組權限**。

```
直接授權：   金鑰 ──(憑證)──► 權限
```

- 所有使用憑證的系統都能**直接**決定是否允許存取：看憑證中的金鑰是否有對應權限即可。直接、簡單。
- 從授權流程中移除了 ACL 與名稱 → 消除了那些攻擊點。

**問題會在簽發憑證時重新出現**——總得有人決定誰可以做什麼，並確保決定被正確編碼進憑證。所有決定的資料庫就相當於 ACL 資料庫，但：

- **更不容易攻擊**：可以分散給做決定的人，移除中央 ACL 資料庫及其弱點；決策者直接簽發適當憑證給使用者，不需要額外的安全關鍵基礎設施。
- **大幅減少對名稱的依賴**：決策者位於階層中低得多的位置，面對的人少得多，常常**親自認識**使用者（至少見過面）——大大有助於避免名稱混淆。

**那可以把名稱從憑證中拿掉嗎？** 不行。

> 正常運作時不使用名稱，但**稽核與日誌**需要。假設銀行剛處理了一筆薪資支付，由該帳戶四把有付款權限的金鑰之一授權。三天後財務長打電話問為何付了這筆錢——銀行知道付款已獲授權，但不能只給財務長幾千個看似隨機的公鑰位元。所以每張憑證仍包含名稱：銀行可以說「授權的金鑰屬於 J. Smith」，財務長就足以弄清楚怎麼回事。
>
> **重點：名稱只需對人類有意義。** 電腦從不試圖判斷兩個名稱是否相同、或名稱屬於哪個人。**人類擅長處理模糊的名稱，電腦喜歡簡單、規範明確的東西——例如權限集合。**

## 7. 憑證系統（Credential Systems）

把直接授權推到極致，就得到完整的**憑證（credential）系統**——**密碼學家的超級 PKI**：你執行的**每一個動作**都需要一份以簽章憑證形式存在的 credential。

**委派**：

```
Alice 有讀寫檔案 X 的 credential
Alice 簽一張給 Bob 公鑰的憑證：
    「金鑰 PK_Bob 經金鑰 PK_Alice 委派，被授權讀取檔案 X」
Bob 要讀 X 時，出示這張憑證 + 證明 Alice 有 X 讀取權的憑證
```

可以加上更多功能：限制委派的**有效期**；限制 Bob **再委派**的能力。

> 作者註：限制再委派是常被要求的功能，但不一定是好主意——它只會誘使 Bob 架一個**代理程式**讓別人用他的 credential 存取資源。代理程式會破壞安全基礎設施，應該被禁止——但前提是沒有營運上的理由需要代理，而**營運上總是有理由需要委派權限**。

**理論上極其強大、有彈性；實務上很少使用。** 四個原因：

| # | 問題 | 說明 |
|---|---|---|
| 1 | **複雜、有開銷** | 存取某資源的權限可能取決於六張憑證組成的鏈，每張都要傳送與檢查 |
| 2 | **鼓勵微管理** | 權限很容易切得越來越細，使用者花太多時間決定要委派給同事多少權限；更大的問題是同事發現權限不夠做事時浪費的時間。有些使用者乾脆把（幾乎）所有權限委派給任何需要任何存取的人——實質上瓦解整個安全系統 |
| 3 | **需要委派語言** | 委派訊息要用電腦能理解的邏輯語言：要強大到能表達所有功能、又簡單到能快速推導結論，還要**經得起未來**。一旦部署，每個程式都要內建解譯器，升級極困難；而不可能設計出滿足所有未來需求的通用語言——仍是研究領域 |
| 4 | **對一般使用者太複雜**（大概無法克服） | 似乎沒有辦法把存取規則以使用者能理解的方式呈現；要求使用者決定委派哪些權限注定失敗 |

**第 4 點的現實例子**：

- 某些學生宿舍習慣由一人去 ATM 替好幾個人領錢——其他學生把**提款卡和 PIN 碼**借給他。極其冒險，卻是社會上所謂教育程度較高的人在做。
- 作者當顧問時，有時因工作需要存取客戶的區域網路。**得到的權限之多令人驚訝**：系統管理員給他們研究資料的無限制存取權，而他們只需要看一兩個檔案。**連系統管理員都很難做對，一般使用者更不可能。**

> 身為密碼學家，若使用者能應付其複雜度，我們會很喜歡憑證系統。人類與安全系統互動的研究無疑還有很多有趣的工作可做。

**但有一個領域，credential 非常有用、而且應該是強制的** ⭐：

> 若使用**階層式 CA**，中央 CA 會簽發子 CA 金鑰的憑證。若這些憑證不含任何限制，**每個子 CA 就擁有無限權力**——等於把系統關鍵金鑰的存放處成倍增加。
>
> 在階層式 CA 中，**子 CA 的權力應由其金鑰憑證中的限制來約束**。這需要一種針對 CA 運作、類似 credential 的委派語言；要施加什麼限制取決於應用——想清楚要建立什麼樣的子 CA、該如何限制它們的權力。

> 對照：X.509 的 **nameConstraints**（例如「此子 CA 只能簽 *.example.com」）與 **pathLenConstraint** 就是這種限制，但實務支援長期不一致。

## 8. 修正後的夢想（The Modified Dream）⭐⭐

總結上述批評，一個更實際的 PKI 樣貌：

1. **每個應用有自己的 PKI 與自己的 CA。** 世界由大量小型 PKI 組成，每位使用者同時是許多不同 PKI 的成員。
2. **每個 PKI 用不同的金鑰**——除非兩個系統在設計上仔細協調，否則不能在不同系統中使用同一把金鑰。使用者的金鑰儲存會有數十把金鑰、數十 KB 的空間。
3. **PKI 的主要目的是把 credential 綁到金鑰**：銀行的 PKI 把 Alice 的金鑰綁到存取她帳戶的 credential；公司的 PKI 把她的金鑰綁到存取 VPN 的 credential。使用者的 credential 有重大變更時，需要簽發新憑證。
4. **憑證仍包含使用者名稱，但主要用於管理與稽核。**

> 這個修正後的夢想實際得多，也比原本的夢想**更強大、更有彈性、更安全**。很容易相信它能解決你的金鑰管理問題——但下一節會遇到**最難的問題**，一個永遠無法完全解決、永遠需要妥協的問題。

## 9. 撤銷（Revocation）⭐⭐⭐

**PKI 中最難解決的問題是撤銷**。有時必須撤回憑證：Bob 的電腦被駭、私鑰外洩；Alice 被調到其他部門，甚至被解雇……

> 問題在於：**憑證只是一串位元**。這些位元被用在很多地方、存在很多地方，**你再怎麼努力也無法讓世界忘記這張憑證**。Bruce 十多年前遺失了一把 PGP 金鑰，至今仍收到用對應憑證加密的 e-mail。（PGP 有自己奇特的類 PKI 結構，稱為**信任網**。）
>
> 而且試圖讓世界忘記本身就不切實際：小偷闖進 Bob 的電腦偷走私鑰，可以肯定他也複製了對應公鑰的憑證。

**撤銷需求的四個變數**：

| 變數 | 問題 |
|---|---|
| **撤銷速度** | 從下達撤銷命令到憑證最後一次被使用，最長允許多久？ |
| **撤銷可靠度** | 某些情況下撤銷不完全有效可以接受嗎？可接受的殘餘風險是多少？ |
| **撤銷數量** | 撤銷系統一次要處理多少筆撤銷？ |
| **連線能力** | 驗證憑證的一方在驗證時是否在線？ |

三種可行的解法：

### 9.1 撤銷清單（CRL）

**CRL** = 包含已撤銷憑證的資料庫。每個要驗證憑證的人都必須查 CRL。

**中央 CRL 資料庫**：

| 優點 | 缺點 |
|---|---|
| 撤銷**幾乎即時**：一旦加入 CRL，就不再授權任何交易 | **所有人必須隨時在線**才能查詢 |
| 非常**可靠** | **單一故障點**：資料庫不可用時什麼都做不了 |
| 撤銷數量**沒有直接上限** | 若改成「CRL 不可用時允許繼續」，攻擊者就會用 **DoS 癱瘓 CRL 資料庫**，摧毀系統的撤銷能力 |

**分散式 CRL**：在全球放十幾台鏡像伺服器、期望夠可靠——但建置與維護昂貴，通常不可行。（別忘了，**人們很少願意在安全上花錢**。）

**把整份 CRL 複製到每個裝置**：

- 美軍 **STU-III** 加密電話就是這樣運作——類似以前發給每個商家的失竊信用卡號小冊子。
- 相對容易做：讓每個裝置每半小時左右從 Web 伺服器下載更新的 CRL（代價是撤銷時間變長）。
- 但限制了 CRL 的大小：通常負擔不起把數十萬筆 CRL 項目複製到每個裝置。作者看過**需求寫著每個裝置要能儲存 50 筆 CRL 項目**的系統——這可能有問題（習題 19.2）。

> 作者的經驗：**CRL 系統的實作與維護都很昂貴**——需要自己的基礎設施、管理、通訊路徑等等；只為了處理相對很少使用的撤銷功能，就需要相當多額外功能。

### 9.2 快速到期（Fast Expiration）⭐

- 利用**已經存在的到期機制**：CA 簽發有效期極短的憑證——**10 分鐘到 24 小時**。
- Alice 每次要用憑證時就向 CA 取得新的一張，在有效期內使用。
- 到期速度可依應用需求調整，但有效期小於 10 分鐘似乎不太實際。

**主要優點**：使用現成的憑證簽發機制，**不需要獨立的 CRL**，大幅降低整體系統複雜度。要撤銷權限，只需告知 CA 新的存取規則。（當然，每個人仍需隨時在線以重新取得憑證。）

> **簡單是我們的主要設計準則之一，所以我們偏好快速到期勝過 CRL 資料庫。** 能否使用快速到期，主要取決於應用是否要求**即時**撤銷，還是可以接受延遲。

### 9.3 線上憑證驗證（OCSP）

**Online Certificate Status Protocol** 在某些領域（如 Web 瀏覽器）頗有進展：

```
Alice ──(憑證序號)──► 可信方（CA 或其委派者）
                      查自己資料庫中的憑證狀態
Alice ◄──(簽章回應：有效 / 已撤銷)──
Alice 用可信方公鑰驗證回應
```

- 與 CRL 一樣：撤銷幾乎即時、非常可靠；也一樣：Alice 必須在線、可信方是故障點。

**比較**：

| 比較 | 結論 | 理由 |
|---|---|---|
| OCSP vs. CRL | **偏好 OCSP** | 避免大量分發 CRL、避免客戶端解析與驗證 CRL → 設計可以更乾淨、簡單、可擴展 |
| OCSP vs. 快速到期 | **多數情況下快速到期較佳** | 沒有可信方的簽章就不能信任金鑰——把那個簽章看成金鑰的新憑證，OCSP 就是**有效期極短的快速到期**。差別在於：OCSP 要**每個驗證者**都去查詢可信方；快速到期則讓**證明者**能把同一個 CA 簽章用於許多驗證者 |

> 後見之明：OCSP 有隱私問題（CA 知道你瀏覽哪些網站）與「查不到就放行（soft-fail）」問題，業界改用 **OCSP Stapling**（由伺服器附上 CA 簽的新鮮回應——正是「證明者攜帶短效簽章」的快速到期思路）。Let's Encrypt 把憑證有效期縮短到 90 天，並在 2025 年起推出 6 天的短效憑證，CA/B 論壇也決議逐步把上限降到 47 天——**快速到期**正在勝出。

### 9.4 撤銷是必要的

- 撤銷很難實作，所以很誘人乾脆不實作。有些 PKI 提案完全不提撤銷，有些把 CRL 列為「未來擴充可能」。
- 實際上，**沒有某種撤銷機制的 PKI 幾乎毫無用處**：現實中金鑰確實會外洩、權限確實需要撤銷。

> 經營一個沒有可用撤銷系統的 PKI，就像經營一艘**沒有艙底泵**的船。理論上船應該水密、不需要艙底泵；實務上船底總會積水，不排掉的話船終究會沉。

## 10. 那 PKI 到底有什麼用？⭐⭐⭐

PKI 討論一開始說：PKI 的目的是讓 Alice 和 Bob 產生共享金鑰、建立安全通道、安全通訊——**不必和第三方交談**就能認證對方。

> **但它做不到。**

**沒有任何撤銷系統能完全離線運作**——原因很容易看出：若 Alice 和 Bob 都不聯絡任何外部方，他們就永遠無法得知對方的某把金鑰已被撤銷。撤銷檢查迫使他們上線；我們所有的撤銷方案都需要線上連線。

**但既然要在線，就不需要龐大複雜的 PKI**——用第 17 章的中央金鑰伺服器就能達到想要的安全等級。

**那 PKI 相對於金鑰伺服器有什麼優勢？**

| 面向 | 金鑰伺服器 | PKI |
|---|---|---|
| **在線需求** | 每個人都必須**即時**在線；聯絡不到伺服器就什麼都不能做，Alice 和 Bob 無法辨認彼此 | 用到期做撤銷時，只需偶爾聯絡中央伺服器；有效期數小時的憑證大幅放寬即時在線的要求 → 適合 **e-mail** 這類非互動應用、某些授權系統、通訊昂貴的情況。即使用 CRL，也可以訂規則決定 CRL 聯絡不到時怎麼辦——信用卡系統就有這種規則：拿不到自動授權時，一定金額以下的交易照樣成立（規則要基於風險分析，包括 CRL 被 DoS 的風險）——**至少有繼續的選項**；金鑰伺服器方案沒有任何替代 |
| **單一故障點** | 是；而且很難分散——它擁有系統中所有金鑰，你真的不想把秘密金鑰散佈到全世界 | CRL 資料庫的安全關鍵性低得多、容易分散；快速到期讓 CA 成為故障點，但大系統幾乎都是階層式 CA → CA 本來就是分散的，故障只影響系統的一小部分 |
| **不可否認性** | 永遠無法提供：中央伺服器擁有和 Alice 相同的金鑰，可以偽造任意訊息讓它看起來像 Alice 送的 | **理論上**可以：Alice 用自己的金鑰簽了訊息，之後不能否認。**實際上行不通**——人們無法妥善保管私鑰；Alice 想否認時只要說「病毒感染了我的電腦、偷走了私鑰」 |
| **最重要金鑰的保護** | 主金鑰材料在**在線**的電腦上 | 最重要的是 **CA 根金鑰**——不必放在在線電腦上，可以安全保存，只在需要時載入**離線**電腦；它只用來簽子 CA 的憑證，很少使用。離線電腦比在線電腦難攻擊得多 → PKI **可能更安全** |

> 所以 PKI 有一些優點——有了很好，但在某些環境中**沒有一個是真正關鍵的優勢**。而且代價高昂：PKI 比金鑰伺服器系統**複雜得多**，公鑰運算也需要多得多的計算能力。

## 11. 該選哪個？⭐

如往常，取決於確切需求、系統規模、目標應用等。

| 系統規模 | 建議 |
|---|---|
| **小型系統** | PKI 的額外複雜度通常不值得 → **用金鑰伺服器比較容易**（PKI 的優勢多半在大型部署才顯著） |
| **大型系統** | PKI 的額外彈性仍然很有吸引力：可以更分散；credential 式擴充讓中央 CA 能**限制子 CA 的權限** → 容易設立涵蓋特定營運範圍的小子 CA，而子 CA 能簽的憑證受限於它自己金鑰的憑證，不會對整個系統構成風險。對大系統，這種彈性與風險限制很重要 |

建置大型系統時：

- **認真考慮 PKI，但也要與金鑰伺服器方案比較**，看 PKI 的優勢是否值得額外的成本與複雜度。
- 一個可能的問題：你真的會想對子 CA 做 credential 式的限制——這需要用邏輯框架表達限制，而**沒有通用框架**可用 → 這最後會變成**依客戶而定**的設計部分，也可能意味著**無法使用現成的 PKI 產品**（它們不太可能有合適的憑證限制語言）。

## 12. 設計觀念整理

| 觀念 | 說明 |
|---|---|
| 名稱是模糊的 | 依上下文、不唯一、會改變、一人多名 |
| 權威來自既有關係 | 雇主之於員工、銀行之於客戶 |
| 沒有人被所有人信任 | 通用 PKI 永遠不會存在 → 許多小 PKI |
| CA 不可外包 | 決定誰拿鑰匙是安全政策的核心 |
| 信任建立在契約上 | 所有基本信任關係皆然 |
| 間接授權繞遠路 | 金鑰 → 名稱 → ACL → 權限，三個攻擊點 |
| **直接授權** | 憑證直接綁權限；名稱只給人看 |
| 人處理模糊、電腦處理精確 | 名稱給人，權限集合給電腦 |
| 憑證系統強大但難用 | 微管理、語言、使用者理解 |
| 子 CA 必須受限 | 否則關鍵金鑰的數量倍增 |
| **撤銷最難、也必要** | 沒有艙底泵的船會沉 |
| 偏好快速到期 | 簡單；OCSP 次之；CRL 最貴 |
| PKI 無法完全離線 | 撤銷迫使上線，那為何不用金鑰伺服器？ |
| 不可否認性是幻覺 | 「病毒偷了我的私鑰」 |
| 小系統用金鑰伺服器 | 大系統認真比較後再考慮 PKI |

> 對照第一本書：Hanson 在 `Atom` 介面中做的事——把字串「內化」成唯一的指標，之後只比較指標、不再比較字串——正是「讓電腦處理精確的東西」。本章的直接授權也是同一個思路：**不要讓程式去比較模糊的名稱**。

## 14. 習題摘要

| 題號 | 題目 | 提示 |
|---|---|---|
| 19.1 | Alice 在多個 PKI 中使用同一把金鑰會有什麼問題？ | 一處外洩、處處外洩；一個 PKI 的撤銷不會傳到其他 PKI；某個系統的簽章（或解密）oracle 可被用來攻擊另一個系統（跨協定攻擊，ch14 的智慧卡案例）；不同 PKI 可藉同一把公鑰**關聯**她的身分與行為（隱私） |
| 19.2 | 每個裝置只能存 50 筆 CRL 項目，這會造成什麼安全問題？ | 第 51 筆撤銷放不下 → 要嘛丟掉舊的（被丟掉的已撤銷憑證「復活」）、要嘛拒絕新的；攻擊者可以**故意讓大量憑證被撤銷**（例如偷很多張、或觸發大規模事件）把清單擠爆；大規模外洩事件（CA 被入侵）時根本不夠用 |
| 19.3 | 裝置因 CRL 被 DoS 而查不到時，有哪些選擇？各自優缺點？ | ①**拒絕**（fail-closed）：安全，但 DoS 直接變成服務中斷；②**接受**（fail-open）：可用，但攻擊者只要先 DoS CRL 就能使用已撤銷的憑證；③**依風險分級**（信用卡模式）：小額/低風險放行、高風險拒絕，搭配事後稽核；④使用**快取的舊 CRL**並設最長容忍時間；⑤重試、記錄並警告 |
| 19.4 | 比較 PKI 與金鑰伺服器，各舉一個適用例子 | 金鑰伺服器：**公司內部數百人的檔案伺服器存取**（Kerberos/AD）——規模小、本來就在線；PKI：**全國銀行間結算網路**或**數萬台 IoT 感測器**——規模大、需要階層化與離線根金鑰、需要子 CA 限制 |
| 19.5 | 比較 CRL、快速到期、OCSP，各舉一個適用例子 | **CRL**：離線或間歇連線的裝置（如 STU-III、門禁讀卡機），撤銷數量少、可定期下載；**快速到期**：VPN 或雲端服務的工作負載身分（每天/每小時換證，如 SPIFFE）、撤銷可容忍數小時延遲；**OCSP**：需要接近即時撤銷且驗證者在線的高價值交易（例如網銀的高額轉帳驗證） |

## 15. 本章重點整理

1. **名稱**是模糊的：依上下文、不唯一、會改變；通用 PKI 無法處理 → 小型、應用專屬的 PKI 好得多。
2. **權威**來自既有關係（雇主、銀行）；通用 PKI 沒有權威來源。
3. **信任**：沒有組織被所有人信任 → **永遠不會有通用 PKI**；CA 不應外包；信任建立在契約上。
4. **間接授權**（金鑰→名稱→ACL→權限）繞遠路、多攻擊點；**直接授權**把權限綁到金鑰，名稱只用於人類稽核。
5. **憑證系統**強大但複雜、鼓勵微管理、需要委派語言、使用者難以理解；但**子 CA 的權限必須受限**。
6. **修正後的夢想**：每個應用一個 PKI、每個 PKI 一把金鑰、憑證綁 credential、名稱用於稽核。
7. **撤銷**最難也最必要：CRL（貴）、**快速到期**（作者偏好）、OCSP（優於 CRL）。
8. 撤銷迫使上線，PKI 的優勢（放寬在線需求、可分散、離線根金鑰）並非決定性；**小系統用金鑰伺服器，大系統仔細比較**。

> **一句話**：現實中的 PKI 不是一個人人信任的大 CA，而是無數個把「權限」綁在金鑰上的小 CA——而且一定要能撤銷，就像船一定要有艙底泵。
