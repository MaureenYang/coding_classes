# 第 20 章　PKI 實務（PKI Practicalities）

> 《Cryptography Engineering》— Ferguson, Schneier, Kohno，本章頁碼：p.295–300

---

## 1. 本章定位

PKI 三部曲的最後一章。實務上，如果你需要 PKI，就得決定**買**還是**自己建**。本章討論設計 PKI 系統時會碰到的實際考量：

1. **憑證格式**——編碼唯一性、權限語言、根金鑰；
2. **金鑰的一生**——從產生到過期的六個階段；
3. **金鑰為何會「磨損」**——為什麼要定期更換。

---

## 2. 憑證格式

憑證只是一個有多個必要與選用欄位的資料型別。

> **編碼必須唯一** ⭐：密碼學中常對資料結構做**雜湊**來簽章或比較。像 XML 這種允許同一資料結構有多種表示法的格式，需要額外小心，才能確保簽章與雜湊總是正確運作。

- XML：同樣的資料可以有不同的空白、屬性順序、命名空間寫法 → 需要「正規化」（canonicalization），而這本身是漏洞溫床。
- X.509：作者不喜歡它的複雜度，但它是另一個選擇（底層的 DER 編碼是唯一的）。

> 對照 ch13 §6.3：「解析不可依賴上下文」；這裡更進一步——**序列化也必須唯一**，否則「被簽的位元組」和「被理解的資料」可能不是同一回事。（後見之明：XML 簽章包裝攻擊（XML Signature Wrapping）一再攻破 SAML 單一登入系統，正是此問題。）

### 2.1 權限語言 ⭐⭐

- 除了最簡單的 PKI 系統，你都會想**限制子 CA 能簽發的憑證**——要把限制編碼進子 CA 的憑證，這就需要一種表達金鑰權限的語言。
- 這大概是 **PKI 設計中最困難的一點**；需要哪些限制取決於你的應用。

> **若你找不到合理的限制，就應該重新考慮是否要用 PKI。** 憑證中沒有限制，每個子 CA 實質上都擁有一把**主金鑰**——這是糟糕的安全設計。你可以只用單一 CA，但那樣就失去了 PKI 相對於金鑰伺服器的許多優勢。

（呼應 ch19 §7、§11：子 CA 必須受限，而且沒有通用框架。）

### 2.2 根金鑰 ⭐

CA 要做任何事都需要一對公私鑰。產生它很直接；公鑰需要和一些額外資料（例如該金鑰的有效期）一起分發給每個參與者。

**自簽憑證（self-certifying certificate）**——一個相當奇怪的構造：CA 為**自己的**公鑰簽一張憑證。

> 雖然叫「自我認證」，**它根本沒有認證任何東西**——這是歷史遺留的誤稱。它不證明金鑰的任何安全性質，因為**任何人都能產生一把公鑰並自簽**。自簽真正做的，是把**額外資料綁到公鑰上**：權限清單、有效期、聯絡人資料等都包含在自簽憑證中。

- 自簽憑證與系統中其他所有憑證使用**相同的資料格式** → 所有參與者都能重用現有程式碼來檢查這些額外資料。
- 它稱為 PKI 的**根憑證（root certificate）**。

**根憑證的初次分發** ⭐⭐

- 必須以**安全的方式**分發給所有參與者：每個人都必須知道根憑證，而且必須是**正確的**根憑證。
- 電腦第一次加入 PKI 時：可能簡單到指向一個本地檔案或可信 Web 伺服器上的檔案，告訴機器「這就是該 PKI 的根憑證」。

> **密碼學無法幫助根憑證的初次分發**——因為還沒有任何金鑰可以用來提供認證。（信任總要從某個非密碼學的地方開始：實體交付、作業系統預裝、人工比對指紋。）

- CA 私鑰若**外洩**，情況相同：根金鑰不再安全後，必須初始化一個**全新的 PKI 結構**，再次以安全方式把根憑證交給每個參與者。

> 這應該是**保護根金鑰安全**的好動機。（呼應 ch19：根金鑰可以存放在**離線**電腦中。）

**根金鑰更替**——比初次分發容易：

```
新根憑證 ── 用舊根金鑰簽章 ──► 參與者可從「不安全」的來源下載
                               （用舊根金鑰驗證，無法被竄改）
唯一可能的問題：某些參與者沒拿到新根憑證
→ 多數系統讓新舊根金鑰的有效期重疊幾個月，留足切換時間
```

**實作細節**：新的 CA 根憑證大概應該有**兩個簽章**：

| 簽章 | 用途 |
|---|---|
| 舊根金鑰的簽章 | 讓現有使用者認得新根憑證 |
| 新根金鑰的自簽 | 給舊金鑰到期**之後**才加入的新裝置使用 |

做法：讓憑證格式支援多重簽章，或乾脆為同一把新根金鑰簽發**兩張獨立的憑證**。

> 後見之明：這正是 Let's Encrypt 的 **ISRG Root X1** 交叉簽章（由 IdenTrust 的 DST Root CA X3 簽署）策略；2021 年舊根到期時，大量舊 Android 裝置與 OpenSSL 1.0.2 用戶端因根憑證儲存區沒更新而連線失敗——印證了「某些參與者沒拿到新根憑證」的風險。

## 3. 金鑰的一生 ⭐⭐

以 Alice 的公鑰為例（CA 根金鑰或其他公鑰同理）。不是所有金鑰都需要所有階段，依應用而定。

```
 產生 ──► 認證 ──► 分發 ──► 主動使用 ──► 被動使用 ──► 過期
Creation Certification Distribution Active use  Passive use  Expired
```

| 階段 | 說明 |
|---|---|
| **產生** | Alice 產生公私鑰對，以安全方式儲存私鑰 |
| **認證** | Alice 帶著公鑰去找 CA 或子 CA 認證——**這是 CA 決定給 Alice 公鑰哪些權限的時刻** |
| **分發** | 依應用而定，Alice 可能要在使用前先分發已認證的公鑰。例：若用於簽章，每個可能收到 Alice 簽章的人都應該**先**有她的公鑰。最好在 Alice 第一次使用前先分發一段時間——**對新根憑證尤其重要**：CA 切換到新根金鑰時，每個人都應該有機會在看到新金鑰簽的憑證之前先認識新根憑證 |
| **主動使用** | Alice 積極用金鑰進行交易——金鑰的正常狀態 |
| **被動使用** | 主動使用之後，必須有一段時間：Alice **不再用它做新交易**，但**大家仍接受**這把金鑰。交易不是瞬間完成的，有時會延遲——一封簽章的 e-mail 很可能要一兩天才送達。Alice 應停止主動使用，並在金鑰過期前留下合理的時間讓所有待處理交易完成 |
| **過期** | 金鑰到期，不再被視為有效 |

**關於分發階段** ⭐：

> 是否需要獨立的分發階段取決於應用——**能避免就避免**。獨立的分發階段必須向使用者解釋，會出現在使用者介面中——這又產生大量額外工作，因為很多使用者不會理解它的意思，也不會正確使用系統。

（呼應 ch8：「使用者無法做出正確的安全選擇」，最好的設計是讓他們不必選。）

**階段如何定義？**

| 方案 | 說明 | 問題 |
|---|---|---|
| **憑證中寫明每個階段轉換的時間**（最常見） | 分發開始、主動使用開始、被動使用開始、過期時間 | 這些時間都影響憑證的運作方式，所以都得呈現給使用者——對一般使用者大概太複雜 |
| **中央資料庫記錄每把金鑰的階段** | 更有彈性 | 帶來一大堆新的安全問題，作者不想這麼做 |
| CRL | 可以覆寫選定的階段期間，立即讓金鑰過期 | — |

**同一把金鑰用於多個 PKI** ⭐

- 一般而言作者認為這是**壞主意**（ch19 §8），但有時無法避免，此時要採取額外預防措施。
- 例：Alice 隨身帶著一個小型**防竄改模組**（智慧卡），裡面存著私鑰並執行數位簽章運算。憑證可以存在公司內網、不受大小限制，但小模組**無法存放無限多把私鑰** → Alice 最後只好在多個 PKI 中使用同一把金鑰。這也意味著她所用的所有 PKI 的金鑰生命週期排程要相近——可能很難協調。

> 若你處理這樣的系統，**務必確保一個 PKI 中的簽章不能被用在另一個 PKI**：
> - 永遠使用**單一**數位簽章方案（例如 §12.7 的方案）；
> - **被簽的位元組字串在兩個不同的 PKI 或兩個不同的應用中絕不相同**；
> - 最簡單的解法：在要簽的字串中加入**唯一識別應用與 PKI 的資料**。

（這正是 ch14 認證慣例「每個被認證字串以唯一識別碼開頭」的延伸——**領域分離（domain separation）**。）

```
簽章輸入 = "PKI=BankX;App=Payments;v=1" ‖ 訊息
簽章輸入 = "PKI=CorpVPN;App=Login;v=1"  ‖ 訊息
→ 同一把私鑰在兩個系統中簽出的位元組永不重疊，簽章無法跨系統挪用
```

## 4. 為什麼金鑰會磨損（Why Keys Wear Out）⭐⭐

我們一再提到金鑰要定期更換——**為什麼？**

**完美世界**：金鑰可以用很久。攻擊者沒有任何系統弱點可利用，只能窮舉——理論上問題就簡化為選擇夠大的金鑰。

**真實世界不完美**，金鑰的秘密性總有威脅：

| 威脅 | 說明 |
|---|---|
| **儲存** | 金鑰必須存在某處，攻擊者可能設法取得 |
| **使用** | 每次使用都是另一個威脅 |
| **傳送** | 金鑰要從儲存位置送到計算的地方——常在同一設備內，但仍開啟新的攻擊途徑；若攻擊者能竊聽這條傳送通道，就拿到金鑰的副本 |
| **密碼運算本身** | 沒有任何有用的密碼函式有完整的安全證明——核心都是「嗯，我們都沒找到攻擊這個函式的方法，所以看起來相當安全」 |
| **旁通道** | 如前所述，旁通道可能洩漏金鑰資訊 |

> 註：常被稱為密碼函式「安全證明」的東西其實不是完整證明，通常是**歸約**：「若你能攻破函式 A，你也能攻破函式 B」。它們很有價值——減少了你必須假設安全的基本運算數量——但不提供完整的安全證明。

> **金鑰保留越久、使用越多，攻擊者拿到它的機會就越高。** 要限制攻擊者知道你金鑰的機會，就必須限制金鑰的壽命。實際上，**金鑰會磨損**。

**另一個理由：限制暴露窗口**

- 假設不幸發生、攻擊者拿到了金鑰 → 系統安全被破壞、造成某種損害。
- **撤銷只在你發現攻擊者有金鑰時才有效**——聰明的攻擊者會設法避免被發現。
- 損害會持續到金鑰被換成新金鑰為止；即使換了，**先前用舊金鑰加密的資料仍然外洩**。
- 限制單一金鑰的壽命，就限制了成功攻擊者的**暴露窗口**。

**短金鑰壽命的兩個好處**：

1. 降低攻擊者取得金鑰的機會；
2. 萬一他仍然得手，限制造成的損害。

### 4.1 合理的壽命是多久？

- 視情況而定。換金鑰有成本，所以不要換得太頻繁。
- 但若十年才換一次，你**無法確定換新金鑰的功能在十年後還能用**。

> **一般原則：很少使用或測試的功能或程序，更可能失敗。** 長期金鑰最大的危險大概就是：**換金鑰的功能從未被使用，所以真正需要時運作不良。**（註腳：這是普遍適用的真理，也是你應該**定期演練緊急程序**——例如消防演習——的主要原因。）

| 情況 | 建議壽命 |
|---|---|
| 一般上限 | **一年**大概是合理的最大值 |
| 需要使用者參與的換金鑰 | 相對昂貴，應不常進行 → 合理壽命**一個月以上** |
| 更短的壽命 | 必須**自動**管理 |

> 對照 ch8「很少執行的程式碼很少被測試」、ch7「訊息編號從 1 開始」、ch14「參數產生程式碼從未被執行」——同一個教訓在全書第四次出現：**讓重要的程序經常被執行**。現代實務（Let's Encrypt 的 90 天憑證、ACME 自動續約）正是把「換金鑰」從十年一次的緊急程序，變成每幾週自動執行一次的例行公事。

## 6. 參考實作：建立自簽根憑證（習題 20.4）

用 Python `cryptography` 函式庫建立一張 X.509 自簽根憑證，並加上本章與 ch19 強調的**權限限制**：`BasicConstraints`（CA、路徑長度 1）、`NameConstraints`（只能簽 example.com 底下的名稱）、`KeyUsage`（只能簽憑證與 CRL）。

```python
import datetime
from cryptography import x509
from cryptography.x509.oid import NameOID
from cryptography.hazmat.primitives import hashes, serialization
from cryptography.hazmat.primitives.asymmetric import ec

key = ec.generate_private_key(ec.SECP256R1())
name = x509.Name([x509.NameAttribute(NameOID.COMMON_NAME, "Example Root CA")])
now = datetime.datetime.now(datetime.timezone.utc)
cert = (x509.CertificateBuilder()
        .subject_name(name).issuer_name(name)            # 自簽：subject = issuer
        .public_key(key.public_key())
        .serial_number(x509.random_serial_number())
        .not_valid_before(now)
        .not_valid_after(now + datetime.timedelta(days=3650))
        .add_extension(x509.BasicConstraints(ca=True, path_length=1), critical=True)
        .add_extension(x509.NameConstraints(permitted_subtrees=[x509.DNSName("example.com")],
                                            excluded_subtrees=None), critical=True)
        .add_extension(x509.KeyUsage(digital_signature=False, content_commitment=False,
                       key_encipherment=False, data_encipherment=False, key_agreement=False,
                       key_cert_sign=True, crl_sign=True, encipher_only=False,
                       decipher_only=False), critical=True)
        .sign(key, hashes.SHA256()))
open("root.pem", "wb").write(cert.public_bytes(serialization.Encoding.PEM))
cert.public_key().verify(cert.signature, cert.tbs_certificate_bytes, ec.ECDSA(hashes.SHA256()))
print("self-signature verifies:", True)
print(cert.subject.rfc4514_string(), cert.not_valid_after_utc.date())
```

實測輸出（並以 `openssl x509 -text` 檢查擴充欄位）：

```
self-signature verifies: True
CN=Example Root CA 2036-10-23
            X509v3 Basic Constraints: critical
                CA:TRUE, pathlen:1
            X509v3 Name Constraints: critical
                Permitted: DNS:example.com
            X509v3 Key Usage: critical
                Certificate Sign, CRL Sign
```

> 注意：自簽簽章能驗證通過，**只證明這張憑證沒被竄改、且由對應私鑰簽出**——不證明它「值得信任」。要信任它，仍得透過**非密碼學的管道**（§2.2）把它安裝為根憑證。

等價的 OpenSSL 指令：

```
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes \
    -keyout root.key -out root.pem -days 3650 -subj "/CN=Example Root CA" \
    -addext "basicConstraints=critical,CA:TRUE,pathlen:1" \
    -addext "keyUsage=critical,keyCertSign,cRLSign" \
    -addext "nameConstraints=critical,permitted;DNS:example.com"
```

## 7. 設計觀念整理

| 觀念 | 說明 |
|---|---|
| 編碼必須唯一 | 簽章與雜湊作用在位元組上；XML 需特別小心 |
| 權限語言最難 | 找不到合理限制，就別用 PKI |
| 無限制的子 CA = 主金鑰 | 糟糕的安全設計 |
| 自簽 ≠ 認證 | 只是把額外資料綁到公鑰，並重用同一格式 |
| 初次分發無法靠密碼學 | 信任根必須來自非密碼學管道 |
| 根金鑰外洩 = 重建整個 PKI | 保護根金鑰的最強動機 |
| 根金鑰更替 | 舊根簽新根、雙簽章、有效期重疊數月 |
| 金鑰六階段 | 產生、認證、分發、主動、被動、過期 |
| 被動使用期 | 讓延遲的交易能完成 |
| 避免使用者可見的階段 | 使用者不會懂 |
| 跨 PKI 簽章要領域分離 | 被簽字串包含應用與 PKI 識別 |
| 金鑰會磨損 | 儲存、使用、傳送、運算、旁通道 |
| 少用的程序會失敗 | 定期換金鑰（≤ 1 年），像消防演習 |

## 8. 延伸閱讀重點

- **Peter Gutmann**：*X.509 Style Guide*；*Engineering Security*（第 8 章 PKI）。
- **RFC 5280**：X.509 擴充欄位（basicConstraints、nameConstraints、keyUsage）。
- **RFC 4210**（CMP）、**RFC 8555**（ACME）：憑證管理與自動化簽發。
- **NIST SP 800-57**：金鑰管理建議——金鑰生命週期與 cryptoperiod 的標準化描述。
- **Somorovsky et al.**（2012）：*On Breaking SAML: Be Whoever You Want to Be*（XML 簽章包裝攻擊）。
- **The Update Framework（TUF）**：軟體更新系統的根金鑰更替與門檻簽章設計。

## 9. 習題摘要

| 題號 | 題目 | 提示 |
|---|---|---|
| 20.1 | 憑證中應該有哪些欄位？為什麼？ | **格式/版本**（未來升級）、**PKI 與應用識別碼**（領域分離）、**序號**（撤銷與稽核）、**簽發者**（建立鏈）、**主體公鑰與演算法**、**權限/credential**（直接授權）、**名稱**（給人稽核用）、**各階段時間**（生效、主動、被動、過期）、**對子 CA 的限制**、**簽章**。原則：每個欄位都要能說出誰會用它、做什麼決定 |
| 20.2 | 你的瀏覽器內建了哪些根 SSL 金鑰？何時建立、何時到期？ | 在瀏覽器或作業系統的憑證管理介面查看；通常有一百多個根，許多有效期長達 20–25 年（例如 ISRG Root X1：2015 年建立、2035 年到期）——遠超過本章建議的「一年」，因為根憑證更替的成本極高 |
| 20.3 | PKI 升級需要新欄位，又要向後相容，會有什麼問題？原本設計時可以如何準備？ | 問題：舊用戶端無法理解新欄位（忽略還是拒絕？）；若新欄位是限制而舊用戶端忽略它，**限制就形同不存在**；版本降級攻擊；兩種格式並存的複雜度。準備：一開始就放**版本號**；定義「**critical**」旗標語意（不認識就必須拒絕，X.509 正是這麼做）；TLV 等可擴充編碼；讓憑證短效以加速汰換舊格式 |

## 10. 本章重點整理

1. 需要 PKI 時要決定**買或建**；憑證格式的**編碼必須唯一**。
2. **權限語言**是 PKI 設計最難的部分；子 CA 若不受限就等於持有主金鑰——找不到合理限制，就重新考慮是否用 PKI。
3. **自簽根憑證**不證明任何事，只是把額外資料綁到公鑰；**初次分發無法靠密碼學**；根金鑰外洩就得重建整個 PKI。
4. 根金鑰更替：舊根簽新根、新根自簽（雙簽章）、新舊有效期重疊數月。
5. **金鑰六階段**：產生、認證、分發、主動使用、被動使用、過期；能避免分發階段就避免；跨 PKI 使用同一把金鑰時必須做**領域分離**。
6. **金鑰會磨損**：儲存、使用、傳送、運算與旁通道都有風險；短壽命降低被竊機會並限制損害。
7. 少用的程序容易失敗 → 金鑰壽命**最多一年**；需使用者參與的至少一個月；更短的必須自動化。

> **一句話**：PKI 的成敗在細節——憑證要能限制子 CA、根金鑰要離線保護並能平順更替，而金鑰要像消防演習一樣定期更換，讓換金鑰這件事永遠能用。
