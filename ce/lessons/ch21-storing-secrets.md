# 第 21 章　儲存秘密（Storing Secrets）

> 《Cryptography Engineering》— Ferguson, Schneier, Kohno，本章頁碼：p.301–314

---

## 1. 本章定位

第 8.3 節談過**暫時性**秘密（如 session key）的儲存；本章處理**長期**秘密——密碼與私鑰——該怎麼存。第四部「金鑰管理」的最後一章。

兩個**互相衝突**的需求：

| 需求 | 說明 |
|---|---|
| **保密** | 秘密必須保持秘密 |
| **不遺失** | 完全遺失秘密（再也找不回來）的風險必須降到最低 |

本章依序檢視各種儲存方式：磁碟 → 人腦 → 可攜式儲存 → 安全權杖 → 安全 UI → 生物辨識 → 單一登入；再談遺失風險、秘密分享，以及如何**抹除**秘密。

---

## 2. 磁碟

直接存在硬碟或其他永久媒體上？可以，但**只有在電腦安全時**才行。

- Alice 把金鑰（未加密）存在 PC 上 → 任何使用她 PC 的人都能用她的金鑰。大多數 PC 至少偶爾會被別人使用；Alice 不介意讓人用她的電腦，但絕對不想同時給出銀行帳戶的存取權！
- Alice 可能用好幾台電腦：金鑰存在家裡 PC 上，在公司或旅行時就無法使用。存在桌機還是筆電？**不希望她把金鑰複製到多個地方**——那只會進一步削弱系統。
- 存在 PDA 或智慧手機？比較不會借人，又隨身攜帶——但小裝置也**容易遺失或被偷**，不希望之後持有裝置的人能存取秘密金鑰。

**加密秘密能改善安全嗎？** 當然，但**用什麼加密？** 需要一把主金鑰，而主金鑰又得存在某處——和加密的秘密放在一起毫無好處。

> 但這是**減少秘密數量與大小**的好技術，常與其他技術搭配：一把 RSA 私鑰有數千位元，用一把對稱金鑰加密並認證後，需要安全儲存的大小就大幅縮小。（呼應 ch8 §4.4：大量資料加密存放，只用 Boojum 保護金鑰。）

## 3. 人腦 ⭐⭐

讓 Alice **記住一個密碼**，用這個密碼加密所有其他金鑰材料。加密後的金鑰材料可以存在任何地方——磁碟，甚至 Web 伺服器，讓 Alice 下載到她當下使用的任何電腦。

**人類出了名地不擅長記密碼**：

- 很簡單的密碼毫無安全性：簡單密碼數量太少，攻擊者全部試一遍即可。
- 母親的婚前姓氏？常是公開資訊；即使不是，攻擊者大概也只要試幾十萬個姓氏。

**好的密碼必須不可預測——也就是有大量的熵**：

| 來源 | 熵 |
|---|---|
| 單一英文單字（約 50 萬字，含完整字典中的冷僻長字） | 最多約 **19 bits** |
| 英文文字 | 每個字母約 **1.5–2 bits** |

**目標該多少？**

- 全書用 256-bit 金鑰達到 128-bit 安全——大多數地方額外成本很低；但這裡要**使用者記住**，更大的金鑰成本很高。256 bits 熵的密碼太麻煩 → 限制在 **128 bits 熵**。
- 樂觀估計每字元 2 bits → 需要 **64 個字元**。**不可接受**，使用者會直接拒絕。
- 妥協成 64-bit 安全（已經非常勉強）？至少 **32 個字元**，仍然太長。別忘了，**現實中多數密碼只有 6–8 個字母**。
- 指定密碼？你試過系統告訴你密碼是「7193275827429946905186」或「aoekjk3ncmakwe」嗎？人記不住——實務上使用者會把它寫下來（§5）。

### 3.1 通行片語（Passphrase）⭐

與密碼本質相同，只是**長得多**。

| 例子 | 長度 | 估計熵 |
|---|---|---|
| 「Pink curtains meander across the ocean.」 | 38 字元 | 約 57–76 bits |
| 「Pink dotty curtains meander over seas of Xmas wishes」 | 52 字元 | 約 78–104 bits |

- 無意義但相當好記；有鍵盤的話幾秒就打完——比打一串隨機數字快多了。
- 依賴的事實：**通行片語比隨機資料容易記得多**。許多記憶術正是把隨機資料轉換成類似通行片語的東西。

**首字母法**：「Wtnitmtstsaaoof,ottaaasot,aboet」看起來完全是亂碼——直到你發現它是莎士比亞「Whether 'tis nobler in the mind to suffer the slings and arrows of outrageous fortune, or to take arms against a sea of troubles, and by opposing end them.」每個字的首字母。

- 當然，Alice **不應使用文學作品中的句子**——攻擊者太容易取得，Alice 書架上的書裡又能有多少合適的句子？她應該**自己發明一個沒有人想得到的句子**。
- 比起完整通行片語，首字母法需要更長的句子，但**打字較少**、按鍵更隨機。作者不知道這種方法每字元有多少熵的估計。

> 通行片語無疑是在人腦中儲存秘密的最佳方式。可惜很多使用者仍覺得難以正確使用；而且即使用通行片語，**要在人腦中存到 128 bits 的熵也極其困難**。

> 後見之明：**Diceware**（擲骰子從 7776 字的字表中選字，每字約 12.9 bits）讓通行片語的熵可以精確計算——10 個字約 129 bits。XKCD 的「correct horse battery staple」漫畫也讓這個想法廣為人知。

### 3.2 加鹽與延展（Salting and Stretching）⭐⭐⭐

兩個聽起來像來自中世紀刑房的技術，能從熵有限的密碼中**榨出最多安全性**。

> 它們簡單又明顯到**每個密碼系統都應該使用**——真的沒有任何藉口不用。

**加鹽（salt）**：一個隨機數，與用密碼加密的資料**存放在一起**。能的話用 **256-bit** 的鹽。

**延展（stretch）**：本質上是一個**非常長的計算**。p 為密碼、s 為鹽、h 為任何密碼學強度的雜湊函式：

```
x0 := 0
xi := h(x(i−1) ‖ p ‖ s)        i = 1, …, r
K  := xr                       （xi 與 K 當然都是 256 bits）
```

用 K 作為真正加密資料的金鑰；r 是迭代次數，**越大越好**（在實用範圍內）。

**攻擊者的觀點**：已知 s 與用 K 加密的資料，嘗試不同密碼找出 K——選一個 p、算出 K、解密資料、看是否合理且通過完整性檢查。**每檢查一個 p，就要做 r 次雜湊**。r 越大，攻擊者的工作越多。

**金鑰檢查值**：有時希望在解密前就能檢查導出的金鑰是否正確，可以計算例如：

```
check = h(0 ‖ x(r−1) ‖ p ‖ s)
```

依雜湊函式的性質，它與 K **獨立**；與鹽一起存放，可在用 K 解密前先檢查密碼。

**如何選 r？** ⭐

- 正常使用時，**每次使用密碼都要做延展計算**——但此時使用者剛輸入密碼，大概花了好幾秒，所以密碼處理花 200 ms 完全可以接受。
- **規則：選擇 r，使得在使用者的設備上從 (s, p) 算出 K 需要 200–1000 ms。**
- 電腦越來越快，所以 r 也應該隨時間增加。理想做法：使用者第一次設定密碼時**實驗性地決定 r**，並把 r 與 s 一起存放。（確保 r 是合理的值，不要太小或太大。）

**賺到了多少？**

```
r = 2^20（略多於一百萬）
攻擊者每試一個密碼要做 2^20 次雜湊
試 2^60 個密碼要 2^80 次雜湊
⇒ r = 2^20 讓密碼的有效金鑰長度多了 20 bits
```

**另一種看法：摩爾定律補償器** ——r 讓攻擊者無法從越來越快的電腦中獲益，因為電腦越快，r 也越大。但這只在**長期**成立：**十年後，攻擊者可以用下一個十年的技術攻擊你今天用的密碼**。所以仍需要不錯的安全餘裕，以及盡可能多的熵。

> **這也是使用具前向安全的金鑰協商協定的另一個理由**：不論應用為何，Alice 的私鑰很可能最終是用密碼保護的。十年後攻擊者能搜尋出 Alice 的密碼——但若被密碼加密的金鑰只用來跑**具前向安全的金鑰協商**，攻擊者什麼有價值的東西都找不到：Alice 的金鑰早已過期，知道她的舊私鑰也無法揭露十年前使用的 session key。（呼應 ch14 §9.4。）

**鹽的作用：阻止規模經濟** ⭐

```
沒有鹽：系統有一百萬個使用者，各自存一個以延展後密碼加密的金鑰檔
  攻擊者：猜一個密碼 p → 算出延展金鑰 K（只算一次）→ 用 K 嘗試解密「每一個」檔案
  → 延展函式每個密碼只需算一次

有鹽：每個使用者的鹽都不同
  → 攻擊者必須對「每個密碼 × 每個檔案」組合各算一次延展
```

對攻擊者是多得多的工作，對使用者代價很小。位元很便宜，所以為了簡單起見建議用 **256-bit 鹽**。

**一個真實的反例** ⭐⭐

> 作者曾看過一個系統，把這一切實作得完美無缺——然後某個程式設計師想改善使用者介面，讓使用者**更快**知道輸入的密碼是否正確，於是**存了一個密碼的檢查碼**——整個加鹽與延展程序就此失效。
>
> 若回應時間太慢，可以降低 r，但**務必確保沒有任何方法能在不做至少 r 次雜湊的情況下判斷密碼是否正確**。

> 後見之明：本書的延展相當於 **PBKDF2**；現代建議使用**記憶體困難**的 **scrypt** 或 **Argon2id**（2015 年密碼雜湊競賽冠軍），讓攻擊者無法用 GPU/ASIC 大量平行破解。2013 年 Adobe 外洩事件中，1.5 億筆密碼用 ECB 模式 3DES「加密」且無鹽——正是本節所有建議的反面教材。

## 4. 可攜式儲存

**最簡單的形式：寫著密碼的紙。**

- 大多數人都以某種形式擁有這種紙，即使是網站這種非密碼系統。多數使用者至少要記六個密碼——太多了，尤其是很少用的系統。所以**使用者會把密碼寫下來**。
- 限制：每次使用時密碼仍要經過使用者的眼睛、大腦和手指 → 為了把使用者的煩躁和錯誤控制在合理範圍內，只能用相對低熵的密碼與通行片語。

> 身為設計者，你不必設計或實作任何東西來使用這種儲存方式——**不論你訂什麼規則、怎麼設計密碼系統，使用者都會這樣存他們的密碼。**

**更進階：某種可攜式記憶體**——記憶晶片卡、磁條卡、USB 隨身碟或任何數位儲存。

- 數位儲存一定大到能存至少 256-bit 的秘密金鑰 → 可以**消除低熵密碼**。
- 可攜式記憶體變得非常像一把**鑰匙**：誰持有它誰就有存取權——所以必須妥善保管。

## 5. 安全權杖（Secure Token）⭐⭐

更好（也更貴）的方案：一台 Alice 可以隨身攜帶的**小電腦**。外型差異很大：智慧卡（和信用卡一模一樣）、iButton、USB dongle、PC Card……主要特性是**非揮發記憶體**加上 **CPU**。

**比可攜式儲存多了的安全強化**：

- 存取儲存的金鑰材料可以用密碼或類似方式**限制**：要先送出正確的密碼，權杖才讓你使用金鑰。
- **抵抗暴力搜尋**：失敗三到五次就停用存取。（當然有些使用者太常打錯，權杖得被「救活」——但救活可以用更長、熵更高的通行片語或金鑰，安全得多。）

**多層防禦**：

```
1. Alice 保護實體權杖（放在皮夾或鑰匙圈上）
2. 攻擊者必須偷到權杖，或至少以某種方式接觸到它
3. 然後還要：實體破開權杖取出資料（權杖通常有防竄改設計），
   或找出解鎖權杖的密碼
```

> 註：它們是**防竄改（tamper-resistant）**，不是**竄改免疫（tamper-proof）**——防竄改只是讓竄改更昂貴。**竄改回應（tamper-responding）**裝置可能偵測到竄改後自毀。

> **安全權杖是目前儲存秘密金鑰最好、最實際的方法之一**——相對便宜，又小到方便攜帶。

**實務問題：使用者的行為** ⭐

- 使用者去吃午餐或開會時，會把權杖**插在電腦上**不拔。
- 使用者不想每次都被要求輸入密碼 → 系統被設定成上次輸入密碼後**幾小時內**都允許存取。
- 攻擊者只要走進來，就能開始使用權杖中的秘密金鑰。

**怎麼解決？**

| 方法 | 效果 |
|---|---|
| 訓練：「辦公室企業安全」影片、尷尬又一點都不好笑的「帶著權杖去吃午餐」海報、「要是再讓我發現你的權杖插著沒人看管，你就會再聽一次這種演講」的訓話 | 有限 |
| **讓權杖同時是辦公室門的鑰匙**——使用者必須帶著權杖才能回到辦公室 | ✅ |
| **改造咖啡機，出示權杖才給咖啡** | ✅ |

> 這類手段讓員工有動機帶著權杖去咖啡機，而不是離開時插在電腦上。**有時安全就是由這種看似愚蠢的措施構成的——但它們比用其他方式強制執行「隨身攜帶權杖」規則有效得多。**（呼應 ch13：**誘因**比規則更能驅動行為。）

## 6. 安全使用者介面（Secure UI）⭐

安全權杖仍有一個重大弱點：**Alice 的密碼要在 PC（或其他裝置）上輸入**。只要信任 PC 就沒問題——但大家都知道 PC 一點也不安全。事實上，不把 Alice 的金鑰存在 PC 上的整個理由，就是**我們不夠信任它**。

**第一步：權杖內建鍵盤與顯示器** → 密碼（更可能是 PIN）直接在權杖上輸入，不必信任外部裝置。

- 保護了 PIN 不外洩。
- 但 PIN 輸入後，**PC 仍會拿到金鑰**，之後它想對金鑰做什麼都行 → 仍受限於整台 PC 的安全。

**第二步：把涉及金鑰的密碼運算放進權杖** ⭐⭐

- 需要在權杖中放**應用專屬**的程式碼 → 權杖很快長成一台完整的電腦——但現在是使用者隨身攜帶的**可信電腦**，可以在權杖上實作每個應用的**安全關鍵部分**。
- **顯示器變得至關重要**：它用來告訴使用者，輸入 PIN 是在授權**什麼動作**。

```
典型設計（銀行付款）：
  使用者用 PC 的鍵盤與滑鼠操作應用
  需要授權付款時：PC ──交易資料──► 權杖
  權杖在自己的螢幕上顯示金額與幾項交易細節
  使用者在權杖上輸入 PIN 授權
  權杖簽署交易細節 ──► PC 完成交易其餘部分
```

> 「**所見即所簽（What You See Is What You Sign）**」——被入侵的 PC 可以竄改它顯示的內容，但改不了權杖螢幕上顯示的金額。

- 目前，具備安全 UI 的權杖對多數應用**太貴**。最接近的大概是 PDA 或智慧手機——但人們會往裡面下載程式，它們也不是從一開始就設計成安全裝置，所以可能**不比 PC 安全多少**。作者希望未來具安全 UI 的權杖更普及。

> 後見之明：這個願望部分實現了——**硬體加密貨幣錢包**（Ledger、Trezor）正是「有螢幕、在裝置上確認交易」的設計；手機的 **Secure Enclave / TEE** 與 **FIDO2/WebAuthn 安全金鑰**也把私鑰運算留在獨立晶片中。歐洲銀行的 PSD2 要求的「動態連結」（簽章綁定金額與收款人）也是同一思路。

## 7. 生物辨識（Biometrics）

想更花俏的話，可以在安全權杖中加入指紋或虹膜掃描器。

**目前的生物辨識裝置不太有用**：

- 指紋掃描器可以做得價格合理，但提供的安全性一般不太好。
- **2002 年，密碼學家松本勉（Tsutomu Matsumoto）**與三位學生展示：只用**家用與手工藝材料**（明膠，即「軟糖手指」），就能穩定騙過他買得到的**所有**商用指紋掃描器。
- 甚至從**潛伏指紋**（你在每個光滑表面上留下的那種）製作假手指，對聰明的高中生來說也不過是個嗜好專題。

> 真正讓作者震驚的不是指紋讀取器能被騙，而是**騙它們竟然如此簡單又便宜**。更糟的是，生物辨識產業一直在告訴我們生物辨識有多安全，從沒告訴我們偽造指紋這麼容易。然後突然一位數學家（甚至不是生物辨識專家）出現，把整個流程炸得粉碎。2009 年的論文顯示這些問題依然存在。

**但指紋掃描器仍然可以很有用**：

| 用法 | 說明 |
|---|---|
| **高安全端：疊加** | 有小螢幕、小鍵盤和指紋掃描器的安全權杖：要取得金鑰，必須**實體控制權杖 + 知道 PIN + 偽造指紋**——比之前所有方案都更費工。大概是目前能做出的**最好的實用金鑰儲存方案**；但會相當昂貴，用的人不會多 |
| **低安全端：防止隨意違規** | 按一下手指很快，可以要求使用者相當頻繁地這麼做 → 提高「確實是本人在授權電腦執行的動作」的信心；讓員工更難把密碼借給同事。不是要擋住精密的攻擊者，而是**阻止隨意違反安全規則**——這可能比當作高安全裝置對安全的貢獻更大 |

> 補充：生物特徵**不是秘密**（你到處留下指紋），也**無法撤銷**（你不能換一根手指）——所以它適合當「多一層」或「本人在場」的證據，不適合當唯一的金鑰。

## 8. 單一登入（Single Sign-On）

一般使用者有太多密碼 → **單一登入**系統非常吸引人：給 Alice 一個主密碼，用它加密她各應用的所有不同密碼。

- 要做得好，**所有應用都必須與單一登入系統溝通**：應用需要密碼時不問使用者，而是問單一登入程式。要大規模實現有很多挑戰——想想有多少不同的應用要被修改才能自動從單一登入系統取得密碼。
- **更簡單的做法**：一個小程式把密碼存在（加密的）檔案中，Alice 輸入主密碼後，用複製貼上把密碼從程式貼到應用。Bruce 設計的免費程式 **Password Safe** 就是做這件事。

> 但它只是 Alice 寫密碼那張紙的**加密數位版**。若你總是用同一台電腦，它很有用、也比紙好——但不是單一登入理念真正想達成的終極方案。

> 後見之明：今天的**密碼管理器**（Bitwarden、1Password、瀏覽器內建）加上自動填入與雲端同步，以及企業的 **SAML / OpenID Connect** 聯合登入，正是本節兩種做法各自的演進；而 **Passkeys（FIDO2）** 則試圖讓密碼本身消失。

## 9. 遺失的風險 ⭐

安全權杖壞了怎麼辦？寫著密碼的紙留在口袋裡被洗衣機洗了怎麼辦？

> 遺失秘密金鑰總是壞事。代價可能從「每個應用重新註冊取得新金鑰」，到「**永久失去重要資料的存取權**」。如果你用一把秘密金鑰加密了寫了五年的博士論文，然後弄丟了金鑰——你就不再有博士論文了，只有一個看起來像隨機位元的檔案。哎喲！

**經驗法則：把「易用」與「可靠」兩個功能分開** ⭐

```
保留兩份金鑰：
  ├─ 一份「容易使用」（例如權杖、密碼管理器）
  └─ 一份「非常可靠」（例如銀行保險箱裡的一張紙）
易用的系統忘了金鑰時，從可靠的儲存系統還原。
```

- 可靠的系統可以非常簡單：**銀行保險箱裡的一張紙**如何？
- 但要小心：依其設計，它很快就會被用來存放你**所有**的金鑰 → 成為非常誘人的攻擊目標。要做**風險分析**，決定用許多較小的可靠儲存點，還是單一大的。

## 10. 秘密分享（Secret Sharing）⭐⭐

有些金鑰需要**超級安全**地儲存——例如 CA 的私有根金鑰。安全地儲存秘密已經很難；**既安全又可靠**更難。

**秘密分享**（Shamir，1979）是一個能幫忙的密碼學解法（名稱有點誤導，暗示你和好幾個人「分享」秘密——其實不是）：

- 把秘密拆成數個**份額（share）**，使得例如 **5 份中任 3 份**就能還原秘密；
- 每份交給 IT 部門的一位資深人員，任三人合作就能還原；
- **真正的技巧**：任意兩人合起來對金鑰**一無所知**。

**Shamir 方案的原理**（補充）：

```
k-of-n：取一個 k−1 次的隨機多項式 f(x)，常數項 f(0) = 秘密
份額 i = (i, f(i))，i = 1 … n
任 k 個點 → 唯一決定 k−1 次多項式 → Lagrange 內插得 f(0)
只有 k−1 個點 → 對每個可能的秘密值，都恰有一個多項式符合 → 完全不洩漏資訊
```

**學術上非常誘人**：

- 每個份額用前面討論的技術之一儲存；
- **k-of-n 規則**結合了**高安全性**（至少 k 人才能取得金鑰）與**高可靠性**（可以遺失 n − k 份而不受影響）；
- 甚至有更花俏的方案，允許更複雜的存取規則，例如「(Alice 且 Bob) 或 (Alice 且 Carol 且 David)」。

**現實中很少使用——因為太複雜** ⭐：

> 實作複雜，但更重要的是**管理與操作**複雜。**大多數公司沒有一群「高度負責又互不信任」的人。**
>
> 試著告訴董事們：每人會拿到一個存著金鑰份額的安全權杖，緊急時要在**週日凌晨三點**到場；喔對了，他們不可以互相信任，即使對其他董事也要保護好自己的份額；每次有人加入或離開董事會，他們都要到安全的金鑰管理室領取新份額。
>
> 實務上這代表董事會出局了。CEO 也不太適合持有份額——CEO 常出差。不知不覺就只剩兩三位資深 IT 主管。他們可以用秘密分享方案，但費用與複雜度讓它不吸引人。

**為何不用更簡單的東西，例如保險箱？** 實體方案（保險箱、銀行金庫）有幾個優點：

- **人人都懂**怎麼運作，不需要大量訓練；
- 已經過**大量測試**——而秘密重建流程很難測試，因為需要大量使用者互動；**你真的不會想要秘密重建流程中有個 bug，害你遺失 CA 的根金鑰**。

> 對照 ch20 §4：「很少執行的程序容易失敗」——秘密重建正是一年也許用不到一次、卻絕對不能失敗的程序。（後見之明：現代的 HSM 與雲端 KMS 常內建 k-of-n 的管理員卡片機制，把秘密分享的複雜度包裝進硬體與流程中；DNSSEC 根金鑰簽署儀式就是公開、可稽核的 k-of-n 實例。）

## 11. 抹除秘密（Wiping Secrets）⭐

任何儲存的長期秘密最終都要被抹除：**一旦不再需要，就應抹除其儲存位置**，以避免未來的外洩。ch8.3 討論過抹除記憶體的問題；**從永久儲存中抹除長期秘密更難得多**。

本章討論的儲存方式涵蓋各種技術——紙、硬碟、USB 隨身碟——**沒有一種附帶有文件記載、能保證資料無法還原的抹除功能**。

### 11.1 紙

- 通常靠銷毀紙本身。一種方法是**燒掉**，再把灰燼磨成細粉，或加一點水攪成漿糊。
- 碎紙也是選項，但許多碎紙機留下的碎片大到**重組頁面相對容易**。

### 11.2 磁性儲存 ⭐

磁性媒體**非常難抹除**，相關文獻少得驚人（最好的是 Peter Gutmann 的論文，但技術細節可能已過時）。

**為何覆寫不能完全刪除舊資料？**

- 資料存在微小的**磁域**中，磁化方向決定編碼的資料；覆寫時磁化方向改變以反映新資料。
- 但讀寫頭**從未完全對齊**，傾向留下部分舊資料未被觸及。

> 覆寫不會完全摧毀舊資料——就像**只刷一層油漆重新粉刷牆壁**，你仍然能隱約看見底下的舊油漆。

- 磁域也可能**遷移**離開讀寫頭——到磁軌側邊或更深入磁性材料——在那裡殘留很久。
- 一般讀寫頭通常讀不回被覆寫的資料，但**拆開磁碟並使用專門設備**的攻擊者可能取回部分或全部舊資料。

**實務上最好的選擇：用隨機資料重複覆寫**。要點：

| 要點 | 說明 |
|---|---|
| **每次覆寫用新的隨機資料** | 有研究者設計了據稱更能抹除舊資料的特定圖樣，但圖樣的選擇取決於磁碟的確切細節；隨機資料可能需要更多次才達到同樣效果，但**在所有情況下都有效**，因此更安全 |
| **覆寫實際存放秘密的位置** | 若只是往檔案寫新資料，檔案系統可能決定把新資料存到**別的位置**，原始資料原封不動 |
| **確保每一輪真的寫到磁碟** | 不只是寫進磁碟快取。自帶寫入快取的磁碟特別危險——可能快取新資料，並把多次覆寫**最佳化成一次寫入**（呼應 ch8：編譯器把 memset 最佳化掉） |
| **抹除範圍要比秘密前後都大一些** | 磁碟轉速從不完全恆定，新資料不會與舊資料完全對齊 |

- 需要幾次？作者不知道有可靠的資訊，但**沒理由選小的次數**——你只需要抹除一把金鑰。（若有大量秘密資料，就用一把金鑰加密存放，**只抹除那把金鑰**。）**50 或 100 次隨機覆寫完全合理。**
- **消磁機**：理論上可行，但現代高密度磁性媒體非常抗消磁，不是可靠的抹除方法；而且使用者實務上也沒有消磁機。
- **即使大量覆寫**，高度專業且資金充裕的攻擊者仍可能還原秘密。要徹底摧毀資料，大概得**摧毀媒體本身**：磁性層黏在塑膠上的（磁碟片、磁帶）可以碎掉再燒；硬碟可以用**帶式砂光機**磨掉盤片上的磁性層，或用**噴燈**把盤片熔成液態金屬。實務上很難說服使用者採取這麼極端的措施，所以**重複覆寫是最好的實用方案**。

### 11.3 固態儲存

EPROM、EEPROM、flash 等非揮發記憶體有類似問題：覆寫不會移除所有痕跡，§8.3.4 的資料殘留機制也在作用。同樣地，**用隨機資料重複覆寫是唯一實用的方案，但絕非完美**。固態裝置一不再需要，就應該**銷毀**。

> 後見之明：SSD 的**損耗平均（wear leveling）**與預留空間讓「覆寫同一位置」幾乎不可能——邏輯位址會被重新對應到新的實體頁，舊頁原封不動留著。2011 年 Wei 等人的研究顯示，對 SSD 單檔覆寫幾乎完全無效。現代解法是**加密抹除（crypto-erase）**：全碟加密，抹除時只銷毀那把金鑰——正是本章「只抹除金鑰」建議的硬體化。

## 12. 參考實作（Python）

示範本章三個可計算的部分：依書中定義的**加鹽與延展**（含自動校準 r 使計算約 200 ms、金鑰檢查值）、**Shamir 3-of-5 秘密分享**，以及習題 21.3 的 **24-bit 鹽碰撞機率**。

```python
import hashlib, secrets, time, math

# ── 1. 加鹽與延展（書中定義：x_i = h(x_{i−1} ‖ p ‖ s)，K = x_r）────────────────
def stretch(p: bytes, s: bytes, r: int):
    x = bytes(32)                                    # x0 := 0（256 bits）
    prev = x
    for _ in range(r):
        prev, x = x, hashlib.sha256(x + p + s).digest()
    K = x                                            # 用來加密資料的金鑰
    check = hashlib.sha256(b"\x00" + prev + p + s).digest()   # 金鑰檢查值 h(0 ‖ x_{r−1} ‖ p ‖ s)
    return K, check                                  # 檢查值也需要做滿 r 次雜湊才算得出

def calibrate(target=0.2):
    """選 r，使使用者的機器上 stretch 約花 target 秒；r 與鹽一起存"""
    r = 1 << 12
    while True:
        t = time.perf_counter(); stretch(b"x", bytes(32), r); dt = time.perf_counter() - t
        if dt >= target / 2:
            return max(1 << 16, int(r * target / dt))   # 合理的下限
        r *= 2

# ── 2. Shamir 秘密分享（k-of-n），在 GF(P) 上 ──────────────────────────────
P = 2**521 - 1                                       # 梅森質數，大於 256-bit 秘密

def split(secret: int, k: int, n: int):
    coeffs = [secret] + [secrets.randbelow(P) for _ in range(k - 1)]
    f = lambda x: sum(c * pow(x, i, P) for i, c in enumerate(coeffs)) % P
    return [(x, f(x)) for x in range(1, n + 1)]

def combine(shares):
    total = 0
    for i, (xi, yi) in enumerate(shares):            # Lagrange 內插求 f(0)
        num = den = 1
        for j, (xj, _) in enumerate(shares):
            if i != j:
                num = num * (-xj) % P
                den = den * (xi - xj) % P
        total = (total + yi * num * pow(den, -1, P)) % P
    return total

# ── 3. 習題 21.3：24-bit 鹽的生日碰撞機率 ────────────────────────────────────
def collision_prob(users: int, bits=24):
    N = 2**bits
    return 1 - math.exp(-users * (users - 1) / (2 * N))

if __name__ == "__main__":
    r = calibrate(0.2)
    s = secrets.token_bytes(32)                      # 256-bit 鹽
    K, chk = stretch(b"Pink dotty curtains meander over seas of Xmas wishes", s, r)
    print(f"r = {r} (≈ 2^{math.log2(r):.1f}) → 每個猜測多花 {math.log2(r):.1f} bits 的工作量")
    print("K =", K.hex()[:16], "…   check =", chk.hex()[:16], "…")

    key = secrets.randbits(256)
    sh = split(key, 3, 5)
    print("3-of-5 any three:", combine([sh[0], sh[2], sh[4]]) == key,
          " two only:", combine(sh[:2]) == key)

    for u in (64, 1024, 4096, 16_777_216):
        print(f"24-bit salt, {u:>10} users: P(collision) ≈ {collision_prob(u):.4f}")
```

實測輸出（r 依機器速度而不同）：

```
r = 219922 (≈ 2^17.7) → 每個猜測多花 17.7 bits 的工作量
K = 5ba504b5e753635a …   check = 60ddb67a49d74b06 …
3-of-5 any three: True  two only: False
24-bit salt,         64 users: P(collision) ≈ 0.0001
24-bit salt,       1024 users: P(collision) ≈ 0.0307
24-bit salt,       4096 users: P(collision) ≈ 0.3934
24-bit salt,   16777216 users: P(collision) ≈ 1.0000
```

> 注意 `check` 的計算用到 x_{r−1}，所以**算出檢查值同樣要做滿 r 次雜湊**——不會重蹈 §3.2 那位程式設計師的覆轍。

## 13. 設計觀念整理

| 觀念 | 說明 |
|---|---|
| 保密 vs. 不遺失 | 長期秘密的兩個衝突需求 |
| 加密縮小秘密 | 用小金鑰保護大秘密，但主金鑰仍要有地方放 |
| 人腦的熵很少 | 單字 ≤ 19 bits；英文每字元 1.5–2 bits |
| 通行片語 | 人腦儲存秘密的最佳方式；自己編句子 |
| **加鹽 + 延展** | 每個密碼系統都該用；鹽 256 bits；r 使計算 200–1000 ms |
| 不可有捷徑 | 任何檢查密碼的方法都至少要 r 次雜湊 |
| 前向安全兜底 | 密碼十年後被破，舊 session key 仍安全 |
| 使用者會寫下密碼 | 不論你怎麼規定 |
| 安全權杖 | 實體持有 + PIN + 防竄改；鎖定失敗次數 |
| 用誘因而非規則 | 門禁卡、咖啡機 |
| 安全 UI | 在權杖上顯示並確認交易內容 |
| 生物辨識 | 易被騙，適合疊加或防隨意違規 |
| 易用與可靠分開 | 保險箱裡的紙當備份 |
| 秘密分享好看不好用 | 組織沒有「負責又互不信任」的人；保險箱更簡單 |
| 抹除很難 | 磁碟覆寫 50–100 次隨機資料；最好銷毀媒體；只抹除金鑰 |

> 對照第一本書：Hanson 的 `Mem` 偵錯實作會在釋放記憶體時**填入特殊值**以抓出懸空指標——這是為了**除錯**而覆寫；本章的抹除是為了**保密**而覆寫，而且要面對快取、檔案系統重新配置、媒體殘留等 Hanson 不必擔心的層層阻礙。

## 16. 本章重點整理

1. 長期秘密有兩個衝突需求：**保密**與**不遺失**。
2. **磁碟**只在電腦安全時可行；加密能縮小秘密，但主金鑰仍需要存放處。
3. **人腦**的熵很少：用**通行片語**（自己編的句子或首字母法），但仍難達 128 bits。
4. **加鹽（256-bit）與延展（r 使計算 200–1000 ms）**是每個密碼系統的必備；不可留任何繞過 r 次雜湊的捷徑；配合前向安全。
5. **可攜式儲存**與**安全權杖**：實體持有 + PIN + 防竄改 + 失敗鎖定；用門禁、咖啡機等**誘因**讓使用者隨身攜帶。
6. **安全 UI**：在權杖上顯示並確認交易內容，不必信任 PC。
7. **生物辨識**易被騙（軟糖手指），適合疊加或防止隨意違規。
8. **單一登入**理想難實現；Password Safe 只是加密版的紙。
9. **遺失風險**：易用與可靠分開，保留一份放在保險箱的備份。
10. **秘密分享**（k-of-n）學術上誘人，實務上管理太複雜，保險箱通常更好。
11. **抹除**：紙要燒成灰；磁碟用隨機資料覆寫 50–100 次並確保真的寫入；固態儲存不再需要就銷毀；最好只需抹除一把金鑰。

> **一句話**：長期秘密要藏得好又不能丟——讓密碼經過加鹽與延展、把金鑰鎖進隨身權杖、在保險箱留一份備份，用完就把它連同媒體一起毀掉。
