## 2. 大整數運算 ⭐⭐

公鑰運算全部依賴大整數運算，而正確實作它並不容易。

- 大整數常式幾乎總是**與平台相關**：例如多數 CPU 有 **add-with-carry** 指令來做多字加法，但在 C 或幾乎任何高階語言中都存取不到。用高階語言做大整數運算通常比平台最佳化版本慢好幾倍——而這些運算正是公鑰效能的瓶頸，收益大到不能忽略。
- 實作細節請參考 Knuth TAOCP、*Handbook of Applied Cryptography* 第 14 章。**對作者而言，真正的問題是：如何測試大整數運算？**

### 2.1 密碼學的失敗率標準

> 我們認為 **2^-64**（約一千八百京分之一）的失敗率**不可接受**，而大多數工程師達到這個標準會非常開心。很多程式設計師似乎認為 2^-20（約百萬分之一）可以接受，甚至很好。我們必須做得好得多——因為我們身處**對抗**的環境。

### 2.2 為何大整數特別難測？

| | 對稱元件（區塊加密、雜湊） | 大整數運算 |
|---|---|---|
| 程式路徑 | 幾乎**不依賴資料** | **依賴資料** |
| 測試 | 簡單的隨機測試就能涵蓋所有資料路徑；AES 的 S-box 打錯一格，幾次加密就抓到 | 傳遞最後進位的程式碼很少用到；除法常有一段程式**每 2^32 甚至 2^64 次除法才執行一次**——隨機測試找不到其中的 bug |

（例外：IDEA 與 MARS 常用分開的程式碼處理特殊情況。）

- 32-bit CPU 上，跑 2^40 個隨機測試還能期望每個 32-bit 字值在資料路徑的每部分都出現過；**64-bit CPU 上這種測試完全行不通**。
- 所以必須**極其仔細地**測試：確認**每條程式路徑**在測試中都被走過——這需要精心製作測試向量。
- 還要測所有**邊界條件**：若有 a < b 的判斷，就要測 a = b − 1、a = b、a = b + 1（在可能達成的範圍內）。
- **最佳化讓情況更糟**：這些常式是效能瓶頸 → 通常高度最佳化 → 更多特殊情況、更多路徑 → 更難測試。

> 對照第一本書：Hanson ch17 的 `XP_div`（多字除法，基於 Knuth Algorithm D）就有一段「估計的商偏大時要修正」的分支，正是這種罕見路徑的典型——Hanson 在書中特別說明了這個情況何時發生。

### 2.3 一個算術錯誤 → 災難 ⭐⭐

**RSA-CRT 故障攻擊**（Boneh–DeMillo–Lipton，1997）：

```
Alice 用 CRT 計算 RSA 簽章時，模 p 的冪次出了一個小錯，模 q 的正確
→ 她送出 σ' = σ + k·q（模 q 正確、模 p 錯誤，所以必為此形式）

攻擊者知道 σ³ mod n（Alice 要開根號的數，只依賴訊息）
(σ + kq)³ − σ³ 是 q 的倍數
gcd((σ')³ − σ³, n) = q   ⇒   n 被分解！
```

> 只要**一個**錯誤的簽章，私鑰就完了。

**怎麼辦？**

1. **不要自己實作大整數常式**——用現成的函式庫。想花時間的話，花在**理解與測試**現有函式庫上。
2. 對函式庫做**非常好的測試**，確保每條可能的程式路徑都被測到。
3. **在應用中插入額外的檢查**（以下各節）。

**順帶一提：旁通道與測試的關係**——為了防旁通道（§8.5、§4），函式庫應該寫成程式路徑**不依賴資料**：多數分支可以換成**遮罩運算**（從 if 條件算出遮罩，用它選取正確結果）。這解決了旁通道問題，但對測試的影響完全相同：要測遮罩運算，仍要產生讓兩種條件都成立的測試案例——同一個測試難題，只是用「程式路徑」解釋比較好懂。

```c
/* 分支版：時間依賴 cond */
r = cond ? a : b;

/* 遮罩版：mask 為全 1 或全 0，路徑與資料無關 */
uint64_t mask = -(uint64_t)(cond != 0);
r = (a & mask) | (b & ~mask);
```

### 2.4 Wooping ⭐⭐

**名稱由來**：David Chaum 與 Jurjen Bos 激烈討論時，突然需要替一個特殊的驗證值命名，情急之下有人說「woop」，結果整個技術就叫這個名字了。Bos 後來在博士論文中詳述此技術，但因為這名字「不夠學術」而拿掉了。

**基本概念**：在一個**隨機選取的小質數**下驗證計算。

> 把它想成一個密碼問題：大整數函式庫想作弊、給我們錯誤的結果，我們的任務是檢查結果是否正確。**用同一個函式庫再算一次不是好主意**——它可能犯一致的錯誤。只要假設函式庫不是**刻意**破壞我們的驗證計算，wooping 就能驗證它。

**做法**：

```
1. 產生一個 64–128 bits 的隨機質數 t（不可固定或可預測——用 PRNG；對其他所有人保密）
2. 對計算中的每個大整數 x，同時保存 x̃ := x mod t（x 的 woop）
   woop 值大小固定、遠小於大整數 → 額外成本不高
3. 輸入：直接算 x̃ = x mod t
   內部計算：用 woop 值「影子計算」結果的 woop，而不是從大整數結果算出

   加法       c = a + b          c̃ = ã + b̃            (mod t)
   乘法       c = a · b          c̃ = ã · b̃            (mod t)
   模加法     c = a + b + k·n    c̃ = ã + b̃ + k̃·ñ      (mod t)   k ∈ {0, −1}
   模乘法     c = a · b + k·n    c̃ = ã · b̃ + k̃·ñ      (mod t)
   模冪       由模乘法（與模平方）組成，逐步傳遞 woop

4. 最後檢查：(x mod t) =? x̃
```

- **難點**：模乘法需要 k̃，必須從模乘法常式中「哄」出 k。建函式庫時加入很容易，**改裝現有函式庫很難**。通用方法：先算 a·b，再用長除法除以 n——商就是 k、餘數就是 c；缺點是明顯變慢。
- woop 輸入有任何錯誤，輸出幾乎一定也錯 → **錯誤會一路傳到最終結果**，所以可以只在最後檢查一次（比每步都檢查有效率）。
- 函式庫的程式碼早在我們選 t 之前就固定了，也不受攻擊者控制 → 可證明函式庫的**任何**錯誤都會被絕大多數 t 值抓到。

**woop 該多大？**

- 隨機錯誤：漏掉的機率約 1/t。
- 但我們的世界沒有隨機：假設函式庫有 bug，而**攻擊者知道**——她能選擇輸入，不只觸發錯誤，還能**選擇錯誤造成的差值**。所以 **t 必須隨機且保密**：不知道 t，她就無法把差值對準「不會被抓到」的值。
- 攻擊者會試圖讓差值同時是**許多** t 的倍數 → 要求 **t 是質數**：要對 16 個不同的 64-bit 質數作弊，至少要精心挑選 16 × 64 = 1024 bits 的輸入；而多數計算中攻擊者能選的輸入位元有限。
- t 越大越好（大質數多得多）；嚴守 128-bit 安全就要 128-bit 的 t。
- **但 woop 不是系統的主要安全機制，只是後備**：woop 驗證一旦失敗，就知道軟體有 bug——程式應**中止並回報致命錯誤**，這也讓攻擊者難以重複攻擊。所以建議 **64-bit 隨機質數**（比 128 bits 省很多開銷，實務上足夠）。負擔不起 64 bits 時，32-bit woop 也比沒有好（32-bit CPU 上有直接的乘除指令，非常有效率）。
- 若攻擊者能提供**大量**資料，**中間值**也要檢查：每個只依賴少量攻擊者位元的中間值都驗證一次，讓作弊更難。

> **作者強烈偏好有 woop 驗證的大整數函式庫**——相對簡單地避免大量潛在安全問題；而且在函式庫中加一次 woop，比在每個使用它的應用中各自加檢查省事得多。可惜作者不知道有任何現成的這種函式庫。

### 2.5 檢查 DH 計算

沒有 woop 函式庫時：

- 我們的 DH 協定本來就有檢查（結果不為 1、結果的階為 q）——但檢查的是**接收方**，不是做計算的那一方。
- 一般而言不想送出錯誤的結果（可能洩漏資訊），但在這個特定情況似乎沒什麼害處：結果錯了，協定總會以某種方式失敗，錯誤會被注意到。
- 只有函式庫被要求算 g^x 卻回傳 **x** 時，協定安全才會崩潰——但這種錯誤一般測試很可能就會發現。
- DH 沒有長期秘密 → 必要時作者會用沒有 woop 的函式庫跑 DH；但能用 wooping 函式庫時仍然會用，求個安心。

### 2.6 檢查 RSA 加密

RSA 加密更脆弱、需要額外檢查——出錯可能洩漏你要加密的秘密，甚至你的私鑰。

| 方法 | 做法 | 缺點 |
|---|---|---|
| 解密回來比對 | 算 c^(1/5) mod n，與 m 比較 | 用很慢的驗證去檢查相對快的計算；而且加密時通常**沒有私鑰** |
| **隨機化檢查**（較佳） | 選隨機 z，檢查 **c · z^5 ≡ (m · z)^5 (mod n)** | 三次五次方運算（c = m^5、z^5、(mz)^5） |

- 隨機的算術錯誤極可能被抓到；z 是隨機的 → 攻擊者無法鎖定會產生錯誤的值。
- 而且在作者的設計中，RSA 只用來加密**隨機值**（§12.6）→ 攻擊者根本無從鎖定。

### 2.7 檢查 RSA 簽章 ⭐

> RSA 簽章非常容易檢查：**簽章者只要對剛產生的簽章跑一次驗證演算法。** 驗證相對很快，算術錯誤極可能被抓到。**每一次 RSA 簽章計算都應該驗證結果——沒有任何藉口不這麼做。**

（這正好擋下 §2.3 的 CRT 故障攻擊：錯誤的簽章根本不會被送出去。）

### 2.8 結論

- 這些檢查是**附加於**大整數函式庫的正常測試之上，**不能取代**任何軟體（尤其是安全軟體）應經歷的正常測試。
- **任何檢查失敗，就表示你的軟體剛剛壞了。** 你不知道是哪種軟體錯誤，繼續工作是不安全的——唯一能做的是**記錄錯誤並中止程式**。

## 3. 更快的乘法：Montgomery 方法 ⭐

模乘法有很多比「完整乘法 + 長除法」快的方法；要做大量乘法時，**Montgomery 方法**最廣為使用。

**核心想法**：計算 x mod n（x 遠大於 n）。傳統長除法是減去 n 的適當倍數；Montgomery 的想法更簡單——**反覆除以 2**：

```
若 x 是偶數：右移一位（除以 2）
若 x 是奇數：先加 n（不改變模 n 的值，且因 n 為奇數使 x 變偶數），再除以 2

n 有 k bits、x ≤ (n−1)² 時，共做 k 次除以 2
結果在 0 … 2n−1 之間（幾乎完全約減）
```

**但等等**——一直除以 2，答案不對！Montgomery 約減給的不是 x mod n，而是 **x / 2^k mod n**，多了一個因子 2^-k。

**壞主意**：重新定義協定，在計算中包含額外的 2^-k 因子。這**混淆了不同層次**——為了某種實作技術修改密碼協定規格。將來在另一個平台上實作時（例如那個平台很慢，但有能直接做模乘法的大整數協處理器），協定中的 2^-k 因子就成了真正的阻礙。

> 呼應 §12.5：**規格與實作必須分離**（PKCS#1 把 CRT 寫進標準也被作者批評過）。

**標準技術：改變數字的表示法**

```
內部用 x · 2^k 表示 x（Montgomery 表示法）

Mont(x·2^k, y·2^k) = x·2^k · y·2^k · 2^-k = (x·y)·2^k     ← 正好是 xy 的表示法

轉入：Mont(x, 2^(2k) mod n) = x · 2^k
轉出：再做一次 k 位元的 Montgomery 約減（除以 2^k）
結果通常 < 2n − 1 → 一次比較 + 必要時減 n
```

**實際實作以「字」為單位**（w-bit 字）：找一個小整數 z 使 x + zn 的最低字全為 0——z 只有一個字，可由 x 的最低字乘上一個**只依賴 n 的單字常數**得到；然後右移一整個字（除以 2^w）。比逐位元快得多。

## 4. 旁通道攻擊 ⭐⭐

第 8.5 節對旁通道談得很簡短，不是因為它們無害，而是因為時序攻擊對**公鑰運算**也很有用，現在一併討論。

### 4.1 對稱元件

| 情況 | 例子 |
|---|---|
| 鼓勵用不同程式路徑處理特殊情況的加密器 | IDEA、MARS |
| 使用執行時間**依資料而變**的 CPU 指令 | 某些 CPU 上的乘法（RC6、MARS）、依資料旋轉（RC6、RC5） |
| **快取時序攻擊** | **AES**：從快取 vs. 主記憶體取得查表資料的時間差 |

本書使用的元件不用前兩類運算，但 AES 仍受快取時序攻擊影響。

### 4.2 公鑰運算的時序攻擊

公鑰運算的程式路徑常依賴資料 → 處理時間幾乎總是隨資料不同。

**情境**：電子商務的安全 Web 伺服器。SSL 協商中，伺服器要解密**客戶端選擇的** RSA 訊息。

```
攻擊者：
  連上伺服器 → 請它解密一個選定的 RSA 值 → 量測回應時間
  常見情況：若金鑰某位元為 1，集合 A 的輸入比集合 B 稍快；為 0 則無差別
  → 對 A、B 各送出數百萬次查詢，找出回應時間的統計差異
  → 其他影響時間的因素用足夠多的查詢平均掉
  → 得到金鑰的一個位元，接著攻擊下一個位元
```

聽起來牽強，但**已在實驗室中做到**，實務上也很可能做到（Kocher 1996；Brumley & Boneh 2003 跨網路攻擊 OpenSSL）。

### 4.3 對策

| 對策 | 評價 |
|---|---|
| **讓每次計算時間固定** | 最直接，但整個函式庫都要以此為目標設計；有些時間差幾乎無法控制（某些值乘法較快、複雜的快取系統——只要記憶體存取模式依賴非公開資料，快取延遲就可能造成時間差）。幾乎不可能消除所有時間差 |
| **加入隨機延遲** | **不能消除**時間差，只是藏進雜訊裡。能取得更多樣本的攻擊者可以平均掉。真實的時序攻擊本來就充滿雜訊，攻擊者本來就在做平均——唯一的問題只是**訊雜比** |
| **強制標準化時間**（作者喜歡） | 開發時選一個比計算可能花的時間更長的 d；記下開始時間 t，算完後**等到 t + d**。稍微浪費，但還好。只防**純時序**攻擊：攻擊者若能監聽 RF 輻射或量測功耗，計算與等待的差別很可能看得出來。但 RF 攻擊需要實體靠近，威脅遠小於可透過網路進行的時序攻擊 |
| **盲化（blinding）** | 源自盲簽章的技術，對某些計算能隱藏（幾乎）所有時間變化 |

**RSA 盲化**（補充說明）：

```
要計算 c^d mod n：
  選隨機 r，計算 c' = c · r^e mod n
  計算 m' = (c')^d = c^d · r mod n         ← 真正的私鑰運算作用在「隨機化」的輸入上
  m = m' · r^-1 mod n
攻擊者選的 c 與實際做冪次的 c' 無關 → 時間與攻擊者的選擇無關
```

**最好的方案：讓整個交易時間固定**

> 不只讓公鑰運算固定時間，還要固定「請求進來」到「回應送出」之間的時間：請求在時間 t 到達，就在 **t + C** 送出回應（C 為常數）。為了確保永不洩漏時間資訊，你最好確定回應在 t + C 時一定已經準備好——為此很可能必須**限制接受請求的頻率**上限。

> 時序攻擊沒有完美的解法——買得到的電腦不可能抵抗像 RF 攻擊那樣真正精密的攻擊。但雖然做不到完美，可以做到相當好。**對公鑰運算的時序要非常小心。**

## 5. 協定的實作 ⭐

實作密碼協定和實作通訊協定差不多：

| 方式 | 說明 | 評價 |
|---|---|---|
| **狀態放在程式計數器** | 依序執行協定的每一步 | 最簡單；但除非用多執行緒，等待回應時整個程式都停住——而回應可能永遠不來 → 通常是壞主意 |
| **明確的協定狀態** | 每收到一則訊息就更新狀態（訊息驅動） | 實作稍多，但**彈性大得多** |

> 對照第一本書：Hanson ch20 的 `Thread` 介面讓「狀態放在程式計數器」的寫法變得可行——每個協定執行一個執行緒，用 `Chan` 等待訊息，其他執行緒照常運作。這是兩種方式的折衷。

### 5.1 在安全通道上執行協定

有時在安全通道上跑密碼協定是合理的：例如每個使用者與**金鑰分配中心**之間都有安全通道，中心用一個簡單協定分配金鑰讓使用者彼此通訊（**Kerberos** 就做類似的事）。

- 若與已交換過金鑰的一方跑協定，就應該使用**完整的**安全通道功能——尤其要實作**重放保護**：很容易做，又能阻止大量對密碼協定的攻擊。
- 安全通道有時讓協定可以走捷徑（例如通道有重放保護，協定本身就不必有）。但**模組化的老規則：協定應盡量減少對安全通道的依賴**。
- 以下討論假設協定跑在**不安全**的通道上——有些不完全適用於安全通道的情況，但這些解法絕不會有害。

### 5.2 接收訊息

每則訊息應以下列欄位開頭：

| 欄位 | 用途 |
|---|---|
| **協定識別碼** | 確切是哪個協定、**哪個版本**（版本識別碼很重要） |
| **協定實例識別碼** | 屬於哪一次執行——Alice 和 Bob 可能同時跑兩次金鑰協商，不能混淆 |
| **訊息識別碼** | 協定中的第幾則訊息——最簡單的方法就是編號 |

- 視情況有些可以**隱含**：例如協定跑在自己的 TCP 連線上，port 與 socket 就唯一識別了本機的協定實例；協定與版本資訊只需交換一次——但**至少要交換一次**，才能確保它們被納入協定中的認證或簽章。

**處理規則**（假設剛收到第 n−1 則、正在等第 n 則）：

```
收到第 n 則             → 依協定規則處理
收到 > n 或 < n−1 的    → 不應被產生 → 必定是偽造 → 忽略內容
收到第 n−1 則           → 可能是我的回覆沒送到（假設傳輸不可靠，以減少依賴）
    與先前收到的第 n−1 則「完全相同」？
        是 → 重送我的回覆（必須與上次送出的完全相同）
        否 → 忽略新訊息。⚠️ 送出第二個不同的回答會破壞許多協定的安全
```

（與 §13.5.6 的規則一致，這裡更具體化。）

**因上述規則忽略了訊息後，要不要中止協定？**

| 情況 | 處置 |
|---|---|
| 協定跑在**安全通道**上 | 一定出了大問題：通道被攻破，或對方行為異常 → **中止協定與通道**：刪除協定狀態與通道狀態，包括通道金鑰 |
| 協定跑在**不安全通道**上 | 被忽略的訊息可能來自試圖干擾的攻擊者。理想上忽略攻擊者的訊息、完成協定——但不一定做得到：若攻擊者偽造的第 n−1 則先到，你就會回覆；之後收到「真的」第 n−1 則只能忽略（不能安全地送第二個回覆），而且你無從得知哪一則是真的。為了有最大機會成功完成協定：**把第二則 n−1 記為錯誤、照常繼續**。若你回覆的是攻擊者的訊息，協定最終會失敗——密碼協定本來就是設計來阻止攻擊者與參與者之一成功完成協定的 |

### 5.3 逾時

- 每次協定執行都有逾時：合理時間內沒收到回應就重送上一則訊息；重送幾次後放棄——無法與對方通訊時，繼續協定沒有意義。
- 最簡單的實作：**把計時訊息送給協定狀態**——用協定自己設定的計時器，或每幾秒送一次的計時訊息。

**洪水攻擊**：送出大量「協定開始」訊息，每收到一則就初始化一個新的協定執行狀態，收到幾百萬則後機器記憶體耗盡、一切停擺——例如 **SYN flood**。在殭屍網路與分散式攻擊的時代，沒有簡單的通用防禦，但這顯示了**刪除舊協定狀態**的重要：協定停滯太久就該刪除。

> 後見之明：SYN cookie、IKEv2 與 DTLS 的 cookie 交換，都是「在對方證明能收到回應之前，不配置任何狀態」的無狀態防禦。

**作者的經驗值**：

```
網際網路上的封包：大約一秒內到達，否則就永遠遺失
5 秒沒收到回覆 → 重送
重送 3 次就夠：若 15 秒內連續遺失 4 則訊息，這條連線也做不了什麼事
20 秒後通知使用者有問題，而不是讓使用者乾等一兩分鐘
```

## 6. 參考實作（Python）

示範本章四個技術：**CRT 故障攻擊**（一個位元的錯誤就分解 n；而簽完先驗證就能擋下）、**wooping**（在秘密的 64-bit 隨機質數下影子計算，抓出注入的函式庫 bug）、**RSA 加密的隨機化自我檢查**，以及**Montgomery 約減**。

```python
import secrets
from math import gcd
from primes import is_prime, generate_large_prime

# ── 1. CRT 故障攻擊：簽章時模 p 的那一半算錯，一個錯誤簽章就能分解 n ──────────
def crt_fault_demo():
    p = generate_large_prime(2**511, 2**512 - 1)
    q = generate_large_prime(2**511, 2**512 - 1)
    n, e = p * q, 65537
    t = (p - 1) * (q - 1) // gcd(p - 1, q - 1)
    d = pow(e, -1, t)
    s = secrets.randbelow(n)                          # 要開 e 次方根的數（只依賴訊息）
    a = pow(s, d % (p - 1), p) ^ 1                    # ← 模 p 的計算出了「一個位元」的錯
    b = pow(s, d % (q - 1), q)
    bad_sig = ((a - b) * pow(q, -1, p) % p) * q + b   # Garner：結果模 q 正確、模 p 錯誤
    found = gcd(pow(bad_sig, e, n) - s, n)            # (σ')^e − s 是 q 的倍數
    return found == q, pow(bad_sig, e, n) == s        # 若先驗證簽章，就不會送出

# ── 2. Wooping：在隨機秘密小質數 t 下「影子計算」，最後比對 ─────────────────────
class Woop:
    def __init__(self, bits=64):
        self.t = generate_large_prime(2**(bits - 1), 2**bits - 1)

    def mulmod(self, a, aw, b, bw, n, nw, buggy=False):
        prod = a * b
        k, c = divmod(prod, n)                        # c = a·b − k·n，k 由長除法取得
        if buggy and prod % 7 == 0:
            c ^= 1 << 100                             # 模擬一個罕見路徑上的 bug
        cw = (aw * bw - (k % self.t) * nw) % self.t   # c̃ = ã·b̃ − k̃·ñ (mod t)
        return c, cw

    def powmod(self, x, s, n, buggy=False):
        t = self.t
        r, rw = 1, 1
        xw, nw = x % t, n % t
        for bit in bin(s)[2:]:
            r, rw = self.mulmod(r, rw, r, rw, n, nw, buggy)
            if bit == "1":
                r, rw = self.mulmod(r, rw, x, xw, n, nw, buggy)
        if r % t != rw:                               # 最後的檢查
            raise ArithmeticError("woop mismatch: library bug — abort!")
        return r

# ── 3. RSA 加密的自我檢查：隨機 z，驗證 c·z^5 = (m·z)^5 (mod n) ───────────────
def check_rsa_encryption(m, c, n):
    z = 2 + secrets.randbelow(n - 3)
    return c * pow(z, 5, n) % n == pow(m * z % n, 5, n)

# ── 4. Montgomery 約減（逐位元教學版）─────────────────────────────────────────
def mont_reduce(x, n, k):
    """回傳 x / 2^k mod n（落在 0 … 2n−1，再視需要減一次 n）"""
    for _ in range(k):
        if x & 1:
            x += n                                    # 加 n 不改變模 n 的值，且變成偶數
        x >>= 1                                       # 除以 2
    return x - n if x >= n else x

def mont_mul(a, b, n, k):                             # 輸入輸出都是 Montgomery 表示法 x·2^k
    return mont_reduce(a * b, n, k)

if __name__ == "__main__":
    print("CRT fault → factor n:", crt_fault_demo())
    W = Woop(64)
    n = generate_large_prime(2**1023, 2**1024 - 1) * 3
    x, s = secrets.randbelow(n), secrets.randbits(256)
    print("woop ok (correct lib):", W.powmod(x, s, n) == pow(x, s, n))
    try:
        W.powmod(x, s, n, buggy=True)
    except ArithmeticError as e:
        print("woop with buggy lib:", e)
    m = secrets.randbelow(n)
    print("RSA enc check ok:", check_rsa_encryption(m, pow(m, 5, n), n),
          " corrupted:", check_rsa_encryption(m, pow(m, 5, n) ^ 4, n))
    N = 0xC5A3F1E9_7B2D4C61; k = N.bit_length()
    a, b = 0x123456789, 0x987654321
    R = 1 << k
    am, bm = a * R % N, b * R % N                     # 轉入：x → x·2^k
    cm = mont_mul(am, bm, N, k)
    print("Montgomery:", mont_reduce(cm, N, k) == a * b % N)   # 轉出：再約減 k 位元
```

實測輸出：

```
CRT fault → factor n: (True, False)
woop ok (correct lib): True
woop with buggy lib: woop mismatch: library bug — abort!
RSA enc check ok: True  corrupted: False
Montgomery: True
```

> 第一行：`True` 表示攻擊者成功用 gcd 求出 q；`False` 表示這個錯誤簽章**通不過驗證**——只要簽章者在送出前驗證（§2.7），攻擊就不可能發生。

## 7. 設計觀念整理

| 觀念 | 說明 |
|---|---|
| 2^-64 都不夠 | 對抗環境中的失敗率標準遠高於一般工程 |
| 資料依賴的路徑難測 | 大整數的罕見分支隨機測試找不到；要精製測試向量與邊界 |
| 一個算術錯誤 = 私鑰外洩 | RSA-CRT 故障攻擊 |
| 用現成函式庫 | 時間花在理解與測試它 |
| **Wooping** | 秘密隨機質數下的影子計算；錯誤會傳遞到最後 |
| 簽完就驗 | 每次 RSA 簽章都驗證，沒有藉口 |
| 檢查失敗 → 中止 | 不知道錯在哪，繼續就不安全 |
| 規格與實作分離 | 不要把 Montgomery 的 2^-k 寫進協定 |
| 隨機延遲沒用 | 只降低訊雜比；要固定時間或盲化 |
| 固定整個交易時間 | t + C 回應，並限制請求頻率 |
| 訊息驅動的狀態機 | 識別協定/實例/訊息；相同重試給相同回覆 |
| 刪除停滯的狀態 | 防洪水；5 秒重送、3 次放棄、20 秒告知使用者 |

## 10. 本章重點整理

1. 大整數運算是公鑰的瓶頸，與平台高度相關；**不要自己寫**，花時間測試現成函式庫。
2. 密碼學的失敗率標準：2^-64 都不可接受。大整數的**資料依賴路徑**讓隨機測試失效 → 測每條路徑與邊界。
3. 一個算術錯誤就可能洩漏私鑰（**RSA-CRT 故障攻擊**）。
4. **Wooping**：秘密的 64-bit 隨機質數 t 下的影子計算，最後比對 x mod t = x̃。
5. DH 的錯誤會被協定察覺；RSA 加密用隨機 z 自我檢查；**RSA 簽章一定要簽完就驗證**。檢查失敗 → 記錄並中止。
6. **Montgomery 乘法**：反覆除以 2（或以字為單位），改用 x·2^k 表示法；不要把 2^-k 寫進協定。
7. 時序攻擊：隨機延遲無效；用**固定時間**、**盲化**，最好讓**整個交易**固定時間。
8. 協定實作：訊息驅動的狀態機；訊息開頭帶協定/實例/訊息識別；相同重試給相同回覆；逾時重送、刪除停滯狀態。

> **一句話**：公鑰的數學沒錯，錯的是算數學的程式——所以要用秘密小質數暗中驗算、簽完就自己驗一遍，並且讓每次回應都花一樣長的時間。
