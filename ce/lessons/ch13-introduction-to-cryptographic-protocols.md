# 第 13 章　密碼協定入門（Introduction to Cryptographic Protocols）

> 《Cryptography Engineering》— Ferguson, Schneier, Kohno，本章頁碼：p.213–225

---

## 1. 本章定位

**密碼協定**：參與者之間交換訊息的過程。第 11 章的 DH 就是一個簡單的協定。

> 協定設計的根本困難：**你失去了控制權。** 之前我們設計的是自己掌控的系統；一旦開始和其他人通訊，就無法控制對方的行為。對方的利益與你不同，可能為了好處而違反規則。

> **設計協定時，必須假設你在和敵人打交道。**

本章不談具體協定（那是第 14 章），而是談**思考協定的框架**：角色、信任、誘因、訊息的分層結構、錯誤處理、重放與重試。

---

## 2. 角色（Roles）

- 「Alice」「Bob」「顧客」「商家」指的不是特定的人或組織，而是**協定中的角色**。
- Smith 先生今天扮演 Alice、Jones 先生扮演 Bob；明天可能顛倒。
- **同一個實體可以扮演任何角色**——三方以上的協定中，甚至可以**同時**扮演多個角色。

> 分析安全性時特別要記住這點：DH 的中間人攻擊中，Eve 同時扮演了 Alice 和 Bob 兩個角色。（Eve 本身也只是一個角色。）

---

## 3. 信任（Trust）⭐

信任是與他人往來的終極基礎。買一條巧克力棒就需要基本的信任：顧客信任商家給糖果、找對零錢；商家信任顧客付錢。雙方都有追索手段——扒手會被起訴，黑心商家會面臨負面宣傳、訴訟，或被揍一拳。

### 3.1 信任的來源

| 來源 | 機制 |
|---|---|
| **道德** | 很少人總是有道德，但大多數人大多數時候有道德；攻擊者是少數。多數人會付錢，即使偷竊容易得可笑 |
| **聲譽** | 人和公司想保護「好名聲」，負面宣傳的威脅促使他們守規矩 |
| **法律** | 文明社會有支援訴訟與起訴的法律體系 |
| **人身威脅** | 被抓到作弊就會受傷害——毒品交易等非法買賣的信任來源之一 |
| **MAD**（相互保證毀滅） | 冷戰術語。溫和版：「你騙朋友，她可能絕交，兩敗俱傷」；兩家公司互告專利侵權也是 |

這些都是讓一方**有誘因不作弊**的機制，而對方知道這個誘因，所以能在某種程度上信任他。這也解釋了為何**面對完全不理性的人，這些機制全部失效**——你無法信任他會依自身最佳利益行事。

### 3.2 網路上的信任很難建立

Alice 住在國外，連上 ACME 網站。ACME 幾乎沒有理由信任 Alice：對海外個人提起訴訟幾乎不可能且極其昂貴，也無法有效損害她的聲譽或威脅她，連 MAD 都用不上——只剩**道德**。

但兩者之間仍有信任基礎：**ACME 有聲譽要保護**。

> **電子商務協定的設計原則** ⭐：任何失敗模式（而且總是有）都應該**對 ACME 有利**。因為 ACME 有誘因透過人工介入妥善解決；若失敗對 Alice 有利，問題就不太可能被妥善處理，而且攻擊者會試圖誘發這種失敗模式來獲利。
>
> 這就是幾乎所有電話、郵購、電子商務都要求**先付款、後出貨**的原因。

### 3.3 信任不是非黑即白

> 你可能把 100 美元交給一個點頭之交，但不會把剛中了 500 萬美元的彩券交給他。我們信任銀行保管金錢，但仍會索取收據和已兌現支票的副本——因為我們不完全信任他們的行政作業。
>
> 「你信任他嗎？」這個問題是**不完整**的。應該問：**「在 X 這件事上，你信任他嗎？」**

### 3.4 風險（Risk）

- 在商業上，信任通常以**風險**的形式表達——風險可以看成信任的反面，被評估、比較、交易。
- 設計密碼協定時用「信任」來談比較容易；但**缺乏信任就是風險**，有時可以用保險等標準風險管理技術處理。
- 記住：**商業人士用風險思考和說話**。想和他們溝通，就要能在兩種觀點間轉換。

## 4. 誘因（Incentive）⭐⭐

**誘因結構**是協定分析的另一個基本元件：各參與者的目標是什麼？他們想達成什麼？即使在現實生活中，分析誘因結構也能得到深刻的結論。

### 4.1 生活中的誘因實例

| 情境 | 誘因結構 | 結果 |
|---|---|---|
| **贊助研究** | 研究者知道客戶想聽什麼、產出「好」結果就有續約；贊助者不發表負面報告 | 菸草公司發表「尼古丁不會成癮」的「科學」報告；**永遠不要相信支持其贊助者的研究** |
| **作者的顧問經驗** | 他們的評估常很嚴厲（評估過的產品平均相當糟） | 有客戶打電話給 Bruce：「停工、寄帳單來。我找到更便宜、寫報告寫得更好的人了。」——猜猜「更好」是什麼意思？ |
| **會計與分析師**（第一版撰寫時） | 報告是為客戶寫的 | 偏袒客戶而非公正評估 |
| **股票選擇權** | 三年內股價上漲 → 發大財；下跌 → 拿黃金降落傘 | 「正面我贏很多，反面我贏一點」→ 偏好高風險短期策略、用會計手法灌水股價 |
| **1980 年代美國儲貸危機** | 政府放寬投資規則，同時**保證存款** | 賺了歸儲貸機構與管理層，賠了由政府買單 → 大量高風險投資虧損 |
| **離婚律師** | 按小時收費 | 有誘因讓離婚充滿敵意；可以打賭他們會在律師費超過財產價值時才建議和解 |
| **嚴格責任法與巨額賠償** | 意外發生時每個參與者都有強烈誘因隱瞞、否認、推卸責任 | 難以查明原因、避免再犯——例如 Firestone 幾乎不可能承認輪胎有問題，讓大家學會做更好的輪胎 |

**修正誘因結構往往相對容易**：例如不讓公司自己付錢請人審計，改由證券交易所安排並付費；審計人員每找到一個錯誤就給一大筆獎金——報告會準確得多。

### 4.2 密碼協定與誘因的兩種互動

1. **依賴誘因結構**：有些電子支付協定**不阻止**商家欺騙顧客，而是給顧客**被騙的證據**——建立密碼學的**鑑識軌跡**。商家就有誘因不讓外面有人握著被騙的證據（可用於訴訟或損害聲譽）。
2. **改變誘因結構**：密碼協定讓某些事變得不可能（從誘因結構中移除），也可能開啟新的可能性與新的誘因——有了網路銀行，就給了小偷入侵你電腦偷錢的誘因。

> 誘因不只是物質的。在人際關係中，最根本的誘因與金錢幾乎無關。保持開放的心態，試著理解是什麼驅動人們，然後據此設計協定。

## 5. 密碼協定中的信任 ⭐⭐⭐

> **密碼協定的功能，是把所需的信任降到最低。**
> 這很重要，值得再說一次：**密碼協定的功能，是把所需的信任降到最低。**
> ——既減少需要互相信任的**人數**，也減少他們需要的**信任程度**。

### 5.1 偏執模型（Paranoia Model）

> Alice 參與協定時，**假設其他所有參與者都在聯手欺騙她**。這是終極的陰謀論。當然，其他每個參與者也都這樣假設。

這是設計所有密碼協定的**預設模型**。

### 5.2 偏離預設模型必須明確記錄

- 令人驚訝的是，這一步經常被忽略——協定被用在**所需信任並不存在**的情境中。
- **SSL 的例子**：SSL 需要可信的憑證，但憑證很容易取得。結果使用者確實在與網站**安全地**通訊，卻不知道**是哪個網站**。大量針對 PayPal 使用者的**網路釣魚**就利用了這個弱點。
- 不記錄所需的信任很誘人，因為它常常「很明顯」——對設計者也許是。但**協定和系統中任何模組一樣，應該有清楚規範的介面**。
- 從商業角度，記錄下來的信任需求**同時也是風險清單**：每一個需要信任的點，都意味著一個必須處理的風險。

> 對照第一本書：Hanson 要求每個介面寫清楚**呼叫者必須滿足的前置條件**（checked / unchecked runtime errors）。協定的「信任需求」正是協定介面的前置條件——沒寫出來，使用者就會在條件不成立的情境下誤用它。

## 6. 訊息與步驟：協定的分層 ⭐⭐

典型的協定描述 = 參與者之間的訊息 + 每個參與者要做的計算。

**兩難**：

- 幾乎所有協定描述都在**很高的層次**，細節大多沒寫 → 便於專注核心功能，但**沒有每個動作的仔細規格，極難寫出安全的實作**。
- 有時看到寫滿所有細節與檢查的規格 → **複雜到沒人完全看懂**。對實作者也許有幫助，但**太複雜的東西不可能安全**。

**解法：模組化**——和通訊協定一樣分層。每一層建立在下一層之上；大多數層對所有協定都一樣，只有**最上層**高度變化，而那正是通常被記錄的部分。

```
┌──────────────────────────────────────────────┐
│  協定本身的邏輯（第 14 章等，通常只描述這層） │
├──────────────────────────────────────────────┤
│  協定執行狀態（狀態機）                       │  §6.4
├──────────────────────────────────────────────┤
│  訊息編碼與解析（TLV、XML……）                 │  §6.3
├──────────────────────────────────────────────┤
│  協定與訊息識別（版本、協定 ID、訊息 ID）     │  §6.2
├──────────────────────────────────────────────┤
│  傳輸層（傳送任意 byte 字串）                 │  §6.1
└──────────────────────────────────────────────┘
```

### 6.1 傳輸層

（向網路專家致歉，借用了這個詞。）對密碼學家而言，傳輸層 = **能把一串 bytes 從一方送到另一方**的底層系統——UDP、TCP、e-mail 都行，怎麼做無關緊要。

- 可能需要額外編碼：同時執行多個協定時需要目的地欄位；用 TCP 時要加長度欄位，在串流上提供訊息導向的服務。
- 要求：傳輸**任意** byte 字串、任何 byte 值、可變長度；**收到的必須與送出的完全相同**（刪除尾端的 0 或任何修改都不允許）。
- 有些傳輸層加入**魔術常數**以提早偵測錯誤或檢查 TCP 串流同步；常數不對就丟棄訊息的其餘部分。
- **重要特例**：在加密的安全通道（第 7 章）上執行協定時，傳輸層還提供機密性、認證與重放保護——協定好設計得多，要擔心的攻擊類型少很多。

### 6.2 協定與訊息識別

- **協定識別碼**通常有兩部分：
  1. **版本資訊**——為未來升級留空間；
  2. 識別是哪一個協定——例如電子支付系統中的提款、付款、存款、退款協定，避免混淆。
- **訊息識別碼**：這是協定中的第幾則訊息（四則訊息的協定，不能搞混哪則是哪則）。

**攻擊者不是可以偽造這些嗎？** 當然可以。這一層**不防主動偽造**，而是偵測**意外錯誤**：

1. **區分攻擊與意外**：系統管理者突然收到大量錯誤訊息時，能區分主動攻擊與設定、版本問題，是很有價值的服務。
2. **自我描述、易於維護**：汽車和飛機都設計成易於維護；軟體更複雜——更有理由為維護而設計。
3. **最重要的理由：Horton 原則**——對協定中的多則訊息和欄位做認證或簽章時，納入訊息識別資訊，就避免了訊息**在錯誤的上下文中被解讀**。

### 6.3 訊息編碼與解析 ⭐

把每個資料元素轉成 bytes 是標準的程式設計問題。**真正重要的是解析**：

> 接收者必須能把一串 bytes 解析回各個欄位，而且**解析不可依賴上下文資訊**。

- 所有版本中都相同的固定長度欄位很好解析。
- 問題始於**欄位的大小或意義依賴上下文**（例如協定中先前的訊息）——自找麻煩。
- 許多訊息最後會被簽章或認證，而認證函式認證的是一串 bytes，通常在傳輸層層級認證最簡單。**若訊息的解讀依賴上下文，簽章或認證就有歧義**——作者曾以這類失誤攻破過好幾個協定。

**好的編碼方式**：

| 方式 | 說明 | 評價 |
|---|---|---|
| **TLV**（Tag-Length-Value） | 每個欄位 = 標籤（是哪個欄位）+ 長度 + 值 | 推薦 |
| **ASN.1** | 最知名的 TLV 編碼 | **複雜得難以置信**，作者敬而遠之；取一個子集會很有用 |
| **XML** | 忘掉炒作，只當資料編碼用 | 只要使用**固定的 DTD**，解析就不依賴上下文 |

> 後見之明：ASN.1/DER 解析器正是無數漏洞的來源（例如憑證解析、BER 簽章偽造）；現代協定多改用 Protocol Buffers、CBOR 或固定格式。作者的直覺是對的。

```
TLV 例：
  Tag   Len   Value
  0x01  0x04  00 00 00 2A         ← 欄位 1：訊息編號 = 42
  0x02  0x05  'h' 'e' 'l' 'l' 'o' ← 欄位 2：使用者名稱
```

### 6.4 協定執行狀態

- 一台電腦可能同時參與多個協定執行 → 需要**協定執行狀態**，包含完成協定所需的所有資訊。
- 需要某種**事件驅動程式設計**（等待外部訊息才能繼續）：每個協定執行一個執行緒/行程，或某種事件分派系統。
- 有了事件驅動的基礎設施，實作協定就相對直接：協定狀態包含一個**狀態機**，指出下一則預期的訊息類型。

> **一般規則：只接受預期類型的訊息，其他一律不接受。**

> 對照第一本書：Hanson ch20 的 `Thread`、`Chan` 介面正是這種事件驅動/每協定一執行緒的基礎設施；用 `Chan_receive` 等待下一則訊息，就是最自然的協定狀態機寫法。

### 6.5 錯誤 ⭐⭐⭐

協定總是包含大量檢查：協定類型、訊息類型、是否為目前狀態預期的訊息、能否解析、密碼驗證……任何一項失敗就是**錯誤**。

> **錯誤需要非常小心處理——它們是潛在的攻擊管道。**

| 做法 | 安全性 | 可用性 |
|---|---|---|
| **不回應任何錯誤、立即刪除協定狀態** | 最安全：攻擊者得到最少資訊 | 不友善：沒有任何錯誤提示 |
| 在**安全的日誌**中記錄錯誤，讓系統管理者診斷 | 好 | 好 |
| 必須送出錯誤訊息時，**盡可能不提供資訊** | 「發生錯誤」通常就夠了 | 尚可 |

**錯誤與時序攻擊的危險交互作用**：Eve 送假訊息給 Alice、等待錯誤回覆——Alice 偵測錯誤並回覆所花的時間，常常透露**錯在哪裡、錯在多深**。

**智慧卡 PIN 碼的真實案例** ⭐⭐

```
設計：4 位數 PIN；錯 5 次就鎖卡
      → 攻擊者猜中的機率 5 / 10000 = 1/2000  （很好，類似設計至今仍廣泛使用）

實作：逐位比對，一發現某位數錯就立刻回報「PIN 錯誤」
      → 回報時間取決於「前面對了幾位」
      → 攻擊者量測時間，就知道第一個錯誤的位數在哪

結果：每一位最多 10 次 → 最多 40 次就窮舉整個 PIN 空間
      5 次內猜中：1/2000 → 1/143
      20 次內猜中：0.2% → 60%
```

**更糟的是**：智慧卡在使用正確 PIN 後會**重設失敗計數器**。如果你拿得到室友的卡：試一兩次、放回去；等他在別處用正確 PIN 刷卡、計數器歸零；再試一兩次……最多 40 次就拿到整個 PIN。

**C 程式碼對照**（補充）：

```c
/* 有漏洞：發現錯誤就提早返回——時間洩漏「對了幾位」 */
int check_pin_bad(const char *entered, const char *stored) {
    for (int i = 0; i < 4; i++)
        if (entered[i] != stored[i])
            return 0;
    return 1;
}

/* 修正：不論對錯都比完全部位數，執行路徑與資料無關 */
int check_pin_ct(const char *entered, const char *stored) {
    unsigned char diff = 0;
    for (int i = 0; i < 4; i++)
        diff |= (unsigned char)(entered[i] ^ stored[i]);
    return diff == 0;
}
/* 另外：失敗計數器必須在比對「之前」先遞增並寫入非揮發記憶體，
   否則攻擊者可以在比對完成、寫入計數器前切斷電源。 */
```

> 錯誤處理太複雜，無法給出一套簡單規則——**我們這個社群對它的了解還不夠**。目前最好的建議：**非常小心，透露越少資訊越好**。

### 6.6 重放與重試 ⭐⭐

- **重放攻擊**：攻擊者錄下訊息，稍後重送。難以偵測——訊息看起來完全合法，因為它**本來就是合法的**。
- **重試（retry）**：Alice 沒收到回應（常見原因：Bob 沒收到她的上一則訊息還在等），於是重送上一則訊息。現實生活中天天發生：再寄一封信、再說一次。

Bob 可能收到攻擊者的重放，也可能收到 Alice 的重試——他必須正確處理，又不能引入安全弱點。

**送出重試**很簡單：計時器到了就重送上一則訊息。

- **UDP**：訊息遺失機率不低 → 短的重試時間（幾秒）。
- **TCP**：TCP 自己有逾時重送，在密碼協定層級幾乎沒理由重試，多數系統也不做。
- 但以下討論假設有重試——因為**處理收到的重試的技術，即使你從不送出重試也一樣適用**。

**收到訊息時的決策表**：

| 收到的訊息 | 判斷 | 處置 |
|---|---|---|
| 正是預期的訊息 | 正常 | 依協定規則處理 |
| 來自協定的「**未來**」 | 很可能是攻擊的一部分 | **忽略**：不改變狀態、不回覆、直接丟棄。效果等同訊息在傳輸中遺失，而協定本來就該能從遺失中恢復 → 永遠安全 |
| 與上一則已回應的訊息**識別相同、內容也相同** | 很可能是重試 | 送出**完全相同的回覆**——不要用不同的亂數重算回覆；也**不要假設**內容相同，**必須檢查** |
| 與上一則已回應的訊息**識別相同、內容不同**（且通過完整性檢查） | **攻擊的跡象**：重試永遠不會不同，兩則中必有一則是偽造的 | 視為**協定錯誤**（§6.5 的一切後果）。只忽略雖然也安全，但會讓偵測到的主動攻擊變少，削弱安全系統的偵測與回應能力 |
| 比上一則**更舊**的訊息 | 可能是延遲很久的原始訊息 | 若還保存當時收到的訊息：相同 → 忽略；不同 → 攻擊，協定錯誤。若沒保存（很多實作不保存）→ **忽略**是安全的選擇 |

> 「更舊的訊息」比想像中常見：Alice 送出的訊息被延遲，幾秒後她送了重試並成功抵達，雙方繼續協定；半分鐘後，Bob 才收到那則原始訊息——以協定的角度，這是一則「非常舊」的訊息。

> 三方以上的協定更複雜（超出本書範圍）；若你參與設計多方協定，要非常仔細地思考重放與重試。

**最後一則訊息的不確定性（兩將軍問題）** ⭐

```
Alice ──── 最後一則訊息 ────► Bob
   她永遠不會得到「已送達」的確認。

若鏈路中斷、Bob 沒收到：
   Bob 會重試上一則訊息 → 也到不了 Alice
   對 Alice 而言，這與「協定正常結束」無法區分

加一則 Bob → Alice 的確認？那則確認就變成新的「最後一則訊息」，問題依舊。
```

> **密碼協定必須設計成：這種不確定性不會導致不安全的行為。**

## 7. 設計觀念整理

| 觀念 | 說明 |
|---|---|
| 假設對方是敵人 | 協定中你無法控制其他參與者 |
| 角色 ≠ 實體 | 一個實體可扮演任何（甚至多個）角色 |
| 信任是「對 X 的信任」 | 不是二元的；商業上叫風險 |
| 失敗要對有聲譽者有利 | 先付款後出貨 |
| 分析誘因 | 誰付錢？誰得利？誘因決定行為 |
| **最小化信任** | 密碼協定的核心功能 |
| 偏執模型 + 記錄偏離 | 信任需求就是協定介面的前置條件，也是風險清單 |
| 分層 | 傳輸 → 識別 → 編碼 → 狀態機 → 協定邏輯 |
| 解析不依賴上下文 | 否則認證有歧義（Horton 原則） |
| 只接受預期訊息 | 狀態機式實作 |
| 錯誤時沉默 | 不回覆、刪除狀態、記安全日誌；注意時序 |
| 重試回覆要相同 | 不重算；內容不同即攻擊 |
| 最後一則訊息永遠不確定 | 設計上要容忍 |

## 10. 本章重點整理

1. 協定中你無法控制對方——**假設在和敵人打交道**。
2. 角色不等於實體；一個人可以扮演任何角色。
3. 信任來自道德、聲譽、法律、人身威脅、MAD；網路上很難建立。信任是「對 X 的信任」，商業上叫風險。
4. 電子商務的失敗模式應對**有聲譽要保護**的一方有利。
5. 分析**誘因結構**；密碼協定既依賴也改變誘因。
6. **密碼協定的功能是最小化所需的信任**；預設偏執模型，任何偏離都要明確記錄。
7. 分層：傳輸層 → 協定/訊息識別 → 不依賴上下文的編碼（TLV）→ 狀態機。
8. 錯誤處理：**沉默、刪除狀態、安全日誌**；小心時序洩漏（智慧卡 PIN 40 次就破）。
9. 重放與重試：未來的訊息忽略；相同重試給相同回覆；內容不同即攻擊；最後一則訊息永遠無法確認。

> **一句話**：密碼協定的目的是讓你盡可能少地信任別人——所以要偏執地假設所有人聯手騙你，並且在出錯時什麼都不說。
