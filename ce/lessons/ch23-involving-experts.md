# 第 23 章　請教專家（Involving Experts）

> 《Cryptography Engineering》— Ferguson, Schneier, Kohno，本章頁碼：p.323–326

---

## 1. 本章定位

全書的最後一章，也是作者給讀者的**臨別忠告**。全章沒有新技術，只有一個主題：

> **密碼學難得可怕——找專家，而且要早。**

作者從一個奇怪的現象講起：

> 密碼學有件怪事：**每個人都覺得自己懂得夠多，可以設計並建造自己的系統。** 我們從不會請物理系二年級學生設計核電廠；也不會讓一位聲稱發現了心臟手術革命性方法的實習護士替我們開刀。但讀過一兩本書的人，卻認為自己能設計密碼系統。更糟的是，他們有時還能說服管理階層、創投，甚至某些客戶，相信他們的設計是切片麵包問世以來最棒的東西。

**Bruce 的第一本書《Applied Cryptography》在密碼學家之間既有名又惡名昭彰**：

- **有名**：讓數萬人注意到密碼學；
- **惡名昭彰**：因為這些人接著**自己**設計並實作了各種系統。

> 一位同事曾對 Bruce 說：「**世界上到處都是讀過《Applied Cryptography》的人設計的爛安全系統。**」

## 2. WEP：一個「穩健地」壞掉的系統 ⭐⭐⭐

802.11 無線網路標準最初的設計包含一個叫 **WEP（Wired Equivalent Privacy）** 的安全通道，用來加密並認證無線通訊。這個標準由一個**沒有任何密碼學家**的委員會設計（呼應 ch22）。從安全角度看，結果**糟透了**。

把 WEP 的每個缺陷對照到本書各章，幾乎就是一份全書的「反面教材」索引：

| # | WEP 的缺陷 | 後果 | 本書對應的原則 |
|---|---|---|---|
| 1 | 選用 **RC4** 串流加密 | 不是最好的選擇，但本身不致命 | ch3：選用經過充分分析的元件 |
| 2 | **nonce（IV）只有 24 bits** | IV 必然重複 → 許多封包用**相同的金鑰流**加密 → C ⊕ C' = P ⊕ P'，聰明的攻擊者能破解加密 | ch4 §5：串流加密**絕不可重用 nonce**；ch7：nonce 由通道內部管理、要夠大 |
| 3 | **沒有把秘密金鑰與 nonce 一起雜湊**，而是直接串接當作 RC4 金鑰 | 最終導致**金鑰還原攻擊**（Fluhrer–Mantin–Shamir，2001） | ch14 §7：**移除代數/結構關係**；ch7：用 SHAd-256 衍生子金鑰 |
| 4 | 用 **CRC** 校驗碼做「認證」 | CRC 是**線性**的 → 用一點線性代數就能修改任何封包而**不被偵測** | ch6：認證要用 **MAC**，不是校驗碼；ch4：加密不提供認證 |
| 5 | 網路中**所有使用者共用一把金鑰** | 金鑰更新困難得多；任何一個使用者都能解讀其他人的流量 | ch17、ch19：每人/每用途各自的金鑰；ch20：金鑰要能定期更換 |
| 6 | 網路密碼**直接當作加密金鑰**，沒有任何金鑰協商協定 | 沒有 session key、沒有前向安全；密碼外洩 = 過去與未來的流量全部外洩 | ch14：金鑰協商；ch21：密碼要經過加鹽與延展 |
| 7 | **加密預設關閉** | 大多數裝置從來沒人去開啟加密 | ch8 §5.1：**沒有選項、預設安全** |

> **WEP 不只是壞了——它是「穩健地」壞了（robustly broken）。**

- 設計 WEP 的替代方案並不容易，因為必須**改裝到現有硬體上**。但別無選擇——原標準的安全性糟到極點。替代方案就是 **WPA**。
- WEP 的故事**並不特別**。它比大多數糟糕的密碼設計得到更多媒體關注，只因為 802.11 是如此成功的產品；作者在其他系統中看過許多類似情況。

> 後見之明：WPA（TKIP）只是過渡方案，2004 年的 **WPA2** 改用 AES-CCMP（ch7 的 CCM 模式，作者之一 Ferguson 是 CCM 的設計者）；2017 年的 **KRACK** 攻擊又發現 WPA2 四向交握在**重送**訊息時會重設 nonce——正是 ch13 §6.6「重試的處理」與 ch4「nonce 不可重用」的又一案例；2018 年的 **WPA3** 改用 SAE（一種 PAKE，ch14 §13）抵抗離線字典攻擊。

## 3. 這是一本危險的書 ⭐

> 《Cryptography Engineering》可能有同樣的效果。

- 有些人讀完這本書，就會轉身去設計密碼演算法或協定。完成時，他們會有一個在自己看來很好、也許還能運作的東西——**但它安全嗎？**
- 也許他們做對了 70%；運氣非常好的話，也許 90%。

> **但在密碼學中，「幾乎正確」沒有任何獎賞。** 安全系統的強度只等於它最弱的環節；要安全，**每一樣東西都必須正確**。而這是你單靠讀書學不到的。

**那為什麼還要寫這本書？**

1. **想學的人總得從某處學起**，而作者不知道有其他合適的書。把這本書當作這個領域的**入門**，即使它不是**操作手冊**。
2. **寫給專案中的其他工程師**：安全系統的每個部分都極其重要，專案中每個人都必須對相關的安全問題與技術有基本了解——程式設計師、測試人員、技術文件撰寫者、管理階層，**甚至業務人員**。每個人都需要對安全問題了解到足以把自己的工作做好的程度。

**最想留給讀者的東西：專業偏執** ⭐

> 我們也希望在你身上灌輸了一種**專業偏執（professional paranoia）**的感覺。如果你學會了這個，你就學到了很多。你可以把專業偏執應用到工作的各個面向。無論是設計自己的協定還是審視別人的，你都會**極度懷疑**——而這只會有助於提升安全。

（回到 ch1：本書第一章就以「專業偏執」作為貫穿全書的心態。）

## 4. 找密碼學專家，而且要早 ⭐⭐⭐

> **如果只能給你一個建議：盡可能使用密碼學專家。**

- 若你的專案涉及密碼學，經驗豐富的密碼設計者的洞見會讓你大大受益。
- **在專案一開始就讓專家參與。** 越早諮詢，長期來看就越便宜、越容易。
- 作者多次在專案進行到很後面才被找來，只能在早已設計或實作完成的部分戳出漏洞。最後的結果**總是很昂貴**——要嘛付出努力、時程與成本，要嘛犧牲最終產品使用者的安全。

**專家也會犯錯，那何必找專家？**

> 密碼學難得可怕，**即使專家設計的系統也經常失敗**。不論你多聰明、在其他領域有多少經驗都沒用——設計與實作密碼系統需要專門的知識與經驗，而取得經驗的唯一方式就是**一做再做**——這當然也包括犯錯。
>
> 那為什麼要找一個也會犯錯的專家？**理由和你找一位合格的外科醫師替你開刀一樣**：不是他們不犯錯，而是他們犯的錯**少得多、也不那麼嚴重**。而且他們以**保守**的方式工作，讓小錯誤不會導致災難性的結果——**他們懂得如何「好好地失敗」（fail well）**。

> 對照：「fail well」正是全書反覆實踐的設計哲學——ch3 的安全餘裕、ch4 選擇耐得住濫用的 CBC、ch7 的失敗時銷毀狀態、ch9 Fortuna 保證必然從外洩中恢復、ch11 每個收到的值都檢查、ch15 的 wooping 與簽完就驗。

## 5. 密碼實作也是專業 ⭐

> **實作密碼系統，幾乎和設計它們一樣是一門專業。**

| | 密碼設計者 | 密碼實作者 |
|---|---|---|
| 可得性 | 可以雇得到 | **難找得多** |
| 需要的人數 | 少 | 多：**一位設計者能為 10 到 20 位實作者創造工作** |
| 業界認知 | 被視為專業 | **大多數人不把它當專業** |

- 程式設計師會從資料庫程式轉到 GUI，再轉到密碼實作。資料庫程式與 GUI 確實也是專業，但有經驗的程式設計師稍加研究就能得到合理的結果。
- **密碼實作不是這樣**：每一樣東西都必須正確，而且**有一個攻擊者在努力讓它出錯**。

**作者所知最好的方法**：

> 找**有能力的程式設計師**，訓練他們做這件事。這本書也許是訓練的一部分，但大部分需要**經驗與正確的專業偏執心態**。就像任何其他專門的 IT 技能，要好幾年才能真正擅長。既然累積經驗要這麼久，一旦他們有了經驗，你就必須**留得住**他們——那是另一個問題，作者很樂意留給別人去解決。

（呼應 ch8：「寫出正確的程式」本身就是業界尚未解決的問題；ch15：大整數運算的測試需要專門的知識。）

## 6. 專案文化與流程 ⭐⭐

**比這本書（或任何書）更重要的，大概是專案文化**：

> 「**安全優先**」不應只是一句口號，它必須被**織進專案與專案團隊的結構之中**。每個人都必須時時刻刻活在、呼吸著、談論著、思考著安全。

- 這極難達成，但做得到：**DigiCash** 在 1990 年代就有這樣的團隊；**航空業**也有同樣無所不在的安全文化（呼應 ch8 §2.4）。
- 這不可能在短期內達成，但絕對是可以努力的方向。
- 本書只是一本關於最重要安全議題的**入門書**，寫給團隊中較技術性的成員。

**安全是一個過程** ⭐

> 如 Bruce 在《Secrets and Lies》中所寫：**「安全是一個過程，而不是一個產品。」**

- 除了安全文化，還需要**安全流程**。航空業有廣泛的安全流程；大多數 IT 產業連**生產軟體**的流程都沒有，更別說生產**高品質**軟體的流程，更別說生產**安全**軟體的流程。
- **寫出好的安全軟體，大致上超出了我們產業目前的技術水準。**
- 但這不代表我們應該放棄——最近已經有一些進展。隨著資訊科技對我們的基礎建設、自由與安全變得越來越關鍵，我們必須持續改善系統的安全性。**我們必須盡力而為。**

> 作者的結語：我們希望這本書能教導那些在安全系統上工作的人實用密碼學的基礎，從而對改善我們的安全系統有些許貢獻。

> 後見之明：本書出版後，業界的「安全流程」確實有所進展——Microsoft SDL、OWASP、Google 的 Project Zero 與漏洞賞金計畫、記憶體安全語言（Rust）的興起、形式化驗證的密碼程式庫（HACL\*、Fiat-Crypto，已被 Firefox、Chrome、Linux 使用），以及 TLS 1.3 在設計階段就引入學術界的形式化分析。作者「必須盡力而為」的呼籲，某種程度上得到了回應。

## 7. 全書回顧：一張地圖

| 部 | 章 | 核心問題 | 一句話答案 |
|---|---|---|---|
| **一、導論** | 1–2 | 密碼學在系統中扮演什麼角色？ | 它只是最弱環節鏈中的一環；要用專業偏執看待一切 |
| **二、訊息安全** | 3 | 用什麼區塊加密器？ | AES-256，並保留替換的彈性 |
| | 4 | 用什麼模式？ | CBC + 隨機 IV（或由通道內部管理 nonce 的 CTR） |
| | 5 | 用什麼雜湊？ | SHAd-256 或截斷的 SHA-512 |
| | 6 | 用什麼 MAC？ | HMAC-SHA-256；遵守 Horton 原則 |
| | 7 | 如何建立安全通道？ | 訊息編號 + 先認證後加密 + 金鑰分離 + 失敗時什麼都不給 |
| | 8 | 實作有什麼陷阱？ | 清除秘密、簡單、斷言常開、旁通道 |
| **三、金鑰協商** | 9 | 亂數從哪來？ | Fortuna：32 個池，不估計熵 |
| | 10–12 | 公鑰的數學？ | 質數、DH（檢查子群）、RSA（摧毀結構） |
| | 13 | 如何思考協定？ | 最小化信任；錯誤時沉默 |
| | 14 | 如何協商金鑰？ | 認證整段對話、對方簽你的 nonce、雜湊最終金鑰 |
| | 15 | 公鑰實作的陷阱？ | wooping、簽完就驗、固定時間 |
| **四、金鑰管理** | 16 | 時鐘？ | 少依賴；只用 UTC；單調且唯一 |
| | 17 | 金鑰伺服器？ | 小系統用 Kerberos 或疊在安全通道上的簡單協定 |
| | 18–20 | PKI？ | 夢想很美；現實是許多小 PKI、直接授權、一定要能撤銷 |
| | 21 | 如何儲存秘密？ | 加鹽延展、隨身權杖、保險箱備份、抹除很難 |
| **五、其他** | 22 | 標準與專利？ | 委員會做不出安全標準；競賽可以 |
| | 23 | 最後的建議？ | **找專家，而且要早** |

## 8. 設計觀念整理

| 觀念 | 說明 |
|---|---|
| 人人都以為自己懂密碼學 | 實際上需要專門知識與多年經驗 |
| WEP 是反面教材大全 | nonce 太短、金鑰未雜湊、CRC 當 MAC、共用金鑰、無協商、預設關閉 |
| 幾乎正確 = 不安全 | 最弱環節決定一切 |
| 書是入門不是手冊 | 也寫給程式設計師、測試、文件、管理、業務 |
| 專業偏執 | 全書最重要的收穫 |
| 早找專家 | 越晚越貴 |
| 專家懂得 fail well | 保守工作，讓小錯不變成大災難 |
| 實作也是專業 | 一位設計者對應 10–20 位實作者；要訓練、要留人 |
| 安全文化 | 「安全優先」要織進團隊的結構 |
| 安全是過程 | 不是產品；業界仍在努力 |

> 對照第一本書：Hanson 在《C Interfaces and Implementations》的序言中說，那本書的目的是讓讀者「**重用**」經過仔細設計與實作的介面，而不是每次從頭寫起。本章的忠告其實是同一句話的密碼學版本：**不要自己發明密碼學——重用專家設計、經過充分審查的元件與協定，把你的心力放在正確地使用它們。** 兩本書最後殊途同歸：好的工程，來自對既有成果的尊重、對介面的嚴謹，以及對錯誤的謙卑。

## 10. 本章重點整理

1. 人人都以為自己能設計密碼系統——但我們不會讓物理系學生設計核電廠。
2. **WEP** 是反面教材大全：24-bit IV 重用、金鑰與 nonce 未雜湊、用線性的 CRC 當認證、全網共用金鑰、密碼直接當金鑰、預設不加密——**穩健地壞掉**。
3. 這本書也可能被誤用：在密碼學中「90% 正確」毫無價值；書是入門，不是手冊，也是寫給專案中每一個人的背景知識。
4. 最重要的收穫是**專業偏執**。
5. **盡可能找密碼學專家，而且在專案一開始就找**；專家也會犯錯，但錯得少、錯得輕，並懂得 **fail well**。
6. **密碼實作也是專業**：訓練有能力的程式設計師、累積多年經驗、留住他們。
7. 「安全優先」必須成為**文化**；**安全是一個過程，不是一個產品**。

> **一句話**：讀完這本書，你最該學會的不是任何演算法，而是專業偏執——並且知道什麼時候該放下自信，去找一位懂得「好好失敗」的專家。
