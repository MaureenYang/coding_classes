# 第 4 章　區塊加密模式（Block Cipher Modes）

> 《Cryptography Engineering》— Ferguson, Schneier, Kohno，本章頁碼：p.63–76

---

## 1. 本章定位

第 3 章的區塊加密器只能處理**固定 16 bytes**。真實訊息長短不一，所以需要**區塊加密模式**——「用區塊加密器建構出來的、能處理任意長度的加密函式」。

本章一開頭就先警告 ⭐：

> **加密模式只防竊聽，不提供認證。** 攻擊者仍可竄改密文，解密照樣會產生（被改過的）明文——有些模式甚至允許**精準地**改動明文的指定位元。

而且在幾乎所有情境下，**被竄改的訊息造成的傷害遠大於明文外洩**。所以：**加密一定要搭配認證**（MAC，第 6 章；組合方式，第 7 章）。

---

## 2. 填充（Padding）

多數模式要求明文長度是區塊大小 b 的整數倍。

**唯一重要的規則：填充必須可逆**——從填充後的訊息能唯一還原原始訊息。

- ❌ **補 0 到滿**：不可逆，`p` 與 `p ‖ 0` 填充後相同。
- 任何可逆填充都**至少會讓某些已對齊的訊息變長**；實務上所有規則都至少加 1 byte。

作者建議的兩種方法：

| 方法 | 做法 | 例（b = 8，剩 3 bytes 空間） |
|---|---|---|
| ① 0x80 + 0x00… | 先補一個 byte 128（0x80），再補 0～b−1 個 0 | `… 80 00 00` |
| ② PKCS#7 式 | 需補 n 個 byte（1 ≤ n ≤ b），每個都填 n | `… 03 03 03` |

- 也可以在開頭放長度 ℓ(P)，但前提是開始處理時就知道長度。
- 區塊數 k = ⌈(ℓ(P) + 1) / b⌉。
- **解密後移除填充時，要檢查每一個填充 byte 是否正確**；錯誤的填充應**和認證失敗同等處理**。

> 延伸：若錯誤訊息洩漏「填充錯了」與「MAC 錯了」的差別，就可能形成 **padding oracle 攻擊**（Vaudenay 2002）。這正是作者要求「同等處理」的原因。

---

## 3. ECB（電子密碼本）

```
Ci = E(K, Pi)          for i = 1..k
```

每個區塊獨立加密。**任何情況下都不要用 ECB。**

問題：**相同明文區塊 → 相同密文區塊**，攻擊者看得見。

- 文章中重複出現的字（例如「ciphertext block」）若剛好對齊區塊邊界；
- Unicode 字串中每隔一個 byte 是 0；
- 檔案格式中大片的 0……

都會讓重複區塊非常常見。（著名例子：ECB 加密的企鵝圖片，輪廓清晰可見。）

---

## 4. CBC（密碼區塊串接）⭐

```
Ci = E(K, Pi ⊕ Ci−1)   for i = 1..k
Pi = D(K, Ci) ⊕ Ci−1
```

```
      P1          P2          P3
      │           │           │
IV ──►⊕    ┌─────►⊕    ┌─────►⊕
      │    │      │    │      │
      E    │      E    │      E
      │    │      │    │      │
      C1 ──┘      C2 ──┘      C3
```

用前一個密文區塊「隨機化」下一個明文區塊。剩下的問題是 **C0（IV）該怎麼選**：

| IV 策略 | 評價 | 原因 |
|---|---|---|
| **固定 IV** | ❌ | 第一個區塊退化成 ECB；相同開頭的訊息會有相同密文開頭 |
| **計數器 IV**（0, 1, 2…） | ❌ | 0 與 1 只差 1 bit；若兩則訊息的首區塊也只差這 1 bit，xor 後**完全相同** → 密文相同 |
| **隨機 IV** | ✅ | 隨機產生 C0，放在密文最前面一起送出；缺點：密文多 1 個區塊（短訊息膨脹明顯） |
| **Nonce 產生的 IV** | ✅（但見 §8） | IV = E(K, nonce)；nonce 通常就是訊息編號，額外負擔極小 |

### 4.1 Nonce 產生 IV 的步驟

1. 指定訊息編號（從 0 開始的計數器，**絕不可回繞**）。
2. 由編號組成 nonce——對同一把金鑰，在**整個系統**中都要唯一（例如雙向通訊要加上方向標記）；大小為一個區塊。
3. 用區塊加密器加密 nonce 得到 IV。
4. 用該 IV 做 CBC 加密。
5. 在密文中附上足以重建 nonce 的資訊（通常就是訊息編號）；**IV 本身不用傳**。

- 32–48 bits 的訊息計數器通常就夠，相比隨機 IV 的 128 bits 省很多；多數通訊系統本來就有訊息編號，等於**零額外負擔**。
- 若攻擊者能**完全控制 nonce**，加密 nonce 時要用**另一把金鑰**。

> **Nonce** = *number used once*：不必保密，但**同一把金鑰下絕對只能用一次**。

---

## 5. OFB（輸出回饋）

```
K0 := IV
Ki := E(K, Ki−1)
Ci := Pi ⊕ Ki
```

訊息本身**不進入**區塊加密器；區塊加密器只用來產生偽隨機的**金鑰流（key stream）**，再與明文 xor ——這就是**串流加密（stream cipher）**。

> 作者特別替串流加密平反：它們非常好用，只是需要小心。最常見的濫用是**重複使用 nonce**。

**優點**

- 加密 = 解密，**只需實作 E**，不必實作 D。
- **不需填充**：最後一塊只用到需要的 bytes 即可。

**危險 ⭐：重複 IV**

```
C ⊕ C' = (P ⊕ K) ⊕ (P' ⊕ K) = P ⊕ P'
```

攻擊者直接得到兩份明文的 xor；只要知道其中一份（實務上很常見），另一份就現形。即使兩份都未知，也有從 P ⊕ P' 還原資訊的技術。

**OFB 的額外缺陷：短週期**

- 金鑰流區塊一旦重複，後面整串都會重複。
- 另一則訊息的 IV 可能恰好等於這則訊息中途的某個金鑰區塊 → 部分金鑰流重用。
- 本質上是碰撞攻擊，約需 2^64 個區塊 → 128-bit 區塊只提供 64 bits 安全的又一例子。

---

## 6. CTR（計數器模式）⭐

```
Ki := E(K, Nonce ‖ i)
Ci := Pi ⊕ Ki
```

```
 Nonce‖1    Nonce‖2    Nonce‖3
    │          │          │
    E          E          E
    │          │          │
P1─►⊕     P2──►⊕     P3──►⊕
    │          │          │
    C1         C2         C3
```

典型配置（128-bit 區塊）：

| 欄位 | 大小 |
|---|---|
| 訊息編號 | 48 bits → 最多 2^48 則訊息 |
| 其他 nonce 資料 | 16 bits |
| 區塊計數器 i | 64 bits → 每則訊息最多 2^68 bytes |

**優點**

- 只需實作 E；加解密相同；不需填充。
- **隨機存取**：任一區塊的金鑰流可直接計算。
- **可任意平行化**，適合高速應用。
- **安全性直接歸約到區塊加密器**：CTR 的任何弱點都會立即變成對區塊加密器的選擇明文攻擊——反過來說，區塊加密器安全，CTR 就安全（除了流量分析與 §8 的資訊洩漏）。

**唯一的要求**：**key/nonce 組合絕不可重用**。

> 常有人以此批評 CTR，但 CBC 也有同樣問題——重用 IV 一樣洩漏資訊。CBC 只是洩漏得比較少；而在模組化設計中，「只漏一點點」也無法仰賴系統其他部分來兜底。

---

## 7. 加密與認證結合的模式

1970–80 年代的模式（ECB/CBC/OFB/CTR）之外，NIST 近年標準化了兩個同時提供**加密 + 認證**的模式：**CCM** 與 **GCM**。第 7 章介紹完認證後再談。

---

## 8. 該用哪一種模式？⭐⭐

| 模式 | 結論 |
|---|---|
| ECB | 不安全，不用 |
| OFB | 可以，但 CTR 全面勝出（且沒有短週期問題） |
| **CTR** | 很好的模式——**前提是能保證 nonce 唯一** |
| **CBC + 隨機 IV** | ✅ **本版推薦** |

**為什麼作者改變立場？**

- 第一版（*Practical Cryptography*）推薦 CTR。
- 但看到**太多應用因為 nonce 產生錯誤而變得不安全**。CTR 要求「即使系統遭受攻擊，nonce 仍唯一」，這在實務上是主要的漏洞來源。
- CBC + 隨機 IV 有缺點（密文較長、需填充、需亂數產生器），但**穩健、耐得住濫用**。

> **不要把任何需要 nonce 的模式暴露給應用程式開發者**——連 nonce 產生 IV 的 CBC 也一樣。若你在開發應用、需要加密模式：**保守一點，用隨機 IV 的 CBC。**

**永遠記得**：加密模式只提供**機密性**。攻擊者仍能得知：

- 你**正在**通訊、**何時**通訊、通訊**多少**、與**誰**通訊 → 這叫**流量分析（traffic analysis）**。防範成本太高，通常只有軍方會做。
- 而且加密模式**不防竄改**——第 7 章會處理機密性 + 真實性。

---

## 9. 資訊洩漏：區塊加密模式的黑暗秘密 ⭐⭐

> **所有區塊加密模式都會洩漏一些資訊**——即使區塊加密器是完美的。

### 9.1 各模式洩漏什麼

**ECB**：Pi = Pj ⇒ Ci = Cj，直接暴露明文結構。

**CBC**：若出現兩個相同的密文區塊 Ci = Cj：

```
E(K, Pi ⊕ Ci−1) = E(K, Pj ⊕ Cj−1)     CBC 定義
      Pi ⊕ Ci−1 = Pj ⊕ Cj−1           兩邊解密
        Pi ⊕ Pj = Ci−1 ⊕ Cj−1         移項
```

攻擊者得到兩個明文區塊的 xor（**128 bits 資訊**）；對英文這類高冗餘明文，往往足以還原兩者。不相等時則得到一條「不等式」。

**CTR**：所有 Ki 都相異（加密的輸入都不同）。因此任兩個密文區塊都告訴攻擊者 `Pi ⊕ Pj ≠ Ci ⊕ Cj`——**每對區塊提供一條明文不等式**。沒有碰撞問題；與理想串流加密唯一的差異是「金鑰區塊永不碰撞」。

**OFB**：無碰撞時與 CTR 相同；**一旦金鑰流碰撞，之後全部碰撞**——災難。這是 CTR 優於 OFB 的另一理由。

### 9.2 碰撞機率

共加密 M 個區塊（不論分成幾則訊息，只看總數），區塊大小 n bits：

```
配對數        ≈ M(M−1)/2
每對相等機率   = 2^-n
期望碰撞數    ≈ M(M−1) / 2^(n+1)   → 當 M ≈ 2^(n/2) 時接近 1
```

- n = 128 → 約 **2^64 個區塊**後預期出現第一次碰撞（生日悖論，§2.7.1）。
- 精確值約為 2^(n/2)·√(π/2)，但粗估已足夠。
- 系統壽命以 30 年計，未來處理接近 2^64 區塊並非不可能。

**小資料量也有風險**：處理 2^40 區塊（約 16 TB），碰撞機率 2^-48 很小——但攻擊者可以對約 2^48 把不同金鑰重複收集：總工作量 2^40 · 2^48 = **2^88**，遠低於 128-bit 設計強度。

### 9.3 如何因應

用 128-bit 區塊加密器**無法輕鬆達到 128-bit 安全**（需要 256-bit 區塊加密器，但沒有成熟方案）。只能盡量接近並**限制損害**：

| 模式 | 每把金鑰的建議上限 | 理由 |
|---|---|---|
| **CTR** | 約 **2^60 區塊**（2^64 bytes） | 2^64 區塊時只漏約 1 bit；2^48 區塊時只能排除約 2^-32 的候選明文 |
| **CBC** | 約 **2^32 區塊** | 一旦碰撞就漏 128 bits；殘餘風險 2^-64 |

- 上限是針對**同一把金鑰加密的總量**。
- 解法：搭配**金鑰協商協定**，金鑰快到上限就換新的——是複雜度，但值得。

### 9.4 關於「我們的數學」

作者坦承隨意假設機率獨立，數學家可能會皺眉。但就像物理學家，密碼學家用「實用」的方式使用數學：密碼學數值本來就被設計成極度隨機，經驗上這種粗估相當準確。

## 10. 設計觀念整理

| 觀念 | 說明 |
|---|---|
| 加密 ≠ 認證 | 加密模式不防竄改；被竄改的傷害通常更大 |
| 可逆填充 + 嚴格檢查 | 填充錯誤要與認證失敗同等處理 |
| 穩健勝過最佳 | CBC+隨機 IV 不是最有效率，但最耐濫用 |
| 不要把 nonce 交給開發者 | nonce 唯一性是實務上最常失守的地方 |
| 安全歸約 | CTR 的安全直接等於區塊加密器的安全 |
| 金鑰用量上限 | 128-bit 區塊的生日界限 → 定期換金鑰 |
| 流量分析 | 加密藏不住「誰、何時、多少」 |

> 對照第一本書：Hanson 的介面設計強調「把容易出錯的責任從呼叫端拿走」（例如由實作負責記憶體檢查）。本章推薦 CBC+隨機 IV，正是同一種思維——**不要把 nonce 唯一性這種難以保證的責任推給使用者**。

## 11. 延伸閱讀重點

- **Padding oracle 攻擊**（Vaudenay, 2002）：說明為何填充檢查與錯誤處理要一致。
- **ECB 企鵝**：最直觀的 ECB 洩漏示範。
- **NIST SP 800-38A**（ECB/CBC/CFB/OFB/CTR）、**SP 800-38C**（CCM）、**SP 800-38D**（GCM）。
- 後見之明：本書出版後，業界走向 **AEAD**（AES-GCM、ChaCha20-Poly1305），以及**抗 nonce 誤用**的模式（AES-GCM-SIV），正是為了解決本章指出的 nonce 問題。

## 12. 習題摘要

| 題號 | 題目 | 提示 / 答案 |
|---|---|---|
| 4.1 | 填充 n 個值為 n 的 byte，但 0 ≤ n ≤ b−1——為何不好？ | 已對齊時 n = 0 不填充，則最後一個 byte 恰為 01、02… 的訊息無法與「有填充」區分 → **不可逆** |
| 4.2 | 比較 CBC 四種 IV（固定/計數器/隨機/nonce）的安全與效能 | 見 §4 表格 |
| 4.3 | CTR 重用 nonce，已知 P 對應 C，求 C' 的明文 | P' = C ⊕ C' ⊕ P = **"This is a secret   Confidential!"** |
| 4.4 | 用指定 AES-256 金鑰解密 CBC 隨機 IV 密文（IV 在前） | 解得 **"Another secret!  And another.   "** |
| 4.5 | 用 AES-ECB 加密三個區塊（第 1、3 塊明文相同） | 密文第 1、3 塊相同（`9B 75 B3 76 …`），親眼看到 ECB 洩漏 |
| 4.6 | CBC 同金鑰：若 C1 = C2'（兩則訊息的密文區塊碰撞），求 P1' | 由碰撞得 P1' ⊕ C0' = P2 ⊕ C1 ⇒ **P1' = P2 ⊕ C1 ⊕ C0'** |

> 4.3–4.5 的答案是實際以 AES 函式庫計算驗證過的。

## 13. 本章重點整理

1. 加密模式**只提供機密性**；一定要搭配認證。
2. 填充必須可逆，移除時要逐 byte 檢查，錯誤視同認證失敗。
3. **ECB 永遠不要用**；OFB 不如 CTR。
4. CBC 的 IV：固定與計數器都不行；**隨機 IV** 或 **nonce 加密成 IV**。
5. CTR 簡單、快、可平行、安全可歸約——但 **key/nonce 絕不可重用**。
6. 作者推薦：**CBC + 隨機 IV**，因為 nonce 太容易出錯。
7. 所有模式都會洩漏資訊；因生日界限，每把金鑰的加密量要設上限（CBC ≈ 2^32、CTR ≈ 2^60 區塊）。

> **一句話**：加密模式決定了區塊加密器「怎麼被用」——選一個耐得住濫用的（CBC + 隨機 IV），別忘了它不管認證，也別讓一把金鑰用太久。
