# 第 1 章　AI Agent 入門

> 《深入理解 AI Agent》— 李博杰（Pine AI 首席科學家），第一章（含引言）

---

## 0. 引言要點（全書導讀）

本書由作者在圖靈《AI Agent 實戰營》（2025 年 8–10 月）與國科大 AI Agent 課程的講稿擴寫而成。成書方式本身就是「Agent 參與」的：作者口述提綱給自家語音 Agent，由它調研、整理初稿，再反覆討論修改，作者稱之為 **whisper coding**（口述式協作）。

**全書的立論**：

> **實踐在前，命名在後。** Skill、harness、loop engineering 等名詞流行之前，大量 Agent 早就在這麼做了，Anthropic 等公司是事後把它們提煉成原則。

作者在 Pine 的實戰經驗印證了這點：Pine 替使用者打電話與營運商協商帳單、與商家交涉退款、取消訂閱，任務動輒幾十輪交涉，任何一步出錯都會造成真金白銀的損失。

| 後來流行的名詞 | Pine 早先的做法 |
|---|---|
| **Skill** | 動態載入提示詞（解決提示詞膨脹）、用命令列執行工具（解決工具列表膨脹）、系統狀態列（讓 Agent 感知環境、時間與使用者狀態） |
| **Harness** | 類似 Claude Code 的方法，處理工具呼叫不穩定、幻覺、危險或越權操作、不遵循指令 |
| **Loop engineering** | **提議者—審核者**（proposer-reviewer），解決模型過早認定任務完成 |

**怎麼趕在名詞流行之前就知道該怎麼做？** 作者認為有兩個關鍵：

1. **擁有一個對 Agent 能力上限要求極高的真實業務**，並且能持續得到真實回饋。業務若不夠難、模型一升級就夠用，你就沒有動力去打磨架構。
2. **建立評估機制。** 沒有評估，就沒有進步；評估讓你分辨一次改動是真的變好，還是只是運氣好（第七章詳述）。

**核心公式**：

```
Agent = LLM + 上下文 + 工具
      = 大腦 + 眼睛 + 手腳
      ≈ Policy（策略）+ Observation Space（觀察空間）+ Action Space（動作空間）
```

> **好的設計原則本就應該穿越模型的迭代週期**：它們描述的不是某個模型的用法，而是智慧系統與世界互動的基本模式。

作者也引用 Richard Sutton 的宇宙演化四階段：塵埃 → 恆星 → 生命 → 設計實體（designed entities）。生物演化是盲目的，Agent 卻能理解自身的運作機制、生成程式碼來自舉（bootstrap），甚至改進自己。

**全書結構**（四個層次）：

| 層次 | 章 | 主題 |
|---|---|---|
| 基礎 | 1 | Agent 的核心公式、ReAct、Harness、編排模式 |
| **建構** | 2–6 | 上下文工程、記憶與知識庫、工具、Coding Agent、互動（非同步／語音／Computer Use／機器人） |
| **評估與進化** | 7–9 | 評估、模型後訓練（SFT／RL）、持續進化 |
| **協作** | 10 | 多 Agent 協作 |

**閱讀建議**：時間有限就先讀第一、二章；第二章的 KV Cache 原理可以先跳過，只記結論。關注訓練的讀者可直接讀第八章，但要搭配第七章（評估是訓練的前提）。

**術語約定**：書中把 reasoning 譯為「**思考**」、inference 譯為「**推理**」，避免一個詞同時承載兩個概念。配套程式碼在 `github.com/bojieli/ai-agent-book`，依 `chapterX/` 組織。

## 1. 本章定位

本章是全書的**概念地圖**：快速引入核心公式、執行迴圈、工程框架和設計模式，替後續章節建立統一的術語。作者建議初讀時先建立整體印象，後面各章都會展開本章提到的某一面。

你可能已經在用 Agent 了：Cursor 寫程式、Deep Research 做調研、Manus 操控瀏覽器、豆包手機助手訂票、Pine 打電話協商帳單。它們的共同點是：**不再是一問一答的被動對話，而是自主規劃步驟、呼叫工具、依結果調整策略**。

> 對照前兩本書：第一本 Hanson 談「介面與實作分離」，第二本 Ferguson 等人談「專業偏執」與「最弱環節」。這本書把兩者帶進 AI 系統：**工具介面的設計**決定 Agent 能走多遠（ACI），而**護欄與驗證**決定它會不會出事。

## 2. 現代 Agent = LLM + 上下文 + 工具 ⭐⭐⭐

這個公式描述的是 **Agent 邊界之內**的工程實作，**不包含 Environment**（環境）。三個元件都要做廣義、但邊界清楚的理解：

| 直覺 | 元件 | 學術概念 | 廣義理解 |
|---|---|---|---|
| **大腦** | LLM | 策略（Policy） | 整個決策核心：預訓練的世界知識，加上後訓練固化的決策策略 |
| **眼睛** | 上下文建構 | 觀察與歷史 | 每個決策點能看到的**全部**資訊：環境、使用者記憶、領域知識、自身狀態、任務進度 |
| **手腳** | 工具介面 | 觀察／行動介面 | 能做的所有事：預定義工具、按需載入的 Skills、動態生成程式碼、委託子 Agent、與使用者溝通、回應外部事件 |

### 2.1 Agent 與 Environment；Model 與 Harness

```
          ┌────────────────── Agent ──────────────────┐
          │   ┌────────┐      ┌──────────────────────┐ │
 觀察 ───►│   │ Model  │◄────►│ Harness              │ │
          │   │（策略）│      │ 建構上下文、工具介面、│ │
          │   └────────┘      │ 迴圈與狀態、權限、    │ │
          │                   │ 驗證、糾正            │ │
          │                   └──────────────────────┘ │
          └───────────────────────────┬────────────────┘
                                      │ 行動
                                      ▼
            Environment：檔案系統、資料庫、網頁、使用者、
                         其他 Agent、物理或模擬世界
```

- 外層是 Agent 與 Environment 的**閉迴圈互動**：Environment 回傳觀察，Agent 選擇行動，行動改變環境、產生下一次觀察。
- 內層是 Agent 內部的 **Model–Harness 結構**。Harness 可以建立、隔離或代理某個環境（例如沙盒），但**不包含** Environment 的狀態與轉移規則。
- 工程公式展開：LLM 對應 Model，「上下文 + 工具」構成**最小 Harness**；生產系統再加上約束、驗證與糾正。

### 2.2 觀察空間與動作空間：模型與世界的介面 ⭐⭐

> **沒有進入觀察空間的資訊，對模型來說就像不存在；沒有進入動作空間的操作，模型即使知道該怎麼做，也只能停留在文字建議。**

> **在底層模型固定時，提升 Agent 表現最主要的系統工程手段，往往就是重新定義或擴展觀察空間與動作空間。**

許多看似需要「更聰明模型」的問題，其實只是介面問題。

| 產品 | 介面上的突破 |
|---|---|
| **Manus** | 把原本分開的三條路線（Deep Research、Coding、Computer Use）合在同一個生產級 Agent 裡：虛擬瀏覽器擴大觀察空間，檔案系統、程式碼執行與命令列擴大動作空間。它不是只靠換更強的模型，而是取三類 Agent 介面的**聯集** |
| **OpenClaw** | 把介面延伸到使用者的數位生活：透過 WhatsApp、Telegram、Slack、Discord、iMessage 等使用者已經在用的管道收任務、回結果；本地 Gateway 連接 Google Drive、Notion 與本地檔案。本地優先，跨越了更大的資料邊界 |

後來 Manus 也加了 Google Drive 連接器與桌面端本地存取，再次說明**產品能力的演進往往就是觀察與動作空間的演進**。

**五個 Agent 產品的三維分析**：

| 產品 | 眼睛（感知） | 手腳（行動） | 策略 |
|---|---|---|---|
| Cursor 等 Coding Agent | 需求文件、程式碼庫、終端機 | 思考、搜尋程式碼、讀寫檔案、執行命令 | 理解需求→搜尋→編輯→測試→除錯 |
| Deep Research | 網路、學術資料庫、本地檔案 | 思考、搜尋、讀網頁、摘要 | 依已有資訊調整搜尋方向，逐步綜合 |
| Browser Use 等 | 螢幕、瀏覽器、檔案系統 | 點選、輸入、滾動、截圖、執行程式碼 | 觀察螢幕→識別元素→操作→驗證 |
| 豆包手機助手 | 手機螢幕、已安裝 App | 點選、滑動、輸入、開 App | 理解意圖→找 App→操作→確認 |
| Pine AI | 帳戶資訊、歷史帳單、服務商知識庫 | 打電話、寄信、填表、與使用者確認 | 收集資訊→制定策略→聯絡→談判→彙報 |

共同點：**開放式動作空間**（能產生任意自然語言與程式碼）、**內部思考**、**持續互動**。

## 3. 工具：Agent 的手腳 ⭐

### 3.1 五類工具（依互動方向）

| 類型 | 方向 | 例子 |
|---|---|---|
| **感知工具** | 讀取資訊 | 搜尋引擎、檔案讀取、API、資料庫 |
| **執行工具** | 改變世界 | 執行程式碼、檔案操作、系統命令、外部 API |
| **協作工具** | 與其他 Agent 或人分工 | 委託子 Agent、請人類確認、多 Agent 協調 |
| **事件觸發工具** | **外部→Agent**（不是 Agent 主動呼叫） | 新郵件、排程時間到、Webhook 回呼 |
| **使用者溝通工具** | Agent→使用者 | 文字訊息、語音通話、郵件，傳達進度或主動關懷 |

第四章完整展開分類與設計原則；事件觸發與使用者溝通工具在第六章。MCP（Model Context Protocol）讓工具接入變得更容易。

### 3.2 工具呼叫的四步

```text
① 宣告工具                       ② 模型決定呼叫
tools: [{ name: "get_weather",   assistant: { tool_calls: [{
          parameters:               function: "get_weather",
            { city: "string" } }]   arguments: { city: "北京" } }] }

③ 結果追加到上下文                ④ 模型依結果回覆
tool: { tool_call_id: "call_1",  assistant: {
        content: '{"temp":28,       content: "北京今天 28°C，晴。" }
                   "sky":"晴"}' }
```

開發者只負責**定義**與**執行**工具；「要不要呼叫、呼叫哪個、傳什麼參數」由模型決定。

### 3.3 工具設計：從最窄能力起步 ⭐

- 只做四則運算 → 一個參數清楚的計算器就夠。
- 要讀試算表、清理缺值、算統計、畫圖 → **受限的 Python 直譯器**比不斷疊加專用工具更好組合。
- 但通用性也擴大了出錯面與攻擊面：程式碼要在**隔離沙盒**中執行，預設不能連網、不能讀授權目錄以外的檔案，並限制時間、CPU、記憶體與輸出大小。
- 長程任務 → **受控的虛擬工作目錄**，存放計畫、中間結果、日誌與產物，讓 Agent 能跨多次執行接續工作；同樣要限制路徑、容量、檔案類型，防止路徑越界。

> **通用基礎能力用於組合與探索；專用工具用於約束高風險與強業務規則的操作。**

支付、刪除資料、寄送郵件、生產部署等，仍應封裝成參數明確、權限受限、全程可稽核的專用工具，必要時加上預覽與人工確認。

> 對照第二本書第 8 章：「沒有選項、預設安全」。這裡的意思相同：高風險操作不要交給萬用執行器，而是做成只能以安全方式使用的專用介面。

## 4. LLM：Agent 的大腦 ⭐

收到請求後，LLM 要解析真實意圖（使用者說的往往不是他真正想要的），把模糊任務拆成可執行步驟，並持續判斷下一步做什麼、要不要呼叫工具。

**內部思考**是 LLM Agent 的獨特能力：行動前先規劃、推演，不改變外部環境，卻能大幅提升行動品質。它之所以有效，是因為預訓練讓模型習得了人類知識中的邏輯規則（數學、因果、問題分解）。所以與傳統強化學習 Agent 不同，**LLM Agent 不是盲目隨機探索，而是在結構化的知識體系上展開**。

### 4.1 模型即 Agent（Model as Agent）

先進模型透過後訓練（特別是 RL），把工具呼叫的**決策策略**內化成原生能力。

但這不代表框架變得不重要：

> **模型越強大，圍繞模型建構的 Harness 就越關鍵。** Harness 原指馬具，不是為了限制馬奔跑，而是把力量引導到正確方向。模型是那匹強大但不可預測的馬，Harness 是把能力引導成可靠任務執行的工程外殼。

模型自主決策空間越大，出錯影響面越大，越需要約束、驗證、糾正。模型廠商的真正優勢不是「讓框架變薄」，而是能**協同最佳化**模型與 Harness。

### 4.2 苦澀的教訓與 Harness 的節奏 ⭐⭐

Rich Sutton 的《苦澀的教訓》（The Bitter Lesson）：AI 研究七十年反覆上演同一幕，研究者把領域知識編碼進系統，短期見效，長期總是輸給能隨算力與資料擴展的通用方法（搜尋與學習）。

那麼 Harness 會不會終將被模型「吃掉」？本書的立場：

> **方向認同，節奏務實。**

- **方向上**：模型會持續吃掉 Harness。工具呼叫、長程規劃都曾靠外部編排，如今已是原生能力。
- **節奏上**：比直覺慢得多。訓練以月計，模型無法一次內化真實業務中所有的約束與偏好。
- **模型此刻的能力邊界，就是 Harness 此刻的價值所在。** 模型還做不穩的，Harness 先補上；模型每內化一層，Harness 就卸下一層，轉而兜底新的能力前沿。

### 4.3 Agent 的三條學習路徑 ⭐⭐

| 路徑 | 發生在哪 | 時間尺度 | 優缺點 | 詳見 |
|---|---|---|---|---|
| **上下文適應** | 當前任務的上下文（示例、狀態、檢索結果） | 立即 | 快、便宜；受上下文視窗與資訊組織限制，不跨會話保留 | 第二章 |
| **外部產物（artifact）更新** | 知識文件、Prompt、Skill、程式與 Harness | 跨任務 | 可稽核、可修訂；使用時仍要經由上下文或工具 | 第三至五、九章 |
| **參數更新** | 模型權重（後訓練） | 訓練週期 | 部署成本高，但能自然、廣泛地泛化（醫療影像、語言風格、隱式決策策略） | 第八章 |

三者不是互斥分類，而是**不同時間尺度上的協同機制**：上下文負責臨場適應，外部產物負責可控積累，參數負責內化難以明說的能力。依可回滾程度由高到低排列，正好也是這個順序（見 §9 的「最小 diff + 可回滾」）。

## 5. 上下文：Agent 的眼睛 ⭐⭐⭐

每次呼叫 LLM 時，上下文由五部分組成：

| 部分 | 內容 | 性質 |
|---|---|---|
| **系統提示詞** | 開發者寫的「崗位說明書」：身分、權限、行為準則；也包含跨會話的**使用者記憶**與動態注入的環境狀態 | **靜態字首** |
| **工具定義** | 工具名稱、功能描述、參數格式 | **靜態字首** |
| **使用者訊息** | 使用者輸入，可能夾帶 RAG 檢索到的外部知識 | 動態軌跡 |
| **模型回覆** | 最多三部分：`reasoning`（思考）、`content`（回覆文字）、`tool_calls`（行動）；不一定同時出現 | 動態軌跡 |
| **工具執行結果** | 框架執行工具後回傳的結果 | 動態軌跡 |

```
上下文 = 靜態字首（系統提示詞 + 工具定義）+ 軌跡（使用者訊息 + 模型回覆 + 工具結果）
```

（2026 年起，生產框架中完整的工具 schema 也可以按需動態載入到上下文末尾而不破壞字首，見第二、四章。）

### 5.1 實驗 1-1：上下文消融 ⭐⭐

**消融實驗**（Ablation Study）：像醫生逐一排除病因，一次拿掉一個元件看系統是否還正常。實驗保留系統提示詞（沒有它連角色認知都沒有），其餘四個元件各缺一個，加上完整基線共五組。

| 拿掉的元件 | 結果 |
|---|---|
| **工具定義** | 無法呼叫任何工具。但**失去行動能力不等於沉默**：模型照樣給出格式工整、語氣篤定的答案，資料卻來自參數記憶，排版和真正有觀測依據的答案一模一樣。它是坦白拒絕還是就地編造，取決於模型的幻覺率與誠實度；提示詞裡「不得自行估計」只能降低、不能消除編造機率 |
| **工具執行結果** | 閉環控制的關鍵。缺了它 Agent「盲目」執行，**反覆重試直到耗盡迭代預算** |
| **思考過程** | 記錄「為什麼這麼做」；若能從工具結果（「發生了什麼」）重建，丟掉幾乎沒有代價 |
| **歷史訊息** | 防止冗餘操作、避免重犯同樣的錯 |

> **關鍵洞察**：上下文決定 Agent 能看到什麼，而 Agent 只能依據看到的資訊做決策。元件並不等價，衡量標準是**它承載的資訊能否從別處重建**；而且模型迭代很快，同樣的消融換了新模型可能得出不同結論，必須實測。
>
> **「給出了回答」不等於「完成了任務」。** 上下文殘缺時的典型失敗不是報錯退出，而是一個看上去毫無破綻的答案。

> 對照第二本書：這正是 Ferguson 等人說的「失敗時要大聲失敗」的反面——Agent 的失敗往往是**安靜且看似正確**的，所以必須有外部驗證（§6）。

## 6. ReAct 迴圈 ⭐⭐⭐

**ReAct**（Reasoning + Acting）：名字只有兩個詞，實際上是三環節的迴圈：

```
思考 → 行動（呼叫工具）→ 觀察（看結果）→ 思考 → …… 直到任務完成
```

**軌跡**（trajectory）：執行過程中不斷累積的訊息歷史。每次呼叫 LLM 的完整上下文 = **靜態字首 + 軌跡**；LLM 產生的回應再追加到軌跡，供下一次呼叫使用。

**最小執行骨架**（書中偽程式碼）：

```python
trajectory = [user_request]

repeat:
    context = stable_prefix + trajectory
    decision = Model(context)
    trajectory.append(decision)

    if decision has no tool call:
        return decision.answer

    for call in decision.tool_calls:        # 獨立的呼叫可以並行
        validated_call = Harness.validate(call)
        observation = Environment.execute(validated_call)
        trajectory.append(observation)
```

職責分工：**Model** 只決定下一步；**Harness** 組裝上下文、校驗並執行工具；**Environment** 產生真實的狀態變化與觀察。

**例：多幣種年度收入彙總**（Q1 2.5M 美元、Q2 2.1M 歐元、Q3 1.8M 英鎊、Q4 380M 日圓）

| 迭代 | 模型做什麼 | 工具結果 |
|---|---|---|
| 1 | 思考「要全部換成美元」，**並行**呼叫三次 `convert_currency` | EUR→2,282,608.7；GBP→2,278,481.01；JPY→2,541,806.02 |
| 2 | 思考「拿到換算結果，要彙總」，呼叫 `code_interpreter` | Total $9,602,895.73，Average $2,400,723.93 |
| 3 | 確認完成，輸出 `FINAL ANSWER` | — |

共 **3 次迭代、4 次工具呼叫**。軌跡不斷追加，讓模型知道目前在哪一步、試過什麼、得到什麼；結構化的軌跡也帶來可解釋性與可除錯性。

### 6.1 實驗 1-2、1-3：「模型即 Agent」的兩種接法

| | 實驗 1-2：Kimi K3 | 實驗 1-3：GPT-5.6 |
|---|---|---|
| 模型 | 約 2.8 兆參數的 MoE，100 萬 token 上下文，原生視覺，常開思考模式 | 支援 **自由格式工具呼叫**（`type: "custom"`，參數直接是原始文字如程式碼或 SQL，省去 JSON 轉義） |
| 工具在哪執行 | `web_search`、`code_runner` 由服務端腳本引擎 Formula 執行 | Responses API 內建網路搜尋與程式碼直譯器 |
| **ReAct 迴圈在哪** | **仍在用戶端**（`agent.py` 裡的 `while` 迴圈） | **整體在服務端閉環** |
| 特色 | 能連續 200～300 次工具呼叫仍保持一致（多數模型數十次就退化） | **意圖澄清**：先問「偏好哪個資料來源？要分析哪些指標？」再動手 |

**常見誤解的澄清** ⭐（感謝讀者在 GitHub Issue #30 指出）：

> **RL 賦予模型的是決策能力**——何時呼叫、呼叫哪個、傳什麼參數、拿到結果後是否繼續、如何把上百次呼叫串成連貫推理。**工具本身及其執行仍由框架或 API 內建工具提供**。RL 最佳化的是決策策略，不是把搜尋引擎或沙盒「裝進」權重。所以**編排迴圈並沒有消失**，只是決策權交給了模型，迴圈本身可能從用戶端移到了服務端。

沒有 OpenAI 額度也能重現：阿里雲百鍊 qwen3.7-plus 的 Responses API 同樣內建 `web_search` 與 `code_interpreter`。

## 7. Harness 工程：模型之外的競爭力 ⭐⭐⭐

前面的實驗也暴露了脆弱點：幻覺（編造不存在的工具或參數）、選錯工具、出錯無法自我恢復。**能跑的 Demo 和可靠的產品之間有巨大的鴻溝**，Harness 工程就是要填這道鴻溝。

> **Agent = Model + Harness**
> **Harness = 上下文管理 + 工具介面 + 約束 + 驗證 + 糾正**
> **Agent ↔ Environment**

Harness 是 **Agent 邊界內、Model 之外**的執行與治理層：工具定義、呼叫適配器、沙盒權限與重置機制屬於 Harness；沙盒內隨行動變化的檔案與程序、外部資料庫、網頁、使用者、物理世界屬於 Environment。**部署位置不改變這條概念邊界。**

### 7.1 五要素 ⭐⭐

| 要素 | 職責 | 核心原則 | 例子 | 詳見 |
|---|---|---|---|---|
| **Context** | 提供感知資訊 | **資訊充分性** | 系統提示詞、知識庫、Agent 狀態列、Sidecar 旁路查詢 | 二、三章 |
| **Tools** | 提供行動手段 | **介面清晰**：命名直觀、參數有例子、邊界有說明 | MCP 工具、程式碼直譯器、搜尋 | 四章 |
| **Constrain** | 設定行為邊界 | **故障安全預設值**：所有能力預設關閉，須顯式開放（像手機 App 權限） | Claude Code 每個工具預設要使用者授權 | 四章 |
| **Verify** | 自動判斷結果對錯 | **輸入隔離**：安全檢查只看結構化資料（如工具回傳的 JSON 欄位），不看模型自由生成的文字（可能被提示注入操縱） | Linter、型別系統、結果校驗 | 五、六章 |
| **Correct** | 發現問題時修正或回退 | **確認無法恢復前，不暴露中間態**（先靜默重試，不把半成品給使用者） | 靜默重試、接續生成、連續失敗時交回人工（熔斷） | 二、五章 |

**模型控制迴圈**（書中骨架）：

```python
observation = Environment.observe()
trajectory = [observation]
while true:
    actions = Model(Harness.build_context(trajectory))
    if len(actions) == 0:
        break
    allowed_actions = Harness.constrain(actions)
    observation = Environment.apply(allowed_actions)
    if not Harness.verify(Environment):
        observation = Harness.correct(Environment)
    trajectory.append(allowed_actions, observation)
```

**上下文與工具讓 Agent「能做事」；約束、驗證、糾正讓 Agent「不做錯事」。** 兩者的重要性隨產品成熟度不對稱地變化：早期框架關注前者，生產級系統的重心已轉向後者。

> **以 Claude Code 為例，它的 Harness 絕大部分程式碼都是約束、驗證與糾正，工具本身只是一小部分。** 包括：流程狀態管理、多層上下文壓縮、權限分類、**熔斷器**（錯誤連續發生時自動「跳電」停止重試）、錯誤恢復（捕獲異常、回滾、重試或交還人類）。

> **產業正在從「能做事」轉向「可靠地做事」，Harness 工程因此成為核心競爭力。**

> 對照第二本書：Verify 的「輸入隔離」原則與密碼學的 **Horton 原則**（認證意思而非字面）、以及「不讓可能被汙染的資料參與安全判斷」是同一個思想；Correct 的「不暴露中間態」則像安全通道的「驗證失敗前不釋出任何明文」。

### 7.2 工程範式的演進：層層包含 ⭐

```
提示工程 ⊂ 上下文工程 ⊂ Harness 工程 ⊂ Loop 工程（⊂ Graph 工程）
```

| 範式 | 關注點 |
|---|---|
| **提示工程** | 最佳化給模型的自然語言指令 |
| **上下文工程** | 系統性管理模型能看到的**所有**資訊（指令、工具定義、歷史、外部知識） |
| **Harness 工程** | 模型在**什麼樣的系統**中執行：約束、驗證、回饋迴圈、錯誤恢復 |
| **Loop 工程** | 跨輪次持續自主運轉：誰發現下一件該做的事、何時驗證、何時才算真正完成（第十章） |
| **Graph 工程**（2026 年 7 月起的說法） | 把 Agent 迴圈、確定性程式、人工審批組織成顯式的執行圖：節點承擔能力、邊規定路由與依賴、結構化狀態沿邊傳遞並在關鍵邊界持久化（LangGraph、Microsoft Agent Framework、Google ADK 早已有類似實踐） |

> **當各家模型能力越來越接近、不再是決定性差異時，競爭優勢就轉移到模型之外的工程實踐。**

**實證**：LangChain 在 **Terminal Bench 2.0** 上，Coding Agent 從 52.8% 提升到 66.5%（排行榜 30 名開外躍升到前 5），**模型沒換**，改的是 Harness：讓 Agent 自動檢查執行結果、偵測是否陷入重複迴圈、最佳化思考策略。

### 7.3 Anthropic 的三個核心原則

| 原則 | 為什麼 |
|---|---|
| **保持簡單** | 從最簡單的方案開始，必要時才加複雜度；直接的 API 呼叫優於複雜框架。**每多一層抽象，都是以後除錯時新的盲區** |
| **保持透明** | 明確顯示規劃步驟、執行日誌、決策軌跡——既為了除錯，也是使用者信任的前提。黑箱裡的錯誤，外部既無法定位也無法糾正 |
| **設計好 ACI**（Agent-Computer Interface） | 從 **Agent 的視角**設計介面，而不是從程式設計師的視角。容易誤用的地方，要從設計上讓錯誤**無法發生**——**防呆**（Poka-yoke，源自豐田生產體系），例如 SIM 卡的缺角、微波爐門沒關就不加熱 |

> 模型與工具之間唯一的溝通管道就是介面本身，**模糊的介面會被模型放大成系統性的錯誤**。

> 對照第一本書：Hanson 一再強調介面要讓錯誤用法在編譯期或執行期被抓到（checked runtime error），ACI 與防呆是同一個想法搬到 LLM 身上——差別在於使用者從「程式設計師」變成了「模型」。

### 7.4 如何選擇模型

模型迭代太快，本書不推薦具體版本，只給方向：

| 面向 | 建議 |
|---|---|
| **閉源** | OpenAI、Anthropic 最常用；能力領先但成本高、受廠商政策限制。**不要只看排行榜，要在自己的任務上評估**（第七章） |
| **開源** | 與閉源差距在 6 個月內，成本顯著較低，可私有化、可微調；國內 Agent 能力較強的有 DeepSeek、Kimi、GLM。**不同模型的工具呼叫能力差異很大**，選前務必實測 |
| **策略邊界** | 基準測試上有某能力，不代表產品允許你使用。不同廠商對網路安全、蒸餾、模型提取、隱私、高風險操作的政策不同；同一任務在聊天產品、Coding Agent、API 可能結果不同。要測：模型願不願意執行、介面有沒有暴露所需能力、條款是否允許。業務關鍵任務要預備人工接管或其他合規模型 |
| **思考能力** | **絕大多數 Agent 需要支援思考（reasoning）的模型**。只有單步簡單任務或點固定位置的簡單 GUI 操作例外 |
| **輸出速度** | 每輪都要等模型輸出完成：20 輪推理、每輪慢 2 秒，就多等 40 秒 |
| **多模態** | 要理解圖片、音訊、影片時是硬性要求，各模型差異很大 |

## 8. 編排模式：工作流與自主 ⭐⭐

**從簡單到複雜的選擇順序**：

```
單次 LLM 呼叫（最佳化提示詞與示例就能解決？）
   ↓ 不夠
工作流（能清楚拆成固定子任務？）
   ↓ 不夠
自主 Agent（需要動態決策與彈性路徑）
```

Agent 系統通常**用延遲與成本換更好的任務效能**，要謹慎權衡是否值得。

**反面例子**：「從百萬條聊天記錄提煉個人記憶」——AI 很容易畫出一條看似嚴謹的流水線：切片→擷取→證據核驗→身分解析→記憶整理→合併複核，最後建事實圖、覆蓋帳本、不可變版本……每個部件單看都有道理，組合起來卻**低效又不可靠**：拓撲固定，遇到新例外就繼續加節點，架構越來越複雜、通用性越來越差；模型原本能依上下文處理的語意判斷，反而被寫死了。

> **Harness 很重要，不等於 Harness 越複雜越好。** Manus 的說法："**Less structure, more intelligence.**"
>
> 給能力足夠的 Agent 清楚的目標、必要的上下文、可組合的工具，用自然語言告訴它如何像人一樣查證、比較、處理衝突；程式只固化**必須始終成立的邊界**（權限、不得覆蓋原始材料、原子發布）。只有業務約束要求、或評估反覆暴露某類穩定失敗時，才升級為專門的驗證器、獨立 Agent 或確定性流程。**好的結構不是替 Agent 預演全部思考，而是守住邊界，把邊界內的決策空間還給模型。**

### 8.1 工作流：確定性的編排

執行路徑由開發者預先寫死，LLM 只在每個節點內部負責理解與生成。

**訂機票四節點**：核實身分 → 搜尋航班 → 付款 → 確認預訂

| 優點 | 說明 |
|---|---|
| **嚴格流程控制** | 「付款前不能預訂」由程式碼強制，不依賴 LLM 判斷 |
| **安全性** | 提示注入或模型犯錯，最多只影響**當前節點**，無法跳到不該執行的分支 |

**侷限**：缺乏變通。使用者付款時臨時想改簽、航班突然取消要推薦替代方案，固定路徑只能走預設的例外分支或交還人類。

**文生圖工作流與「適配層」** ⭐：

- 使用者說「畫一個 AGI 實現後程式設計師的工作場景」，但 Stable Diffusion 只吃逗號分隔的英文標籤。
- 所以工作流要有兩個節點：① LLM **改寫提示詞**（還要思考：「AGI 之後程式設計師不必寫程式了，所以畫他在海邊曬太陽，用腦機介面指揮 AI 員工」）；② 呼叫生圖模型。
- 這個 LLM 節點做的是**翻譯**，因為工具「聽不懂人話」。這種**替工具或模型的能力短板打補丁**的 Harness 程式碼，稱為**適配層**。
- 換成**原生影像生成**的多模態模型（Nano Banana 2、GPT-Image 2），改寫節點就不需要了。

> **實驗 1-4**：同一句大白話分別走「改寫 + SD」與「原生生圖」兩條路。分兩類需求對照：描述具體的（如指定海報文案）與寬泛的（如 AGI 工作場景）——後者工作流路線仍可能有優勢。

> **Harness 裡替模型短板打補丁的部分，會隨模型變強被模型自己內化。** 光在本章就發生了好幾輪：few-shot 示例、「讓我們一步一步思考」被指令微調與推理模型內化；輸出格式修復、JSON 解析容錯被結構化輸出與原生工具呼叫內化；文生圖的提示詞改寫被原生多模態吃掉。**每一輪內化，消滅的都是「翻譯」與「腳手架」這類適配層程式碼。**

### 8.2 自主 Agent：動態自主決策

執行路徑不是預先定義的，而是依**環境回饋**即時決定。

訂機票例：使用者說「訂下週三去上海的機票」→ Agent 先搜尋 → 發現要登入 → 先核實身分 → 回來搜尋 → 最便宜的要轉機 → 主動問使用者 → 使用者不要轉機 → 調整條件……

- 要能自主規劃、識別失敗、調整策略，而不是出錯就停。
- **自主不等於無限制**：必須有明確的**停止條件**——任務完成、達到最大迭代次數、遇到不可恢復的錯誤。常見退出條件：呼叫最終輸出工具、回應中沒有工具呼叫、出錯或達最大輪數。
- 本質上就是**在迴圈中使用工具的 LLM**——也就是 ReAct。
- 適用：開放式、難以預測步數的問題，例如 SWE-bench、Computer Use、迭代搜尋研究。
- 代價：成本更高、**複合錯誤**風險。部署前要在沙盒充分測試、設護欄與監控、在關鍵決策點加入人機協作檢查點。

### 8.3 兩種模式的混合

| 混合方式 | 說明 |
|---|---|
| **分段混合** | 有嚴格合規要求的流程用工作流；需要彈性的部分切到自主模式。n8n 可以在同一個視覺化系統中同時放工作流節點與自主 Agent 節點 |
| **Agent 寫工作流** | 先由自主 Agent 讀完任務、自行決定拓撲並產生編排程式碼；程式碼產生後，執行階段就退回工作流的確定性（第十章詳述） |

### 8.4 主流框架對比

| 框架 | 定位 | 編排 | 開發方式 | 適用 |
|---|---|---|---|---|
| **Codex Harness** | Codex 的開源 Agent 執行層 | 自主 | 程式碼優先，可嵌入自家應用 | Coding Agent、嵌進產品 |
| **Claude Agent SDK** | 生產級 Agent 框架 | 自主（工具迴圈 + 子 Agent） | 程式碼優先 | 複雜自主任務 |
| **LangChain / LangGraph** | 通用 LLM 應用框架 | 工作流 + 自主 | 程式碼優先 | 多步驟工作流 |
| **n8n** | 視覺化工作流自動化 | 工作流 + 自主 | 低程式碼 | 業務自動化、非技術團隊 |
| **Dify** | LLM 應用開發平臺 | 工作流 + 對話 | 低程式碼 | 企業 RAG、知識庫 |
| **CrewAI** | 角色化多 Agent 編排 | 多 Agent | 程式碼優先 | 團隊式任務分解 |
| **OpenClaw** | 開源全能個人 Agent | 自主 + 事件驅動 | 配置 + 程式碼（自託管） | 個人助理、多平臺訊息整合 |
| **DeepSeek Harness** | Agent 自進化框架 | 一切皆外掛 | 程式碼優先 | 開發者、研究者 |
| **Pi** | 極簡 Coding Agent 框架 | 自主 | 程式碼優先 | 開發者 |

- **Codex Harness** 有三條整合路徑：`codex exec`（腳本與 CI 的一次性任務）、Codex SDK（第三方應用啟動、恢復、串流處理任務）、app-server（JSON-RPC 提供持久工作階段、事件流與審批回呼）。
- Claude Agent SDK 與 Claude Code 也是類似關係，但 Claude 開放的是 SDK 介面，Harness 實作本身不開源。

> 框架發展很快，你讀到時很可能已經換了一批。**學會某個框架的用法並不重要**；關鍵在於它能否用**最小的抽象層**讓你專注於業務邏輯。

## 9. 護欄與安全性 ⭐⭐⭐

護欄（Guardrails）是「約束、驗證、糾正」的核心實作手段，構成**分層防線**：單一護欄不太可能足夠，組合多個專門護欄才有韌性。可以先針對已識別的風險設置，發現新漏洞再逐步增加。

**另一類失敗：誤拒絕**——為了攔截危險請求，模型也拒絕了合法但形式敏感的任務（如授權的安全測試、蒸餾研究）。所以護欄評估既要測「該拒絕的有沒有被攔」，也要測「明確允許的能不能正常完成」。

### 9.1 三層護欄：依「被繞過的難度」排序 ⭐⭐

| 層 | 管什麼 | 機制 | 依賴模型判斷？ |
|---|---|---|---|
| **上下文層** | **模型能看到什麼**（內容進入上下文之前攔截） | 相關性分類器（程式設計助手被問「帝國大廈多高」）、安全分類器（越獄、提示注入）、內容審核、規則（黑名單、長度限制、正則防 SQL 注入）、來源標註與「指令／資料」分離 | 最依賴 |
| **執行層** | **模型能做什麼**（動作生效之前驗證） | **工具風險評級**（依可逆性、權限、財務影響分低／中／高，高風險要額外審查或人工確認）；**輸出檢查**（PII 過濾、品牌一致性）——回覆使用者本身也是一次動作 | 較少 |
| **資料層** | **世界最終能被改成什麼樣** | 資料庫行級安全策略、約束與校驗器、受控檢視與預存程序、由受信任執行環境綁定、無法偽造的存取上下文 | **不依賴** |

- **越獄 vs. 提示注入**：越獄是**使用者自己**試圖繞過安全限制；提示注入是攻擊者透過**外部資料**（網頁、文件）間接操縱模型。
- **Anthropic 的 Constitutional Classifiers**：① **規則驅動**——用自然語言規則產生合成資料訓練輸入輸出分類器；② **上下文聯合判斷**——把提問與回答放在一起看（「如何使用食品調味料」單看無害，對照提問才發現是化學試劑的暗語）；③ **兩級篩查**——極輕量的探針直接讀模型內部啟用、幾乎零成本檢查所有對話，可疑的再交給強分類器複審，所以第一級誤報多也不影響體驗。
- **上下文層的結構性上限**：**處在同一個上下文裡的 Agent，很難判斷自己是否已被注入**。所以它只能降低攻擊成功率，給不出保證——這就是需要下面兩層的原因。
- **執行層的關鍵**：複核必須由**上下文之外**的機制完成——獨立審查行程、最小權限憑證、沙箱隔離、人在迴路——否則會和被注入的 Agent 一起淪陷。
- **資料層的價值**：恰恰在於**不依賴上面兩層是否正確**。即使注入得手、生成的程式碼漏寫了權限判斷，越權操作仍會在資料層被拒絕（第五章以動態生成軟體為例展開）。

> 對照第二本書：這正是**縱深防禦**——而且三層依「被繞過的難度」排序，與密碼學中「不要讓安全依賴於系統其他部分的正確性」完全一致。資料層之於 Agent，就像第 7 章安全通道之於應用：無論上層怎麼出錯，底層的保證依然成立。

### 9.2 人工干預（Human in the loop）

讓 Agent 在無法完成時**優雅地轉移控制權**：客服升級到人工、Coding Agent 交還開發者。部署早期尤其重要，有助於找出失敗模式、邊緣情況，建立健全的評估週期。

觸發條件：

1. **超過失敗閾值**：重試或操作次數設上限，超過就升級人工。
2. **高風險操作**：敏感、不可逆、高風險（大額退款或付款），至少在團隊對 Agent 可靠性建立足夠信心之前，都要人工監督。

## 10. Harness 五要素與全書結構的對應

> 全書只有一個結構骨架：**Agent = LLM + 上下文 + 工具**。**Agent = Model + Harness** 不是並列的另一套劃分，而是「建構」這一塊內部的一個透鏡。

| Harness 重點 | 對應章 | 核心內容 | 安全關注點 |
|---|---|---|---|
| 上下文設計 | 第二章 | 提示工程、狀態列、壓縮、Skills | 提示注入、資訊洩露 |
| 上下文擴展（知識持久化） | 第三章 | 使用者記憶、RAG、結構化索引、智慧體化 RAG | 敏感資訊、隱私 |
| 工具設計與安全約束 | 第四章 | 工具分類、權限、MCP、非同步 | 誤操作、未授權存取、不可逆操作 |
| 工具的驗證與糾正 | 第五章 | Coding Agent 的 Harness、測試驅動、程式碼化規則 | 身分冒用、責任歸屬 |

- 第六章（互動）擴展的是觀察與動作空間本身的**模態與時機**；第七至九章討論**怎麼知道 Harness 建對了、怎麼讓它持續變好**；第十章把單一 Agent 換成多 Agent 協作結構。
- **安全不按章劃分**，是貫穿全書的**橫切關注點**，掛在三層護欄的骨架上。

**Anthropic 的長時執行 Agent 實踐**：把複雜任務拆成「**初始化 Agent**」（設定環境、分解任務列表）與「**執行 Agent**」（每個會話增量推進並留下清楚的交接產物），以結構化 Harness 解決長任務中「**上下文耗盡**」與「**過早宣告完成**」兩個模型本身無法解決的問題。

## 11. 貫穿全書的五個設計模式 ⭐⭐⭐

| 模式 | 定義 | 為什麼成立 | 出現在 |
|---|---|---|---|
| **提議者—審核者**（Proposer-Reviewer） | 產出與評判由**兩個不共享上下文**的角色承擔；評判方看的是**產物本身**（渲染結果、測試輸出、結構化參數），不是產出方的推理 | **自審不可靠**：同一上下文的模型想不到自己沒想到的，也很難判斷自己是否已被注入 | 三章知識更新、四章工具審批與驗證（Sidecar 是唯讀變體）、五章簡報／影片／日誌實驗、七章 UI 評估、九章更新提案、十章對等協作 |
| **漸進式披露**（Progressive Disclosure） | 先給一份可檢索的目錄，再按需載入細節 | 同時最佳化**上下文預算**與**選擇精度** | 二章 Skills（後設資料常駐、正文按需）、三章分層檢索、四章主動工具發現與分頁截斷、十章 Agent 發現 |
| **只增不改**（Append-only） | 狀態以追加演進，已寫下的不回頭改 | 換來**可快取、可重放、可稽核** | 二章 KV Cache 字首穩定（改動越靠前、作廢的快取越多）、三章事件式記憶、四章新工具 schema 追加到軌跡末尾 |
| **邊界集 + 保留集**（Boundary Set + Retention Set） | 每次修改同時在「**應當改變**」與「**不應被影響**」兩批樣本上驗證 | 只測前者會把過擬合當進步；只測後者會把無效修改當安全 | 七章回歸任務、八章訓練與評估隔離、九章更新提案驗證 |
| **最小 diff + 可回滾** | 每次修改盡量小、帶來源、可單獨回滾 | 讓**歸因**成為可能 | 三章知識更新、五章程式碼補丁、九章 Prompt 與程式更新；三條學習路徑也依可回滾程度排列 |

> 對照前兩本書：「只增不改」就是 Hanson 書中**不可變資料**（如 `Text`、`Atom`）帶來的好處；「最小 diff + 可回滾」呼應密碼學第 20 章「讓換金鑰這種程序經常被執行」——小而頻繁的改動才可靠。「提議者—審核者」則是第二本書第 3 章「讓其他專家攻擊你的設計」的 Agent 版本。

## 12. 設計觀念整理

| 觀念 | 說明 |
|---|---|
| Agent = LLM + 上下文 + 工具 | 大腦、眼睛、手腳；不包含 Environment |
| 擴展介面是最大槓桿 | 模型固定時，擴展觀察與動作空間往往讓不可解變可解 |
| 失敗常常是安靜的 | 「給出回答 ≠ 完成任務」，殘缺上下文產生毫無破綻的錯誤答案 |
| 元件價值看可重建性 | 能從別處重建的資訊，丟掉代價低 |
| 編排迴圈不會消失 | RL 內化的是決策，不是工具執行；迴圈可能移到服務端 |
| 模型越強，Harness 越重要 | 自主空間越大，出錯影響面越大 |
| 方向認同，節奏務實 | Harness 終將被模型吃掉，但比直覺慢；此刻的能力邊界就是 Harness 的價值 |
| 適配層會被內化 | few-shot、思維鏈提示、JSON 容錯、提示詞改寫 |
| 生產重心在保障層 | 約束、驗證、糾正佔 Harness 大部分程式碼 |
| 先簡單後複雜 | 單次呼叫 → 工作流 → 自主 Agent |
| Less structure, more intelligence | 程式守邊界，邊界內的決策交給模型 |
| 防呆（Poka-yoke） | 讓錯誤從設計上無法發生 |
| 三層護欄 | 上下文 → 執行 → 資料，越下層越不依賴模型判斷 |
| 同一上下文無法自證未被注入 | 審核必須在上下文之外 |

## 14. 思考題摘要（含書附參考答案要點）

| # | 題目 | 參考答案要點 |
|---|---|---|
| 1 ★★ | 只能加一項：更強模型、更豐富上下文、還是更多工具？ | 先找短板：通常優先補**上下文**（觀察空間）；超出推理能力才換模型；動作空間不足（如連不到內部系統）才加工具。依據是**分析失敗軌跡**，定位瓶頸在感知、決策還是行動 |
| 2 ★★★ | ReAct 的累計快取讀取量隨輪數近似二次成長，如何降低？ | 第 i 輪讀約 i 長度的字首，累計 1+2+…+n = O(n²)（二次成長的是**累計快取讀取費用**，軌跡長度與 KV Cache 佔用仍是線性）。達到 token 閾值時**批次**壓縮早期軌跡、只留結論與關鍵狀態；大型中間結果外置、按需檢索；子 Agent 隔離。**不要每輪都壓縮**——傷效能，又增加壓縮呼叫與快取重建成本 |
| 3 ★★ | 模型越自主、Harness 卻越重要，如何共存？ | 馬與韁繩：自主空間越大、出錯面越大，越需要約束、驗證、糾正。框架價值從「編排 LLM 呼叫」轉向保障層：權限分類、熔斷、錯誤恢復、壓縮、工具生態 |
| 4 ★★ | 除了工具結果缺失，還有什麼會讓 Agent 無限迴圈？如何偵測與終止？ | 工具反覆報同樣錯誤、幻覺呼叫不存在的工具、壓縮丟了關鍵狀態、思考被剝離導致 API 報錯、任務本身無解。機制：最大迭代次數；偵測重複呼叫（工具 + 參數**指紋**）；超過失敗閾值升級人工 |
| 5 ★ | 用感知、行動、策略三維分析你常用的 AI 產品 | 開放題：仿照 §2.2 的表格寫出眼睛、手腳、策略 |
| 6 ★★ | 航班訂票客服該用工作流還是自主 Agent？ | 主體用工作流（四節點保證合規順序、把注入攻擊面限在單節點）；理解需求、改簽、航班取消推薦替代方案等開放環節切到自主 Agent；大額付款或退款加人工確認 |
| 7 ★★★ | 工具多數時候低風險，特定參數下變高風險（如 `delete_file`），如何動態評估？ | 評級物件從「工具」細化到「**工具 + 參數**」，呼叫時依可逆性、權限、影響面計算；用**規則式確定性檢查**（路徑黑白名單、正則）而不是模型判斷；驗證只看結構化資料以防注入 |
| 8 ★★ | 受限的動作空間何時優於開放式？ | 高合規、高風險、錯誤不可逆（退款、付款）：受限選項本身就是約束，天然防呆 |
| 9 ★★ | 使用者不在線、回應慢或指令模糊時，Agent 該怎麼辦？ | Fail-safe：高風險操作在沒確認時**暫停**而不是預設執行；先做可逆的低風險部分，記錄高風險部分便於人類決策與 Agent 恢復；用非同步溝通工具通知並設逾時；指令模糊就做意圖澄清 |
| 10 ★★★ | 舉一個會隨模型進步而過時的工程手段 | ① 約束取樣強制工具呼叫格式（格式遵循變好後收益降低，但高風險場景仍保留確定性驗證）；② 外部知識庫彌補模型無法持續學習（可能縮小範圍，但即時更新、精確檢索、權限、溯源仍有獨立價值）；③ 規定所有能力都必須走標準工具呼叫格式（Skills 已示範用文字描述 + 通用命令列的另一條路）；④ 規定提示詞與工具定義必須放在上下文開頭（Skills 與動態工具發現已在中途或末尾載入） |

## 15. 本章重點整理

1. **Agent = LLM + 上下文 + 工具 = 大腦 + 眼睛 + 手腳**，對應策略、觀察、行動；公式不包含 Environment。
2. **模型固定時，擴展觀察與動作空間是最大的能力槓桿**——Manus 取三類 Agent 介面的聯集，OpenClaw 延伸到使用者的數位生活。
3. 上下文 = **靜態字首**（系統提示詞 + 工具定義）+ **軌跡**；消融實驗顯示元件不等價，且失敗往往是看似完美的錯誤答案。
4. **ReAct**：思考→行動→觀察的迴圈；RL 內化的是**決策**而不是工具執行，編排迴圈不會消失。
5. **Agent = Model + Harness**；Harness = 上下文 + 工具 + **約束 + 驗證 + 糾正**；生產重心在後三者，Harness 是核心競爭力。
6. 範式層層包含：提示 ⊂ 上下文 ⊂ Harness ⊂ Loop（⊂ Graph）工程。
7. 對 Harness 的立場：**方向認同苦澀的教訓、節奏務實**；適配層會被模型內化。
8. 編排：**單次呼叫 → 工作流 → 自主 Agent**，可混合；"Less structure, more intelligence"。
9. **三層護欄**：上下文層、執行層、資料層，依被繞過的難度排序；同一上下文無法自證未被注入。
10. **五個設計模式**：提議者—審核者、漸進式披露、只增不改、邊界集 + 保留集、最小 diff + 可回滾。

> **一句話**：Agent 就是「大腦 + 眼睛 + 手腳」在迴圈中與世界互動；真正決定它能不能上線的，是包在模型外面、負責約束、驗證與糾正的那層 Harness。
