# 第 9 章　Agent 的持續進化

> 《深入理解 AI Agent》— 李博杰，第九章

---

## 1. 本章定位：能力悖論

> 今天的 Agent 能**零樣本**解決從未見過的複雜任務，卻可能在處理了一萬次相似任務之後，**隔天仍犯第一天的錯誤**。

- **持續學習**（continual learning）：能否自主從經驗中學習——正成為 Agent 從「會完成任務」走向「能夠可靠工作」的關鍵，也是下一代模型的核心研究課題。
- 與早年「學新任務就忘舊任務」的持續學習研究**不是同一個問題**：遺忘只是子問題，更難的是**沒有人告訴模型今天的經歷裡哪些做對、哪些做錯**。模型本身的持續學習能力目前仍遠遠不足。

**為什麼會這樣？**
- 部署後的模型不會因一次推理就改參數；第二章的上下文學習只在**目前任務內**適應，上下文結束就消失。
- ⭐ **保存經歷 ≠ 從經歷中學習**：把一百條軌跡放進長上下文或向量庫，可以找回案例，卻**不會自動完成跨案例比較**——哪些步驟在成功軌跡中反覆出現？哪些做法只在舊版介面有效？某次成功是正確策略還是環境偶然？學習發生在系統主動完成「**評價、對照、歸納、驗證**」之後，而不是日誌寫入磁碟的那一刻。

| | 第三章 使用者記憶 | 第九章 經驗學習 |
|---|---|---|
| 沉澱什麼 | 「使用者與世界是什麼樣子」 | 「**在什麼條件下應該如何行動**」 |
| 讓 Agent | 記得更多 | **從聰明變得熟練** |

**為什麼不讓模型每次任務後直接訓練自己？**
- 生產環境很少提供乾淨的學習訊號——**使用者滿意 ≠ 合規**；
- 局部參數更新可能造成遺忘、策略漂移、安全退化；
- 依未驗證的回饋直接改參數 → **錯誤經驗與提示注入被固化並放大**；
- 基礎模型的週期性訓練提升通用能力，卻無法及時吸收每個 Agent 每天遇到的私有規則、工具變化與局部經驗。

> ⭐ **持續進化**（本書用語，區別於權重層面的持續學習）：在模型自身尚無法可靠持續學習時，先把「學習」建構為**模型外圍的一套自主系統**——記錄執行證據、驗證結果與過程、從多條軌跡提取共通性，再決定更新知識、指令、程式或參數。所有修改先形成**候選版本**，經迴歸測試與安全檢查才改變下一輪執行。

**需要的元件早已就位**：第二章任務內狀態、第三章知識基礎設施、第五章創造工具與修改系統的後設能力、第七章評估與驗證、第八章更新參數 → 第九章把它們組織成閉環。

> 全書定位：本章建的是第一章發現迴圈中的**實驗與回饋**段——提案已經有了，問題是怎樣用一次紮根真實觀測的實驗判斷它有沒有讓系統變好，並把結果送回下一輪。

## 2. 從執行軌跡中取得學習訊號 ⭐⭐⭐

> 起點是第七章的評估。如果系統不知道任務是否完成、哪一步造成成敗，模型產生的「反思」只能是一種猜測。

### 2.1 三層軌跡驗證

| 層 | 回答 | 證據 | 判定方式 |
|---|---|---|---|
| **結果驗證器**（底層，最優先建立） | 事情是否真的辦成 | 測試結果、資料庫狀態、工具回傳；Coding 跑測試與型別檢查，退款 Agent 查訂單狀態與實際退款金額 | 程式碼 |
| **過程驗證器**（中層） | 是否以**允許的方式**辦成 | 政策庫、權限表、動作軌跡。刪除失敗測試也能讓測試通過；口頭承諾「7 天內退款」也能暫時換來滿意 | 程式碼 |
| **品質驗證器**（上層） | 是否讓使用者舒服 | 耐心、合規替代方案、證據掌握、自然精簡 | LLM-as-a-Judge + Rubric（逐項評分並引用軌跡證據） |

### 2.2 客服 Agent 的七個評價面向（表 9-1）

| 面向 | 驗證問題 | 主要證據 | 層 |
|---|---|---|---|
| 任務結果 | 核心訴求是否解決 | 最終環境狀態、工具結果 | 結果 |
| 規則遵循 | 是否違反政策、權限、必要流程 | 政策庫、動作軌跡 | 過程 |
| 隱私邊界 | 是否洩漏不應提供的資訊 | 回覆文字、資料存取紀錄 | 過程 |
| 事實可靠性 | 陳述是否有知識或工具結果支持 | 引用來源、工具回傳 | 跨兩層（可比對部分程式驗，其餘 Rubric） |
| **承諾—行動一致性** | 聲稱完成的操作是否真實發生 | 回覆與工具日誌對照 | 過程 |
| 表達品質 | 自然、精簡，避免重複與樣板化 | 對話全文、語言 Rubric | 品質 |
| 合規變通 | 原方案不可行時是否找到允許的替代路徑 | 使用者目標、政策與後續動作 | 品質 |

### 2.3 驗證器的輸出形態決定它能否成為「學習訊號」

單一總分只反映優劣，無法指出該改哪裡。可供學習的評價至少包含四項：

1. 任務**成功 / 部分成功 / 失敗**；
2. **每個面向**各自的結論；
3. 每條結論對應的**證據位置**（哪一輪對話、哪一次工具呼叫）；
4. **失敗的類型標籤**。

> ⭐ **驗證器應被允許在證據不足時拒絕評分**——與其把低信心結論當作事實固化下來，不如把該案例排除在學習集之外。

> **實驗 9-1 ★★ 為客服 Agent 建構軌跡驗證器**：對照「只輸出一個總分」與「逐維度輸出結論、證據與置信度」，看哪種更能區分任務失敗、規則違規、虛假承諾、表達問題。只有保留「**哪裡錯、為什麼錯、證據在哪裡**」，後續模組才知道該更新知識、Prompt、程式還是參數；低置信度案例不自動進入學習集。

> 對照第七章：失敗歸因的「首錯步號 + 類別 + 證據」在這裡變成了學習系統的輸入格式。

## 3. 持續進化的四種方法 ⭐⭐⭐

> 學習訊號說明 Agent **應該**改變，卻沒說改變應發生在**哪裡**。選擇更新方式的首要依據不是經驗出現了多久，而是**目標能力能否由某種載體自然表達**。

**表 9-2　四種方式的適用邊界**

| 更新方式 | 適合承載 | 主要優勢 | 主要限制 |
|---|---|---|---|
| **經驗知識庫** | 事實、經驗規律、例外與來源 | 更新快、可追溯、可隨需檢索 | 依賴檢索與模型正確套用 |
| **Prompt 與 Skill** | 可語言化的判斷原則與操作規範 | 可解釋、作用範圍可控 | 容易膨脹、衝突或被忽略 |
| **程式與 Harness** | 確定性流程、工具與強約束 | 可測試、執行穩定、成本低 | 開發與維護成本較高 |
| **模型參數** | 高維度感知、生成風格與隱式策略 | 泛化強、推理成本低 | 更新與迴歸成本高 |

- 四者**不互斥**：醫療影像 Agent 靠參數辨識病灶、知識庫提供最新指引、程式碼計算風險指標；客服的自然語氣來自後訓練、企業政策由知識與 Skill 提供、關鍵合規由伺服器端程式碼把關。
- 同一能力可以**拆到多個載體**：事實 → 知識庫；解釋例外的原則 → Skill；不可繞過的權限 → 程式門控；高維識別 → 參數。
- **路由結果只是更新提案，尚未獲得發布資格。**

> 對照第八章 §16.1：同一張「能力能否被外部符號充分表達」的判準表，第八章從參數角度看，這裡從四種載體平行看。

## 4. 方法一：將經驗沉澱為知識 ⭐⭐

| | 第三章 知識 | 第九章 經驗知識 |
|---|---|---|
| 來源 | 使用者對話、文件、資料集 | **Agent 的行動軌跡與結果** |
| 例子 | 「該航空公司要求特殊餐點提前二十四小時預訂」（領域知識） | 「**訂票前先檢查特殊餐點截止時間**，避免付款後才發現無法滿足」（行動經驗） |

**原始軌跡不適合作為正式知識單元**（長、嘈雜、含工具原始輸出、偶然繞路、環境細節）。三層資料：

```
不可變的原始軌跡（稽核）
   → 單次執行分析記錄（本次成敗與候選教訓）
      → 多條同類軌跡比較、分群、歸納 → 面向未來的 Markdown 知識文件
         （適用場景、建議策略、禁止做法、例外條件、證據來源、最近驗證時間）
```

- 與第三章 **User as Code** 相同的兩階段思維：先把事實附加到不可變日誌，再週期性重建結構化模型 → **把記錄與整理分開**，避免一次偶發成功或網路故障立即改變 Agent，也讓系統能在看過多條成敗軌跡後再判斷共通性。
- **經驗文件不是單純的軌跡摘要**：真正具遷移價值的內容來自**對照**——成功軌跡做了什麼、失敗軌跡缺少什麼；某策略在哪些環境版本有效、在哪些前置條件下失效。

**五步提煉管線**：

| # | 步驟 |
|---|---|
| 1 | 保存不可變的軌跡與環境結果 |
| 2 | 單次執行的結構化分析：任務類型、所需能力、觀察到的策略、錯誤與例外 |
| 3 | 按任務家族聚合，為每條候選規律建「**哪些軌跡支持、哪些軌跡反駁**」的**證據表** |
| 4 | 只有達到支持門檻的候選才寫入正式文件 |
| 5 | 在**未參與提煉的新任務**上測試遷移效果 |

正式知識與候選分析**分庫存放** → 可重新歸納而不竄改原始證據，環境版本變化時能**精確撤銷某條結論**。

**GAIA + AWorld 案例**（前者像考卷，後者像考場與實驗紀錄系統）：
- 舊做法：一次成功後立刻產生策略摘要、向量化入庫。
- 更嚴謹：先用 GAIA 答案驗證器標記成功/部分成功/失敗，再比較同一任務家族的多條路徑——**成功軌跡貢獻候選策略、失敗軌跡貢獻排除性知識、部分成功軌跡協助辨識「哪一段有效、哪一段仍有問題」**。
- **Reflexion** 的自然語言反思可以參與產生候選教訓，但**反思本身不是證據**；只有與環境結果相符、獲得跨軌跡支持、在新任務上展現正向遷移的內容才進入正式文件。

> 呼應第三章 §15「知識更新當 PR」：三層分離（證據 / 知識 / 服務）在經驗學習中同樣適用。

## 5. 方法二：將經驗寫成指令 ⭐⭐⭐

> 知識庫給「**可以參考的資料**」；Prompt 與 Skill 規定「**應該怎樣行動**」。只有當多條相似軌跡反覆暴露同一種策略錯誤，且錯誤能用語言清楚描述時，才值得提升為指令。

| 概念 | 作用範圍 |
|---|---|
| **系統 Prompt** | 對所有任務生效 |
| **Skill** | 匹配到某個領域或工具時按需載入 |
| **程式／Harness** | 權限與其他硬約束 |

**相關方法**：
- **Karpathy 的「系統提示學習」**（System Prompt Learning）：模型遇到問題後，用一句清楚的話提醒未來的自己。
- **DSPy**：在開發集上搜尋指令與範例；**OPRO**：根據歷史提示及其得分提出提案；**GEPA**：從失敗軌跡的自然語言反思中生成並篩選提案。
- 這些適合離線批次最佳化；生產環境更適合**可稽核的最小更新提案** + 快速回滾。

> 與第二章提示工程的區別：第二章討論怎樣組織一份好 Prompt；本節討論**什麼回饋足以觸發修改、更新提案怎樣安全發布**。修改應是**帶來源的最小 diff**，而不是每次重寫整份 Prompt（第一章命名的「最小 diff + 可回滾」模式）。待驗證版本必須同時在**觸發失敗的邊界集**（要改善）與**正常工作的保留集**（不能退化）上測試。

### 5.1 例子一：轉接邊界的規則化（τ²-bench telecom）

- 政策只有兩條原則：請求超出動作範圍才轉接；轉接前應先盡力解決。強模型下沒問題；換**弱模型**後缺陷暴露——工具報錯後反覆重試、最終轉接人工，**提煉集 20 條中 19 條如此結束**。
- 把 19 條失敗軌跡交給模型自行歸納 → 若干條可執行規則追加到政策末尾 → 在未參與提煉的任務上：**通過率 12.3% → 19.3%，原本通過的任務無一被改壞**。

**四個觀察**：

| 觀察 | 內容 |
|---|---|
| **提煉材料決定能歸納出什麼** | 只給失敗摘要與錯誤文字 → 「同一工具反覆報錯即不應繼續呼叫」（**教訓**）；補上 Agent 與使用者各自的工具清單 → 「網路狀態、SIM 卡、APN 屬於使用者裝置側，應引導使用者自行操作」（**職責歸屬**） |
| **模型會把觀察到的行為當作應然的行為** | 第一版規則有「連續三次失敗即轉接人工」「使用者兩次未提供號碼即轉接人工」——軌跡中最頻繁的就是轉接人工，模型便視為合理兜底；但在這套評估中轉接必然判失敗 → **把失敗寫進了規範**。→ 提煉產物須經**與提煉者相互獨立的驗證** |
| **被修復的往往是極樸素的缺陷** | Agent 需要使用者的電話號碼，卻把「**請您提供您的電話號碼**」填進查詢工具參數，連續五次報錯後轉接——**它已經判斷出應當詢問使用者，卻把這句話說給了工具**。規則生效後先在對話中問、拿到號碼再查；查 SIM 卡被工具拒絕 → 引導使用者重新插拔 SIM 卡 → 通過 |
| **行為指標佐證** | 越界呼叫使用者側工具次數、參數缺失即發出的呼叫次數**均下降約八成** → 通過率提升來自規則修復了具體動作 |

> **實驗 9-2 ★★ 從 τ²-bench 失敗軌跡提煉轉接與工具使用規則**：提煉集與遷移集在上游倉庫本就互不相交；規則由模型歸納而非人工撰寫；三臂（原始 / 兩個進化版本）只替換策略檔案，使用者模擬器不變；除通過率外記錄轉接比例、越界呼叫、參數缺失呼叫。

**移植到航空客服**：使用者對退票費、改簽費、行李政策有異議 → Agent 未查政策、未解釋、未找合規替代就 `transfer_to_human`。正確邊界：**一般政策爭議無須轉接，只有使用者明確要求人工或出現安全相關情形才必須轉接**。

> **實驗 9-3 ★★ 基於失敗軌跡最佳化航空客服 Prompt**：從失敗軌跡提取規則遵從、任務解決、合規變通三維，生成一條帶來源的最小 Prompt 補丁，與初始版本、人工調優版本對照；邊界案例改善 + 舊任務不退化 + 過發布門檻才灰度。重點：**不是讓模型自由改寫一大段文字，而是把可歸因的失敗轉成作用域明確、可回滾、可驗證的局部規則**。

### 5.2 例子二：需求澄清 Skill——從「直接開工」到「先確認再執行」

- 「把登入頁改成支援企業登入」——立刻開工會替使用者在身分提供商、回退方式、相容舊使用者、上線範圍上做出他沒考慮過的選擇；但每個任務都先問十幾個問題又把簡單修改變成訪談。

> **問得太少會導致返工，問得太多會增加打擾。** Skill 要表達的不是「所有任務都必須確認」，而是一條**帶作用域的判斷路徑**。

**初版流程**：判斷歧義程度、風險、返工成本 → 低風險易撤銷的小改動「**說明假設後直接執行**」→ 涉及架構、資料、權限、公開介面、大範圍改動則**集中提出少量真正會改變方案的問題** → 生成短 Spec/Plan（目標、非目標、關鍵取捨、假設、驗收標準）給使用者確認 → 確認後執行；過程中發現 Spec 不成立就暫停重新確認。

**持續進化從執行證據開始**：
- 記錄任務、澄清問題、Spec 版本、使用者修改、執行結果、交付後返工。
- 負回饋可能是「做出來的和我想的不一樣」，也可能是「**你問得太多了**」；正回饋：一次確認後順利交付、主動改 Spec 後返工減少、低風險任務沒被多餘問題打斷。
- **單獨一句抱怨不足以觸發更新**，必須與具體軌跡、任務型別、結果關聯。
- 多條軌跡指向同一缺口 → 最小 Skill 更新提案：多個認證架構任務在交付後才發現要相容舊登入 → 要求執行前確認「身分提供商、回退路徑、相容範圍」；大量拼寫修復都被先問一輪 → **收窄**高風險與高歧義的觸發範圍。

**對照實驗**：「直接執行」vs.「先提問再執行」vs.「提問後生成 Spec、確認後執行」，按複雜度分層；指標：需求偏差率、返工次數、澄清輪數、首次有效產出時間、使用者放棄率、Spec 被修改比例、高風險操作錯誤率。**減少偏差的同時沒顯著增加打擾**，且在未參與提煉的任務上通過迴歸，才灰度。

**Skill 與 Harness 的邊界**：

| Skill | Harness |
|---|---|
| 理解語境、主動提問、整理 Spec、說明取捨 | 在缺少確認時**否決高風險寫入、直接操作 `main`、繞過發布流程** |
| — | 否決器**不能**替模型決定 PR 怎麼描述，也不能代替模型選需求方案 |

穩定的對話軌跡之後還能生成第八章所需的 SFT/RL 資料。

> **實驗 9-4 ★★ 進化需求澄清與 Spec 確認 Skill**：低風險低歧義組 + 高風險組（架構、權限、資料、公開介面）× 三種流程；Agent 生成 Skill 更新提案，必須經留出任務迴歸、**打擾成本檢查**、高風險否決器驗證。持續進化**不是把每次抱怨直接追加到 Prompt**。

> 對照第五章 §4「需求澄清」與第七章「歧義處理」錯誤類別：同一個問題在三章分別以工作流程、評估類別、可進化 Skill 的形式出現。

## 6. 方法三：將經驗寫成程式 ⭐⭐⭐

> 穩定、重複、可驗證的操作，每次都讓模型重讀文件再推理不經濟 → **編譯為工作流程、工具或 Harness 程式碼，讓一次探索變成可重複執行的程式**。第五章提供修改系統的能力；本章提供**由經驗觸發、受驗證閉環約束的自我修改方法**。

**可修改的對象**：

| 層 | 例子 |
|---|---|
| 操作層 | 瀏覽器軌跡 → 參數化工作流程；變動 API → 轉接器 |
| 控制層 | 工具路由、重試、熔斷、上下文壓縮策略 |
| 驗證層 | 依生產失敗新增參數檢查、狀態驗證器、迴歸測試 |
| 架構層 | 增加 Reviewer Agent、改變規劃與執行之間的資訊流 |

### 6.1 瀏覽器工作流程：從探索到可驗證的小程式

> 類比試算表的**巨集錄製**：第一次發郵件時多模態 Agent 觀察—思考—行動找到「撰寫、收件者、主旨、內文、傳送」；之後只有收件者與內容不同，沒必要再讓模型從像素與 DOM 重新發現整條路徑。

| # | 生命週期 | 要點 |
|---|---|---|
| 1 | **擷取軌跡** | 導覽、點擊、輸入、下拉；動作參數、URL、XPath/CSS/`id`/`role`/`aria-label`/`data-testid` 等定位證據——**定位資訊只用來再次找元素，不能證明任務已完成** |
| 2 | **參數化** | 把 `test@example.com`、主旨、內文識別為 `{recipient}`、`{subject}`、`{content}`；其餘穩定動作不變（教學版用正規表示式；正式系統用結構化任務輸入或受約束的擷取模型） |
| 3 | **定義狀態檢查** | 動作前後檢查（「傳送按鈕可見」「導覽後 URL 屬於目標網站」）+ 整體最終狀態檢查（「**寄件備份中出現新郵件**」）。⚠️ **動作執行成功 ≠ 任務成功**；最終檢查必須讀真實頁面或後端狀態 |
| 4 | **驗證候選** | 首次成功只產生 `candidate`；把沙盒帳號重設到獨立初始狀態再完整重播，全部檢查通過才 `validated`。有副作用且**沒有安全重設回呼**的任務只能保存候選供稽核，**不能為了驗證而在正式帳號重複執行** |
| 5 | **比對與重播** | 依意圖與關鍵字找工作流程、擷取參數、Playwright 直接執行；**不需逐步呼叫 LLM**，但仍等元素可用並完成所有檢查 |
| 6 | **失效與重學** | 找不到元素、檢查失敗、API Schema 改變、最終狀態錯 → 立即停止後續動作，舊版移到 `invalid`，退回完整 Agent 重新探索；舊檔保留供稽核，**不能繼續被靜默命中** |

- **PreAct**（作者論文 arXiv:2606.17929）：這類程式在重複任務上 **8.5–13 倍**端到端加速，重播不逐步呼叫語言模型。
- ⚠️ 流程記憶必須同時具備**動作前驗證、動作後驗證、儲存前獨立驗證**；否則會出現危險假象：**重播覆蓋率 100%，每個按鈕都點過，但某個欄位其實是空的，任務從未完成**。

> **實驗 9-5 ★★★ 從瀏覽器軌跡產生可驗證工作流程**（`browser-use-rpa`）
> - **四階段**：① 完整 Agent 探索「向 `test@example.com` 發主旨『測試郵件』的訊息」→ `candidate`；② `validation_reset` 還原沙盒後獨立完整重播 → 全部檢查通過才入正式能力庫；③ 收件者、主旨、內文都不同的同類任務 → 比對、填參、Playwright 重播，不進逐步 LLM 循環；④ 修改按鈕定位、頁面文字或最終狀態 → 舊工作流程立即 `invalid` 並回傳 `fallback_required=True`。
> - **對照**：簡化基準只統計動作有沒有拋例外；實驗組驗證動作前後頁面與最終狀態；比較「**欄位為空但已點擊傳送**」「**Save 已點擊但資料未寫入**」等假成功場景的誤判率。
> - **驗收**：沒有重設回呼就停在候選區；驗證失敗的版本不可檢索；參數化重播**不得重用首次執行的收件者或內容**；頁面變化後必須停止危險的後續動作。**只有同時滿足這些條件，加速結果才有意義。**

> 呼應第五章「系統介面卡 → RPA」與第六章「Computer Use 世界模型」：同一個想法的三個階段——用 Computer Use 探索、固化為程式、用狀態檢查防止靜默失效。

### 6.2 自我修改 = 可稽核的軟體發布流程

> **Agent 修改自身程式碼，不代表執行中的程序直接覆寫自身。**

```
從穩定版本建立候選分支 → Coding Agent 產生最小修補
  → 靜態檢查 → 單元測試 → 安全掃描 → 失敗軌跡重播 → 舊任務迴歸
  → 可分階段部署的新版本
```

**可證偽的變更契約**（只有「修補儘量小」不足以可靠歸因）：
- 失敗證據、推斷根因、歸屬的 Harness 元件、候選修改；
- **預期修復的行為** + **可能受損的既有行為** + 分別驗證兩者的案例。
- **Agentic Harness Engineering**（AHE）的三層可觀測性：**元件**（可編輯元件都有檔案層級表示）、**經驗**（大量軌跡先整理為可逐層下鑽的證據）、**決策**（每次編輯**執行前聲明影響預測**，下一輪結果驗證）→ 分數上升才能與具體機制建立關聯，而不是一次無法解釋的試錯。

**候選產生器的輸入不應只有失敗案例**（**Self-Harness**）：
- **必須保留的成功行為**——告訴 Agent 修復時不能破壞什麼；
- **先前遭拒的修改記錄**——避免換一種說法重複提交已失敗的方案。
- 失敗證據 + 成功約束 + 歷史嘗試 = 一個**有邊界的候選空間**，比把全部原始碼與日誌一股腦塞給修改 Agent 更容易產生局部、可驗證的變更。

> 對照 Ferguson《Cryptography Engineering》：「提交前先寫下你預期的安全屬性與威脅」——可證偽的變更契約就是把「預期效果」寫在動手之前，讓結果可以反駁它。

**工具創造也遵循相同協定——Alita 案例**：要從一段由《魔戒》咕嚕配音演員解說的 YouTube 360 VR 影片中，找出恐龍首次出現後緊接著提到的數字 → 發現缺字幕讀取能力 → 搜尋並測試 `youtube-transcript-api` → 封裝為字幕工具 → 答案 `100000000`。**只有安全掃描、功能測試與後續任務重複使用都通過，新工具才進入能力庫。**

| 章 | 關心 |
|---|---|
| 第四章 主動工具發現 | 既有工具中哪個適合 |
| 第五章 | 如何編寫工具 |
| **第九章** | **什麼執行證據觸發創造，新工具如何成為經過驗證的長期能力** |

> **實驗 9-6 ★★★ 由失敗軌跡觸發 Agent 自我修改**（`self-modifying-agent`）
> - 輸入：多條「`retryable=false` 的錯誤仍被連續呼叫」軌跡。
> - **流程**：診斷模組聚合不同任務中的相同故障，**達到跨軌跡支持門檻**才建修改請求，定位到穩定版本的 `retry_policy.py` → 候選產生器讀取失敗診斷、**需保留的暫時性故障恢復行為**、先前遭拒的修改、穩定原始碼 → **先提交影響預測**（「不可重試錯誤呼叫次數應下降、暫時逾時恢復率不應下降」）再輸出最小 diff → 只能寫入**隔離候選目錄** → 驗證 Harness 編譯、重播原始失敗、檢查不可重試錯誤立即停止並開啟熔斷器、再測暫時逾時仍按原門檻重試。
> - **診斷對照**：「只在 Prompt 加一句不要重複呼叫」是**修改層級錯誤**——可確定執行的重試約束應進程式。
> - **驗收**：全部通過只產生 `release_to_canary`；任一失敗 → `reject_candidate`。`release_manifest.json` 記錄失敗叢集、來源軌跡、根因、目標元件與檔案、diff、預期修復、潛在退化、檢查結果、候選與**回滾版本**；遭拒候選也保留失敗原因。**產生修補的 Agent 不能修改穩定程式碼、驗證器、稽核日誌或批准自身發布的門檻。**

> **實驗 9-7 ★★ 由使用者回饋觸發高風險操作確認門**（`harness-safety-gate`）：只有多條使用者糾正、負評、事後稽核都指向「高風險操作未確認」才建修改請求；分類器依工具名與參數辨識危險刪除、`git push --force` 等；**一次性確認權杖綁定具體操作和參數**；候選須過 AST/靜態檢查、含**偽造與重用權杖**的邊界重播、保留集重播。結果：真實 `gpt-4o-mini` 候選未通過未完成任務、正常操作、一次性權杖檢查，**被安全門拒絕**；決定性候選通過並進入 `release_to_canary`。

> 對照 Ferguson《Cryptography Engineering》：一次性權杖綁定「操作 + 參數」並測試偽造與重放——就是 nonce 與 MAC 綁定訊息內容的同一原理。

### 6.3 案例：DeepSeek Harness（`dsh`）一切皆外掛

- 第一章把 `dsh` 歸為「Agent 自進化框架」。其底座 **Cordis** 論文：傳統組合是**靜態**的（函式呼叫、模組匯入、類別繼承在編譯期確定）；外掛系統與自進化 Harness 需要**動態組合**（執行中裝入、卸下、重新配置）。**Agent 的每一次自我修改，本質上都是一次動態組合。**

| 維度 | 問題 | 關心 |
|---|---|---|
| **時間可組合性** | 元件被移除時，它對共享環境的修改能否被完整、安全地撤銷？（追蹤每次資源配置、事件註冊、狀態變更） | **改了什麼** |
| **空間可組合性** | 元件能否結構化、可驗證地宣告、發現、解析彼此的依賴，並在依賴變化時協調生命週期？ | **依賴什麼** |

- 缺時間可組合性 → 每次自我修改都要**整體重啟**，丟掉程序內累積狀態，進行中任務反覆被打斷；缺空間可組合性 → 模組只能用臨時手段察覺依賴變化，一次簡單替換可能**靜默破壞依賴方或引入迴圈依賴**。
- **Cordis 的思路**：把編譯期概念提升到執行期——
  - 效果系統 → **可撤銷效果**：每次上下文變換攜帶明確的逆操作，元件移除時上下文隨之恢復；
  - 協效果（coeffect）系統 → **反應式協效果**：元件把需要的依賴宣告成規格，上下文每次變化都按規格通知它啟用、失效或無關；
  - 再用動態組合演算推廣到交錯的元件系統——**可組合性必須是可傳遞的**。

> ⭐ **自我進化的上限，不取決於模型能寫出多好的程式碼，而取決於承載它的系統有多可組合。** 所以 `dsh` 讓模型適配器、工具登錄檔、工作階段日誌乃至 Agent 主迴圈本身都是外掛——**不存在一個只能由人類維護的特權核心**。

- 但可組合性解決「能不能安全地裝卸」，**沒解決「該不該裝」**：模型寫出的外掛只活在程序記憶體裡，重啟即消失，**不能被自動提升為正式外掛**，要留下來必須走 worktree + Pull Request 那條更慢的路。
- 進化也有代價：執行中的外掛改變模型可見的工具集與提示片段 → 請求前綴一變，**KV Cache 從變化處失效** → `dsh` 外掛文件要專門描述對上下文與 KV Cache 的影響。

> 對照 Hanson《C Interfaces and Implementations》：介面與實作分離 + 資源的配對釋放（`Mem_alloc`/`Mem_free`、`Except` 的清理）——Cordis 的「可撤銷效果」就是把「每次配置都有對應的釋放」提升為執行期由環境追蹤的保證；「反應式協效果」則是把介面依賴從編譯期的 `#include` 變成執行期可協商的規格。

## 7. 方法四：將經驗寫入參數 ⭐⭐

- 知識、指令、程式都假設目標能力**能被外部符號較完整地表達**；醫療影像理解、自然語音韻律、**消除文字中樣板化的「AI 味」**、長程規劃等很難壓縮成規則或流程 → 後訓練寫入參數。
- **是否參數化不單由「任務是否長期穩定」決定**：新影像設備帶來的領域偏移仍可能需要 LoRA 或持續微調；快速變化的語言風格可用週期性偏好訓練。**穩定性影響更新頻率與成本，能力的表示性質決定主要載體。** 反之，長期穩定的轉帳審批規則也不應只靠參數記憶。
- 關鍵是把經評價的生產軌跡轉成訓練資料：高品質示範 → SFT；明確偏好 → 成對資料；可靠環境獎勵 → RL。訓練前去隱私、濾錯誤軌跡、保留獨立迴歸集；訓練後檢查通用能力與安全對齊是否遺忘。（細節見第八章 §15 表 8-5。）

## 8. 從更新產物到更新「更新方法」 ⭐⭐⭐

四種方法回答經驗**寫到哪裡**；另一條**正交軸**：最佳化的是某份產物的**內容**，還是**產生、管理、驗證這些產物的方法**（Lilian Weng, *Harness Engineering for Self-Improvement*）：

```
單條規則或記憶 → 結構化上下文 → 工作流程 → Harness 程式碼 → 產生候選方案的最佳化器程式碼
                         （五種搜尋尺度，不是五種新載體）
```

| 層 | 代表 | 要點 |
|---|---|---|
| **只改產物內容**（預設選擇） | 系統提示加一條局部規則；經驗文件補一個例外 | 範圍小、易歸因與回滾。⚠️ **反覆讓模型重寫整份 Prompt 或記憶會退化**：為求簡潔，少數重要細節在多輪改寫後逐漸消失；彼此制約的條件被合併成一句過度抽象的原則 |
| — | **ACE**（Agentic Context Engineering） | 上下文維護成**帶穩定識別碼的條目集合**；生成、反思、整理模組提**增量更新**，再以**確定性邏輯合併與去重**——而不是每輪重寫一個越來越短的文字區塊。為「最小 diff、保留來源」提供具體案例 |
| **改「上下文如何被建構」** | **MCE**（Meta Context Engineering） | 內層：在給定管理方法下最佳化當前任務的上下文產物；外層：依多輪執行與驗證結果，修改**搜尋、選擇、過濾、格式化**這些操作本身。改一條檢索規則是改內容管理機制；**比較多種機制並保留遷移效果更好的版本**，才是學習「如何管理上下文」 |
| **工作流程** | **AFlow** | 多個 LLM 呼叫組成的工作流程表示為**程式碼圖**，透過執行回饋搜尋節點與控制流程的組合 |
| **整個 Harness** | **Meta-Harness** | Coding Agent 讀候選 Harness 的**原始碼、分數、軌跡**，搜尋決定資訊如何儲存、檢索、呈現的程式碼 → 程式碼不只是一次生成的產物，**連同評估歷史一起成為持續搜尋的對象** |

> 對照第二章「壓縮的反面」：ACE 的教訓與「上下文壓縮會丟失關鍵資訊」同源——**有損的重寫會一代代累積損失**；穩定 ID + 增量 diff 才能保住細節。

### 8.1 回饋成本問題與 Dream-RSI

- 外層搜尋的探索策略決定：從哪個候選繼續、何時另開分支、並行投入多少 Worker、何時停止——好壞要經很長的生成—評估鏈才顯現。若每個候選策略都重新呼叫 Agent 和評估器，**最佳化探索策略本身可能比完成任務更昂貴**。
- **Dream-RSI**：把已完成的發現過程存為**發現樹**，當作經驗性的**回放模擬器**（replay simulator）：
  - 根節點 = 初始工作區；每個子節點存從某歷史狀態繼續嘗試後的**工作區快照、候選產物、評估診斷、分數**；
  - 候選策略透過**與線上相同的介面**逐步選擇要展開的葉節點或從根開新分支；回放器只揭示已記錄的結果，不必再跑底層 Agent 與評估器；
  - **只逐步揭示當前已展開的子樹** → 候選策略能比較分支、順序、並行批次、停止時機，**又不能偷看線上決策時尚不可見的未來結果**。

```
線上探索（當前策略生成新發現樹）
   → 構造回放世界（樹加入歷史模擬器池）
      → 離線做夢（策略開發 Agent 修改探索策略程式碼，按品質、成本、並行效率比較）
         → 入選策略重新上線 → 產生新樹 → 擴大下一輪可回放的範圍
```

- 候選集合保留當前策略 → 新版本**至少不會在已有歷史的平均回放分數上更差——但這只是歷史內的保證**。

**三種歷史重用的區別**：

| 方式 | 改變 Agent 的 |
|---|---|
| 軌跡總結成知識或 Prompt | **知道什麼** |
| 瀏覽器工作流回放 | **怎樣重複執行** |
| 發現樹回放 | **怎樣組織探索** |

> 發現樹回放**不是能預測任意動作後果的完整世界模型**，只能重組歷史中實際走過的分支，不能保證在舊樹上得分更高的策略能遷移到新任務。它不是第五種更新載體，而是一種**產生並驗證更新提案的新機制**——產物仍屬程式/Harness，新意在於把歷史**變成可反覆互動的離線評估環境**，把自我進化推進到「**如何分配探索計算**」的元策略層。

> 呼應第六章：世界模型讓 Computer Use「推測執行」；Dream-RSI 讓探索策略在「歷史世界模型」中推測執行——但支援域僅限走過的分支。

> **實驗 9-8 ★★★ 把這本書交給 Hermes：它能升級自己嗎？**（構想由讀者 Grace 貢獻）
> - 不預設待修問題、不提供功能清單；只給**本書十章正文 + Hermes 原始碼**，要求先理解原則、再檢視自身實作、**自主選擇**一項值得做的改進。
> - 穩定版本、獨立 Reviewer、驗收測試**位於 Hermes 的修改權限之外**；必須完成「閱讀 → 對照 → 選題 → 修改 → 驗證」；被退回時審查意見只作下一輪學習訊號，不能繞過門檻宣告成功。
> - **實際執行**：Hermes 自主發現現有執行軌跡缺少**可直接供後續學習使用的結構化證據**（正是本章 §2 的主題）→ 選擇把執行結果整理為保守的學習訊號，親自改原始碼並補測試；前三輪獨立審查分別發現候選與真實資料格式、不同保存路徑、計數語義的不一致；每次回到原會話繼續修正，**第四輪才被接受**。
> - **結論邊界**：證明 Agent 能從長篇知識提煉原則、映射到自身程式碼、在外部驗證約束下完成一次自我更新；**不證明這項更新已提升下游任務成功率**——那需要單獨的消融實驗。

## 9. 建構可長期執行的持續進化閉環 ⭐⭐⭐

### 9.1 雙循環結構

```
┌─ 線上執行循環 ────────────────────────┐
│ 只負責完成任務 + 記錄證據；不直接改寫正式 Agent │
└──────────────┬───────────────────────┘
               │ 版本化的經驗庫與評估集
┌──────────────▼───────────────────────┐
│ 離線進化循環                             │
│ 彙整軌跡 → 診斷根因 → 產生候選 → 驗證門檻 → 發布新版本 │
└───────────────────────────────────────┘
```

### 9.2 Voyager：完整持續進化循環的範例

Minecraft 中依據目前能力選新目標 → 環境回饋反覆修改程式 → 驗證成功存入技能庫 → 組合舊技能解更難任務。

| 機制 | 作用 | 缺了會怎樣 |
|---|---|---|
| **自動課程生成器** | 依目前物品、環境、已掌握技能提出難度適中的下一個目標 | 不知道下一步該學什麼（探索變隨機漫遊） |
| **技能庫** | 成功程式存為可檢索、可組合的程式碼（高階採集技能可呼叫移動與製作等基礎技能） | 每次任務仍要從頭開始 |
| **迭代提示機制** | 把環境觀察、執行錯誤、自我驗證結果帶回下一輪生成，直到真正通過 | 只有自我反思而沒有環境驗證 → 技能庫累積錯誤 |

### 9.3 發現迴圈：假設、實驗、評估、回饋

- Voyager 遵循的正是由**假設、實驗、評估、回饋**構成的發現迴圈——數百年沉澱的**科學方法論**。
- **Discovery Loop**（Jeff Dean、Sanjay Ghemawat、Quoc Le、Oriol Vinyals 於 2026-08-05 創立的公益公司）：自動化完整實驗迴圈、把原本序列的實驗大規模平行化——本質上是 Agent 自我進化在科學領域的應用。
- **要避免自說自話、自我評價良好，就必須遵從科學方法論。**

> 全書的發現迴圈分工：第三章建**提案**段、第七章建**證據**段、第九章建**實驗與回饋**段。

### 9.4 Harness 更新能力 ≠ Harness 受益能力 ⭐⭐

| 能力 | 意思 |
|---|---|
| **Harness 更新能力**（harness-updating） | 從軌跡中產生有價值的持久修改 |
| **Harness 受益能力**（harness-benefit） | 任務 Agent 在後續執行中**找到、啟用並正確使用**這些修改 |

- 一個 Skill 可能寫得完全正確，但較弱的任務模型**沒在合適場景載入它**，或**載入後無法長期遵循** → 最終成績看起來「沒有進化」。**不能只用端到端分數反推更新器好壞。** Lin 等人的模型替換實驗：兩種能力與基礎模型能力的關係不同。

**表 9-3　分層評估指標**

| 指標 | 回答 | 主要證據 |
|---|---|---|
| **候選修改有效率** | 更新器是否提出有價值的修改 | 候選在獨立驗證中的接受率與增益 |
| **產物啟用率** | 任務 Agent 是否在正確場景載入新 Skill、記憶、工具 | 檢索、路由、工具呼叫軌跡 |
| **遵循成功率** | 啟用後是否依新規則或流程執行 | 動作序列與過程驗證器 |
| **保留任務集增益** | 是否改善了未參與進化的任務（泛化） | 保留集成功率、品質、成本 |

> 對照第七章 §8「取得資訊 ≠ 用對資訊」：同一個區分在進化層面重現——**寫出來 ≠ 載入 ≠ 遵循 ≠ 有用**。

**長期評價的五類結果**：
- **迴歸**：新經驗是否與既有經驗衝突、原能通過的案例是否退化；
- **泛化**：在測試集未涵蓋的場景中的提升；
- **Token 效率**；
- **安全性**：規則、隱私、拒絕邊界是否隨進化漂移；
- **長期工程品質**：維護複雜度、架構一致性、所有權邊界、向後相容、未來遷移與除錯負擔。

> **只解決目前失敗案例的問題，卻在其他既有案例或新領域中退化，不能算是成功的持續進化。**

> **實驗 9-9 ★★★ 評估 Agent 是否持續進化**（`self-evolution-eval`）
> - 目的：區分「**會保存一次回饋**」「**只會不斷附加**」「**能夠更新、遷移並保留能力**」——避免用重複執行同一批題目冒充持續進化。
> - **四階段任務流**（14 題順序）：
>
> | 階段 | 內容 |
> |---|---|
> | 學習 | 退款、身分驗證、行李政策等具共通潛在規律的任務 |
> | 遷移 | 改變表述、使用者、局部環境 |
> | 規則變化 | 行李上限 **20kg → 23kg**，要求替換或淘汰舊知識 |
> | 保留 | 重測沒變的能力與目前有效規則，衡量是否遺忘 |
>
> - 每個帶回饋的任務**結束後**才允許更新外部記憶；當前題目的預期動作不能提前洩漏；**由模型外 Harness 計算結果**。
> - **對照組**：`static`（不持久化）、`append_only`（記得第一版規則，卻不處理衝突或淘汰）、`evolving`（保存版本並以新證據替換舊規則）；`--profile llm` 讓真實 LLM 經歷相同任務流。
> - **指標**：逐階段準確率與學習曲線、遷移準確率、**收到新規則後恢復正確所需的任務數**、舊能力保留率、**負向遷移率**、安全 Rubric 通過率、Token/延遲/儲存成本；用 Prompt/Skill/Harness 更新的系統還要分別記錄候選修改有效率、產物啟用率、遵循成功率。
> - **即使最終準確率較高，只要仍引用已廢止規則、依靠違規捷徑完成任務，或更新後遺忘原有能力，都不能判定為持續進化。**

## 10. 可驗證閉環的邊界：當「完成」不等於「進步」 ⭐⭐

- 閉環在 Coding、工具呼叫、業務狀態變更上最容易成立（測試、環境狀態、確定性規則快速回饋）。
- 開放式科研、策略規劃、複雜產品設計：訊號來得慢、正確答案不唯一，真正重要的目標——**研究品味、長期價值、可維護性**——難以寫成即時分數 → Harness 可能把流程執行得非常完整，卻只是穩定產出「**看起來像成果的東西**」。

**自動科研的壓力測試**（Trehan & Chopra, *Why LLMs Aren't Scientists Yet*）：四次從研究想法到論文的端到端嘗試，**三次在實作或評估階段失敗**，只有一次完成全程。

| 問題 | 表現 |
|---|---|
| **實作漂移** | 原方案一變難，Agent 逐漸退回訓練資料中較熟悉、但已偏離研究假設的一般實作 |
| **認識論上的過度樂觀** | 訊號可能仍只是雜訊，系統卻開始解釋結果、增加修補、宣告發現；**失敗與陰性結果更容易被忽略** |
| **隱性判斷力不足** | 能跑實驗，卻不知道哪些基準真正重要、哪個異常值得追查、何時應放棄假設 |

**不能只靠換一個更會寫論文的模型，而要改變證據與監督結構**：

| 做法 | 說明 |
|---|---|
| **結論與證據分離** | 對引用、數字、方法、結論分別記錄證據來源，最終文件只是**證據圖的一種呈現**（ScientistOne 的 Chain-of-Evidence；提高可追溯性，但不自動保證問題有價值） |
| **保留負面結果** | 失敗實驗、遭拒候選、停止原因寫入不可變日誌，**與成功結果同等可檢索**；否則進化模組只看到倖存方案，反覆探索已證偽的路徑，並學會把模糊結果解讀為成功（**倖存者偏差**） |
| **維持搜尋多樣性** | 不只保留目前最高分的一條鏈；依機制差異、程式碼新穎性、假設類型保留若干**暫時低分但不同質**的分支，避免所有方案收斂成同一個容易得分的範本 |
| **讓人類在更高層介入** | 不只是在危險工具呼叫前按「批准」，而是**定義問題、審查評價標準、解釋反常結果、決定何時停止**——這些高層判斷比逐步接管執行更難自動化、也更有價值 |

> 呼應第七章 §6.2 古德哈特定律與第八章 reward seeking：在回饋模糊的任務裡，「完成流程」最容易被誤當成「推動目標」。

## 11. 持續進化的安全邊界 ⭐⭐⭐

自我進化可能把**一次錯誤變成長期風險**：
- 網頁、郵件、工具輸出中的**提示注入若被總結為經驗**，可能跨會話反覆生效；
- 自動搜尋到的**惡意套件被封裝為工具**，影響從一次沙盒執行擴散到所有後續任務；
- **有缺陷的驗證器**持續批准看似進步、實際退化的候選。

> 自我進化系統除了驗證「是否更強」，還必須限制「**誰能改什麼、依據來自哪裡**」。

| 邊界 | 內容 |
|---|---|
| **一、證據與指令隔離** | 原始網頁與工具輸出是**不可信證據**，不能直接寫入 Skill 等能力；先經 LLM 總結，再以版本控制 + **Pull Request** 提交，經**不同來源的 reviewer LLM** 審閱後才合併 |
| **二、候選能力與正式能力隔離** | 新知識、Prompt、Skill、程式、參數都先進**不能服務真實流量**的候選區；新程式碼與外部相依還要經沙盒、權限檢查、**供應鏈掃描**、行為測試；通過才成為正式能力 |
| **三、安全機制不可自我修改** | 業務 Agent 可以改 Prompt、Skill、知識庫、工具；**不能改批准自身更新的驗證器、測試案例、發布門檻、稽核日誌與穩定版本備份**——否則只需降低門檻或刪除失敗案例，就能把退化偽裝成進步 |

> 對照第三章（Proposer/Reviewer 權限分工）、第五章（信任邊界下移到資料層）、第七章（每個特性可獨立關閉）：**信任根必須在被修改者觸及不到的地方**。
>
> 對照 Ferguson《Cryptography Engineering》：系統的安全取決於「**可信計算基（TCB）**」——讓它盡可能小，且不允許系統的其他部分修改它。

## 12. 睡眠學習：整合、遺忘與能力保鮮 ⭐⭐

「睡眠學習」是對離線整合的**認知類比**，不要求真的在夜間執行。線上 Agent 完成任務並附加不可變證據；背景學習程序在閒置期或滿足門控條件時讀一批新經歷，比較新舊結論、合併重複、解決衝突、提出候選並執行迴歸。

> 把蒐集與整理分開 → 防止一次偶發成功、網路故障或惡意輸入**立即改寫長期能力**；也允許用更大批次、更便宜的模型完成整理。

**五步週期**：

| # | 步驟 | 內容 |
|---|---|---|
| 1 | **觸發** | 時間間隔、新增軌跡數、儲存容量或錯誤頻率達門檻，且當前沒有高優先級線上任務 |
| 2 | **定向** | 讀正式知識、Prompt、Skill 目錄與版本，了解既有能力與**不可修改邊界** |
| 3 | **蒐集與整合** | 從近期已評價軌跡找新訊號，合併重複，標記衝突與適用條件，**優先局部修補** |
| 4 | **驗證與審批** | 在遷移集、保留集、安全集評估候選；高風險寫入等人工核准 |
| 5 | **修剪與索引** | 更新索引；長期不用或被推翻的能力標記為過期、封存或刪除，**保留來源與回復版本** |

**兩個案例**：

| 系統 | 記憶機制 |
|---|---|
| **Claude Code 自動記憶** | 每個專案維護 `MEMORY.md` 索引 + 依主題拆分的詳細檔；會話啟動只載入索引的**有界前綴**，其餘隨需讀取；索引接近上限時要求 Agent **合併或移出細節**。說明純文字記憶也需要容量限制、分層載入、主動整理——但目前主要是**會話中持續寫入**，不能等同於固定的夜間背景任務 |
| **Hermes（Nous Research）** | 有界的 `MEMORY.md` 與 `USER.md` + **SQLite/FTS5** 歷史會話檢索 + 隨需載入的 Skill + 可選外部記憶（Honcho）。歷史檢索**回傳原始訊息而不是先由 LLM 摘要**（避免把檢索與生成混成不可稽核的一步）；任務含較多工具呼叫、從錯誤或死路恢復、收到使用者修正、發現非顯然工作流程時 → **背景復盤**建立或局部修訂 Skill；寫入可經審批門控；獨立的 **Curator** 追蹤 Skill 使用、陳舊、封存狀態，閒置期做確定性修剪並可選 LLM 合併；變更前保存快照，錯誤整理可回滾 |

**持續進化不是無限增長**——第二章的上下文腐化會在更長時間尺度重現：經驗文件互相衝突、Prompt 被邊界規則淹沒、Skill 庫重複、多次微調造成災難性遺忘。週期性離線整理：

- 合併重複經驗，保留來源與版本；
- 把局部規則**從全域 Prompt 移到領域 Skill**，維持全域 Prompt 整潔；
- Prompt 與 Skill 結構清楚，**像一本寫給新進員工的指導手冊**，避免「**99 條軍規**」式的規則羅列；
- 重新驗證長期未使用的工具；
- 刪除被新證據推翻的知識；
- **從原始基座模型重新訓練 LoRA**（而不是在 LoRA 上疊 LoRA）——與第一章三層護欄資料層的道理相同：**真正的保證必須來自被修改者無法觸及的那一層**。

> 呼應第三章 §15.2「定期整理」：去重合併、回到原始資料核查、限定情境——睡眠學習是同一套機制擴展到 Prompt、Skill、工具與參數。

## 13. 設計觀念整理

| 觀念 | 本章體現 |
|---|---|
| **保存 ≠ 學習** | 學習發生在評價、對照、歸納、驗證之後 |
| **持續進化在模型外圍** | 模型尚無法可靠持續學習 → 先建外圍自主系統 |
| **學習訊號要結構化** | 成敗 + 各面向結論 + 證據位置 + 失敗類型；證據不足可拒絕評分 |
| **按表示性質選載體** | 知識 / 指令 / 程式 / 參數；可拆到多個載體 |
| **記錄與整理分開** | 不可變軌跡 → 單次分析 → 跨軌跡歸納；正式與候選分庫 |
| **反思不是證據** | Reflexion 的反思要經環境結果、跨軌跡支持、遷移驗證 |
| **最小 diff、邊界集 + 保留集** | 系統提示學習；轉接規則 12.3% → 19.3% 且無改壞 |
| **提煉材料決定歸納品質** | 加上工具清單才學到職責歸屬 |
| **模型會把常見行為當應然** | 「三次失敗就轉人工」把失敗寫進規範 → 需獨立驗證 |
| **動作成功 ≠ 任務成功** | 工作流程三重驗證；欄位空也能「點過」 |
| **沒有安全重設就不驗證** | 有副作用的工作流程停在候選區 |
| **可證偽的變更契約** | 預期修復 + 可能受損 + 影響預測先於修改 |
| **候選空間要有邊界** | 失敗證據 + 必須保留的成功行為 + 遭拒歷史 |
| **修改層級要對** | 可確定執行的重試約束進程式，而非 Prompt |
| **可組合性決定進化上限** | Cordis：可撤銷效果 + 反應式協效果；沒有特權核心 |
| **增量合併勝過反覆重寫** | ACE 穩定 ID 條目 |
| **最佳化「方法」也是最佳化** | MCE、AFlow、Meta-Harness、Dream-RSI |
| **歷史內保證 ≠ 遷移保證** | 發現樹回放只在支援域內有效 |
| **寫出 ≠ 載入 ≠ 遵循 ≠ 有用** | 候選有效率、啟用率、遵循率、保留集增益 |
| **完成 ≠ 進步** | 自動科研的實作漂移、過度樂觀、判斷力不足 |
| **保留負面結果與多樣性** | 防倖存者偏差與範本收斂 |
| **信任根不可自我修改** | 三道邊界；TCB 越小越好 |
| **進化也要遺忘** | 睡眠學習的修剪與封存；從基座重訓 LoRA |

## 16. 思考題摘要（含書附參考答案要點）

| # | 題目 | 參考答案要點 |
|---|---|---|
| 1 ★★ | 經驗文件有三次成功一次失敗支持，失敗發生在新 API 版本——推翻還是適用條件變了？ | **先按 API 版本、任務條件、環境狀態把四條證據分層，而不是按數量投票**。若舊策略只在舊版本成功、新版本穩定失敗 → **收窄適用範圍並生成新版本候選**；若在相同版本與前置條件下也失敗 → **降低置信度或撤銷** |
| 2 ★★ | 滿意度上升但違規率也上升，為何不能把滿意度當單一學習訊號？如何設護欄？ | 滿意度可能獎勵違規退款、洩露資訊、過度承諾 → **只能是品質指標，不能覆蓋安全底線**。護欄至少包括**規則違規、隱私洩露、無證據陳述、承諾—行動不一致、越權操作**；設**不可被平均分抵消的硬閾值**，再在合規候選中比較解決率、合規變通、簡潔性、滿意度 |
| 3 ★★★ | 「虛假承諾」可用 Prompt、Harness 或參數緩解，依什麼證據選修改位置？ | **先定位根因**：模型知道工具未執行卻用完成式措辭 → 最小 Prompt 規則；承諾可由回覆文字與工具狀態**確定性比較** → Harness 檢查更可靠，也應作為**高風險場景的最後防線**；問題橫跨大量表達方式、反映廣泛的語言—行動對齊 → 再考慮參數訓練。**優先選最小、最易驗證、最易回滾的修改**，並在失敗集與舊任務保留集上比較 |
| 4 ★★★ | Agent 能改工具與驗證器，卻不應改批准自身更新的信任根——怎麼劃界？ | 可進化的程式碼放在**低權限沙盒**，只允許生成修補和測試；**權限系統、API 金鑰、發布控制設定、更新驗證器屬於安全機制，沙盒內的 Agent 無讀寫權限**；Agent 生成的修改必須由安全機制在隔離環境中**重現、迴歸**後才能發布 |
| 5 ★★ | 經驗庫增長後檢索錯誤與衝突抵銷收益，如何設計版本、時效、淘汰？ | 每條經驗保存**來源軌跡、適用條件、環境版本、驗證時間、置信度**；衝突條目**不靜默覆蓋**，按條件分支或標記；週期性「**睡眠學習**」合併重複條目 |
| 6 ★★★ | 為醫療客服設計參數、知識、Skill、程式碼協同的持續進化方案 | **參數**：醫學語言理解、自然有同理心的表達、複雜意圖識別；**知識庫**：最新指南、藥品說明、機構政策，**回答必須引用來源**；**Skill**：問診資訊收集、風險分級、轉人工、追蹤流程；**伺服器端程式碼**：身份驗證、隱私最小化、禁忌校驗、**緊急風險升級**、權限邊界。生產軌跡先按醫療安全、事實可靠、承諾—行動一致、表達品質評價，再分別生成四類候選；任何參數或流程改動都必須過**醫療安全保留集 + 人工複核**後灰度 |

## 17. 本章重點整理

1. **能力悖論**：零樣本能解新任務，一萬次後仍犯第一天的錯；**保存經歷 ≠ 從經歷中學習**。
2. 模型自身尚無法可靠持續學習 → **持續進化**：在模型外圍記錄證據、驗證、歸納、決定更新哪個載體；所有修改先成候選、過迴歸與安全檢查。
3. **三層軌跡驗證**（結果 → 過程 → 品質）；客服七面向；可學習的評價 = 成敗 + 各面向結論 + **證據位置** + 失敗類型；證據不足可拒評。
4. **四種載體**：知識庫、Prompt/Skill、程式/Harness、參數——依**能力的表示性質**選，可拆到多個載體；路由結果只是提案。
5. **經驗知識**：不可變軌跡 → 單次分析 → 跨軌跡證據表 → 正式文件 → 遷移測試；成功給策略、失敗給排除性知識；**反思不是證據**。
6. **經驗指令**：系統提示學習、DSPy/OPRO/GEPA；**帶來源的最小 diff + 邊界集/保留集**；τ²-bench 轉接規則 12.3% → 19.3%；提煉材料決定歸納品質；模型會把常見行為當應然 → 獨立驗證；需求澄清 Skill 要在返工與打擾間找平衡；Skill 理解語境、Harness 否決高風險。
7. **經驗程式**：操作 / 控制 / 驗證 / 架構四層可改；瀏覽器工作流程六步生命週期（**動作成功 ≠ 任務成功**；無安全重設不驗證；失效即 `invalid`）；PreAct 8.5–13 倍加速。
8. **自我修改 = 軟體發布流程**：**可證偽的變更契約**（AHE 三層可觀測性、影響預測先於修改）；候選空間含成功約束與遭拒歷史（Self-Harness）；工具創造同協定（Alita）；修改層級要對（重試約束進程式）；確認門用一次性權杖。
9. **DeepSeek Harness / Cordis**：時間與空間可組合性；可撤銷效果 + 反應式協效果；**自我進化的上限取決於系統有多可組合**；沒有特權核心，但記憶體外掛不能自動轉正；進化會擊穿 KV Cache。
10. **經驗參數**：高維能力進參數；穩定性影響頻率、表示性質決定載體。
11. **更新「更新方法」**：規則 → 結構化上下文 → 工作流程 → Harness → 最佳化器；ACE 增量合併防重寫退化；MCE 內外雙循環；AFlow、Meta-Harness；**Dream-RSI 發現樹回放**——低成本比較探索策略，但只有歷史內保證。
12. **Hermes 讀本書自我升級**：四輪外部審查後接受；不等於下游提升。
13. **雙循環**（線上執行記證據、離線進化發布）；Voyager 的課程 + 技能庫 + 迭代提示；**發現迴圈 = 科學方法論**。
14. **更新能力 ≠ 受益能力**：候選有效率、產物啟用率、遵循成功率、保留集增益；五類長期結果（迴歸、泛化、Token、安全、工程品質）；static / append_only / evolving 對照。
15. **完成 ≠ 進步**：自動科研的實作漂移、過度樂觀、判斷力不足 → 結論與證據分離、保留負面結果、維持多樣性、人在更高層介入。
16. **三道安全邊界**：證據與指令隔離、候選與正式隔離、**安全機制不可自我修改**。
17. **睡眠學習**：觸發 → 定向 → 整合 → 驗證審批 → 修剪索引；Claude Code 有界索引、Hermes 原始訊息檢索 + Curator；進化也要遺忘，**從原始基座重訓 LoRA**。

> **一句話**：Agent 的「學習」今天還得建在模型外面——把每次執行變成帶證據的評價，按能力的性質把經驗寫進知識、指令、程式或參數，每一次修改都是一個可證偽、可回滾、經獨立驗證的候選，而批准修改的那一層，永遠不讓被修改者碰到。
