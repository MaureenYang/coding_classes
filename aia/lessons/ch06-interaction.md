# 第 6 章　互動：觀察與動作空間的擴展

> 《深入理解 AI Agent》— 李博杰，第六章（「建構 Agent」部分的最後一章）

---

## 1. 本章定位：撤掉「輪流發言」這個前提

第一章的論斷：**底層模型固定時，提升 Agent 表現最主要的系統工程手段，是重新定義或擴展觀察空間與動作空間。** 第二至五章一直在兌現它——上下文決定觀察裡裝什麼、記憶與知識庫把觀察延伸到跨會話、工具定義能做什麼、程式碼讓它自己創造新動作。

但這些擴展都在同一個前提下：**Agent 與世界輪流發言**——Agent 思考時，世界被預設為靜止。這個前提太自然，很少被當作假設寫出來。本章要撤掉它。

### 1.1 兩根軸：模態與時機

| | 觀察空間的擴展 | 動作空間的擴展 |
|---|---|---|
| **內容**（第二至五章） | 上下文工程、記憶與知識庫 | 工具、程式碼生成 |
| **模態**（本章） | 語音、螢幕、物理感測器 | 說話、點擊、關節運動 |
| **時機**（本章） | 世界主動推送、連續流 | 跨回合、可打斷、可搶佔 |

- **模態**決定觀察與動作的**形式**（只讀文字，還是也能聽、看、感知力矩；只輸出 token，還是也能發聲、點擊、驅動關節）。
- **時機**決定**節奏**（主動去取 vs. 世界推來；回合內做完 vs. 跨回合、可中斷、可搶佔）。

> ⭐ **回合制是模型與介面的一種互動約定，不是環境的性質。** 郵件在模型思考時抵達、使用者在它說到一半時插話、頁面在兩次截圖之間變了樣、杯子在機械臂伸手途中被碰倒。截至 2026 年 9 月，**GPT-6 Astra** 已提供原生非同步工具呼叫與回合中途追加指令——本章同時討論原生支援與相容既有同步介面兩條路線。

### 1.2 四個時間尺度

| 尺度 | 場景 | 觀察側 | 動作側 |
|---|---|---|---|
| 秒 — 天 | **非同步與事件驅動** | 世界主動喚醒 Agent（郵件、計時器、回呼） | 先發起，後續靠事件收尾 |
| 10 ms — 1 s | **語音** | 邊說邊聽，不等一句說完 | 邊想邊說，可被打斷、可改口 |
| 亞秒 — 秒 | **Computer Use** | 螢幕在兩幀之間持續變化 | 動作後必須重新確認現實仍符合計畫 |
| 毫秒 | **機器人** | 感測器連續回流 | 動作分塊：一次規劃一小段，可被搶佔 |

## 2. 非同步與事件驅動：當世界主動找上門 ⭐⭐⭐

這一節**模態不變（仍是文字），只有時機變了**——從回合制邁出的第一步。第四章五類工具中剩下的**事件觸發**與**使用者溝通**兩類在此討論。

### 2.1 為什麼需要非同步

> 同步架構像**只會排隊的櫃檯**——一次一個顧客；智慧助手像**靈活的秘書**——桌上擺著郵件、電話、來訪者，按緊急程度決定先處理哪個，處理一半還能為更急的事暫停。

三項核心能力：
- **非同步執行是常態**：長任務不應阻塞互動；
- **事件優先順序的動態判斷**：取消當前（緊急）、加入佇列（常規）、並行處理（獨立輕量查詢）；
- **中斷與恢復的流暢性**。

> ⚠️ 先檢查模型與 API 是否支援這種訊息時序：有的要求先補齊工具結果才能繼續；有的允許工具保持未完成、模型繼續工作並在生成中接受更新。前者需要事件佇列、任務控制代碼與相容層；後者可直接用原生非同步協定。**兩者都仍需應用程式管理事件來源、工具生命週期與結果歸屬——程式碼用了 `asyncio` 不等於模型具備原生非同步能力。**

**事件驅動的非同步 Agent 架構**：不再輪詢「有沒有新訊息」，而是新訊息到達時自動觸發；所有輸入、輸出、思考、外部互動都統一建模為**事件流**。

### 2.2 OpenClaw 的機制與短板

Gateway 控制平面接收多渠道訊息並路由到 Agent。三種內建自動化：

| 機制 | 性質 | 說明 |
|---|---|---|
| **Hooks** | 生命週期事件 | 會話建立、重置等（像 GitHub Actions 觸發器）——**只響應框架內部事件，不引入外部世界的新變化** |
| **Cron** | 時間驅動 | `0 9 * * 5` = 每週五上午 9 點；週報、月初彙總 |
| **Heartbeat** | 時間驅動 | 每 N 分鐘喚醒一次檢查，憑判斷力避免警報疲勞 |

- 內建渠道（IM、Web）的訊息本身是**推送式**的；但讓 Agent 在沒有使用者訊息時「自己動起來」的只有 Cron 和 Heartbeat，都是**時間驅動**。
- **短板**：內建渠道之外的任意**第三方事件源**（新郵件、外部 API 回呼、緊急通知）缺乏即時接入通道 → 只能等下一個 Cron/Heartbeat 週期。

### 2.3 案例：PineClaw

**Pine AI** 代替使用者打真實電話（協商帳單、取消訂閱、保險理賠）。通話中隨時需要使用者介入：
- **即時身份驗證**：客服要安全碼或 OTP；
- **三方通話確認**：要求帳戶持有人幾秒內接聽；
- **決策確認**：對方提出降價方案，是否接受？

若靠 5 分鐘一次的 Heartbeat → 客服等不到驗證碼就掛電話；縮到秒級輪詢又浪費大量請求。

**解法：Channel 機制**——在 Gateway 與 Pine API 之間建立即時事件通道；電話接通、需要輸入、通話結束時即時推送 → 響應延遲**從分鐘級降到秒級**。

> **真正的「主動服務」不僅需要 Agent 能定時檢查事件，更需要事件能主動通知 Agent。**

## 3. 事件觸發工具與使用者溝通工具 ⭐⭐

### 3.1 事件觸發工具（三類）

| 工具 | 處理 | 例子 |
|---|---|---|
| **定時器** `set_timer` | 依賴物理時間的事件 | **一次性**：週六被要求「給 DMV 打電話」→ 設「下週一上午 10:00 致電 DMV」；**循環**：每小時查伺服器健康、每週五發報告；外部服務不支援推送時只能循環查詢——OpenClaw 的 Heartbeat 正是這種機制的系統化 |
| **後台任務監控** `monitor_shell` | 長時間後台命令 | 不斷「盯著看」浪費 token；等全部跑完又無法及時發現問題（甚至卡死無法介入）→ Claude Code 的 **monitor** 工具：監控新增輸出或含特定關鍵詞的輸出 |
| **外部事件通道** `connect_channel` | 新郵件、API 回呼、IM | PineClaw 的 Channel |

設計：清晰的觸發條件與**過濾規則**（避免無關事件浪費算力）；事件載荷帶足上下文（減少喚醒後的額外查詢）。

### 3.2 使用者溝通工具

- Claude Code、Manus 等用原生 ReAct 迴圈：assistant 訊息直接給使用者，使用者要打開指定會話，往往看得到工具呼叫過程。
- **OpenClaw 打破了這一典範**：使用者無需感知會話存在，也不必關心工具細節；雙方都能**隨時**給對方發訊息（不是一問一答）→ 被評價為有「**活人感**」，像秘書透過簡訊非同步溝通。OpenClaw 不直接呈現 assistant 訊息，而是用**專門的工具**發訊息，可附圖片檔案、依緊急程度加推播。
- 多模態溝通：結構化卡片、提醒郵件、生成式 UI。
- 設計：支援非同步（使用者不一定在線）、已讀/未讀追蹤、多渠道一致性。

**多渠道溝通與召回**：
> **通知機制同時也是使用者召回機制。** IM、簡訊、郵件、電話、推送——依緊急程度、使用者狀態、內容性質、偏好選渠道；長任務完成時主動通知；定期任務的通知幫使用者建立固定互動習慣。

### 3.3 虛擬身份與隔離執行環境 ⭐⭐

| 選擇 | 風險/優點 |
|---|---|
| Agent 直接管理使用者個人帳號 | 便捷，但出錯或被攻破時**使用者全部數位身份暴露** |
| **Agent 擁有獨立虛擬身份**（如秘書有自己的辦公電話與郵箱） | 專屬通訊帳號、儲存、計算環境；**身份的明確性反而增強溝通的真實性** |

- **虛擬電腦**（VM/容器）與**虛擬手機**（Android 模擬器）：OS 級隔離；自己的帳號、家目錄、憑證；可追溯可稽核。**沙盒隔離的是程式碼執行；虛擬電腦/手機隔離的是整個數位身份。**
- 兩個現實挑戰：
  1. **反自動化**：CAPTCHA、IP 信譽偵測；資料中心 IP 易被識別 → 常需**住宅代理**；
  2. **必須以本人身份登入時**：**Human-in-the-Loop 認證**——透過 VNC/RDP 讓使用者在視覺化環境親自登入，看得到 Agent 的完整介面；會話令牌在有效期內複用，避免頻繁打擾。
- **共享檔案系統**（卷掛載如 `/workspace/shared`）：資料以**路徑引用**而非內容複製傳遞，避免佔用上下文。例：使用者上傳 CSV → 虛擬電腦中的 Agent 分析並存回圖表 → 主 Agent 只回傳圖表路徑。

## 4. 事件處理機制 ⭐⭐⭐

### 4.1 骨架：事件迴圈與安全點

```
for {
    events = queue.drain()      // 取出若干事件
    trajectory.append(events)
    response = LLM(trajectory)
    run(response.tool_calls)
}                               // ≈ Go 的 for { select { ... } }
```

- **同步介面實作：事件在每輪迴圈的邊界被消費**。LLM 推理、工具執行時，新事件先在佇列等，到達**安全點**（一段推理結束、一次工具返回）再處理。
- **原生非同步**：允許在模型仍在思考/輸出時接收新要求，由系統選時機處理。
- 兩者都有邊界，只是由不同層管理。**工具取消仍需執行器回應取消訊號**（像檢查 Go 的 `ctx.Done()`）；**收到「停止」訊息本身不會撤銷已經發生的動作。**

三種策略的本質（以同步事件迴圈理解）：

| 策略 | 本質 |
|---|---|
| **佇列式** | 讓事件等到下一個**自然出現**的安全點 |
| **取消式** | **主動提前製造**一個安全點 |
| **並行式** | 另起一個迴圈，不必等主迴圈的安全點 |

### 4.2 事件的結構化建模

| 維度 | 內容 |
|---|---|
| **來源（誰）** | 使用者本人、聯絡人、陌生人、系統通知 |
| **渠道（方式）** | 電話、簡訊、IM、郵件、社群、定時器、非同步工具結果、命令列監控更新 |
| **內容（什麼）** | 文字、情感、緊急程度、是否需回覆 |
| **上下文（背景）** | 回覆舊對話還是新發起、與當前任務的關聯 |

```json
{
  "source": {"type": "email", "sender": "client@example.com"},
  "channel": "gmail_webhook",
  "content": {"subject": "退款請求", "body": "訂單 #12345 希望退款..."},
  "context": {"priority": "high", "customer_tier": "vip", "related_orders": ["#12345"]}
}
```

> 只有清晰建模，Agent 才能**不把使用者輸入誤當工具結果，也不把藏有指令的工具結果誤認為使用者指令**（提示注入）。n8n 等平台的觸發器生態（Webhook、定時器、郵件、資料庫變更、檔案監聽）——每一種觸發器都是 Agent 感知世界的一個「感官」。

### 4.3 基於緊急度的三種處理策略

| 策略 | 適用 | 步驟 | 例子 |
|---|---|---|---|
| **取消式** | 緊急事件 | ① 停止當前操作（取消串流、對同步工具發取消訊號）② 清空佇列 ③ 佇列事件 + 緊急事件一起追加到軌跡 ④ 立即重新呼叫 LLM | 「停止！我說錯了」→ 立即重新理解真實意圖，避免執行錯誤操作 |
| **佇列式** | 常規事件 | ① 放入佇列末尾不打斷 ② 等當前操作完成 ③ 任一 `tool.result` 返回時，若佇列非空則**一次性**全部追加 ④ LLM 綜合處理 | 搜尋中使用者補充「只看最近一個月」→ 搜尋結果返回時兩者一起呈現，省一次往返 |
| **並行式** | 獨立輕量查詢 | 判斷獨立性與複雜度 → 在並行推理會話中獨立執行 → 立即回覆；查詢與回覆追加到主軌跡並**標明「與主任務並行執行」** | 分析大量資料時使用者問「今天天氣怎麼樣？」——與主任務無關、要快、成本低 |

**緊急度判定**：
- 緊急：`user.interrupt`、`supervisor.instruction`、`agent.interrupt`、標記緊急的外部觸發（系統告警、支付失敗）。
- 非緊急：`user.input`、`agent.input`、`tool.result`、`timer.trigger`、常規外部觸發。
- **寫死規則有侷限，事件語義決定處理方式**：「馬上停下來」→ 取消；「今天天氣怎麼樣」→ 並行；「報告用中文發給我」→ 佇列。**建議用輕量分類 LLM 作為事件路由器。**

> **取消點必須是工具或推理能安全收尾的位置；未完成的工具結果用顯式佔位符表示，不能偽造成功。**

> **實驗 6-1 ★★★ 事件驅動的郵件處理 Agent**
> - 事件源：`on_email_received`、`on_im_message`、`on_sms_message`、`on_github_pr_update`、`on_github_issue_update`、`on_timer_expire`、`on_webhook_received`、`on_user_inactive`、`on_process_timeout`、`on_resource_alert`；統一事件佇列，按到達順序處理。
> - 驗證：三封郵件——**會議邀請**（查日曆衝突、起草接受/拒絕）、**客戶投訴**（擷取關鍵資訊、標高優先順序、通知使用者）、**行銷廣告**（自動歸檔）；全程無需使用者介入。

## 5. 不支援原生非同步時的相容方案 ⭐⭐⭐

**問題**：Agent 正在搜尋聯絡人（工具未返回），使用者突然說「先幫我查一下明天的天氣」。若介面要求未完成的工具呼叫先取得結果，就無法直接處理新訊息——這是**所選協定與模型組合的限制**，不是所有 LLM 的規律。

**核心思想**：**常態下讓 LLM 看到標準同步軌跡，只在打斷時插入佔位符修復格式。**

| 規則 | 內容 |
|---|---|
| **1** | 及時記錄 API 已完成的 assistant 訊息與工具呼叫；伺服器端管理的 reasoning 狀態按供應商接續協定保留，**不自行拼接不可見的思考文字** |
| **2** | 工具**完成時**才記錄 tool result；執行中軌跡處於「部分完成」 |
| **3** | 工具執行中被打斷 → 為未完成工具生成**佔位符**（「工具正在後台執行，請優先處理新事件」）+ 追加打斷事件 + 重新呼叫 LLM。從 LLM 視角，assistant message 仍有配對的 tool result |
| **4** | 沒有原生 steering 或中途接續介面時：取消未完成的生成，保留已確認完成的訊息與工具狀態，追加新事件後重新請求。**不能假定半截輸出或隱藏推理可作為合法前綴任意回填** |
| **5** | 非打斷事件進佇列，當前週期完成後一次性追加 |

```
1. Agent 呼叫 search_contacts → assistant message 立即寫入（規則 1）
2. 未返回時使用者問天氣 → 為 search_contacts 生成佔位符 tool result（規則 3）
   → 追加天氣查詢 → 重新呼叫 LLM（軌跡格式完全合法）
3. 天氣回覆完畢後 search_contacts 真實結果到達 → 作為新事件（帶來源與任務 ID）追加（規則 2）
   → 讀取聯絡人，繼續起草郵件
```

**佔位符的語義風險**：模型可能把「**任務已啟動**」誤當「**任務已完成**」，在真實結果返回前作出依賴它的判斷 → 用明確任務狀態與結果驗證防止；評估中要檢查**是否編造了尚未抵達的資料**。（作者也提醒：不能僅憑一次失敗就歸因於某個未公開的訓練過程。）

### 5.1 用任務控制代碼表達非同步語義

傳統 `phone_call` 隱含「呼叫即完成」（撥打並等到通話結束）。非同步範式下把**啟動與完成解耦**：

```
initiate_phone_call  → 立即返回任務 ID + 初始狀態（「呼叫已發起，正在撥號」）
phone_call_connected → 事件
phone_call_ended     → 事件
```

> **工具的名稱與描述本身就要傳達非同步語義**——看到 `initiate_` 模型自然推斷是「發起」而非「完成」。描述再強化：「此工具將啟動由子 Agent 處理的電話任務。成功發起後立即返回任務 ID，您可繼續處理其他事項。通話結束後會收到單獨的通知事件。」（呼應第四章：工具描述是 ACI 的核心。）

### 5.2 佇列式處理中的注意力分散

批次事件時，模型可能**只回應最後一個事件**而遺漏前面的要求（原生非同步也一樣要檢查）。兩層干預：
- **提示詞**：「收到多個連續事件時，請確保全面考慮所有資訊。」
- **狀態列標記 + 彙總**：

```text
[未處理事件 1/4] Tool result from database_query：...
[未處理事件 2/4] User 補充說明：只看北京地區的資料
[未處理事件 3/4] 系統提醒：報告截止時間還有 30 分鐘
[未處理事件 4/4] User 詢問：進度如何？
上面有 4 個未處理事件，包括 1 個工具結果、2 條使用者訊息、1 個系統提醒。請確保回應涵蓋所有資訊。
```

> **實驗 6-2 ★★★ 帶並行與打斷能力的非同步 Agent**（相容同步介面的執行階段）
> 1. **非同步工具執行**（≥ 3–5 秒）：長命令執行中使用者問「現在幾點了？」→ 立即回應，結果返回後再呈現。
> 2. **事件佇列與批次處理**：長任務期間連續收到「記得用日語回覆」「整理成網頁」→ 完成時一次處理 → 生成日語網頁。
> 3. **打斷**：「取消」→ 立即停止、取消非同步工具、軌跡記錄打斷與取消。
> 4. **並行工具的取消與狀態查詢**：「同時執行三個指令碼，哪個先完成就看剩下的進度，沒超過 50% 就取消」——速度每秒 3%、2%、1%；約 33 秒時第一個完成，查得其餘約 66% 與 33% → 取消後者；整合報告。

## 6. 模型原生非同步：GPT-6 Astra ⭐⭐

| 能力 | 意義 | 例子 |
|---|---|---|
| **非同步工具呼叫**（Async tool calling） | 把「發起行動」和「取得結果」分開；能獨立推進的繼續做，**依賴結果的決策留到結果抵達之後** | 查會議場地時先整理議程與準備清單，場地資訊回來再比較方案 |
| **回合中途引導**（Mid-turn steering） | 使用者可在 Agent 思考或組織回答時追加「預算減少了」「人數變了」；系統保留已完成的工作，把新約束帶入後續 | 不必等整輪結束才表達變化（接收與調整之間仍可能有延遲） |

> 系統仍要分清來源、記住哪些已完成哪些在等待。**修改計畫 ≠ 停止正在執行的工具，更不會自動撤銷已發生的動作**——執行、取消、狀態管理仍由執行階段負責。並非所有模型都具備原生能力 → 依支援範圍選原生或相容方案。

### 6.1 從「能接收非同步訊息」到「可靠處理非同步任務」

必查三件事：
1. **結果歸屬與未完成狀態**：延遲結果歸入正確任務？結果缺席時不編造？
2. **任務恢復與動作控制**：處理新要求後能繼續原任務？區分「修改計畫」與「停止執行」？
3. **多條更新的綜合使用**：同時遵守預算與人數，而不是只記得最後一條？

評估要涵蓋兩層：**模型是否理解了變化** + **系統是否按變化正確執行**。

> **實驗 6-3 ★★★ 原生非同步與回合中途引導**：選會議場地——發起耗時查詢後先做不依賴結果的準備；期間使用者補充預算與人數；查詢完成後依全部約束選擇。對比同步工具、原生非同步、回合中途引導三種方式；再用不支援原生能力的模型對照，分辨**模型能力**與**執行階段編排**各自解決什麼。

## 7. 語音：最自然的人機介面 ⭐⭐⭐

正常說話速度約為打字的**四倍**，且不佔用雙手與視線 → 適合把 Agent 放進持續運作、隨時可被打斷的迴路（前言提到的 **whisper coding**）。兩個方向：使用者對 Agent 說話；Agent 代替使用者對外部世界說話（如 Pine 打電話）。

> **語音模型決定「能回答什麼」；互動架構決定「能否聽清楚、及時回應、自然交接發言，並在通話中完成確認與工具呼叫」。**

### 7.1 三種互動範式（出自 OpenAI GPT-Live 的總結）

| 範式 | 核心結構 | 優勢 | 限制 |
|---|---|---|---|
| **級聯** | VAD → ASR → LLM → TTS | 模組清楚、易替換與除錯 | 延遲累積；副語言資訊在介面處遺失 |
| **端到端 Omni** | 原生音訊輸入輸出，按輪次 | 延遲較低；保留語氣、情緒、環境聲 | 仍依賴輪次；訓練與除錯成本高 |
| **全雙工** | 原生音訊，**持續聽、說、決策** | 重疊說話、自然打斷、連續串流 | 訓練、控制、評估最複雜 |

> 共同主線：**擺脫「必須輪流說話」的假設，以及 VAD 對發言權的猜測。** 級聯與 Omni 仍要劃分輪次；全雙工把「誰該說話」變成模型持續做出的決策。

### 7.2 範式一：級聯流水線

| 模組 | 作用 | 常見瓶頸 |
|---|---|---|
| VAD | 判斷是否說完 | 靜音閾值 → 等待與誤切分 |
| ASR | 音訊轉文字 | 識別延遲、上下文遺失 |
| LLM | 理解與生成 | 首 token 延遲；開 reasoning 更久 |
| TTS | 文字轉語音 | 首包合成、播放緩衝 |

串行時等待會累積（延遲瀑布）；生產中的排隊會進一步放大空載延遲。

> **實驗 6-4 ★ 傳統語音 Agent**：WebSocket 串起麥克風、Silero VAD、本地 Whisper、串流 LLM、Fish S1 TTS——後續方案的級聯基線。

**串行感知的三個問題**：① 延遲累積（必須等一段靜音）；② 資訊遺失（有聲/無聲二值訊號表達不了猶豫、情緒、附和、環境聲）；③ 上下文被切斷（電郵、人名、專有名詞被分片識別出錯）。

**優化：串流感知**（保留模組化）：

| 手段 | 做法 |
|---|---|
| **ASR 邊聽邊轉** | VAD 偵測開始說話後按固定間隔呼叫 ASR 產生暫時轉錄；說完後確認最終文本 |
| **LLM 推測執行** | 暫時轉錄一產生就送 LLM；最終文本相同就不重算，否則取消重來 |
| **LLM 分段輸出** | 第一段適合播報的文字一完成就交 TTS |
| **TTS 增量合成** | 持續回音訊區塊，生成、合成、播放重疊 |

- 真正的串流 ASR 需要模型本身支援：**Whisper** 解碼器雖是自迴歸，但**編碼器需要完整音訊片段**，不能直接等同串流模型。
- 基於 LLM 的串流聽覺模型：從連續音訊輸出文字與語義事件，保留整段對話上下文，用世界知識處理品牌、人名。
- **端點判斷做進識別器**：綜合語義與靜音判斷一句話是否完整。⚠️ 訓練標籤**只能用決策時刻可見的資訊**，否則「上帝視角」會產生線上無法重現的判斷。
- 輸出**聲學事件標記**：`speak_start/end`、`interrupt`、`emotion`、`laugh`、`sigh`、`noise`——與文字 token 形成統一事件流。

> **實驗 6-5 ★ 用 Qwen2-Audio 模擬串流感知**：Qwen2-Audio 本身不是串流模型，以**遞增音訊前綴**模擬連續感知，與 600ms VAD + Whisper 對照。

### 7.3 範式二：端到端 Omni

- 同一模型直接聽音訊、生成回覆並輸出語音 → 有機會保留情緒、語調、環境聲。
- 理解：能聽出停頓；生成：唱歌、特殊語調等豐富副語言。
- **仍假設輪流說話**，通常靠 VAD 劃分發言權 → 使用者報數字時中途停頓仍可能被誤判為說完。

> **實驗 6-6 ★★ 本地 MiniCPM-o 4.5**：關閉 thinking mode，比較「直接從音訊作答」vs.「同模型**自級聯**先轉錄再作答」——測的是音訊資訊是否被保留，**不是**「邊想邊說」。

### 7.4 範式三：全雙工互動模型

- 不預設輪次：持續聆聽、持續說話，反覆決定繼續、停頓、打斷或呼叫工具（同聲傳譯需要兩者重疊）。
- **Kyutai Moshi**（2024）：早期研究案例。
- **Thinking Machines Lab「互動模型（Interaction Model）」**：互動性內建於模型，而非由 VAD 等外部 harness 拼裝；**微輪次**以短音訊塊推進，讓靜音、重疊、打斷都保留在連續上下文；可把完整對話**委派給後台推理模型**，自己維持話頭，結果回來再在合適時機接入。
- **OpenAI GPT-Live**：把全雙工帶到生產規模——能等待、附和、被打斷、即時翻譯；同樣把複雜任務委派給後台模型。

## 8. 認知時序：即時互動與深度思考 ⭐⭐⭐

> **互動品質與智能上限是不同維度**：前台模型要在使用者仍在線時回應；背景模型可以想更久。

| 方案 | 做法 | 問題 |
|---|---|---|
| **一：快思考應付，慢思考回答** | 快模型幾百毫秒先回應，慢模型背景深推 | 簡單問題被重複處理；複雜問題**前後矛盾**（快模型建議買、慢模型發現缺關鍵功能 → 幾秒內聽到互相衝突的答案）。根因：**兩個實例各自完成了一次獨立思考** |
| **二：快思考互動，慢思考建議** | 背景模型透過狀態欄/專用介面傳建議，前台維持對話並決定怎麼說 | 通信間接：前台可能誤解建議、看不到背景的中間思考 → 能自然等待結果，**但不能真正邊想邊說** |
| **三：端到端統一思考與表達** | **Step-Audio R1**：**MGRD**（模態錨定思考蒸餾）讓模型依聲學特徵思考——篩選真正引用音高、節奏、語調的思考過程來訓練，並用 RL 防止跳過思考直接猜；**MPS 雙腦架構**：構思腦持續產出思考片段，表達腦收到片段就結合已有回覆立即生成語音，流水線並行 | 前者保證「**想得對**」，後者解決「**說得及時**」；但思考與即時表達要一起重訓 |

### 8.1 快慢分離 vs. 端到端思考的取捨

- 統一模型最直接實現「邊想邊說」；解耦設計更容易**替換背景大腦**。
- ⭐ 快慢分離的工程優勢：**直接承接慢模型的迭代紅利**——更強的思考模型發布後只換背景模型，不必重訓整套即時語音系統；統一路線則把推理與互動綁在同一訓練週期，每次升級都要重新兼顧智能、延遲、自然度。
- **不必然犧牲效果**：截至 2026 年 8 月，採快慢分離的 **Pine AI 語音 Agent 在 τ³-Voice Leaderboard 第一**，超過 Grok Voice、GPT-Realtime-2。

**「端到端」的兩個含義（兩條獨立的軸）**：

| 軸 | 意思 | 例子 |
|---|---|---|
| **語音通路端到端** | 直接收音訊、出音訊，不經離散文字串接 | Omni（仍按輪次）、互動模型（可邊聽邊說）都是 |
| **認知架構端到端** | 即時互動與深度思考在同一模型內共享狀態、共同訓練 vs. 前台快 + 背景慢 | Thinking Machines Lab：**語音通路端到端 + 認知架構快慢分離** |

> 對照 Hanson《C Interfaces and Implementations》的模組化精神：穩定的介面（前台互動）與快速演進的實作（背景推理）分開，各自獨立替換——這是快慢分離能「承接慢模型紅利」的原因。

### 8.2 更像人的語音合成

- 傳統 TTS **太流暢、停頓太少**，反而暴露機器身份；停頓、填充詞、偶爾的重複是人類表達不確定與思考的訊號。
- 主 LLM 輸出控制標記：**THINKING**、**EMO:happy**、**SPEED:0.8x** → TTS 映射為停頓、韻律、語速、笑聲、嘆氣。
- 實作：訓練能理解控制標記的 TTS；或 voice cloning，為不同情緒準備參考片段。

> **實驗 6-7 ★★ Fish Audio S1 控制標記 TTS**：多參考音訊庫；比較無標記、單一參考、多個參考三種設定。

## 9. Computer Use：GUI 自動化 Agent ⭐⭐⭐

語音是一維聲音流、強調「**何時開口**」；Computer Use 是二維螢幕、強調「**下一步點哪裡**」，以及語音中不存在的問題——**動作執行後，現實是否仍與計畫一致**。

```
截圖 → 多模態模型（截圖 + 任務）→ 思考 + 一個具體動作 → 執行層執行 → 等介面響應 → 再截圖 …
```

> ⭐ 區分**看懂介面**（多模態理解，一次截圖問答可測）與**完成任務**（理解與動作生成閉環，處理載入、狀態變化、誤操作、不可逆後果）。難點不只是截圖上答對，而是**每一步之後重新確認現實是否仍符合計畫**。

三個設計維度：**動作空間、視覺定位、模型架構**。

### 9.1 動作空間（Anthropic 參考實作的三類工具）

| 工具 | 能力 |
|---|---|
| **computer** | 滑鼠：移動、左/右/中鍵、雙擊/三擊、拖拽、按下/鬆開；滾動四方向可配修飾鍵；鍵盤：`type`（字元間隔 12ms 模擬真實打字）、組合鍵、長按；感知：截圖、游標位置、等待 |
| **bash** | 長久會話、120 秒超時、**哨兵字串**偵測命令結束、跨呼叫保持狀態 |
| **str_replace_editor** | 字串匹配安全編輯：檢視、建立、替換、插入、撤銷 |

> 這是清楚的動作空間設計，**不是私有協定**：只要 Harness 能把相同的截圖、動作約束、執行結果轉成目標模型支援的格式，Claude、開放權重視覺模型、自託管端點都能驅動同一個迴圈。

> **實驗 6-8 ★ 執行 Computer Use**：路徑 A——Anthropic Computer Use Demo（容器封裝 Ubuntu 桌面）；路徑 B——`chapter6/computer-use-open-model`，經 OpenRouter 用開放權重 **Qwen3-VL 32B Instruct** 驅動 browser-use，或自架 vLLM/SGLang。

### 9.2 視覺定位（Grounding）⭐⭐⭐

兩大思路：

```
① 選擇題（先標註，模型選編號）
     ├─ 純視覺標註：原始 Set-of-Mark（分割模型切區域）
     └─ 結構化元素索引：DOM / Accessibility Tree
② 純座標預測（模型直接報座標）
```

> 選擇題比填空題容易答對：「點選 [123]」vs.「點選螢幕 (350, 464) 處的按鈕」。直接輸出座標需大量訓練，且在不同解析度下容易出錯。

**① Set-of-Mark（SoM）**：微軟研究院 2023 年提出，為釋放 GPT-4V 的定位能力。**純視覺**——用 SAM、SEEM 等分割模型切候選區域、疊加編號；模型報編號，系統換算中心座標。**不需要 DOM**，原生桌面軟體、遊戲同樣適用。

**② 結構化元素索引**（SoM 思想在 Web 上的結構化實現，browser-use 為代表）：
1. 透過 **CDP**（Chrome DevTools Protocol）取 DOM 樹與無障礙資訊；
2. 偵測可互動元素；
3. 標唯一 ID 並在截圖上畫邊界框；
4. 同時生成文字列表：

```text
[1] <input type="text" placeholder="Search" aria-label="Search" />
[2] <button id="submit-btn" aria-label="Submit form" />
[3] <input type="text" placeholder="Enter your name" value="" />
[4] <a href="/docs" aria-label="Documentation" />
```

**不省 token**（要把標註資訊全發給模型），但定位準確穩定，免去分割模型的漏檢誤檢。

**③ 純座標預測**（**SeeClick**、Claude computer use）：在海量 GUI 截圖—元素位置配對資料上訓練，把「點選提交按鈕」直接映射到座標。

⚠️ **解析度匹配與雙向座標縮放**：
- Claude 訓練用 **XGA（1024×768）、WXGA（1280×800）、FWXGA（1366×768）**；輸入解析度不匹配 → 座標**系統性偏移**（像在小地圖量距離直接用到大地圖）。
- **按寬高比選目標解析度**：真實 2560×1440（16:9）→ 選 FWXGA 1366×768；截圖等比縮放送入；模型輸出 (683, 384) → 反向映射 (683×2560/1366, 384×1440/768) ≈ **(1280, 720)**。
- 若硬把 16:9 拉進 4:3 的 1024×768 → 畫面橫向壓扁 → 座標系統性偏移。

**選擇邏輯**：
- **結構化資訊可得** → 優先 DOM/Accessibility Tree 索引（最精確穩定）；
- **不可得**（Photoshop 等原生軟體、Canvas/WebGL、遊戲）→ 視覺標註（對未經 GUI 訓練的通用模型更友好）或座標預測（對做過 GUI 定位訓練的模型更直接）；
- 兩者在**小元素與密集介面**上精度仍有差距。

> **實驗 6-9 ★ browser-use 自動瀏覽**：Playwright + 多模態模型 + SoM 視覺化模式（每次決策前存帶標註框的截圖）；「打開 Google 查詢舊金山天氣」→ 選搜尋框、輸入「San Francisco weather today」、提交、從結果頁擷取溫度與天氣。

### 9.3 能看動畫、能聽聲音的 Computer Use：AOI ⭐⭐

隱含假設：**螢幕是靜止的**。現實螢幕會放影片、彈出轉瞬即逝的通知、播放會議人聲——每 3–5 秒才睜一次眼、完全沒耳朵的 Agent 對「兩幀之間發生的事」既看不見也聽不到。

> 該被重新設計的不是「動作介面」，而是「**觀察介面**」（Li & Shi, arXiv:2606.29472）——**Agent–電腦觀察介面（AOI）**：把連續的環境觀察轉成模型便於處理的離散事件。

| 技術 | 做法 |
|---|---|
| **螢幕關鍵影格截圖** | 小模型判斷螢幕是否有**有意義的變化**，只在明顯變化時截圖；變化頻繁時每秒 1 張就有不錯效果 |
| **音量門控的語音轉寫** | 有聲音才呼叫語音辨識，文字放入上下文 → Agent「聽得到」 |
| **把畫面敘述成文字** | 模型把截圖描述成一句話；原圖之後被清出上下文，這句文字仍在 → **多模態互動歷史壓縮** |

> 呼應第二章：這是「上下文壓縮」在多模態上的版本——有損的影像換成持久的文字摘要。

### 9.4 Computer Use 的世界模型 ⭐⭐

- 觀察介面不消除**規劃延遲**：仍是串行「截圖—思考—點擊」。**OSWorld-Human** 效率研究：即使任務成功，Agent 的步驟數與等待時間仍明顯多於人類——**準確率達人類水準 ≠ 已足夠實用**。
- 人類會**先預測動作後果**：變化符合預期就沿計畫繼續；偏離才停下重新觀察 → 世界模型實現類人的「**推測執行**」。
- 桌面狀態不只是像素：視窗、焦點、捲動位置、輸入框內容、載入狀態、權限、網路回應。

```text
桌面狀態 + click/type/scroll/wait ──> 下一狀態的表示
```

- 用途：點擊前比較候選動作後果；頁面載入期間準備下一步；彈窗一閃而過時依狀態差異恢復；刪除檔案前在隔離虛擬桌面中預測是否出現不可逆確認視窗。
- **重點不是生成逼真的未來截圖，而是預測完成任務所需的、可檢查的狀態差異。**
- **Photon-1**（Induction Labs，2026-07）：僅用 **3 萬 H200 GPU 小時**預訓練；每影格壓成離散潛在 token，**自迴歸預測動作後的下一狀態表示**（不逐像素生成）；影像生成器只用於視覺化，非推論必要；再透過虛擬機上的線上訓練學會輸出 computer-use 動作。（數據為公司揭露。）

> 對照第五章：推測執行與「LLM 推測執行 + 最終文本相同就不重算」、Cursor 的推測解碼是同一招——**先按預測做，驗證不符再回退**。

### 9.5 移動端：生態壁壘比技術更難

- 技術差異：動作空間接入系統無障礙 API（Android **AccessibilityService**）讀元素、下點擊與輸入；觸控手勢讓座標語義改變（同一 (x, y) 是單擊、長按還是滑動起點？需額外手勢型別）。AndroidWorld 等基準在此評測（第七章）。
- **真正卡住的是生態壁壘**：曾有手機廠商讓 AI 助手自動操作微信、淘寶、支付寶，很快遭平台限制。
- 根因：**商業模式衝突**——平台靠**流量與注意力**變現（資訊流廣告、推薦引導、衝動消費）；Agent 不看廣告、不衝動消費、直奔目標 → 每次操作都在侵蝕平台商業模式根基。
- 不只是 CAPTCHA 層面的技術對抗，而是**結構性利益衝突**，短期難以調和。

## 10. 機器人操作：以 XLeRobot 整理桌面為例 ⭐⭐⭐

**貫穿任務**：「把紅色杯子放進托盤，把黃色廢紙放進垃圾盒，最後重新觀察並確認桌面狀態。」
- 真機實驗：6-10、6-12（需機械手臂、標定、緊急停止裝置、現場觀察員）；
- 本機 GPU 模擬：6-11、6-13、6-14；
- 真機與模擬分開報告，但**任務目標、動作語義、成功條件保持一致**。

一個能用的機器人系統至少要回答四個問題：
1. 人想完成什麼任務？
2. 接下來先做哪個子任務？（→ **長程規劃**）
3. 目前技能具體輸出哪些動作？（→ **VLA / 動作原語**）
4. 動作執行後，現實是否仍符合計畫？（→ **世界模型** + 新觀察）

另加：**從模擬遷移到現實**處理訓練畫面與真實相機、執行器的差異。缺任何一個回饋環節，即使高層模型知識與規劃能力足夠，仍可能做不完。

### 10.1 硬體與演算法的分工：「固定硬體、替換操作者」

> ⭐ **幾百美元的 XLeRobot 透過遙操作已能完成這種連續多步桌面任務**——這不是「硬體勉強可行」，而是明確的診斷證據：**對這個任務，硬體本體不是瓶頸，演算法才是。**

- 診斷方法：保持相機、手臂、夾爪、佈置、成功條件不變，先讓**人接管閉環**。人會持續修正定位、選動作、控時機、處理抓取失敗——自主系統與人的差距正落在這些**閉環能力**上。
- 範圍限定：只說明硬體跨過了本任務的負載、精度、工作空間門檻，不代表能勝任所有開放環境。
- 遙操作入口：鍵盤、Xbox 手把、Switch Joy-Con、VR。人類操作者會自然做演算法必須顯式實作的事：靠近杯子減速、杯子滑動修正抓取點、沒夾住紙重新觀察、放入後檢查。**遙操作不只是收集示範資料，也是一種診斷實驗。**

> **實驗 6-10 ★ 真機遙操作**：多輪重複，記錄相機畫面、操作者輸入、手臂狀態、動作時間、抓取失敗、重試、最終狀態。驗收不能只看「似乎收拾好了」：杯子在托盤內、廢紙在垃圾盒內、手臂回到安全姿態、全程無碰撞越界、**無未經確認的人工代做**。
>
> **實驗 6-11 ★ 模擬器理想控制上限**：二維桌面模擬器隨機擺放，理想控制器（不辨識影像、不選錯動作）→ 「感知與決策都正確時至少能做到什麼」；測成功率、步數、路徑長度，改變初始位置與規模。**非致動模擬，不代表真機已運行。** 兩條參考線：6-10 是真實硬體上的**人類閉環**；6-11 是模擬中的**理想閉環**。

### 10.2 機器人控制的基本結構

| 層級 | 核心問題 | 輸出 | 時間尺度 |
|---|---|---|---|
| 任務目標 | 人想完成什麼 | 「把杯子和廢紙歸位」 | 分鐘 |
| 長程規劃 | 先做什麼後做什麼 | 先杯子、再廢紙、最後檢查 | 秒到分鐘 |
| 基本技能 | 要完成哪個狀態變化 | `pick(red_cup)`、`place(red_cup, tray)` | 約 1–3 秒 |
| VLA / 技能策略 | 技能具體怎麼動 | 夾爪的一小段動作或連續軌跡 | 約 1–10 Hz 推論 |
| 底層控制與安全層 | 如何穩定及時地執行 | 關節/末端控制量、限速、緊急停止 | 約 50–1000 Hz |

- 常見工程分工，不是唯一架構（VLA 可承擔部分高層判斷；規劃器可以是規則、VLM 或最佳化器）。
- 但**一定要把「任務順序」和「眼前動作」分開**：否則高層推論延遲拖慢底層控制，底層高頻控制又讓高層處理大量無關細節。
- 對 XLeRobot：**模型不直接輸出任意關節角**；只選 `pick`、`place`、`verify_state`、`stop` 等有邊界的技能，由經標定、限速、帶逾時的執行器變成真實動作。

> 呼應第四章 ACI 與第五章「約束優先於指導」：給模型一組**有邊界的動作原語**，而不是無限制的關節空間——就像給 Coding Agent 結構化的 `apply_patch` 而不是任意寫檔。

### 10.3 長程規劃與任務分解

```text
處理紅色杯子 → 清理黃色紙張 → 檢查桌面
         └─ pick(red_cup) → place(red_cup, tray) → verify_state()
```

- 每完成一個技能就得到一個**可檢查的節點**；抓取失敗只重試當前步；物體被挪動或目標改變只重規劃受影響的後續步驟。
- 工具要簡單：**一次呼叫只做一件事、動作範圍固定、有逾時、執行後立即重新觀察**。

> **實驗 6-12 ★★ Gemini Robotics-ER 1.5 自主整理**（真機；RoboCrew 風格智慧體迴圈）
> - 只開放五個工具：`observe_scene`、`pick`、`place`、`verify_state`、`stop`。
> - 每個技能後**必須重新觀察檢查後置條件**；失敗只重試當前技能；使用者喊停、物體離開工作區、狀態無法確認時必須 `stop`。
> - **模型不能直接輸出任意關節角，也不能僅憑自己說過「已完成」就跳過真實檢查。**
> - 驗收與 6-10 完全相同；任務語義必須來自模型觀察、動作必須來自工具呼叫、最終狀態必須由新觀察確認；人只負責啟動、急停、安全監護。→ 可直接比較「**同一硬體、同一任務，人類閉環與模型閉環之間還差什麼**」。

### 10.4 VLA 控制

```text
當前觀察 + 技能指令 → 動作
```

- 高層只提交 `pick(red_cup)`；VLA 決定從哪個方向接近、夾爪何時閉合、以什麼軌跡抬起；執行後重新拍攝，**確認杯子確實被夾住**才允許 `place`。
- **工具呼叫定義期望的狀態變化；VLA 定義如何透過連續動作實現它。**

| 路線 | 代表 | 特點 |
|---|---|---|
| 離散動作 token | **RT-2、OpenVLA** | 像生成文字一樣逐個輸出；易與語言模型結合 |
| 連續軌跡 | **π₀** | 直接生成連續平滑軌跡；更適合平滑運動 |

> 真正的取捨在**動作怎麼表示**，而不只是模型大小。

**動作分塊（action chunking）**：大模型每秒推論 1–10 次，控制器每秒更新幾十到上千次 → 模型一次生成一小段未來動作，控制執行緒高頻執行，模型在背景準備下一段，把推論等待藏進執行時間。

> ⚠️ **代價**：動作段越長越平滑，但這段時間看到的新畫面越少——杯子被碰動時，它可能仍在執行根據舊畫面生成的動作。**動作分塊是平滑性與反應速度的取捨，不是免費加速。**

### 10.5 VLA 的局限

| 局限 | 說明 |
|---|---|
| **訓練資料有限** | 機器人示範遠少於網路文字影像；見過「杯子」這個詞 ≠ 見過各種材質與摩擦下的杯子 |
| **只學會模仿，不一定懂後果** | 行為複製學的是「示範者下一步怎麼做」，沒要求回答「這個動作會造成什麼」 |
| **機器人各不相同** | 自由度、座標系、夾爪、執行器延遲不同，動作不能直接搬 |
| **觀察可能過時** | 動作塊執行中物體被移動、遮擋、碰倒，模型仍依上一幀決策 |

> 語言模型知道「杯子」是什麼，不代表知道摩擦、接觸、液體晃動、電源線怎樣改變未來狀態。**VLA 回答「現在該做什麼」；還需要另一類模型回答「做了之後可能發生什麼」。**

### 10.6 世界模型

```text
當前狀態 + 候選動作 → 預測下一狀態或未來片段 → 比較候選結果
                    → 選擇動作 / 重新規劃 / 安全停止
```

- 三件事：**看懂目前狀態、預測不同動作的結果、把預測交給規劃器或控制器**。
- 只會描述影片的 VLM 或只會生成畫面的模型**不會自動變成可靠的機器人世界模型**——它必須知道動作是什麼，並能預測動作對物體與環境的影響。
- **V-JEPA 2**（Meta）：在內部狀態中預測未來；**World-Action Model**：明確學習「動作—未來觀察」關係。可與 VLA 配合，不必取代。

| 用法 | 說明 |
|---|---|
| **動手前** | 比較抓取、推動、等待等候選，選風險小的 |
| **執行時** | 真實觀察 vs. 預測，偏差就縮短動作、停止或重規劃 |
| **訓練時** | 用影片、模擬、失敗軌跡學狀態變化，減少真機試錯 |

例：廢紙被杯子部分遮住 → 比較「先抓紙」「先移杯子」「換抓取方向」，**不需要生成逼真影片**，只要能預測哪個更可能讓紙變得可抓、哪個可能碰倒杯子。

> ⭐ **動作執行後，真實攝影機觀察仍是最終事實；預測只能幫助選擇，不能代替驗收。** 預測越遠誤差越大；逼真的未來畫面也可能不符合真實的接觸與摩擦。需要短期預測、即時觀察、不確定性估計、**獨立的硬體安全控制器**。**「會生成影片」≠「能指導機器人動作」**（Genie 3、Cosmos 可做互動模擬或視覺化）。

> **實驗 6-13 ★★ 模擬器中三種閉環對比**（同任務、同五工具；抓取偶發可恢復的瞬時失敗）
>
> | 策略 | 做法 |
> |---|---|
> | **開環執行** | 一次生成完整動作序列，中途不重新觀察 |
> | **逐步檢查** | 每個 `pick`/`place` 後重讀狀態，失敗只重試當前技能 |
> | **預測式執行** | 再加短期世界模型，先比較候選技能預期結果 |
>
> 比較成功率、工具呼叫開銷、失敗恢復能力，並檢查成功是否都由 `verify_state` 的**新觀察確認**。要驗證的基礎關係：**開環會把一次局部失敗帶到任務末尾；逐步檢查能恢復；動作預測進一步幫候選排序；最終是否完成仍由環境回饋決定。**

### 10.7 從模擬到真實（Sim2Real）

6-13 在模擬中穩定 ≠ 6-12 真機會同樣成功。部署時同樣的杯子、廢紙、托盤、垃圾盒出現在**不同背景、光照、相機位置、遮擋**中；手臂遇到**不同摩擦、感測器雜訊、執行器延遲**——差異夠大，模擬中學會的動作就可能失效。

> **實驗 6-14 ★★★ RGB 跨環境測試**：每個樣本是整理桌面中的一個局部決策（依 RGB 判斷往哪個方向接近，或是否已可抓取）；四種結構相同的視覺策略——只看固定畫面 / 改變背景 / 改變物體外觀 / 同時改變背景、外觀、光照、雜訊（**域隨機化**）；在原始與新環境測試準確率。回答的是窄問題：**訓練時主動擴大畫面變化範圍是否有助於適應新相機畫面**；即使改善，真機仍需相機標定、執行器測試、完整安全閉環。

## 11. 全章共享的控制骨架與原語 ⭐⭐⭐

```text
持續感知
  → 判斷當前狀態與時機
  → 選擇回覆或動作
  → 讓輸出進入環境
  → 觀察回饋
  → 繼續、修正、重試、停止或重新規劃
```

| 原語 | 事件驅動（秒—天） | 語音（毫秒—秒） | Computer Use | 機器人（毫秒） |
|---|---|---|---|---|
| **喚醒** | 定時器、Channel、monitor | VAD / 端點判斷 / 全雙工持續決策 | 關鍵影格、音量門控 | 感測器回流 |
| **安全點** | 推理結束、工具返回 | 一句話/片段邊界 | 每個動作後重新截圖 | 每個技能後 `verify_state`、每個控制週期 |
| **取消** | 取消串流、取消工具、佔位符 | 使用者插話打斷 TTS | 偏離預期就停 | 丟棄剩餘 chunk、急停 |
| **搶佔** | 取消式處理緊急事件 | 全雙工打斷 | — | 安全事件搶佔動作塊 |
| **快慢分離** | 並行式處理輕量查詢 | 前台互動 + 背景推理 | 世界模型推測執行 | 高層規劃 1–10 Hz + 底層控制 50–1000 Hz |

## 12. 設計觀念整理

| 觀念 | 本章體現 |
|---|---|
| **回合制是約定，不是環境性質** | 原生非同步（Astra）與相容層兩條路線 |
| **事件要能主動通知 Agent** | PineClaw Channel 把分鐘級延遲降到秒級 |
| **結構化事件防混淆、防注入** | 來源、渠道、內容、上下文四維建模 |
| **安全點決定何時能消費事件** | 佇列＝等自然安全點；取消＝製造安全點；並行＝不等 |
| **不偽造成功** | 佔位符顯式標未完成；檢查是否編造未抵達的資料 |
| **工具名就是語義** | `initiate_phone_call` 傳達「發起而非完成」 |
| **修改計畫 ≠ 撤銷動作** | steering 改的是後續，已發生的副作用要靠執行階段處理 |
| **虛擬身份隔離數位身份** | 秘書有自己的郵箱；必要時 HITL 認證 |
| **互動品質與智能上限是兩個維度** | 快慢分離承接慢模型紅利；兩種「端到端」是兩條軸 |
| **重新設計觀察介面** | AOI：關鍵影格、音量門控、畫面敘述成文字 |
| **選擇題勝過填空題** | SoM / DOM 索引把座標預測變成 ID 選擇；解析度按寬高比匹配 |
| **預測幫助選擇，觀察負責驗收** | 世界模型不能代替 `verify_state` |
| **固定硬體、替換操作者** | 遙操作證明瓶頸在演算法 |
| **任務順序與眼前動作分開** | 分層控制；模型只選有邊界的技能 |

## 15. 思考題摘要（含書附參考答案要點）

| # | 題目 | 參考答案要點 |
|---|---|---|
| 1 ★★ | 事件優先順序需要語義理解時，該由規則引擎還是 LLM 判斷？ | **分層混合**：型別明確的事件用規則硬編碼（零延遲、確定，但分不出「馬上停下來」與「今天天氣」）；語義模糊的交給**輕量分類 LLM 路由器**——代價是數百毫秒、額外費用、可能誤判，且要像 Sidecar 一樣只讀結構化欄位防注入 |
| 2 ★★ | 佇列積壓 20 個事件，如何組織呈現使模型不遺漏？ | 先用規則 + 輕量 LLM **分類去重**；緊急事件（告警、使用者中斷）單獨走取消式，不混入批次；超長工具結果截斷持久化到檔案，只留頭尾與路徑；末尾狀態列加**彙總清單**（各類數量 + 要求逐條回應） |
| 3 ★★★ | 虛擬身份 vs. 以使用者本人身份操作，什麼場景選哪個？ | **預設虛擬身份**：後台自主、可稽核，被攻破時不暴露全部數位身份；需應對 CAPTCHA/IP 信譽（住宅代理）。必須本人的場景（帳戶驗證、三方通話確認）用 **HITL 認證**（VNC/RDP 親自登入）。判準：**對方是否要求帳戶持有人本人**、操作風險與憑證範圍 |
| 4 ★★ | 端到端語音難以除錯，如何設計可觀測性？ | 讓模型伴隨輸出**可讀中間表示**（Moshi 的「內心獨白」文字流、`<emotion>`/`<noise>` 等聲學標記）；用**自級聯**定位錯誤層（同模型先轉錄再推理，對照端到端結果，判斷錯在感知還是思考）；離線按副語言理解、輪次判斷等維度分項迴歸 |
| 5 ★ | 「邊想邊說」該模仿人類的填充詞與自我糾正嗎？ | 模仿**有訊號價值**的不完美：停頓、填充詞是思考的外化，可掩蓋延遲，由 LLM 決定插入位置；**不模仿破壞信任的自我糾正**——快慢矛盾（「到底買不買？！」）讓信任崩塌；MPS 顯示 CoT 開頭多是複述問題，**早開口說鋪墊是安全的**，無需說錯再改 |
| 6 ★★ | 標註不完整時要回退到座標預測嗎？ | 應保留座標預測**兜底**——唯一不依賴標註的路線；更實用的是**混合動作空間**：可標註的元素仍用 ID。座標預測須做解析度匹配與等比縮放 |
| 7 ★★ | 不熟練操作者的遙操作資料如何影響 VLA？如何篩選？ | VLA 主要靠模仿學習，**低品質示範會把抖動、繞路、猶豫與失敗動作當成正確策略學進去**。呼應第八章：**資料比架構更關鍵** |
| 8 ★★★ | 若從序列管道走向端到端的趨勢延續，五年後互動層會怎樣？ | 依 Thinking Machines Lab 主張，**互動性內建於模型**而非外掛 harness，隨智慧一同擴展；Computer Use 從逐幀截圖走向連續觀察；具身世界模型全面實現；但前沿推理模型發展快，**快慢解耦不會消失**——互動模型 + SOTA 思考模型的協同可能是長期架構 |
| 9 ★★ | Computer Use 押注純視覺，還是維護結構化與視覺兩條路？ | **短期雙路徑並存**：結構化索引可得時最準穩；純視覺是原生軟體、Canvas、遊戲的唯一選擇。模型 grounding 能力強時結構化索引優勢不顯著；**長期純視覺上限更高** |
| 10 ★★ | 動作分塊的效率與環境突變的反應如何平衡？ | 分塊本質是**拿反應性換平滑性**；塊長只需滿足「推理時間 < 塊執行時間」的下限，不盲目加長；執行中讓感知模型持續運行，偵測突變即**丟棄剩餘動作重新推理**（相當於語音的「打斷」）；靜態場景長塊省算力、動態場景短塊保反應 |
| 11 ★★★ | 「說錯再糾正」「先點再看」「走一步看一步」如何避免不可挽回的後果？ | **按可逆性給動作分級**：快思考只許執行可逆動作；不可逆操作交慢思考把關；快模型不允許執行會造成不可逆後果的工具呼叫 |
| 12 ★★★ | 任選一原語比較事件驅動與機器人動作分塊的實作差異；由什麼決定？ | 以「取消」為例：事件驅動在**兩次工具呼叫之間的安全點**取消，秒級延遲可接受；動作分塊必須**毫秒內生效**，丟棄剩餘 chunk 重新觀察，慢一步就撞上障礙。**觀察取得成本最不關鍵**（兩邊都能廉價重新觀察）；決定差異的是 **環境變化速度**（安全點要多密集）× **動作可逆性**（錯過安全點的代價——多發一封郵件可以補道歉，撞倒的杯子無法撤銷）。規則：**安全點密度匹配環境變化速度；安全點之外需要多少額外防護（硬體急停、獨立安全控制器、二次確認）取決於動作多不可逆**——這也解釋了第四章高風險操作用事前審批、機器人用獨立於模型的硬體安全層 |

## 16. 本章重點整理

1. 本章撤掉「**Agent 與世界輪流發言**」的前提；擴展觀察與動作空間的**模態**與**時機**兩根軸；**回合制是互動約定，不是環境性質**。
2. 四個時間尺度：事件驅動（秒—天）、語音（10 ms—1 s）、Computer Use（亞秒—秒）、機器人（毫秒）。
3. **事件驅動**：OpenClaw 的 Hooks/Cron/Heartbeat 只有時間驅動能讓 Agent 自主動起來 → PineClaw **Channel** 讓事件主動通知 Agent（分鐘級 → 秒級）。
4. **事件觸發工具**（定時器、`monitor_shell`、`connect_channel`）與**使用者溝通工具**（專門工具發訊息、多渠道、通知即召回、「活人感」）。
5. **虛擬身份 + 隔離環境**（虛擬電腦/手機、住宅代理、HITL 認證、共享檔案系統傳路徑）。
6. **事件迴圈與安全點**；結構化事件四維建模；**取消式 / 佇列式 / 並行式**三種策略；用輕量 LLM 作事件路由器；取消點要能安全收尾，未完成要顯式標示。
7. **相容方案五規則**：常態保持標準同步軌跡，只在打斷時插佔位符；**啟動與完成解耦**（`initiate_phone_call`）；用狀態列標記與彙總防只回應最後一個事件。
8. **GPT-6 Astra**：非同步工具呼叫 + 回合中途引導；修改計畫 ≠ 停止或撤銷動作；檢查結果歸屬、任務恢復、多更新綜合。
9. **語音三範式**：級聯（模組清楚、延遲累積）→ Omni（保副語言、仍按輪次）→ **全雙工**（持續聽說決策）；串流感知（邊聽邊轉、推測執行、分段輸出、增量合成）；端點判斷只用決策時刻可見資訊。
10. **認知時序**：快應付慢回答（會矛盾）、快互動慢建議（不能真正邊想邊說）、端到端統一（Step-Audio R1：MGRD + MPS）；**快慢分離承接慢模型紅利**（Pine AI τ³-Voice 第一）；兩種「端到端」是兩條獨立的軸。
11. **Computer Use**：看懂介面 ≠ 完成任務；動作空間（computer / bash / editor）；**視覺定位**：SoM、DOM/Accessibility 索引、座標預測（**按寬高比匹配解析度並雙向縮放**）。
12. **AOI** 重新設計觀察介面（關鍵影格、音量門控、畫面敘述成文字）；**世界模型**讓 Computer Use 推測執行（Photon-1）；移動端的真正障礙是**商業模式衝突**。
13. **機器人**：XLeRobot 遙操作證明**硬體不是瓶頸、演算法才是**；分層控制（任務 → 規劃 → 技能 → VLA → 底層安全）；模型只選**有邊界的技能**；每步 `verify_state`。
14. **VLA**（RT-2/OpenVLA 離散 token vs. π₀ 連續軌跡）；**動作分塊是平滑與反應的取捨**；VLA 回答「現在做什麼」，**世界模型**回答「做了會怎樣」，但**預測只能幫助選擇，不能代替驗收**；Sim2Real 用域隨機化測試適應性。
15. 全章共享一條控制骨架與一組原語：**喚醒、安全點、取消、搶佔、快慢分離**。

> **一句話**：真實世界不會等模型想完——讓 Agent 能被世界喚醒、在安全點接受打斷、用快慢分離兼顧即時與深思、以有邊界的動作原語行事，並且永遠以新的觀察而不是自己的預測或宣稱來判定任務是否完成。
