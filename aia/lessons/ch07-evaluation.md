# 第 7 章　Agent 的評估

> 《深入理解 AI Agent》— 李博杰，第七章（第三部分「評估與進化」的第一章）

---

## 1. 本章定位

前六章完成了單 Agent 的建構。但**建構完成 ≠ 建構正確**；只有能穩定測量結果，後續的訓練與進化才有可靠方向。

開發者面對大量沒有明顯正確答案的設計選擇：用什麼模型？開哪些工具？知識庫存什麼、怎麼組織？使用者記憶怎麼做？提示詞與 Skills 怎麼組織？Harness 要加哪些約束？評估結果怎麼變成進化的學習訊號？

| 方法 | 做法 | 回答 |
|---|---|---|
| **對比實驗** | 改變一個變數，看效果變化 | 這個改動有沒有用 |
| **消融實驗**（ablation） | 逐一**關閉 Harness 的某個元件** | Harness 內部哪個部件重要 |
| **模型替換實驗**（model swap） | **固定 Harness，只換模型** | 瓶頸在模型還是在 Harness |

> ⭐ **評估的物件不應只是模型，而應是模型與 Harness 的組合體。** 同一模型在不同 Harness 中可能差異懸殊（第五章 LangChain 只改 Harness 就大幅提升）。
>
> **Model swap 解讀**：換強模型分數不漲 → 瓶頸在 Harness；換弱模型分數大跌、分數隨模型能力大幅波動 → 表現主要由模型決定（是任務本身難，還是 Harness 過度依賴模型先驗，要再分析）。

**為未來的模型開發產品**：新模型在公開基準更好 ≠ 在你的任務上更好（可能 regression）；有了自己的評估集，即使現在模型不夠，也可以先完成產品與評估集，持續追蹤新模型，一達門檻就上線。

**評估體系的四個環節**：

```
什麼算成功（指標） → 任務從何而來（資料集） → 由誰驗證（驗證器） → 分數如何轉為決策
```

> 全書定位：本章建的是第一章發現迴圈中的**證據**段——失敗歸因決定後續的提案（第三章）有沒有可依之據。

## 2. 一條評估任務的解剖：τ²-bench telecom ⭐⭐⭐

τ²-bench 是 Sierra 的開源專案；任務檔 `data/tau2/domains/telecom/tasks_small.json`。

```jsonc
{
  "id": "[mobile_data_issue]airplane_mode_on|user_abroad_roaming_enabled_off",
  "ticket": "使用者手機無法上網，狀態列顯示 'No Service'。客戶 John Smith，號碼 555-123-2002，
             目前在法國。速度測試結果為 excellent 才算解決。不更換套餐，必要時願意充值 2.0 GB 流量。",
  "user_scenario": { "instructions": {
      "known_info": "You are John Smith with phone number 555-123-2002. You are currently abroad in France.",
      "unknown_info": null,
      "task_instructions": "…express mild frustration after the first unsuccessful attempt.
         You will consider the issue resolved only when speed test returns excellent …
         always ground your responses on the results of tool calls. … Never make up the results of tool calls."
  }},
  "initial_state": { "initialization_actions": [
      { "env_type": "user",      "func_name": "turn_airplane_mode_on" },
      { "env_type": "user",      "func_name": "turn_roaming_off" },
      { "env_type": "assistant", "func_name": "enable_roaming",
        "arguments": { "customer_id": "C1001", "line_id": "L1002" } } ]},
  "evaluation_criteria": {
      "actions": [ { "requestor": "user", "name": "toggle_airplane_mode" },
                   { "requestor": "user", "name": "toggle_roaming" } ],
      "env_assertions": [ { "func_name": "assert_mobile_data_status", "expected_status": true },
                          { "func_name": "assert_internet_speed", "expected_speed": 200, "expected_desc": "excellent" } ],
      "communicate_info": null, "nl_assertions": null,
      "reward_basis": ["ENV_ASSERTION"] }
}
```

### 2.1 四處設計

| 設計 | 說明 |
|---|---|
| **顯式建模使用者的認知邊界** | `known_info` 只有姓名、號碼、所在國家；真正的故障原因（飛航模式開、漫遊關）不在其中 → 使用者不知情、無法主動陳述 → Agent 只能提問、引導使用者查詢。這是**漸進式資訊透露**在任務定義層的實作：不是靠一句「不要一次說完」的提示詞，而是把使用者知識範圍建模為獨立欄位 |
| **防止使用者模擬器被 Agent 忽悠** | 三類約束：**情緒**（首次失敗後輕度不滿）、**驗收口徑**（只有 excellent 才算解決）、**事實錨定**（裝置狀態必須以工具返回為依據）。缺少事實錨定 → 模擬使用者會順著 Agent 的引導確認「已解決」→ **評估退化為兩個模型互相確認** |
| **雙方都不具備完全資訊** | 飛航模式與漫遊開關在**使用者側**；營運商側 `enable_roaming` 在 **Agent 側**。故障形態：營運商側已開通、裝置側關閉 → Agent 查資料庫只會得到「配置正常」→ 故障在資料庫不可見的一側，只有引導使用者查詢才能發現 |
| **多維度的過程與結果校驗** | `env_assertions` 驗終態；`actions` 驗關鍵動作是否發生；`communicate_info` 與 `nl_assertions` 驗必要資訊是否告知使用者 |

### 2.2 一次真實執行的軌跡

> **實驗 7-1 ★ 執行 τ²-bench 並對比 τ-bench 的演進**：通讀任務定義（已知資訊、任務指令、初始狀態、成功條件）→ 執行評估 → 觀察多輪對話 → 分析失敗模式（政策違規、資訊遺漏、過度轉接人工）。

**成功軌跡**（`reward = 1.0`）：
- 前十餘輪為帳戶識別：查得客戶 C1001，逐一查 L1001/L1002/L1003 流量。
- 第 17 條給出**錯誤結論**：「號碼 555-123-2002 不在您的活躍線路中」——只基於 L1001 一條查詢；使用者堅持後才查 L1002 對上。
- 第 30 條**使用者**呼叫 `check_network_status()`、`check_status_bar()` → `Airplane Mode: ON | ... | Data Roaming Enabled: No`。
- ⭐ **雙控（Dual-Control）**：發出工具呼叫的是**使用者**而非 Agent——模擬使用者有自己的工具集（`check_status_bar`、`toggle_airplane_mode`、`reseat_sim_card`、`run_speed_test`）。
- 關飛航、開漫遊 → 測速 275 Mbps Excellent → 兩條 `env_assertions` 通過。

**滿分軌跡中未被捕獲的問題**：政策首段「You should only make one tool call at a time」，但第 4 條一次發了 `get_customer_by_phone` 與 `get_customer_by_name`。驗證器沒抓到，因為 `reward_basis` 只看終態。

> 這不是疏漏，而是**二元獎勵的固有代價**：用過程顆粒度換取跨模型可比的單一數字。生產評估往往需要更多——不只判對錯，還要指出問題出在哪。

**失敗軌跡**：Agent 選了 L1001（3.2/5 GB 用量）；`get_details_by_id(L1001)` 明確返回號碼 555-123-2001，**它讀到了卻沒修正判斷** → 數十條無關排查 → 轉接人工。完成了一半（引導使用者關閉省流模式，被環境驗證），但線路錯誤導致 2 GB 充值未執行 → 三條終態斷言全失敗。

> 與後文 AndroidWorld 案例同型：**修正判斷所需的證據已進入上下文，Agent 未據此回溯。**

## 3. 評估指標：成功的定義 ⭐⭐⭐

五條任務過四條 = 0.8——它可用嗎？退款客服：五分之一的使用者拿不到應得退款；挖漏洞的安全 Agent：五次中四次已屬可觀。**差別在業務場景對成功率的要求。**

### 3.1 技術奇觀：Pass@k 看能力上限

- **Pass@k**：同一任務跑 k 次，**至少一次通過**就算通過；連續得分則取最好的一次，記為 **Best@k**。
- 適用：科研發現、漏洞挖掘、開放式創作——人類可以從 k 條候選中挑最好的。
- Anthropic 長時 Agent：自主工作一週從頭寫出 C 編譯器、找重要數學猜想的反例、找到存在幾十年的重大安全漏洞。
- 應用公司也用「技術奇觀」：**Manus**（虛擬電腦、持續工作半小時到一小時）、**OpenClaw**（「活人感」、IM 派任務、主動回饋、自己喚醒去查郵件）。早期成功率不高、token 很貴，但通用框架 + 最強模型 → 複雜任務 Pass@k 高 → 在社群被大量分享，是產品成功的關鍵。

### 3.2 業務可靠性：Pass^k

- **Pass^k**（讀作 Pass consecutive k）：同一任務連續跑 k 次，**每一次都通過**，且不觸發安全、合規、幻覺等一票否決項。
- 若各次獨立、單次成功率 p：

```
Pass@k = 1 − (1 − p)^k
Pass^k = p^k

p = 0.6, k = 5：
  Pass@5 = 1 − 0.4^5 ≈ 99.0%   ← 幾乎總能「至少成功一次」
  Pass^5 = 0.6^5     ≈ 7.8%    ← 連續五次都不出錯仍很難
```

- 前者衡量探索的天花板；後者才接近支付、退款、權限變更、生產部署的可靠性要求。
- 報告必須寫清 **k 次的口徑**：同一任務的 k 次獨立取樣，還是生產流水線上連續 k 個任務？
- **有副作用的操作不能「重試直到成功」**，應在沙盒或可回滾環境中取樣，每一次失敗都記入可靠性指標。

> 對照 Ferguson《Cryptography Engineering》：安全系統看的是「最弱的一次」而非「最好的一次」——Pass^k 就是業務 Agent 的「安全邊際」思維。

## 4. 評估環境 ⭐⭐

**評估環境** = 一套能重複執行的裝置：同一初始狀態 + 同一 Agent → 可比較的結果。

### 4.1 五個組成要素（以 telecom 任務為參照）

| 要素 | 在 telecom 中 | 要點 |
|---|---|---|
| **資料集** | 任務檔：初始狀態 + 工單 + 模擬器規範 + 驗收標準，一條記錄一個用例 | — |
| **環境狀態** | 資料庫中的客戶、線路、套餐、帳單 + 裝置側的飛航、漫遊、省流開關、剩餘流量 | **可重置**（`initialization_actions` 即重置腳本）；真實性（符合業務邏輯）+ 可控性（每次回到同一起點） |
| **工具介面** | Agent 側：查客戶、查用量、充值、轉人工；使用者側：裝置開關 | **原子操作**——不存在「解決使用者上網問題」這類高層抽象，否則規劃與推理被工具吸收，評估退化為考單次函式呼叫 |
| **評分標準** | `evaluation_criteria` 四層檢查 + `reward_basis` 聚合規則 | — |
| **執行協定** | 模擬使用者輸出 `###STOP###`；輪數上限；模擬使用者耐心耗盡主動結束 | **溝通效率過低本身即計為失敗** |

### 4.2 人機互動型 vs. 工具呼叫型

- **工具呼叫型**（程式碼、資料分析、數學）：沒有對話對方，只與工具互動，正確性由執行驗證；環境狀態是檔案系統或資料庫，評分是測試程式碼，協定退化為「持續呼叫工具直到給出答案或耗盡輪次」。
- **Verifiers 框架**的環境分層（表 7-1）：

| 環境型別 | 狀態保持 | 工具呼叫 | 典型用例 |
|---|---|---|---|
| `SingleTurnEnv` | 無 | 無 | 單輪問答、數學題 |
| `ToolEnv` | 無 | 多輪 | 搜尋 + 資訊綜合 |
| `StatefulToolEnv` | 有 | 多輪 | 修改資料庫記錄 |
| `SandboxEnv` | 有 + 隔離 | 多輪 | 程式碼執行與測試 |

- 支援並行取樣與軌跡快取（觀察、行動、獎勵全保存），便於分析回放；工具失敗要返回清晰錯誤而非單一失敗標誌。

> **工具呼叫型驗證行動；人機互動型驗證引導。**

## 5. 評估資料集的設計 ⭐⭐⭐

### 5.1 基準設計的橫向對照（表 7-2）

| 基準 | 被測能力 | 任務來源 | 環境扮演者 | 驗證器 |
|---|---|---|---|---|
| **τ²-bench** | 客服人機互動 + 工具呼叫 | 人工編寫 + 組合生成 | 使用者模擬器 + 業務資料庫 | 四層檢查按 `reward_basis` 聚合為二元 |
| **SWE-bench Verified** | 軟體開發 | GitHub 真實 issue，人工篩選 | 程式碼倉庫 + 測試套件 | FAIL_TO_PASS / PASS_TO_PASS 雙重驗證 |
| **AndroidWorld** | 操作 Android GUI | 參數化範本實例化 | 真實 Android 模擬器 | 最終 UI 狀態斷言 |
| **OSWorld** | 操作 Linux 桌面 | 從預置中間狀態啟動 | 真實虛擬機 | 134 個獨立評估函式 |
| **Terminal-Bench** | Linux 終端、coding | 人工編寫 | Docker 容器 | 檔案系統檢查 + 真實執行 |
| **GAIA** | 蒐集資訊的通用助手 | 人工編寫 + 專有附件 | 開放網路 | 精確字串匹配 |

### 5.2 驗證器：核實事實，而非 Agent 的自我陳述

> Agent 很容易寫一篇洋洋灑灑的報告說任務全部完成，但事實上根本沒完成。

- **SWE-bench Verified 把「修復完成」拆成兩個獨立命題**：
  - **FAIL_TO_PASS**：修復前失敗、修復後通過 → 問題確已解決；
  - **PASS_TO_PASS**：修復前後都通過 → 未引入新缺陷；
  - 只驗前者 → Agent 可刪改妨礙通過的斷言矇混；只驗後者 → 等於沒驗。兩組同時 → 「已修復」與「未破壞」各自可證。另確認測試自身穩定，排除 **flaky test**。
- **OSWorld**：134 個評估函式、完整 OS 權限；資料庫任務不只確認報告檔存在，還連線資料庫核實 SQL 是否執行；瀏覽器任務分析 DOM、檢查 cookie 與 localStorage、向後端發驗證請求。
- **Terminal-Bench** `build-linux-kernel-qemu`：從原始碼建構 Linux 6.9、在 `start_kernel` 加自訂 printk、生成 initramfs、在 QEMU 執行，成功標準是**啟動日誌出現該訊息**——無法偽造。

> 對照 Hanson《C Interfaces and Implementations》：FAIL_TO_PASS + PASS_TO_PASS 就是「新功能的測試 + 迴歸測試」——兩者缺一，介面契約都無法被證明仍成立。

### 5.3 難度劃分：讓評估集不快速過時，並具診斷價值

**GAIA** 466 題三級：

| 級別 | 需要 | 人類 | GPT-4 | 失敗指向 |
|---|---|---|---|---|
| Level 1 | 1–2 個工具 | 93.9% | 30.3% | 基礎工具使用 |
| Level 2 | 多步思考 | 91.8% | 9.7% | 多步規劃與資訊整合 |
| Level 3 | 複雜組合 | 87.3% | 0% | 長序列思考與複雜性管理 |

- **Terminal-Bench**：mlflow 模型註冊（簡單）→ 7z 密碼破解（中）→ git 伺服器 + webserver 多元件整合（難）→ **FEAL 差分密碼分析**（最難）。
- **τ²-bench 陷阱任務**：使用者聲稱「客服已批准取消」，實際不符政策 → 檢驗**壓力與誤導下**能否維持正確判斷。

### 5.4 資料洩漏防範

| 基準 | 手法 |
|---|---|
| **GAIA** | 答案無法直接檢索：概念簡單、路徑開放（從某日 NASA 每日天文圖出發 → 識別宇航員 → 查所屬宇航員組 → 算太空停留最短者 → 嚴格格式「姓氏，分號分隔，千位分隔符」）；必須組合多資訊源；部分附件網路上不存在 |
| **AndroidWorld** | **單一範本派生大量實例**：「將聯絡人 `[CONTACT_NAME]` 的電話改為 `[NEW_PHONE]`」每次隨機參數 → 回放固定操作序列失效、近乎無限實例、可固定部分參數精確測量特定因素 |
| **Terminal-Bench** | **金絲雀識別符號**（canary GUID）：模型若能輸出含該 GUID 的內容 → 資料已進入訓練集。**不阻止洩漏，但使洩漏可被偵測** |

### 5.5 品質控制與長期維護

> 高品質評估集極難；多數現行形態都是初版投入使用、暴露問題後**逐輪修補**的結果。

**τ-bench → τ²-bench 的五處重新設計**：

| # | 問題 | 改法 |
|---|---|---|
| 1 | 任務指令過於籠統，**答案可被猜測** | 劇本拆成 `known_info` 與 `task_instructions`；使用者不知悉的資訊 Agent 無從推測 |
| 2 | 成功條件不精確，驗證誤判 | 「網路已恢復」→「測速 excellent 才算解決」——針對**敷衍性修復**（壓症狀不解根因） |
| 3 | 使用者模擬器過於機械 | 補上情緒、耐心上限、事實錨定——接近真實又保持可復現 |
| 4 | 使用者不只參與對話也參與操作 | **雙控環境**；使用者改變狀態後 Agent 必須重新呼叫工具才能獲知 → 驗證覆蓋「Agent 是否真的讀到了使用者側的結果」 |
| 5 | 任務實例動態生成 | 姓名、號碼、故障組合參數化批次生成 → 覆蓋率 + 抗洩漏 |

- **SWE-bench Verified：發布前淘汰 71%**——OpenAI 從 2294 題隨機抽 1699 題，93 名精通 Python 的開發者逐條檢查（描述清晰？測試覆蓋邊界？穩定？參考 patch 引入新錯？難度合理？）→ 僅 **500** 題通過。高淘汰率 → 訊雜比更高、評估成本降約 **80%**（完整跑一遍前沿模型常要數千美元）。
- **OSWorld：發布後 15 個月暴露 300 餘個問題**——環境（反爬、CAPTCHA、動態內容）、描述歧義、驗證過嚴/過鬆、初始狀態不完整；港大約 10 人小組與 MoonShot AI、OpenAI、ByteDance Seed TARS、Anthropic、Simular 合作兩個月修復（鎖版本與離線備份、改寫歧義、人工建立正確基線、完整性校驗）。

> **實驗 7-2 ★ 人肉執行基準任務**：從 GAIA、AndroidWorld、SWE-Bench Verified、Terminal-Bench、OSWorld-Verified 各挑簡單、中等、困難一題親手完成。回答：① 描述是否有多種合理解釋？驗證器認可哪一種？② **若想矇混過關，成本最低的路徑是什麼？驗證器能否攔截？**

### 5.6 評估集的三個來源

| 來源 | 用途 | 特點 |
|---|---|---|
| **公開基準** | 粗篩模型、借鑑設計手法 | 任務分布與業務不一致；GAIA 漲兩個百分點與退款成功率無必然關係 |
| **自建業務集** | 模型選型、Harness 設計決策 | 覆蓋真實任務分布；τ²-bench 可作為需要模擬使用者的骨架，換領域資料與工具即可 |
| **生產軌跡迴流** | 迴歸用例 | 使用者糾正、點踩、事後狀態檢查/規則驗證器/LLM 評審發現的問題 → 失敗歸因 → 沉澱。**成本最高、準確性也最高** |

起步時只有公開基準 + 少量手寫業務集；上線一段時間後，**生產迴流用例成為主體**。

## 6. 自動化評估方法 ⭐⭐⭐

公開基準的驗證器幾乎都是**確定性**的（跑測試、斷言 UI 狀態、字串匹配）：不引入模型開銷、完全可復現、可納入 CI、便於跨模型排名。**代價**：只能說結果對不對，不能給錯誤原因——τ²-bench 那條失敗得 0 分，不會告訴你是線路選錯還是漏充值。另外，許多判斷寫不成斷言：投訴回覆是否得體？報告是否遺漏關鍵資訊？記憶檢索是否弄錯人物關係？

**驗證方式譜系**（橫軸：可機械驗證程度）：

```
確定性驗證器 ──→ 檢查項清單 ──→ Rubric + LLM-as-a-Judge ──→ 配對比較
（測試、斷言、匹配）                  （生產評估主體）
```

> ⚠️ **向右移動不意味著放棄左側**：凡是能寫成程式化斷言的都繼續用斷言；LLM 評判只用於確實無法機械判定的維度。確定性檢查更便宜、更穩定、更適合長期迴歸。（呼應第五章「約束優先於指導」。）

### 6.1 LLM-as-a-Judge 與 Rubric

**已知侷限**：
- **長度偏差**：偏向更長更詳盡的回覆，即使內容不更正確。三個防範手段：① Rubric 顯式懲罰冗長、規定長度上限；② 配對比較前先把兩候選長度控制到相近；③ **定期審計評分與回答長度的相關性**——高分幾乎總伴隨長回答 → 評判被長度帶偏，回爐修 Rubric。
- 相同輸入多次評判會波動。

**Rubric 四準則**（Scale AI「Rubrics as Rewards」）：

| 準則 | 要點 |
|---|---|
| **基於專家指導** | 反映領域知識、核心事實與推理步驟（醫療 Rubric 含診斷標準與必須避免的醫學錯誤）；否則只能捕捉語言流暢度 |
| **全面覆蓋** | 事實準確、邏輯連貫、完整性、安全性；不只正面標準，還要明確**陷阱（Pitfall）**——高風險常見錯誤 |
| **標準重要性權重** | 必要項（Essential）、重要項、可選項、陷阱項；支援**一票否決（Veto）**——客服中幻覺必須否決，也防關鍵詞堆砌式獎勵作弊 |
| **自包含評估** | 每項獨立可操作，不依賴評價者領域知識。❌「回應展示了深刻理解」→ ✅「引用了至少兩個權威理論並準確解釋如何支援結論」 |

- 為每個維度定義客觀可驗證的等級、具體示例與**邊界案例**。
- 主動防範 **Reward Hacking**：明確懲罰幻覺、討好使用者、關鍵詞堆砌、迴避棘手問題。
- **Rubric 是迭代產物**：試用收集評價者分歧 → 從抽象準則演化為詳盡的**判例集**。

**範例：使用者記憶 Rubric**（問題「我女兒的兒科醫生是誰？」需跨兩次對話關聯「女兒叫 Lily」+「帶 Lily 看了 Dr. Chen」）

```yaml
rubric:
  dimensions:
    - name: 事實正確性
      weight: essential
      scoring:
        4_優秀: "準確回答 Dr. Chen，且關聯到女兒 Lily"
        3_良好: "準確回答 Dr. Chen，但未提及是 Lily 的醫生"
        2_及格: "給出了正確醫生但附帶不確定的額外資訊"
        1_不及格: "給出錯誤醫生名，或回答不知道"
    - name: 資訊完整性
      weight: important
      scoring: { 4_優秀: "主動補充相關資訊（如上次就診時間、診斷結果）", ... }
    - name: 思考正確性
      weight: important
      scoring:
        4_優秀: "正確關聯'女兒=Lily'和'Lily的醫生=Dr. Chen'兩條跨會話資訊"
        1_不及格: "錯誤關聯（如把使用者自己的醫生當成女兒的醫生）"
    - name: 幻覺檢測
      weight: veto             # 一旦觸發，總分歸零
      scoring:
        pass: "所有資訊均可溯源到歷史對話記錄"
        fail: "編造了對話中不存在的資訊（如虛構就診日期、診斷結果）"
  edge_cases:
    - "如果使用者有多個女兒且分別看不同的醫生，應追問是哪個女兒"
    - "如果記憶中同時存在'Dr. Chen'和'陳醫生'，應識別為同一人"
```

> Rubric 不只給分數，也指出下一步改哪裡：是沒找到資訊、弄錯人物關係，還是加入了沒根據的內容？

> **實驗 7-3 ★★ Rubric 化使用者記憶評估**：把第三章 `user-memory-evaluation` 的單一 pass/fail LLM 評判升級為多維度 Rubric——事實正確性（**Precision**：給出的資訊中有多少正確）、事實完整性（**Recall**：應給的資訊中有多少被提及）、思考正確性、思考主動性、幻覺檢測（一票否決）；四檔制、每檔具體標準、示例與邊界案例。

> **實驗 7-4 ★★ Advanced JSON Cards vs. RAG vs. 混合**（60 題 × 3 = 180 條真實 API 軌跡）
>
> | 系統 | 基礎回憶 | 多會話消歧 | 跨會話隱藏關聯 | 整體 |
> |---|---:|---:|---:|---:|
> | Advanced JSON Cards | 95% | 60% | 50% | 68.3%（41/60） |
> | RAG | 90% | 40% | 15% | 48.3%（29/60） |
> | 混合系統 | 80% | 70% | 50% | 66.7%（40/60） |
>
> - **混合方案沒有自然勝出**：3 題做到兩種單一方案都做不到的事，但另 8 題不如較好的單一方案；與逐題最佳單一方案相比平均更低。
> - 純 RAG 基礎回憶與卡片相近，一到跨會話關聯就跌到 **15%**。
> - 180 次評判中**幻覺否決觸發 28 次**——一票否決項的重要性。
> - 註：這裡的「混合」與第三章 §17 主張的雙層記憶架構方向一致，但**實測說明架構理念 ≠ 自動勝出**，要在自己的評估集上驗證。

### 6.2 同源模型問題與多源評判

- Agent 與評判模型同家族 → Agent 可能學會利用評判的偏好與盲點。
- **古德哈特定律**：當一個度量指標變成最佳化目標，它就不再是好的度量指標。更隱蔽的是，Agent 會**逐漸學會避開評判不擅長偵測的錯誤型別**，讓評分系統看起來一切正常。
- **多源異構評判**：Agent 用 Claude → 評判用 GPT-5 和 Gemini；不同家族偏見往往**正交**，很難同時「欺騙」所有評判者。相同 Rubric、加權平均或一致性檢查；部署時可用單一模型快評，定期用完整多源評判做品質審計。

> 與第三、四章的「異源 Proposer/Reviewer」是同一原理：獨立性來自來源差異。

### 6.3 多模態 LLM-as-a-Judge

| 方向 | 評什麼 |
|---|---|
| **TTS** | 準確性、自然度、音色一致度、情感表達——能發現 WER 抓不到的韻律問題 |
| **ASR** | **語義影響判斷**：「今天天氣」錯無傷大雅；「轉賬一千」變「一萬」可能造成嚴重後果 |
| **UI** | 提議者—審核者作為**評估方法**：文字溢位、對比度、按鈕位置 |
| **影片剪輯** | 關鍵幀驗證起止點與特效 |

> **實驗 7-5 ★★ 全自動 TTS 評估流水線**：準確性、自然度、情感表達、音色一致性四維；多樣語料（長度、文體、情感、數字/專有名詞/多音字/方言）；接 OpenAI、ElevenLabs、Fish Audio、Minimax、豆包；多模態評判直接收音訊；**保存評判模型名稱、參考與候選音訊雜湊**以便追溯複核。

**小規模實測**（OpenAI 與 Fish Audio 各四段，Voxtral 評分）：準確性 5.00 / 自然度 4.00 兩家相同；情感與音色 Fish 4.00 / 3.00、OpenAI 3.75 / 2.75。

> ⚠️ **但還不足以判斷哪家較好**：每家只有四段；更重要的是，**固定參考音訊來自 Fish S1**——用它比音色本來就對 Fish 有利。比通用 TTS 就不該把「像不像 Fish 的參考音色」納入總分；比聲音複製則應讓所有方案模仿同一目標說話者，並以人工盲聽校準。
>
> **選擇哪份參考答案、參考圖片或參考音訊，本身就是評估設計的一部分，不是無關緊要的準備工作。**

規模擴大後可訓練**生成式獎勵模型**自動評判（第八章）。

## 7. 失敗歸因：從整條軌跡定位首個錯誤 ⭐⭐⭐

每條失敗軌跡要記錄：**錯誤類別、首次出現不可接受行為的步驟、對應的工具呼叫或模型輸出、可複核的證據**。LLM 可以協助，但**仍需人工閱讀**——**失敗歸因往往反映的是產品問題**，不只是技術問題。錯誤分類隨產品完善可多達數百種，可作為歸因標註 Agent 的提示詞或 Skill。

### 7.1 Coding Agent 的初始錯誤分類

| 錯誤類別 | 典型表現 | 首個錯誤的定位方式 |
|---|---|---|
| **需求理解與歧義處理** | 漏條件、範圍理解寬了/窄了；兩個同名設定檔直接選一個既不說明也不追問 | LLM 把原始需求與 Agent **實際做的事**逐條對照，定位第一處偏離，再回溯造成它的工具呼叫或答覆 |
| **流程與規範缺失** | 未跑單元測試就提交；未寫 Plan 就改程式碼；引入外部依賴而倉庫已有內部等價物；繞過架構約定 | 找第一次違反流程的動作（首次 `git commit`、首次寫檔），回看之前有沒有讀過約定來源 |
| **工具呼叫錯誤** | 同一檔案反覆編輯失敗；JSON/schema 錯；特殊字元導致抄寫、跳脫、寫入錯誤 | 記第一次失敗的請求與錯誤回傳；**重複失敗屬於後續症狀** |
| **hack 驗證環境** | 改斷言、加 skip、mock 掉被測邏輯；聲稱「測試已通過」但根本沒跑 | 第一次改動測試或驗證邏輯的 message；把**完成聲明與軌跡中真實執行過的指令交叉核對** |
| **修改不完整** | 改了函式簽章與三處呼叫方，漏了第四處動態呼叫、另一語言的綁定或 schema | Agent 聲稱的影響面與真實影響面做**集合差**，取第一個遺漏項，回看檢索用了什麼關鍵字 |
| **對使用者的資訊回饋錯誤** | 工具與環境全對，告訴使用者的卻錯了；把部分完成說成全部完成；漏必須告知的事 | 把答覆中每個事實斷言與工具回傳逐條對齊，取第一條無法溯源或矛盾的斷言 |
| **非功能性迴歸** | 改公開 API/schema 而無遷移腳本；為讓校驗通過而刪校驗 | 第一次做出該改動的 message，看是否意識到動的是公開介面 |
| **模型執行異常** | 輸出截斷、無故停止、逾時、沒做收尾就結束 | 第一個異常終止位置；區分模型停止、Harness 逾時、工具服務故障 |
| **過早停止任務** | 多目標只完成一部分；未窮盡方案就宣布不可能 | 第一次遺漏目標或放棄探索的決策，與最終驗證失敗分開記錄 |

**歸因記錄要結構化**（JSON/YAML）：步驟號、工具名、觀察證據；**區分根因與後果**、可恢復性、信賴度。

> 例：`edit_file` 回傳 `old_string` 比對失敗，之後連續三次重試仍未寫入 → 主因是「檔案編輯與工具呼叫錯誤」，**三次重試是後果，不是三個獨立根因**。多類別並存時按「**最早且能解釋後續失敗**」選主因。

**規則先篩、LLM 再定位**（比全部丟給 LLM 更便宜也更準）：
- 完成聲明 vs. 實際執行指令的交叉核對；
- diff 是否觸及測試斷言與 skip 標記；
- diff 是否改公開 API/schema 而無遷移檔。

保存時連同**任務目標、環境狀態、Agent 版本、工具集版本、完整軌跡**一起存，以便迴歸。

### 7.2 三類典型錯誤

**① 「做對了但說錯了」**——最容易被整體成功率掩蓋（多數評估只查環境狀態）。
- τ²-bench 單獨計分：帶資訊告知要求的 704 次執行失敗 240 次，其中 162 次告知出錯；**80 次（佔失敗三分之一）環境狀態正確但回報資訊錯誤**。
- **AndroidWorld 記帳案例**：把 `expenses.jpg` 的開銷錄入記帳 App；32 步**沒有任何一步報錯**，自行宣告完成；驗收說應寫入的記錄（`Dress`、¥436.35）不存在。
  - 第 8 步思考：*「I cannot actually see the content/details of the expenses in the image」*——它知道沒拿到資料，卻既沒停下也沒回報；
  - 第 11 步四條開銷**憑空出現**，此後每次輸入都忠實執行捏造的資料。
  - **首錯在第 8 步，而那一步既沒報錯，也不是工具呼叫。**
  - ⭐ **根因歸屬容易記錯**：T3A 是純文字 Agent，觀察空間只有元素樹、**根本沒有影像像素** → 根因不是「模型不會 OCR」，而是 **Harness 的觀察通道缺失**，外加**沒給 Agent 一個「資訊拿不到」的合法退出動作**。記成模型能力問題 → 去換模型或做 OCR 訓練；真正該做的是補觀察通道和退出動作。

> **實驗 7-6 ★★ AndroidWorld 失敗歸因**（不需模擬器或 API；`t3a.md`、`t3a_failed.md` 50 餘條失敗）
> 1. 抽 ≥ 10 條**靜默失敗**（無工具報錯，自行宣告完成或耗盡步數，只有驗證器判失敗）；
> 2. 標首錯步號，註明是工具呼叫還是 assistant message；定位法：**事實錨點比對**（陳述 vs. 工具回傳逐步對齊）、**軌跡前綴二分**（截到第 k 步交給人接手，救得回來 → 錯在 k 之後）；不能用搜尋報錯關鍵字代替；
> 3. 結構化記錄：任務、首錯步號、類別、根因責任方、原文證據、主因 vs. 後果；
> 4. 與 `t3a_failed_analysis.md` 對照——該筆記把圖片轉錄失敗記成「視覺模型缺乏 OCR 能力」，**現成的歸因筆記不是標準答案**；
> 5. 挑 3 條首錯在 assistant message 的軌跡 → 截首錯前前綴 → 寫可接受動作集合與禁止動作 → **軌跡前綴迴歸任務**。

**② 作用域敏感的文件格式錯誤**
- 使用者說「引號格式不對」≠ 全域字元取代。至少區分 ASCII 直引號、中文彎引號、Markdown 反引號；同一字元在中文、英文原文、行內程式碼、程式碼區塊、註解、JSON、路徑中語法角色不同。
- 評估資料先解析成帶作用域的片段：`ZH_PROSE`、`EN_PROSE`、`QUOTED_SOURCE`、`INLINE_CODE`、`CODE_BLOCK`、`CODE_COMMENT`、`JSON_OR_SCHEMA`，各存允許變換、必須保護的字元、修改後的驗證結果。
- 前綴迴歸要求**最小修改**，同時檢查中文風格、英文原文保持率、程式碼與 JSON 語法、非目標文字的編輯距離；**規則無法確定作用域時，保留原文並請求澄清應是允許動作**，猜測性修改不算通過。

> 呼應第四章 Cursor 彎引號案例：同一個「引號」問題，從工具層（靜默轉換）到評估層（作用域判斷）都要分清作用域。

**③ 精確複製錯誤：`old_string` mismatch 的逐層定位**

不能只歸因「模型抄錯了」。保存同一字串的 **byte 雜湊、Unicode code point 序列、tokenizer token ID 序列**，沿鏈路找首個差異：

```text
原始檔案 byte → 工具回傳 → Harness 序列化 → 模型上下文
→ 模型 token 輸出 → 解碼字串 → JSON/tool-call 解析 → 工具比對
```

- 探針：直接複述、長上下文抽取、放入工具參數、相似字串選擇；空格、換行、反斜線、Unicode 組合字元、低頻 token。
- 指標：byte-exact、code-point-exact、token-exact match、首次分歧位置、真實工具成功率。
- **模型在直接探針中正確而工具呼叫失敗 → 修 tokenizer、序列化、Harness 或工具協定；只有首個差異出現在模型輸出時，才轉成第八章的複製訓練資料。**

> 對照 Ferguson《Cryptography Engineering》：編碼層的不一致（同一「字串」在不同層有不同 byte 表示）是經典的安全與正確性陷阱——要在每一層邊界做規範化比對，才能找到真正出錯的那一層。

## 8. 端到端迴歸 vs. 軌跡前綴迴歸 ⭐⭐⭐

| | 端到端迴歸任務 | 軌跡前綴（trajectory prefix）迴歸任務 |
|---|---|---|
| 做法 | 從初始狀態與使用者請求開始完成整個任務，檢查終態、必要輸出、安全條件 | **凍結**已有上下文、對話、工具回傳、環境狀態，只要求下一步（或幾步）可觀察動作 |
| 優點 | 最接近生產結果；驗證改動沒破壞完整流程 | **成本低**；隔離單個策略或工具問題；直接檢查決策邊界 |
| 缺點 | 難判斷失敗在哪一步 | 需要先建好失敗分類與歸因系統 |
| 例子 | OSWorld、AndroidWorld、τ-bench | 由失敗歸因產生 |

> 對高可靠的生產級 Agent，**軌跡前綴迴歸集往往比端到端迴歸集更重要**。

**答案是「可接受動作集合」，不是唯一動作**：可以要求「先讀倉庫規則」「先詢問使用者」「拒絕危險操作」，同時列出禁止動作。

**從失敗類別到迴歸任務**（Coding Agent）：

| 失敗類別 | 迴歸任務 |
|---|---|
| 流程缺失 | 端到端任務，帶計畫文件與測試驗收條件 |
| 工具呼叫錯誤 | 截斷出錯前綴編成邊界任務：修格式、跳脫特殊字元、改用合適工具 |
| 執行異常 | 截斷、逾時、工具故障的恢復場景 |
| 完成度與邏輯 | 多目標清單、剩餘任務提醒、「尚未證明不可能」的邊界 |
| 需求理解與歧義 | 有多種合理解釋的任務凍結成前綴，「**先澄清**」列入可接受動作 |
| 症狀修復與驗證造假 | 驗收補上「**不得修改測試斷言**」與「**完成聲明必須附帶真實執行過的指令輸出**」兩條硬約束 |
| 資訊回饋 | 對**答覆內容本身**設斷言，不只檢查環境狀態 |

> 評估資料集是第八章後訓練與第九章自我進化的基礎。

> **實驗 7-7 ★★ 多種表示法的前綴邊界評估**：給模型已知記憶、目前指令、前綴、工具回傳、環境狀態，只要求下一個可觀察行動；11 個案例以 **JSON Cards、Markdown、Python-like** 三種編碼、確定性規則評分；33/33 無 API 錯誤完成，**每種表示均為 6/11**。→ **只改變表示法不會自動修好應用策略。**

> ⭐ 本章小結的關鍵句：**獲得一條資訊和正確地將它用於當前決策是兩種不同能力。** 端到端迴歸保證基本任務不退化；前綴邊界集直接檢查作用域判斷、當前指令覆蓋、澄清、危險動作前確認。

## 9. 配對比較與模型排名 ⭐⭐

- **Elo 評分**：大量兩兩對決量化相對能力。A 1200、B 1000 → 預測 A 勝率約 **76%**；爆冷時調整幅度更大 → 快速收斂。
- 統計基礎：**Bradley-Terry 模型**——每個模型一個潛在實力分數，勝負機率由分數差決定；**Elo 是它的線上更新形式**。

```
A 對 B 的預期勝率 = 1 / (1 + 10^((R_B − R_A)/400))
  R_A = 1200, R_B = 1000 → 1 / (1 + 10^(−0.5)) ≈ 0.76
更新：R_A ← R_A + K · (實際結果 − 預期勝率)
```

- **Chatbot Arena**：匿名隨機對決、使用者盲選，數百萬次投票。優點：不需「絕對標準」；限制：**排名取決於使用者問了什麼**（大量程式設計題 → 程式設計強的模型偏高）。
- **位置偏差（Position Bias）**：LLM 評判系統性偏向某位置（通常是先出現的）。緩解：**交換順序各評一次**取平均；更嚴格：兩次一致才計入，否則記平局或送人工。Arena 隨機化展示位置讓偏差在大樣本下抵消。

> **實驗 7-8 ★★ 從配對資料建排行榜**：用 Chatbot Arena 開源投票資料；初始 1000 分、按時間順序增量更新 Elo；排序並算兩兩勝率矩陣，與官方榜**大體一致即可**——官方用 **Bradley-Terry 極大似然**一次性求解（與順序無關），這裡的線上 Elo 受 K 因子與處理順序影響，分值不會精確一致。第二部分：按週/月切片做 **D3.js 長條圖競賽動畫**，觀察技術突破時刻、格局演變、模型生命週期。

## 10. 評估驅動的模型選型 ⭐⭐⭐

### 10.1 選型的關鍵維度

**吞吐量 vs. 延遲**——先懂推理兩階段：

| 階段 | 做什麼 | 決定 |
|---|---|---|
| **Prefill** | 一次性讀入完整上下文 | **TTFT**（Time To First Token，首字延遲）= 排隊 + Prefill；上下文越長越慢 |
| **Decode** | 逐 token 生成 | 出字速度（tokens/s）與**思考時長**：50 tokens/s 生成 2000 個思考 token = 40 秒 |

| 指標 | 說明 |
|---|---|
| 輸入/輸出吞吐量 | 對應 Prefill / Decode 速度 |
| TTFT | 使用者感知的「反應快慢」 |
| **思考延遲** | 不同模型思考 token 數可差數倍，且**思考長度與效果不一定正相關** → 在自己的負載上實測 |
| **p95 尾部延遲** | 比平均值更能反映體驗——均值被大量快請求拉低，掩蓋少數使用者的嚴重卡頓 |
| **成本** | 輸入/輸出/快取 token 定價；**便宜但成功率低的模型因頻繁重試可能更貴** → 看每任務平均成本與成本—效能比 |
| **效能** | 日常看 **Pass@1**；關鍵操作優先 **Pass^k**；探索性任務 **Pass@k/Best@k**；開放式任務用 Rubric 多維 |
| **速率限制與可靠性** | RPM/TPM；高峰動態限額；分佈外資料、對抗輸入、長時執行穩定性（模式崩潰、注意力分散） |
| **預算—能力曲線** | 單點成績不足以判斷長程能力，要報告效能隨牆鐘時間、token、工具呼叫、算力預算的曲線 |

> **RE-Bench 人機對照**：每環境 **2 小時**總預算下，最佳 Agent 得分約為人類專家的 **4 倍**；但人類從加時間獲益更大——**8 小時**時已略超最佳 Agent，跨多次嘗試合計 **32 小時**時約為其 **2 倍**。→ **短預算領先不能外推成長時間執行能力**；選型要在接近真實任務時長的多個預算點比較。

**多模型協同**：輕量模型處理簡單請求、強模型處理複雜任務、專用模型處理子任務（影像、程式碼）——但要驗證整體效益是否超過增加的複雜度。⚠️ 反例：把「**9.9 跟 9.11 哪個大**」「**要洗車，家離洗車店 50 公尺，走路去還是開車去**」當簡單問題交給輕量模型 → 決策錯誤。

### 10.2 模型行為策略：何時停止閱讀、開始修改

- 不只比「能不能做成」，還要比**預設會怎麼做**——Coding Agent 的**行動閾值**：有的先廣泛探索（把過早修改的風險估得高），有的憑少量局部證據先改再用測試補理解（把「再讀一個檔」的機會成本估得高）。
- 兩個來源：Harness 中的系統提示詞；**模型的行為策略**（後訓練是關鍵來源：SFT 軌跡示範「讀到什麼程度再動手」、過程獎勵獎懲工具路徑、結果獎勵強化整套策略）→ 模型學到的不只是寫程式，也包括**工程習慣**。（呼應第五章 §4.2。）

> **實驗 7-9 ★★ 固定 Coding Harness 中測行動閾值**（`model-action-threshold/experiment.py`；OpenRouter 呼叫 GPT-5.6-sol 與 Claude Sonnet 5）
> - 固定系統提示、工具 Schema、倉庫、測試命令、最大輪次；**中性提示**既不要求讀足、也不要求儘快編輯；三類任務各 ≥ 3 次、**交替模型執行順序**。
> - 記錄：首次修改前的工具呼叫數、讀取檔案數、搜尋次數、牆鐘時間；首個修補通過率、返工次數、最終成功率、變更檔案數、token。
> - **因果判斷**：中性實驗回答「同一 Harness 下行為是否隨模型變化」；要測 Harness 調節作用，另用 `--policy explore-first` 單獨跑一組，**不混在同一模型比較裡**。換模型行為變、同模型跨 Harness 保持傾向 → 更支持**模型效應**；反之 → **Harness 效應**。
> - 驗收：初始倉庫先確認測試失敗；完整 `模型 × 任務 × 重複` 單元、零 API 錯誤、獨立最終測試、可稽核軌跡；`manifest.json` 驗設定與觀察檔雜湊。已保存 18/18 單元實測，但**不能當成永久排行榜**。

### 10.4 評估驅動的持續迭代

情境：系統基於 Claude，Gemini 發布新模型、公開基準更好且更便宜。問題不是「Gemini 是否比 Claude 強」，而是「**在我的任務上，好多少？切換成本是什麼？**」

> 有評估體系的團隊數小時內就能回答：可能發現新模型在簡單任務更優更便宜，但複雜多輪工具編排的核心場景成功率降 5%——**確認差異超出雜訊**後，決策變成「簡單任務遷移降本、複雜任務保留原模型」的**差異化策略**，而非盲目全量切換。

> **實驗 7-11 ★★ 多維度模型效能基準**：GPT/Claude/Gemini/Doubao 等閉源 + Qwen/Kimi/DeepSeek 開源；同模型不同提供商（DeepSeek 官方 vs. Siliconflow），驗證 Artificial Analysis；8K/32K/128K 輸入、512/2048 輸出；TTFT、端到端延遲、思考長度與延遲；每配置 ≥ 100 次，算標準差/p50/p95/p99；一週每小時探測可用性，算故障率、**MTTR**、最長連續可用時間；逐步提高並行找限流點；計算典型多輪 Agent 任務成本。
>
> **實驗 7-12 ★★ 使用者記憶端到端選型**：掃三個選擇點——嵌入模型（BGE-M3/OpenAI/豆包，top-5 準確率、延遲、成本）、reranker（含「**不用 reranker**」基線，量化邊際價值）、主模型。關鍵是讀出**元件間的協同**：更強的嵌入可能讓 reranker 多餘，更強的主模型可能彌補檢索不足——**選型是系統性權衡，不是逐個挑最強。**

## 11. 評估結果的統計顯著性 ⭐⭐⭐

n 個用例、成功率 p，標準誤粗估：

```
SE(p) ≈ sqrt( p(1 − p) / n )

n = 100, p = 0.70 → SE ≈ 0.046 → 95% 信賴區間 ≈ 70% ± 9 個百分點
→「新模型 73% 對舊模型 70%」不足以支持切換
```

- **配對分析**優先：同一批任務逐題記錄誰勝出，用 **McNemar 檢定**或**配對 bootstrap**，而不是直接相減兩個獨立成功率。
- 每個配置用多個隨機種子（3–5 次），報告均值與波動；單次執行只能篩方向。
- 預期收益只有 2–3 個百分點、評估集只有幾十題 → 先擴大樣本（SE 按 1/sqrt(n) 縮小）。

```python
for task in paired_tasks:
    for seed in fixed_seeds:
        a = run(config_a, task, seed)
        b = run(config_b, task, seed)
        record_paired_delta(verifier(a), verifier(b))
return paired_bootstrap_or_mcnemar(all_deltas)
```

- **配對**＝兩組共享任務與隨機條件，而不是各抽一批樣本再比平均。
- **多重比較**：並行驗多個假設時收緊門檻，或對正向結果獨立複跑。

> 實務判準：**分差要超過雜訊、在配對分析中成立、並且能夠複現**，才值得據此切換模型或發布改動。

> 對照 Ferguson《Cryptography Engineering》對隨機性的態度：沒有足夠樣本與正確統計方法的「看起來比較好」，和「看起來很隨機」一樣不可信。

## 12. Agent 的可觀測性 ⭐⭐

> 借自分散式系統：你沒法打開系統內部看，只能透過日誌、指標、追蹤推斷——像醫生透過體溫、血壓、影像診斷。Agent 更難：同輸入可能不同輸出、執行路徑複雜、思考不透明。

價值：**問題診斷**（重播全過程而非猜）、**持續最佳化**（哪些任務多輪迭代、哪些工具成功率最低、哪些檢索總是空）、**成本管理**（不同任務差一兩個數量級，找異常高成本案例）、為系統與模型改進累積資料。

**資料基礎：Trace / Span 樹**

```
trace（一次任務執行）
└─ span: Agent 主迴圈
   ├─ span: LLM 呼叫（輸入輸出、起止時間、token、錯誤）
   ├─ span: 工具呼叫
   └─ span: 檢索
```

- 標準協定：**OpenTelemetry**（通用分散式追蹤）+ **OpenInference**（LLM 特有語義約定：提示詞、模型參數、token 用量）→ **採集與分析解耦**，避免被單一平台鎖定。
- 平台：**LangSmith**（另有 Langfuse、Arize Phoenix）——非同步批次採集不影響延遲；A/B 測試（分流、自動對比、快速回滾或漸進擴量）、提示詞版本管理（每版關聯效能資料）、協作共享問題案例。

> ⭐ **可觀測性資料最有價值的去向，是迴流成評估資產**：生產軌跡篩出失敗與可疑案例 → **脫敏**（去隱私、金鑰）→ 沉澱為評估集新用例與迴歸測試 → 評估集成為**隨產品演化、持續貼近真實分佈的活資產**。可觀測性負責「看見」，評估負責把觀察固化為可反覆檢驗的標準。

## 13. 從 Benchmark 報告到系統改進 ⭐⭐⭐

本質：**Harness 迭代最佳化的方法**——用評估資料定位薄弱環節（上下文不足？約束缺失？驗證不夠？回饋不及時？）→ 針對性改進 → 重新評估。

> ⚠️ **看到表現下降時，先檢查解題系統本身，再動 Agent。** 常見來源：資源不足導致程序被殺（隨機性失敗）、**驗證器本身有 bug** 把正確答案判失敗、測試用例與生產脫節。這些在數字上和模型退化一模一樣，只有審查完整軌跡才能區分。

### 13.1 AndroidWorld Wi-Fi 子集案例

**讀報告**：116 項各跑一次，整體約 88%；但 4 項 `SystemWifiTurn*` 中有 3 項失敗，軌跡反覆出現來回切頁、無法確認最終狀態。兩種可能：不知道設定入口在哪，或取得的介面資訊不完整。

> 只看 88% 會忽略這個小而集中的失敗群；只增加步數上限又可能把「**看不到介面**」誤判成「**不夠耐心**」。先找失敗集中在哪，再重播軌跡分清問題出在**看、想、做還是驗**。

**表 7-5　三輪實驗**（同模型、任務參數、隨機種子、步數上限、模擬器；交替兩組執行順序；**每輪只改一個變因**）

| 實驗 | 唯一改動 | 對照→實驗成功率 | token 比 | 下一步 |
|---|---|---:|---:|---|
| **H1** | 加入導覽提示與最終狀態檢查要求 | 25% → 25% | 0.47× | 沒提升，沿用原提示 |
| **H5** | 不相容的 accessibility feed → AndroidWorld 支援的 **UIAutomator** 元素樹 | 25% → 100% | 2.498× | 效果明顯但 token 過多 |
| **H5C** | 只刪除不可見、無文字、不可操作的容器節點 | 100% → 100% | 0.506× | 成功率不變、token 減半 → 進入完整複測 |

**兩個教訓**：
1. **提示寫得再詳細，也補不回 Agent 根本沒看到的資訊**——遇到這類失敗先檢查輸入，不要繼續堆提示詞。
2. **輸入也不是越多越好**——完整元素樹解決「看不見」卻帶來大量無用 token；去掉無語義節點後仍全成功、token 減半。

> 全程沒換模型，只調整 Harness 呈現介面的方式，先後解決「**能不能完成**」與「**完成是否划算**」。（呼應第六章 AOI：重新設計觀察介面。）

**持續迭代**：H5C 過了 4 項只代表值得進入下一輪，**不等於可以部署**——下一步：補齊第三方應用，在 Pixel 6 / API 33 標準環境對 116 項各跑 5 個種子；成功率不能下降、token ≤ 原方案 75%、延遲 ≤ 1.5 倍。完成前**不能把子集上的 4/4 寫成系統整體 100%**。

> **一輪證據只能支持與其規模相稱的下一步。** 好的 Benchmark 報告不只給分數，還說清結論適用在哪、哪些底線尚未通過、下一輪要驗證什麼。

> **實驗 7-13 ★★★ AndroidWorld 評估與改進**：① 診斷（逐任務表 × 能力標籤矩陣）② 建假設（表層→中層→深層，每個假設明確預期提升與驗證方法）③ 分階段實驗（重現 H1、H5、H5C，記錄 token、延遲與退步）④ 資料驅動決策（低成本高收益優先，高成本限定關鍵場景）⑤ 迭代（小規模通過只能進入完整複測，116 × 5 之後才討論部署；報告保留環境差異、樣本數與未完成部分）。

## 14. 生產級 Agent 的內部評估基礎設施 ⭐⭐

以 OpenClaw 及頭部 Coding Agent 的公開分析為例——**把 ML 研究的實驗方法論系統性嵌入產品工程**。

| 元件 | 要點 |
|---|---|
| **消融基礎設施** | 總開關同時停用多個主要特性（思考、壓縮、自動記憶、後台任務）→ 「**裸模型」基線** → 回答「這個特性真的改善了體驗，還是只是感覺有用？」。開關必須在**啟動路徑極早期**注入（在任何模組級常數捕獲配置前）→ 必須從一開始設計進架構。定期消融發現「**特性債務**」——曾經有效但隨模型進化已不再必要的特性。**每個主要特性都應可獨立關閉** |
| **AB 測試** | **多臂而非二元**（控制組 + 三個漸進更嚴的變體 → 劑量—效應關係）；⭐ **區分機制指標與目標指標**——「縮短計畫檔長度」的計畫長度是**機制**，目標可能是「降低會話級成本」；縮短計畫可能導致更多編輯—檢查—編輯迴圈反而增加總輸出 → **以目標為準**；**護欄指標**（滿意度、操作次數、錯誤率不能變差）；**記錄基線統計**（樣本量、分位數、相關性如「拒絕率隨計畫大小單調遞增」） |
| **雙層特性開關** | **編譯時期開關**：建構時把程式碼物理移除，內部特性在外部建構中根本不存在，也是乾淨的消融；**執行時開關**：服務端下發 + 本地磁碟快取，**寧可讀稍舊的快取也不阻塞啟動**；分組由實驗平台（如 GrowthBook）；**每個特性的曝光事件每會話最多記錄一次**。特性開關是**一等公民級架構元件** |
| **提示詞敏感性評估** | 專用工具在指定 git 版本上提取**完整渲染後**的系統提示（動態條件展開後的最終文字）→「哪個 commit 改了提示詞？對評估集影響是什麼？」實踐：提示詞**可確定性渲染**、版本化快照、**每次變更跑評估迴歸，像程式碼跑 CI** |
| **隱私感知的分析** | 分析介面只接受經特殊型別包裝的值，**型別名本身就是稽核線索**（宣告「已驗證這不是程式碼或檔案路徑」）→ 隱私約束從文件規範變成**編譯時期強制的型別檢查**。隱私與評估不對立——迫使你想清楚真正需要度量什麼 |

> 外部評估告訴你「Agent 有多好」；內部評估基礎設施告訴你「**哪個改變讓它變好了**」。

> 對照 Hanson《C Interfaces and Implementations》：用型別系統把「這個值已被驗證」編碼進介面（如不透明指標/ADT）——讓錯誤用法在編譯期就不可表達，而不是靠文件提醒。

## 15. 模擬環境：從評估到後訓練的橋樑 ⭐⭐

評估的終點不是打分而是改進；改進的最強形態是**訓練** → 評估環境演化為**模擬環境**：讓 Agent 反覆練習、自動打分的虛擬操場。

| | 評估環境 | 模擬環境 |
|---|---|---|
| 互動頻率 | 數千次 | **數百萬次** |
| 隨機化 | 可有可無 | **必要**（防死記特定配置） |
| 回饋 | 事後 | **即時** |

**兩端怎麼接**：
- 評估資產近乎直接轉成訓練訊號：定義清晰的 Rubric 或驗證器本質上就是 **RLVR**（Reinforcement Learning with Verifiable Rewards）的**獎勵函式**——驗證腳本就是獎勵腳本。
- 訓練的新要求：① **可靠的 reset 語義**（數百萬個 episode 都要回到確定乾淨的初始狀態，否則梯度被殘留狀態汙染）；② **遠高於評估的吞吐**（並行度與單實例開銷決定訓練是否可行）。（第八章展開。）

| 類別 | 例子 |
|---|---|
| **數字環境** | **AWorld** 為 GAIA 建可控 MCP 沙盒：**26 個 MCP 伺服器、126 個工具函式**，避免真實 API 的封鎖與副作用，可重放可稽核；分散式架構 **7695 秒 → 525 秒（14.6×）**，無狀態設計每實例獨立 |
| **具身環境** | **RoboTwin2**：物理引擎雙臂操作，隨機化位置、朝向、外觀；多相機視覺 + 關節狀態；**動作分塊**實現即時控制。OSWorld 用 VM 快照實現可重置；AndroidWorld 聚焦移動應用 |

> **實驗 7-14 ★★ OpenVLA + RoboTwin2**：讀 `SimpleVLA-RL` 與 OpenVLA 文件（視覺編碼器 + 語言模型 + 動作解碼器端到端）；配置 RoboTwin2（**三視角 RGB + 14 維關節狀態**觀測、**14 維控制向量**動作）；研究 `move_can_pot` 的隨機化與空間約束；評估預訓練模型，重點看動作分塊的影響。

**保真度權衡與領域隨機化**：高保真遷移更好但開銷大；隨機化適度提升泛化、過度讓任務過難。**領域隨機化**在物理參數、視覺外觀、感測器噪聲引入大範圍變化——像在各種光照角度下都練過抓取。數字環境的 sim-to-real 表現為介面渲染、響應時間差異 → 隨機化延遲與失敗來緩解。（呼應第六章實驗 6-14。）

## 16. 設計觀念整理

| 觀念 | 本章體現 |
|---|---|
| **評估的是「模型 + Harness」** | 消融定位 Harness 部件；model swap 區分瓶頸 |
| **指標要匹配業務** | Pass@k 看天花板、Pass^k 看可靠性；寫清 k 的口徑 |
| **讓模擬器不可被忽悠** | 認知邊界欄位、事實錨定、驗收口徑、雙控 |
| **驗證事實，不信自我陳述** | FAIL_TO_PASS + PASS_TO_PASS；OSWorld 查資料庫與 DOM；QEMU 啟動日誌 |
| **評估集是活資產** | τ-bench → τ²-bench 五處修補；SWE-bench 淘汰 71%；OSWorld 15 個月 300 個問題；生產迴流 |
| **防洩漏靠生成機制** | 參數化範本、組合資訊源、專有附件、canary GUID |
| **能斷言就斷言** | 驗證譜系向右只用於無法機械判定的維度 |
| **Rubric 要可驗證** | 四準則、veto、邊界案例、判例集；防長度偏差 |
| **參考物本身是評估設計** | Fish 參考音色對 Fish 有利 |
| **異源評判防古德哈特** | 多家族評判者偏見正交 |
| **首錯與根因** | 首錯可能不是工具呼叫；根因可能在 Harness 觀察通道；重試是後果 |
| **逐層定位** | byte → code point → token → 解析 → 比對 |
| **可接受動作集合** | 前綴迴歸不要求唯一答案，「先澄清」可以是正解 |
| **取得資訊 ≠ 用對資訊** | 換表示法不會自動修好應用策略 |
| **配對、多種子、可複現** | McNemar / bootstrap；SE ≈ sqrt(p(1−p)/n) |
| **最佳化效果不可相加** | 快取 + 壓縮 ≠ 28.3% + 17.5% |
| **先查解題系統再動 Agent** | 驗證器 bug、資源不足會偽裝成退化 |
| **一次只改一個變因；證據與結論規模相稱** | H1 → H5 → H5C；4/4 ≠ 100% |
| **機制指標 ≠ 目標指標** | 計畫長度 vs. 會話成本；護欄指標 |
| **每個特性可獨立關閉** | 消融開關、特性債務、雙層特性開關 |
| **驗證器即獎勵函式** | 評估環境 → 模擬環境 → RLVR |

## 19. 思考題摘要（含書附參考答案要點）

| # | 題目 | 參考答案要點 |
|---|---|---|
| 1 ★★ | LLM-as-a-Judge 是否有系統性盲區？如何偵測與校正？ | 存在：**長度偏差**、風格偏差、同源模型被鑽空子（古德哈特）。偵測：建 **100–200 例人工金標集**，測評判與人類的 **Cohen's kappa**；定期審計評分與長度相關性；紅隊構造對抗案例。校正：Rubric 顯式懲罰冗長、限長度；**不同模型家族多源異構評判** |
| 2 ★★★ | 防洩漏的「貓鼠遊戲」有終局嗎？設計根本抵抗洩漏的方法 | 靜態題庫無終局，只能追趕。根本出路：**公開「生成機制」、私有化「具體實例」**——像 τ²-bench、AndroidWorld 參數化範本每次隨機實例化，驗證基於**最終環境狀態**而非固定答案序列 |
| 3 ★★ | 「有幫助」「語氣恰當」等主觀維度如何設計可靠 Rubric？ | 把抽象標準**翻譯成可驗證行為**；每檔配具體示例與邊界案例；Rubric 是迭代產物——收集評價者分歧，演化為**判例集**；多評委加權/一致性檢查，分歧送人工；在金標集上校準一致率 |
| 4 ★★ | 模擬使用者本身也是 LLM，如何驗證其品質？ | τ-bench 初版教訓：模擬器太機械、指令太簡（Agent 能猜對）。驗證：**人工抽檢**模擬對話（是否遵守漸進透露、不編造腳本外資訊）；用**小樣本真實使用者**測試，看與模擬評估的**排名是否一致** |
| 5 ★★ | 非傳遞偏好可能出現在哪？如何影響排名？ | 多維權衡時（A 準但慢、B 快但簡略、C 詳盡但貴），不同評判者/任務看重不同維度；Arena 排名本就依賴提問分佈。影響：BT 把實力壓成單一分數，非傳遞時排名不穩、隨對局分佈漂移。緩解：**按能力維度分別排名、報告兩兩勝率矩陣** |
| 6 ★★ | 單次成功率 60% 的 Agent 該報哪個指標、k 取多少？ | 先看**失敗是否可回滾**：可自動重試且無外部副作用（檢索、草稿、補全）→ 報 **Pass@k**，k = 實際允許的重試次數；不可逆（付款、退款、發信、部署）→ 報 **Pass^k**。p = 0.6 時 Pass@5 ≈ 99.0%、Pass^5 ≈ 7.8%，只報前者會嚴重高估。**k 取自部署現實**：Pass@k 取重試預算，Pass^k 取一次值班或一批任務的連續執行次數；重試成本高可兩段式（Pass@1 粗篩 → 少數候選跑 Pass^k）；寫清 k 與取樣口徑，有副作用在沙盒中取樣、每次失敗都計入 |
| 7 ★★ | 有限預算下如何最大化評估資訊量？ | 先**失敗分群**，縮到診斷價值最高的任務；低成本、**單一變因的配對測試**；小樣本只作擴大測試的門檻，不是部署證據；標準誤保守篩選 + McNemar 配對分析；預期差異小於雜訊就擴充評估集；並行篩多方案要校正多重比較並獨立重跑正向結果 |
| 8 ★ | 如何設計 UI 元素樹的自動裁剪規則，又不誤刪有用資訊？ | 「**預設刪除、有證據才保留**」：保留可見、有文字、可操作、可聚焦、可捲動、帶狀態值或無障礙標籤的節點，及其到根的最短祖先路徑與必要相鄰標籤；刪純排版容器、摘要重複子樹。裁剪前後確認可操作元素 ID、狀態與值未遺失，保留截圖作視覺備援。先在失敗軌跡重播，再用**未參與調整的應用**做迴歸；成功率、token、延遲都是護欄，**任何無障礙任務退步都應阻止發布** |
| 9 ★★ | 漸進式資訊透露如何影響評估？模擬策略失真時結論還可靠嗎？ | 若透露策略失真，Agent 可能只是學會「**適配模擬器**」（古德哈特），**絕對分數不具參考價值**；模型間**相對排序可能仍有參考價值**。補救：用真實對話校準模擬器、人工抽檢、明示結論適用邊界 |

## 20. 本章重點整理

1. 評估對象是**模型 + Harness**；對比、消融、model swap 三種實驗各答不同問題；有評估集才能「為未來的模型開發產品」。
2. 四個環節：**什麼算成功、任務從何而來、由誰驗證、分數如何轉為決策**。
3. **τ²-bench telecom**：`known_info` 建模認知邊界、事實錨定防忽悠、**雙控**、多維校驗；二元獎勵以過程顆粒度換可比性。
4. **Pass@k vs. Pass^k**：p = 0.6、k = 5 → 99.0% vs. 7.8%；技術奇觀 vs. 業務可靠性；有副作用不能重試到成功。
5. **評估環境五要素**：資料集、可重置的環境狀態、原子工具、評分標準、執行協定；Verifiers 四類環境。
6. 資料集設計：驗證事實（**FAIL_TO_PASS + PASS_TO_PASS**、OSWorld 134 函式、QEMU 日誌）；分級難度有診斷價值（GAIA）；防洩漏（組合資訊源、**參數化範本**、canary）；品質靠長期維護（SWE-bench 淘汰 71%、OSWorld 300 個問題）；三個來源（公開、自建、**生產迴流**）。
7. 驗證譜系：能斷言就斷言；**Rubric 四準則** + veto + 邊界案例；防長度偏差與位置偏差；**多源異構評判**防古德哈特；多模態評判；**參考物的選擇本身就是評估設計**。
8. **失敗歸因**：首錯步號 + 類別 + 證據；結構化、分主因與後果；規則先篩、LLM 再定位；根因可能是 Harness（觀察通道、缺退出動作）而不是模型。
9. 作用域敏感格式錯誤與 `old_string` 的**逐層定位**（byte → code point → token → 解析）。
10. **端到端迴歸 + 軌跡前綴迴歸**；答案是可接受動作集合；**取得資訊 ≠ 用對資訊**（三種表示法各 6/11）。
11. **配對比較**：Elo 是 Bradley-Terry 的線上形式；位置偏差交換順序評兩次。
12. **選型維度**：TTFT/Decode、思考延遲、p95、成本—效能比、速率限制、**預算—能力曲線**（RE-Bench 2 小時 4× → 32 小時 0.5×）；行動閾值是模型學到的工程習慣。
13. **成本**：上下文累積、工具回傳反覆計費；四組開關對照——**最佳化不可相加**。
14. **統計顯著性**：SE ≈ sqrt(p(1−p)/n)；**配對分析**（McNemar、bootstrap）、多種子、多重比較、可複現。
15. **可觀測性**：trace/span、OpenTelemetry + OpenInference；生產軌跡脫敏後**迴流成評估資產**。
16. **從報告到改進**：先查解題系統；一次只改一個變因（H1 → H5 → H5C）；提示補不回看不到的資訊；證據規模決定下一步。
17. **內部評估基礎設施**：消融總開關、多臂 AB 與**機制 vs. 目標指標**、雙層特性開關、提示詞 CI、型別化的隱私分析。
18. **模擬環境**是評估到後訓練的橋：驗證器即 RLVR 獎勵函式；需要可靠 reset 與高吞吐；領域隨機化。

> **一句話**：評估不是一次考試，而是一套持續把真實失敗變成可重複檢驗標準的科學工程——指標配合業務、驗證只信可複核的事實、歸因找到最早的那一步、統計分得清訊號與雜訊，每一次改動都只改一件事並讓證據決定下一步走多遠。
